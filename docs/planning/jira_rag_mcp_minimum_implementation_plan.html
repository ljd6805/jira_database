1. 프로젝트를 한 문장으로

초기 목표
“계정이 조회 가능한 Jira 데이터를 안전하게 보존하고, BGE-M3/FAISS로 관련 근거를 찾아, MCP가 그 근거와 출처를 Agent에게 전달하고, Agent LLM이 최종 답변을 만든다.”
가장 쉬운 비유 RAG는 오픈북 시험입니다. LLM에게 회사의 모든 Jira를 외우게 만드는 대신, 질문이 들어오면 먼저 관련 페이지를 찾아 책상 위에 펼쳐 주고 그 근거 안에서 답하게 합니다.

2. 먼저 용어 네 개

Jira업무·버그·요청을 Issue 카드로 관리하는 시스템입니다. 이 프로젝트의 원천 데이터입니다.
Embedding문장을 숫자 vector로 바꾸는 기술입니다. 의미가 비슷한 문장을 문자열 일치보다 잘 연결할 수 있습니다.
RAG질문과 관련된 근거를 먼저 검색해 LLM에게 함께 제공하는 방식입니다.
MCPAgent가 “검색해 줘”, “이 Issue 근거를 보여 줘” 같은 도구를 표준 방식으로 호출하게 하는 연결 규격입니다.
BGE-M3현재 사내에서 제공되는 embedding 모델. 현재 M8 계약은 BAAI/bge-m3, dense dimension 1024입니다.
FAISSvector 사이의 가까운 후보를 빠르게 찾는 index. 원문 저장소도, 답변 생성 LLM도 아닙니다.

4. 초기 최소 범위

포함하려던 것

접근 가능 프로젝트, 프로젝트별 최근 Issue 파일럿, 제목/설명/상태/유형/댓글, 관계, Attachment metadata, 원문 JSON, metadata DB, BGE-M3 embedding, FAISS 검색, 읽기 전용 MCP.

의도적으로 미룬 것

전체 Issue 무제한 수집, Attachment 본문/이미지 분석, 복잡한 Ontology/Graph DB, Jira 쓰기, 완전 자동 scheduler, 운영 웹 UI, 정교한 사용자별 권한 매핑.

왜 범위를 줄였나? 처음부터 “Jira 전체 + 모든 첨부 + 그래프 + 권한 + UI”를 만들면 검색 자체가 맞는지 검증하기 전에 시스템이 너무 커집니다. 먼저 한 바퀴가 끝까지 도는지를 확인하려는 전략이었습니다.

6. 초기 “Raw → Chunk → Embedding” 그림은 어떻게 바뀌었나?

초기 Baseline

Jira 제목·설명·댓글을 검색하기 좋은 100~500 token Chunk로 나누고 직접 embedding하는 그림을 상정했습니다.

현재 Pipeline

M1~M5에서 먼저 Knowledge Input → Light Structured Knowledge를 만들었습니다. M8-01 실측 결과 Knowledge Item 자체가 짧고 atomic해 baseline은 Item 1 = Embedding Unit 1, 기본 Chunk 없음입니다.

초기 계획이 “틀렸다”기보다 학습 결과로 구체화된 것입니다. 처음엔 원문 Chunk가 합리적 가정이었지만, 실제 Knowledge Item 길이와 구조를 측정한 뒤 더 단순한 baseline으로 바꿨습니다.

7. 원문/DB/Vector를 왜 분리해야 하나?

Source / RAW

사실을 되돌아갈 기준. 재처리와 감사의 근거.

SQLite

Issue Version, Generation, Attempt, Knowledge Item, Evidence, Review와 mapping 관리.

Embedding / FAISS

의미 검색을 빠르게 하기 위한 파생 검색 artifact. 원문을 대체하지 않음.

검색 ID → stable mapping → Knowledge Item → Evidence → Source Entity → ANALYSIS / RAW

현재는 이 원칙이 M6/M7의 jira_id → iv_ → kc_ → kg_ → ka_ → ki_ → ke_ identity와 Evidence round-trip으로 구체화됐습니다.

9. MCP는 왜 답변을 직접 만들지 않나?

근거 보존

MCP가 원문을 먼저 강하게 요약하면 예외 조건이나 불확실성이 사라질 수 있습니다.

테스트 분리

검색 오류와 최종 답변 오류를 별개로 재현하고 디버깅할 수 있습니다.

재사용

서로 다른 Agent/LLM이 같은 MCP 검색 서비스를 공통으로 사용할 수 있습니다.

MCP output = evidence + identifiers + source refs Agent LLM = comparison + explanation + final answer

11. 테스트 철학도 발전했다

수집은 count/경고/중복으로

“보인다”가 아니라 30 Issue, 278 Comment, warning 0처럼 deterministic 결과로 검증했습니다.

Knowledge는 Reviewer만 믿지 않음

M4에서 Human Validation 5/5를 추가했습니다.

DB는 round-trip과 idempotency로

M7에서 Evidence Failure 0, FK Failure 0, integrity OK, same-run idempotent true를 확인했습니다.

Embedding은 count/index/dimension/atomic publish로

M8-02에서 schema와 identity를 코드로 검사하고 M8-03 실제 API Gate를 남겼습니다.
