FAISS + Active Retrieval
상세 계약

Pilot에서는 exact/full-rebuild로 검색 구조의 결정성과 무결성을 검증합니다. 정식 서비스에서는 새로 생기거나 변경되거나 비활성화된 Knowledge만 처리하는 delta-first 운영으로 확장합니다.

Pilot의 FAISS 내부 locator. stable Knowledge identity가 아닙니다.

6. 정식 서비스는 Delta First

변경 없음 → 아무 작업 없음 새 Knowledge → 새 embedding만 생성 → index add 변경 Knowledge → old entry 제거/비활성 → 필요한 vector만 계산 또는 재사용 → new entry add 삭제/비활성 Knowledge → index entry 제거/비활성

변경 여부는 기존 source_hash → issue_version → active generation → accepted attempt → knowledge_item → embedding_text_hash 구조를 활용합니다.

7. 같은 Text면 Vector 재사용

vector_cache_key = H(embedding_text_hash, embedding_contract_hash) 새 ki_ / 새 emb_ lineage + 같은 text hash + 같은 ec_ → 기존 vector 재사용 → BGE-M3 API 호출 생략
Lineage와 계산 cache를 분리합니다. emb_는 Knowledge lineage를 보존하고 vector cache는 비용 최적화 역할만 합니다.

8. Production Incremental FAISS ID

현재 bare IndexFlatIP는 순차 position을 사용하므로 remove 시 뒤 번호가 이동할 수 있습니다. 운영형 exact 후보는 다음과 같습니다.

IndexIDMap2(IndexFlatIP) + stable int64 vector_id vector_id ↔ embedding_id (emb_) ↔ knowledge_item_id (ki_)

Stable vector_id는 SQLite에서 collision 없이 관리하는 방식을 우선합니다.

9. ANN 확장 시

IndexIVFFlat

Explicit ID/remove와 큰 N의 검색량 감소 측면에서 incremental 운영 후보입니다.

IndexHNSWFlat

빠른 검색이 강점이지만 FAISS에서는 remove를 직접 지원하지 않아 tombstone + periodic rebuild가 필요합니다.

IndexFlatIP

ANN recall을 검증하는 exact test oracle로 보존합니다.

10. Full Rebuild의 정식 서비스 역할

평상시 → delta update 주기적 / 필요시 → full rebuild

Full rebuild는 tombstone/fragmentation 정리, integrity 재검증, embedding contract 변경, index migration, backfill, 장애 복구에 사용합니다.

운영 기본 = delta-first · full rebuild = maintenance / recovery / migration
