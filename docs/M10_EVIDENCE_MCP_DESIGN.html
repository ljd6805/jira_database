M10 DESIGN PROPOSAL · 2026-08-26

찾아낸 Knowledge에
“실제 Jira 근거”를 붙이기

M9는 질문과 관련 있어 보이는 Knowledge를 찾았습니다. M10은 그 Knowledge가 실제 Jira의 어느 설명·댓글·첨부·관계·Custom Field에서 나온 것인지 다시 찾아 붙이고, Agent가 사용할 수 있는 Evidence Package와 MCP 도구로 제공하는 단계입니다.

DESIGN IN PROGRESS · 구현 전 계약 확정 단계
먼저 이것만

M10을 한 문장으로 말하면

M9가 찾아낸 “관련 있어 보이는 문장”에 실제 Jira 원문 근거를 붙여서, Agent가 믿고 사용할 수 있게 만드는 단계입니다.
M9 "이 Knowledge가 질문과 비슷합니다." ↓ M10 "그 Knowledge는 이 Jira Issue의 이 Comment/Description을 근거로 합니다. 실제 원문은 이것입니다." ↓ Agent / LLM "근거를 확인했으니 이 범위 안에서 답변하겠습니다."

1. 지금까지를 아주 단순하게 보면

M0 Jira 사실을 안전하게 수집 ↓ M1 Issue별 완전한 사실 Package ↓ M2 검색용 Knowledge 의미 카드 ↓ M3 생성·검증·Review 품질 Loop ↓ M4 실제 Jira 30건 실전 검증 ↓ M5 실제 Knowledge 분포 측정 ↓ M6 DB Logical Schema 설계 ↓ M7 실제 SQLite DB ↓ M8 Knowledge → BGE-M3 vector ↓ M9 질문 → 관련 Knowledge Top-3 검색 ↓ M10 실제 Jira Evidence를 붙여 Agent/MCP에 제공 ← 지금 여기
M10이 중요한 이유 M9까지는 “검색 엔진”이 완성된 것입니다. M10을 통과해야 검색 결과가 실제 Jira 근거를 포함한 AI가 사용할 수 있는 지식 도구가 됩니다.

2. 예시 하나로 M9와 M10 차이 이해하기

아래 Issue Key와 내용은 구조 설명을 위한 가상 예시입니다.

사용자 "부팅 중 PMBus timeout은 어떻게 해결했지?" M9가 찾은 Knowledge Top-3 1. "retry를 추가한 뒤 문제가 재현되지 않았다." 2. "초기화 순서를 변경해 timeout을 방지했다." 3. "PMBus 통신에서 간헐적인 timeout이 발생했다." 여기까지 M9 ──────────────────────────────── M10이 1번 Knowledge의 ki_를 따라가면 Knowledge "retry를 추가한 뒤 문제가 재현되지 않았다." ↓ Knowledge Evidence (ke_) ↓ comment:5001 ↓ 실제 Jira Comment "Boot sequence에서 PMBus read timeout 발생. retry count를 3으로 변경한 이후 재현되지 않음." ↓ Evidence Package - 가상 Issue: DEMO-123 - Evidence type: comment - Comment ID: 5001 - 실제 원문 - M9 rank/score
비유 M9가 도서관 검색에서 “이 책 37페이지가 관련 있어 보입니다”라고 알려주는 사서라면, M10은 실제 37페이지를 열어 중요한 문장에 책갈피를 붙이고 “이 문장이 근거입니다”라고 건네주는 사서입니다.

3. M9와 M10을 딱 구분하면

단계답하는 질문결과
M9어떤 Knowledge가 질문과 의미상 가까운가?rank, score, emb_, ki_, category
M10그 Knowledge의 실제 Jira 근거는 무엇인가?Knowledge statement + Evidence 원문 + 출처 정보
Agent그 근거들을 종합하면 사용자에게 어떻게 답해야 하는가?최종 자연어 답변
검색 점수는 사실 인증서가 아닙니다. cosine score가 높다는 것은 의미가 가깝다는 뜻이지, 그 Knowledge가 반드시 정답이라는 뜻은 아닙니다. 그래서 Evidence가 필요합니다.

4. Evidence Builder가 실제로 하는 일

1 · KNOWLEDGE

ki_ 확인

M9의 knowledge_item_id가 현재 active accepted Knowledge인지 확인하고 statement를 읽습니다.

2 · EVIDENCE

ke_ 따라가기

Knowledge Item에 연결된 Evidence row를 조회하고 6종 source type에 맞게 실제 데이터를 읽습니다.

3 · PACKAGE

한 덩어리로 구성

rank/score, Knowledge, 실제 Evidence와 안전한 출처 식별자를 Agent가 쓰기 쉬운 JSON으로 묶습니다.

M9 candidate ki_ ↓ knowledge_item.statement ↓ knowledge_evidence (ke_ 1..N) ↓ summary / description / comment / attachment / relationship / custom_field ↓ Evidence Package

5. MCP는 왜 M10에 있는가?

M10에는 Evidence Builder와 MCP라는 두 가지가 함께 등장합니다. 둘은 같은 것이 아닙니다.

Evidence Builder · 내부 로직

ki_ → ke_ → 실제 Jira source를 따라가서 믿을 수 있는 근거 묶음을 만드는 코드입니다.

MCP · Agent가 들어오는 입구

Agent가 내부 SQLite, FAISS, 파일 경로를 몰라도 표준 Tool 호출로 검색과 근거 조회를 사용할 수 있게 하는 외부 인터페이스입니다.

Agent │ │ MCP tool call ▼ Jira Knowledge MCP ├─ M9 Retrieval └─ M10 Evidence Builder ↓ Knowledge + 실제 Evidence + 출처 ↓ Agent의 생성형 LLM이 최종 답변
고정 원칙 MCP 내부에는 생성형 LLM을 넣지 않습니다. MCP는 검색·DB 조회·Evidence 복원처럼 검증 가능한 일을 하고, 최종 설명은 Agent의 LLM이 담당합니다.

6. M10에서 재사용하는 이미 끝난 것

M7 DB

30 active Generation, 285 Knowledge Item, 502 canonical Evidence.

M7 Evidence 계약

6종 Evidence reference parsing과 accepted evidence round-trip Gate가 이미 존재합니다.

M8

ki_ ↔ emb_가 deterministic하게 연결된 285개 vector.

M9

질문 → exact cosine Top-3 → emb_ → ki_까지 완료.

따라서 M10에서 새 DB를 다시 설계하지 않습니다. 이미 만든 연결을 읽고 조합하는 것이 핵심입니다. 여기서 세계관을 다시 만들면 프로젝트만 갑자기 장편 판타지가 됩니다.

7. 결정안 A · Evidence Package Schema

추천

후보 중심 Package

검색 후보 하나 안에 Knowledge와 그 Evidence를 같이 둡니다. Top-3 규모에서는 중복 최적화보다 사람이 읽기 쉽고 Agent가 join하지 않아도 되는 것이 중요합니다.

{
  "rank": 1,
  "score": 0.84,
  "knowledge_item_id": "ki_...",
  "category": "actions_and_decisions",
  "statement": "...",
  "issue": {
    "issue_key": "DEMO-123",
    "status": "Resolved"
  },
  "evidence": [
    {
      "evidence_id": "ke_...",
      "type": "comment",
      "source_id": "5001",
      "text": "...",
      "truncated": false
    }
  ]
}

대안 · Evidence를 따로 모으기

Knowledge 배열과 Evidence 배열을 분리하면 중복은 줄일 수 있지만 Agent가 다시 ID join을 해야 합니다. 현재 Pilot 규모에서는 이 복잡도가 이득보다 큽니다.

8. 결정안 B · 6종 Evidence Resolver

Evidence type실제 sourceAgent에게 보여줄 핵심
summaryissue_version.summaryIssue summary text
descriptionissue_version.descriptionDescription text + format
commentcommentComment ID, 작성자, 시각, body
attachmentattachment파일명, MIME, 크기, content_available
relationshiprelationship관계 type/text와 양쪽 Issue
custom_fieldcustom_field_value + catalogField 이름과 표시값
새 규칙을 만들지 않습니다. M7의 기존 parse_evidence_ref()와 round-trip 규칙을 그대로 재사용하고, M10은 실제 내용을 읽어 반환하는 Resolver를 추가합니다.

9. 결정안 C · 실패 정책

추천

Runtime은 candidate 단위 격리

Top-3 중 하나의 Evidence가 깨졌다면 그 candidate는 정상 results에서 제외하고 warning에 남깁니다. 나머지 정상 candidate는 반환합니다.

Offline Gate는 엄격하게

accepted Knowledge의 missing Evidence, stale active lineage, 내부 경로 노출은 0건이어야 합니다. 하나라도 있으면 M10 Gate FAIL입니다.

Runtime
valid candidate   → results[]
broken candidate  → 제외 + warnings[]
all broken         → typed error

CI / Real-run
accepted evidence missing > 0 → FAIL
stale active lineage > 0      → FAIL
local path leak > 0           → FAIL

10. 결정안 D · Candidate / Evidence Budget

추천

M9 Top-3 유지

실제 M9에서 Rank 3 noise가 관찰됐지만 임의의 global threshold를 만들 충분한 근거는 없습니다. Top-3을 Evidence와 함께 먼저 평가합니다.

추천

연결된 canonical Evidence는 우선 전부

Pilot에서는 각 Knowledge Item의 Evidence를 모두 포함하고, 실제 payload가 너무 길다는 측정이 생길 때 truncation 한도를 확정합니다.

11. 결정안 E · MCP Tool Surface

추천 · Tool 1

search_jira_knowledge

일반 자연어 질문용입니다. 질문 임베딩 → M9 검색 → M10 Evidence resolve까지 내부에서 처리하고 Evidence Package를 반환합니다.

input
query: string
top_k: int = 3

output
results: EvidencePackage[]
warnings: Warning[]
추천 · Tool 2

get_jira_issue

특정 Issue를 알고 있거나 검색 후 더 자세히 보고 싶을 때 current issue snapshot과 관련 source 정보를 제공합니다.

input
issue_key: string

output
summary / description / status
comments
relationships
attachments metadata
custom fields
provenance
왜 Tool을 더 쪼개지 않나? 내부 코드는 search / resolver / builder로 모듈화해도, Agent가 후보마다 다시 resolve Tool을 호출하게 만들 이유는 없습니다. 외부 MCP surface는 작게 유지합니다.

12. 결정안 F · Stale Retrieval 방지

M9 index와 M7 DB의 갱신 시점이 다르면 M9가 과거 ki_를 반환할 수 있습니다. M10은 결과를 믿기 전에 DB에서 active accepted 여부를 다시 확인합니다.

M9 candidate ki_ ↓ knowledge_item ↓ knowledge_attempt ↓ knowledge_generation ↓ 정상 조건 state = active AND accepted_attempt_id = item의 attempt AND content_available = 1
조건 불일치 시 조용히 사용하지 않습니다. 정상 답변에서 제외하고 STALE_RETRIEVAL_INDEX 계열 warning/error로 드러내며 M9 index 갱신 대상으로 봅니다.

13. M10에서 하지 않는 것

❌ LLM 답변 생성

MCP 내부에서 별도 생성형 LLM으로 요약/답변하지 않습니다.

❌ Retrieval 재설계

M9 Top-k, cosine threshold, reranker를 근거 없이 M10에 섞지 않습니다.

❌ Production update 확장

IndexIDMap2, delta update, HNSW/IVF 같은 production hardening은 별도 후속 단계입니다.

14. M10 구현 후 사용자가 느끼는 변화

지금 M9

질문 ↓ 관련 Knowledge Top-3

M10 완료 후

질문 ↓ 관련 Knowledge Top-3 ↓ 각 Knowledge의 실제 Jira 근거 ↓ 원문 + 출처 ↓ Agent가 근거 기반 답변
M10이 끝나면 “Jira를 의미 검색할 수 있다”에서 한 단계 더 나아가, Jira에서 관련 사례를 찾고 실제 근거를 함께 Agent에게 제공하는 RAG/MCP 시스템의 핵심 경로가 완성됩니다.

15. 구현 순서 제안

1
M10-01 Contract Freeze

이 문서의 Evidence Package, Resolver, 실패 정책, MCP 2-tool surface를 확정합니다.

2
M10-02 Evidence Repository / Resolver

ki_ → ke_ → source read path와 6종 Resolver를 구현하고 unit test를 추가합니다.

3
M10-03 Evidence Builder

M9 candidate를 후보 중심 Evidence Package로 조립하고 stale/partial failure를 처리합니다.

4
M10-04 MCP

search_jira_knowledge, get_jira_issue 두 도구를 얇게 연결합니다.

5
M10-05 Real-run Gate

실제 질문 → M9 → M10 → Evidence 원문까지 round-trip하고 citation/missing/stale/path leak을 검증합니다.

16. 현재 결정이 필요한 것

아직 구현 전입니다. 추천안은 다음과 같습니다: ① 후보 중심 Evidence Package ② M7 6종 Resolver 규칙 재사용 ③ Runtime candidate 격리 + Offline 엄격 Gate ④ M9 Top-3 + canonical Evidence 우선 전부 ⑤ MCP 2 tools ⑥ stale active 재검증. 이 계약을 확정한 뒤 코드를 시작합니다.
