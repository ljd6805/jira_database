M10 DESIGN PROPOSAL · 2026-08-26

검색 후보를
“근거가 있는 답변 재료”로 바꾸기

M9는 관련 Knowledge Item을 찾는 데 성공했습니다. M10은 그 ki_를 M7 SQLite의 ke_와 실제 Jira source row로 round-trip하여, Agent가 바로 사용할 수 있는 Evidence Package와 MCP 인터페이스로 제공하는 단계입니다.

DESIGN IN PROGRESS · 구현 전 사용자 합의 필요

1. 지금 정확히 어디까지 왔나

M7 SQLite active accepted Knowledge + canonical Evidence ↓ M8 BGE-M3 285 Knowledge Item → 285 × 1024-d vector ↓ M9 FAISS query → Top-k candidate rank + score + emb_ + ki_ + category ↓ M10 ← 지금 여기 ki_ → statement → ke_ → source row → Evidence Package → MCP ↓ Agent / LLM 검색 결과 + 원문 근거로 최종 답변
고정된 전제
M7 Identity/Schema, M8 Embedding Unit, M9 Top-3 exact cosine baseline은 M10에서 다시 설계하지 않습니다. MCP 내부에 생성형 LLM도 넣지 않습니다.

2. M10의 최소 책임

RESOLVE

Knowledge Resolve

M9의 knowledge_item_id가 현재 active accepted lineage에 속하는지 확인하고 statement를 읽습니다.

EVIDENCE

Evidence Resolve

knowledge_evidence를 따라 summary/description/comment/attachment/relationship/custom_field source를 복원합니다.

MCP

Agent Surface

로컬 경로와 내부 DB 구조는 숨기고 Knowledge와 근거, 출처 식별자만 안정된 JSON 계약으로 제공합니다.

3. 결정 1 · Evidence Package Schema

추천안 A

후보 중심 Package

검색 후보마다 Knowledge와 Evidence를 함께 묶습니다. Agent가 rank/score와 근거를 한 덩어리로 이해하기 쉽습니다.

{
  "rank": 1,
  "score": 0.84,
  "knowledge_item_id": "ki_...",
  "category": "actions_and_decisions",
  "statement": "...",
  "issue": {
    "issue_key": "...",
    "status": "..."
  },
  "evidence": [
    {
      "evidence_id": "ke_...",
      "type": "comment",
      "source_id": "...",
      "text": "...",
      "truncated": false
    }
  ]
}
대안 B

Knowledge / Evidence 분리

Knowledge 후보 배열과 Evidence source 배열을 응답 최상단에서 분리하고 ID로 연결합니다. 중복은 줄지만 Agent 입장에서는 join이 하나 더 필요합니다.

추천: Pilot은 후보 중심 Package로 갑니다. 데이터가 285개 규모이고 Top-3이므로, 응답 압축보다 이해 가능성과 provenance 보존이 더 중요합니다.

재사용 원칙
M7의 기존 parse_evidence_ref()와 accepted evidence round-trip 검증 로직을 버리지 않습니다. M10 resolver는 같은 type/key 규칙 위에 “내용을 읽는 기능”만 추가합니다.

5. 결정 3 · 실패 정책

추천안

신뢰 우선 · candidate 격리

Evidence가 하나라도 DB에서 사라졌다면 그 candidate를 정상 result로 내보내지 않습니다. 다른 정상 candidate는 계속 반환하고, 응답에 구조화된 warning을 남깁니다.

왜 전체 요청을 즉시 죽이지 않나?

Top-3 중 하나가 깨졌다고 나머지 두 개의 정상 근거까지 버릴 필요는 없습니다. 대신 Quality Gate에서는 accepted Evidence 누락을 0건으로 강제합니다.

Runtime
- valid candidate   → results[]
- broken candidate  → excluded + warnings[]
- all candidates broken → typed error

Offline / CI Gate
- accepted evidence missing > 0 → FAIL
- stale active lineage > 0      → FAIL
- local path leak > 0           → FAIL

6. 결정 4 · Candidate / Evidence Budget

추천안

Top-3 유지 + Evidence 전부

M9의 default Top-3을 그대로 사용하고, 각 Knowledge Item에 연결된 canonical Evidence row는 Pilot에서 모두 포함합니다.

긴 본문은 안전장치

한 Evidence text가 지나치게 길 때만 문자 수 기준 truncation을 적용하고 truncated=true를 표시합니다. 정확한 한도는 M10 real-run에서 실제 payload 분포를 보고 확정합니다.

지금 임의로 cosine threshold나 Evidence 2개 제한을 만들지 않습니다.
M9 실측에서 score가 가까워도 의미 품질이 달랐습니다. 먼저 Top-3 + 실제 Evidence를 Agent 관점에서 평가한 뒤 줄입니다.

7. 결정 5 · MCP Tool Surface

추천안 · 2 tools

1) search_jira_knowledge

query를 받아 M9 search + M10 Evidence resolve까지 한 번에 수행합니다. 일반 질문은 이 도구 하나로 끝납니다.

input
query: string
top_k: int = 3

output
results: EvidencePackage[]
warnings: Warning[]
retrieval: rc_/fi_ metadata subset
추천안 · 2 tools

2) get_jira_issue

정확한 issue key를 알고 있거나 검색 결과를 더 깊게 확인할 때 current issue snapshot을 제공합니다.

input
issue_key: string

output
issue summary/description/status
comments
relationships
attachments metadata
custom fields
provenance
search와 resolve를 별도 MCP tool로 쪼개지 않는 이유
Agent가 매 candidate마다 두 번째 tool call을 만들 필요가 없습니다. 내부 모듈은 search/resolver/builder로 분리하되 외부 도구는 얇게 유지합니다.

8. 결정 6 · Stale Index / DB 불일치

추천안

ki_가 더 이상 active accepted가 아니면 정상 검색 결과로 사용하지 않는다

M9 index가 과거 snapshot을 보고 있고 M7 DB가 갱신되었다면 같은 ki_가 historical이 되었을 수 있습니다. M10은 candidate resolve 시 active accepted lineage를 다시 확인합니다.

M9 candidate ki_
  ↓
knowledge_item → knowledge_attempt → knowledge_generation
  ↓
PASS only if
  generation.state = 'active'
  AND generation.accepted_attempt_id = item.attempt_id
  AND attempt.content_available = 1
불일치 시: 조용히 historical Knowledge를 답변에 넣지 않습니다. STALE_RETRIEVAL_INDEX 계열 warning/error로 드러내고 M9 rebuild/delta update 대상임을 명시합니다.

9. 제안하는 내부 모듈 구조

src/jira_collector/ ├─ evidence/ │ ├─ models.py # EvidenceSource / EvidencePackage │ ├─ repository.py # ki_/ke_/issue DB query │ ├─ resolver.py # 6종 type resolver │ └─ builder.py # candidate → package ├─ retrieval/ # M9 그대로 재사용 └─ mcp/ └─ server.py # 2 tools, 생성형 LLM 없음 tools/jira_knowledge/ └─ validate_m10_evidence_package.py tests/ ├─ test_evidence_repository.py ├─ test_evidence_resolver.py ├─ test_evidence_builder.py └─ test_mcp_tools.py

모듈은 책임만 분리하고 별도 framework 계층을 만들지 않습니다. 함수는 작게 유지하고 type별 resolver를 독립 테스트할 수 있게 합니다.

11. 구현 순서 · 합의 후 진행

1
Contract 고정

이 문서의 6개 결정을 확정하고 schema/error code를 freeze합니다.

2
Repository + Resolver

SQLite만 대상으로 ki_/ke_/6종 source round-trip을 구현합니다. 아직 MCP를 붙이지 않습니다.

3
Evidence Builder

M9 RetrievalCandidate를 EvidencePackage로 변환하고 stale/partial 정책을 테스트합니다.

4
Real-run Gate

실제 285 Knowledge / 502 canonical Evidence 기준으로 resolve 성공률과 payload 분포를 측정합니다.

5
MCP 2 tools

검증된 service만 tool로 노출하고 OpenCode/Agent에서 end-to-end 호출을 확인합니다.

6
문서 동기화

M10 Completion, Current Status, Pipeline, Hub를 HTML 기준으로 업데이트합니다.
