M10 FINAL DESIGN · 2026-08-27

검색 후보를
“근거가 있는 답변 재료”로 바꾸기

이 문서는 M10 설계 검토 당시의 추천안을 현재 확정 계약과 구현 결과에 맞춰 정리한 쉬운 설명서입니다. M10의 핵심은 M9가 찾은 Knowledge에 실제 Jira Evidence를 붙이고, Agent가 MCP로 안전하게 사용할 수 있게 만드는 것입니다.

DESIGN FROZEN · IMPLEMENTATION PASS · REAL-RUN NEXT

1. 한 문장 역할

M10 = “이 Knowledge가 왜 맞는지 실제 Jira 근거를 붙여 Agent에게 주는 단계”
M9 "이 Knowledge가 질문과 비슷합니다." ↓ M10 "그 Knowledge의 실제 근거는 이 Jira 설명/댓글/관계입니다." ↓ Agent "그 근거를 바탕으로 최종 답변하겠습니다."
도서관 비유 M9가 관련 책을 찾아준다면 M10은 실제 페이지를 열고 근거 문장에 책갈피를 붙여주는 단계입니다.

2. 왜 M9만으로 끝내지 않았나?

검색 문장 ≠ 원문

M9가 찾는 것은 압축된 Knowledge Item입니다. 실제 Jira 문장과 동일한 것은 아닙니다.

출처가 필요

Agent가 답하려면 어느 설명·댓글·관계가 그 Knowledge를 뒷받침하는지 알아야 합니다.

오류 추적

검색은 맞았는데 답이 틀렸는지, Evidence 자체가 잘못 연결됐는지 분리해야 합니다.

3. 전체 연결

사용자 질문 ↓ BGE-M3 query embedding ↓ M9 FAISS Top-3 rank + score + emb_ + ki_ ↓ M10 active/accepted 확인 ↓ ki_ Knowledge statement ↓ ke_ Evidence refs ↓ summary / description / comment / attachment / relationship / custom_field ↓ Evidence Package ↓ MCP Agent / LLM

4. 확정 결정 ① 후보 중심 Evidence Package

{
  "rank": 1,
  "score": 0.84,
  "knowledge_item_id": "ki_...",
  "category": "key_findings",
  "statement": "검색된 의미 문장",
  "issue": {
    "issue_key": "...",
    "status": "..."
  },
  "evidence": [
    {
      "evidence_id": "ke_...",
      "type": "comment",
      "text": "실제 원문"
    }
  ]
}

Knowledge와 Evidence를 따로 배열로 나눠 Agent에게 다시 join시키지 않고, 검색 후보 하나를 한 Package로 이해하게 합니다.

5. 확정 결정 ② M7의 6종 Evidence 계약 재사용

type실제 sourceAgent에 필요한 것
summaryissue_version.summarytext
descriptionissue_version.descriptiontext + format
commentcommentbody + author/time
attachmentattachmentfilename/mime/size metadata
relationshiprelationshiptype/text/source-target
custom_fieldcustom_field_value + catalogfield name + display value
새 Evidence 문법을 만들지 않습니다. M7에서 이미 검증된 summary, comment:<id> 같은 ref 규칙을 그대로 사용합니다.

6. 확정 결정 ③ 깨진 후보는 격리

정상 candidate → results[] 깨진 candidate → 제외 + warnings[] 모든 candidate 실패 → typed error

Top-3 중 하나의 source가 깨졌다고 나머지 정상 결과까지 버리지는 않습니다. 대신 Real-run/CI Gate에서는 warning과 missing Evidence가 0이어야 합니다.

7. 확정 결정 ④ Top-3 유지

M9 실데이터에서 Rank 3에 noise가 있기도 했지만 score가 가까운 후보의 의미 품질이 항상 같지는 않았습니다. 그래서 M10이 시작되자마자 global threshold/reranker를 임의 추가하지 않았습니다.

Pilot: M9 Top-3 + 각 Knowledge Item의 canonical Evidence를 우선 모두 사용하고, 실제 Agent 품질/부하를 측정한 뒤 줄입니다.

8. 확정 결정 ⑤ MCP는 2개 Tool

search_jira_knowledge

질문 → BGE-M3 → M9 → M10 Evidence Package까지 한 번에 처리하는 일반 검색 도구.

get_jira_issue

Issue key를 이미 알고 있거나 검색 결과를 더 깊게 확인할 때 current snapshot을 읽는 도구.

내부 모듈은 search/resolver/builder로 분리하지만 외부 MCP call은 불필요하게 세분화하지 않습니다.

9. 확정 결정 ⑥ stale Knowledge 재검증

M9 candidate ki_ ↓ knowledge_item → knowledge_attempt → knowledge_generation ↓ 사용 조건 state = active accepted_attempt_id = item.knowledge_attempt_id content_available = 1

M9 index와 DB snapshot이 어긋난 경우 historical Knowledge를 조용히 답변에 섞지 않습니다.

10. Read-only / 보안 설계

MCP annotation read_only_hint = true open_world_hint = false SQLite mode=ro PRAGMA query_only=ON 외부 응답에서 제외 source_path source_page 로컬 DB 경로 사내 endpoint/header/secret
중요: annotation은 힌트이므로 DB 자체도 read-only로 열어 실제 쓰기를 막습니다.

11. MCP 내부 생성형 LLM 없음

MCP 검색 + Evidence 복원 Agent LLM 근거 비교 + 최종 자연어 답변

이 경계를 유지하면 Retrieval 문제와 Answering 문제를 따로 테스트할 수 있습니다.
