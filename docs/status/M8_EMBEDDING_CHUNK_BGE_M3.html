4. Knowledge ID와 Embedding ID를 왜 따로 두나?

Knowledge identity ki_ = knowledge_item_id Embedding Contract ec_ = model + model_profile + text_profile + dimension + contract version Embedding Artifact emb_ = H(knowledge_item_id, embedding_text_hash, ec_)

Knowledge의 의미 identity와 “어떤 모델/텍스트 규칙으로 만든 vector인가”는 다른 개념입니다. 같은 Knowledge Item을 다른 모델이나 text profile로 재임베딩할 수 있기 때문입니다.

중요: FAISS position ≠ embedding_id ≠ knowledge_item_id. Endpoint, API key, custom header도 embedding identity material이 아닙니다.

6. Runtime Secret과 Custom Header

사내 API가 표준 Bearer API key만 쓰지 않고 별도 HTTP header를 요구할 수 있어 M8-02 runtime에 custom header 전달 기능이 추가됐습니다.

# OpenAI-compatible endpoint BGE_M3_ENDPOINT=<internal embeddings endpoint> # Bearer 인증을 쓰는 경우만 BGE_M3_API_KEY=<secret> # 여러 custom header를 JSON object로 전달 BGE_M3_HEADERS_JSON='{"X-Custom-Header-1":"value1","X-Custom-Header-2":"value2"}'
HTTP request에는 사용

BGE_M3_HEADERS_JSON의 key/value는 실제 embeddings HTTP 요청 header에 forwarding됩니다.

Identity / Artifact에는 미포함

Header 이름/값은 ec_, emb_, stdout, embedding JSONL의 identity/content로 넣지 않습니다.

보안 경계 실제 사내 header 이름과 값은 문서나 Git artifact에 기록하지 않습니다. runtime secret/config로만 주입합니다.

7. 285개가 왜 5 request인가?

285 corpus rows Batch 1 = 64 Batch 2 = 64 Batch 3 = 64 Batch 4 = 64 Batch 5 = 29 ──────────── Total = 285

64를 초과한 batch 설정은 시작 전에 거부합니다. 응답은 배열의 물리 순서를 맹신하지 않고 OpenAI-compatible data[].index를 authoritative mapping으로 사용합니다.

✓ index 누락 없음
✓ index 중복 없음
✓ index 범위 오류 없음
✓ response count = request count
✓ vector dimension = 1024
✓ 285 corpus → 285 embeddings
