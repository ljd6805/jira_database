M7은 구조화 저장입니다. M8은 “문장의 의미를 비교할 수 있는 숫자 표현”을 만듭니다.

M9와 차이

M8은 vector를 만들기만 합니다. 어떤 vector가 질문과 가까운지 찾는 FAISS 검색은 M9입니다.

M8 완료 후

질문과 Knowledge를 같은 의미 공간에서 비교할 수 있는 검색 재료가 준비됩니다.

M8의 핵심 역할 사람이 읽는 Knowledge 문장을 컴퓨터가 의미 거리로 비교할 수 있는 좌표로 바꾸는 단계입니다.

1. 입력 경계

knowledge_generation.state = active AND accepted_attempt_id IS NOT NULL ↓ accepted knowledge_attempt AND content_available = 1 ↓ knowledge_item ↓ 285 embedding units

M8 baseline은 Knowledge Item 1개 = Embedding Unit 1개입니다. 현재 statement 길이는 mean 114.01자, p95 206.4자, max 447자여서 선제 Chunk가 필요하다는 근거가 없었습니다.

2. Embedding이라는 말이 낯설다면

"부팅 중 PMBus timeout이 발생했다" ↓ BGE-M3 [0.013, -0.087, 0.221, ... 총 1024개 숫자] "PMBus 통신이 기동 시 timeout 난다" ↓ BGE-M3 [비슷한 방향의 1024개 숫자] 의미가 비슷하면 → vector 사이의 cosine 값이 더 높아질 가능성이 큼

1024개의 각 숫자를 사람이 해석할 필요는 없습니다. 중요한 것은 같은 모델과 같은 계약으로 만든 vector끼리 의미적 가까움을 계산할 수 있다는 점입니다.

3. Identity

Knowledge jira_id → iv_ → kc_ → kg_ → ka_(attempt_no) → ki_ → ke_ Embedding ec_ = embedding contract emb_ = H(knowledge_item_id, embedding_text_hash, ec_) FAISS position ≠ emb_ ≠ ki_

emb_는 “이 Knowledge를 이 Embedding 계약으로 vector화한 결과”의 안정적인 식별자입니다. M9의 배열 위치인 FAISS position과 혼동하지 않습니다.
