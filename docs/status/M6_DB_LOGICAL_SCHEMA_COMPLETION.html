M6를 이해하려면 네 단어만 먼저

Issue

Jira에서 장기간 같은 업무를 가리키는 identity. jira_id가 authoritative key입니다.

Version

그 Issue의 내용이 실제로 달라진 한 시점의 immutable 의미 상태입니다.

Generation

특정 Version을 특정 Knowledge Contract로 지식화하는 하나의 lineage입니다.

Attempt

Generation 안에서 실제로 Worker가 생성한 1차·2차·3차 시도입니다.

비유 Issue는 “한 문서의 파일명”, Version은 저장된 문서 버전, Generation은 그 버전을 같은 규칙으로 번역하는 작업 묶음, Attempt는 번역 1차/2차/3차 시도입니다. 최종 번역만 남기면 왜 다시 번역했는지 이력이 사라집니다.

1. 가장 먼저 분리한 것: Run ≠ Version

월요일 Pipeline Run ─┐ 화요일 Pipeline Run ─┼─ 같은 source_hash → 같은 issue_version 재사용 수요일 Pipeline Run ─┘ 목요일 내용 변경 새 source_hash → 새 issue_version

Pipeline을 여러 번 실행했다고 Jira Issue의 의미가 매번 새로 생기는 것은 아닙니다. M1의 source_hash가 같다면 같은 의미 상태로 보고 기존 Version을 재사용합니다.

pipeline_run“언제 파이프라인을 돌렸는가”라는 관찰 시점입니다.
issue_version“Issue의 의미 내용이 언제 달라졌는가”를 나타내는 immutable 상태입니다.
issue_version_observation어떤 Run에서 어떤 Issue Version을 관찰했는지 둘을 연결합니다.

2. History 저장과 검색 대상은 다르다

DB History

과거 Version, 실패 Attempt, 과거 Review를 보존합니다. 감사와 재현을 위한 기록입니다.

기본 Retrieval

사용자 검색에는 승인된 active Generation + accepted Attempt의 Knowledge만 기본 포함합니다.

History Storage ≠ Active Retrieval Corpus 과거를 저장한다고 과거의 모든 실패/중간 결과를 검색 결과에 섞어야 하는 것은 아닙니다.

3. Generation과 Attempt를 왜 분리했나?

Issue Version └─ Knowledge Generation ├─ Attempt 1 │ ├─ Knowledge Item │ └─ Review → REGENERATE ├─ Attempt 2 │ ├─ Knowledge Item │ └─ Review → PASS └─ accepted_attempt_id → Attempt 2

M5 실제 데이터에서 30건 중 6건이 재생성됐습니다. Generation 하나에 결과만 덮어쓰면 “1차에서 어떤 결함이 있었고 왜 2차가 생겼는지”가 사라집니다.

Legacy 현실도 보존 M4의 failed historical Attempt는 Review 파일은 남아 있지만 당시 Knowledge 본문은 보존되지 않은 경우가 있습니다. M7에서는 content_available=false로 기록하고 존재하지 않는 본문을 추정 복원하지 않습니다.

4. ID Ladder — ID가 많아 보이는 이유

jira_idJira Issue의 authoritative identity
iv_Issue Version — jira_id + source_hash 기반 의미 상태
kc_Knowledge Contract — 어떤 Schema/Skill 규칙으로 추출했는지
kg_Knowledge Generation — Version + Contract의 retry lineage
ka_Knowledge Attempt — Generation 안의 실제 attempt_no 회차
ki_Knowledge Item — 검색용 의미 문장 하나
ke_Knowledge Evidence — Item이 가리키는 근거 하나

파생 ID는 versioned canonical JSON → UTF-8 → key 정렬 → 의미 없는 whitespace 제거 → SHA-256 full lowercase 64 hex 규칙을 공통 사용합니다. Timestamp는 identity material이 아닙니다.

왜 deterministic ID인가? 같은 의미 입력을 다시 처리했을 때 같은 ID가 나와야 중복을 만들지 않고 idempotent하게 적재할 수 있기 때문입니다.

5. 최종 15개 Entity를 역할별로 보기

① Run / Jira 사실

pipeline_run issue issue_version issue_version_observation

“언제 봤는가”와 “무엇이 바뀌었는가”를 분리합니다.

② Evidence Source

comment attachment relationship custom_field_catalog custom_field_value

Knowledge가 실제 근거로 되돌아갈 수 있는 source entity입니다.

③ Knowledge / Audit

knowledge_generation knowledge_attempt knowledge_item knowledge_evidence knowledge_review review_finding

생성 lineage, 실제 Attempt, 의미 Item, Evidence, 품질 검토 이력을 보존합니다.

6. 핵심 Cardinality

pipeline_run 1 ── N issue_version_observation issue 1 ── N issue_version issue_version 1 ── N knowledge_generation knowledge_generation 1 ── N knowledge_attempt knowledge_attempt 1 ── N knowledge_item knowledge_item 1 ── N knowledge_evidence knowledge_attempt 1 ── 0..1 knowledge_review knowledge_review 1 ── N review_finding

읽는 법: 1 ─ N은 왼쪽 한 건에 오른쪽 여러 건이 연결될 수 있다는 뜻입니다. 예를 들어 Knowledge Item 하나에 Evidence가 여러 개 붙을 수 있습니다.

7. Evidence round-trip — DB 설계의 핵심

Evidence refDB에서 돌아갈 곳쉽게 말하면
summaryissue_version.summaryIssue 제목/요약 근거
descriptionissue_version.descriptionIssue 설명 근거
comment:<id>comment(source_run_id, source_issue_key, comment_id)특정 댓글
attachment:<id>attachment(source_run_id, attachment_id)특정 첨부 metadata
relationship:<id>relationship(source_run_id, relationship_id)특정 Issue 관계
custom_field:<field_id>custom_field_value(source_run_id, source_issue_key, field_id)특정 Custom Field 값
Accepted Attempt에서는 Evidence resolver 실패를 허용하지 않습니다. Knowledge가 근거를 주장하는데 실제 Source를 찾을 수 없다면 integrity failure입니다.

8. Active Publish는 어떻게 안전하게 바뀌나?

현재: G1 = active 새 Issue Version 등장 → G2 = candidate G2 Review PASS 전 → G1 active 유지 G2 PASS → 같은 transaction에서 G1 = historical G2 = active

즉 “가장 최근에 관찰한 Issue Version”과 “현재 검색에 사용해도 되는 승인된 Knowledge”는 같은 개념이 아닙니다. SQLite partial UNIQUE index로 Issue당 active Generation은 최대 1개만 허용하도록 M7에 넘겼습니다.

9. M6에서 일부러 하지 않은 것

SQLite DDL

Logical Schema를 물리 테이블로 구현하는 것은 M7.

Chunk / Embedding

검색 vector를 어떤 단위로 만들지는 M8.

FAISS

Vector index와 retrieval은 M9.

M6 Gate PASS / DONE “무엇을 저장할지”를 먼저 고정한 뒤 M7이 “실제로 어떻게 SQLite에 저장할지” 구현하도록 책임을 넘겼습니다.

10. 이해 점검

Q. Pipeline을 두 번 돌리면 무조건 Issue Version도 2개인가?아니요. source_hash가 같으면 기존 Version을 재사용합니다.
Q. Attempt 1이 실패하고 Attempt 2가 PASS하면 Attempt 1을 삭제하나?아니요. 가능한 이력은 보존합니다. 다만 legacy에 본문 자체가 없으면 내용을 지어내지 않습니다.
Q. 과거 Generation도 FAISS에 모두 넣나?아니요. 기본 Retrieval corpus는 승인된 active Knowledge로 제한합니다.
