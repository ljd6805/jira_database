1. M6의 핵심 구분

Pipeline Run ≠ Issue Version

Run마다 동일 Issue snapshot을 복제하지 않습니다. source_hash가 바뀔 때만 새 의미 Version을 만듭니다.

History Storage ≠ Active Retrieval

Historical Version/Knowledge는 DB에 보존하되 기본 RAG/FAISS에는 승인된 active Knowledge만 포함합니다.

same source_hash → existing issue_version 재사용 different source_hash → new issue_version DB → current + historical 보존 Retrieval→ active accepted knowledge만 기본 포함

2. Deterministic ID ladder

jira_id authoritative identity ↓ iv_ issue_version ↓ kc_ knowledge_contract ↓ kg_ knowledge_generation ↓ ka_ knowledge_attempt + attempt_no ↓ ki_ knowledge_item ↓ ke_ knowledge_evidence

versioned canonical JSON → UTF-8 → sorted keys → insignificant whitespace 제거 → SHA-256 full lowercase 64 hex를 공통 규칙으로 사용합니다. Timestamp는 identity material이 아닙니다.

3. Generation과 Attempt 분리

Issue Version └─ Knowledge Generation ├─ Attempt 1 │ ├─ Knowledge Item │ └─ Review ├─ Attempt 2 │ ├─ Knowledge Item │ └─ Review └─ Attempt N

knowledge_generation은 같은 Issue Version + Knowledge Contract의 retry lineage, knowledge_attempt는 immutable 실제 생성 시도입니다. M4 legacy failed Attempt는 Review는 남지만 당시 Knowledge 본문이 없으므로 존재하지 않는 내용을 추정 복원하지 않습니다.

Accepted Attempt에서 하나라도 resolver가 실패하면 integrity failure입니다. Polymorphic source를 억지 FK로 만들지 않고 exact ref + type-specific validator를 선택했습니다.

6. Active publish 계약

G1 active + 새 Version/G2 candidate G2 Reviewer PASS 전 → G1 active 유지 G2 PASS → 같은 transaction에서 G1 historical / G2 active

따라서 “latest observed Issue Version”과 “approved active Knowledge Generation”은 다른 개념입니다. SQLite partial UNIQUE index로 Jira Issue당 active Generation 최대 1개를 DB 수준에서 강제합니다.
