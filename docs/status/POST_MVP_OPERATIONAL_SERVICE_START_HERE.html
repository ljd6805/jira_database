1. 현재 프로젝트 위치

M0~M11 = Functional MVP · DONE / PASS Jira 수집 → Knowledge 생성/검토 → Versioned SQLite → BGE-M3 Embedding → FAISS Top-3 Retrieval → Evidence round-trip → MCP 2 tools → OpenCode 자동 Tool 선택 → Jira description/comment 근거 추적 여기까지 실제 사용자 환경에서 검증 완료
중요한 해석

이것은 최종 서비스 완료가 아닙니다. 지금까지는 한 번 준비된 Pilot 데이터로 전체 기술 경로가 실제로 동작한다는 것을 증명한 MVP입니다.

2. 최종적으로 서비스해야 하는 것

A. 지속적인 Jira 업데이트

신규/수정 이슈와 comment, relationship, custom field 변화가 다음 sync에 반영되어야 합니다.

B. Project 추가·변화 반영

매 sync에서 접근 가능한 프로젝트 전체를 discovery하고 새 프로젝트는 자동으로 초기 ingest 대상에 포함합니다.

C. 변경분만 하위 파이프라인 갱신

unchanged는 재사용하고 new/changed만 Issue Version → Knowledge → Embedding → FAISS까지 전파합니다.

D. 중앙 MCP 서비스

팀원 OpenCode는 Remote MCP endpoint만 사용하고 서버가 SQLite/FAISS/.env/BGE 설정을 소유합니다.

E. 운영 자동화

주기 실행, checkpoint/resume, retry, 실패 격리, logging, health, 상태 확인이 필요합니다.

F. 접근권한 정책

프로젝트 권한 상실과 팀원별 Jira 접근권한을 중앙 서비스에서 어떻게 처리할지 반드시 결정해야 합니다.

3. 목표 운영 흐름

Jira ↓ Project Discovery ├─ 신규 Project → Initial Ingest ├─ 기존 Project → Delta Sync └─ 사라짐/No Access → 정책 판단 ↓ Issue Delta Detection ├─ unchanged → reuse ├─ new → 새 Version 생성 └─ changed → 새 Version 생성 ↓ Knowledge Delta ↓ Embedding Delta ↓ FAISS Active Update ↓ Central Remote MCP / HTTPS ↓ Team OpenCode

4. 이미 합의된 원칙 · 다시 논의하지 않아도 되는 것

항목현재 합의
Jira 접근읽기 전용 REST API. 인증 계정이 볼 수 있는 프로젝트를 discovery.
Jira 호출 제한보수적 baseline 20 requests/minute, concurrency 1.
원본 우선RAW가 사실의 최종 기준.
Version 판단source_hash 동일이면 기존 Issue Version 재사용, 변경이면 새 Version.
History / ActiveHistory는 보존하고 Active Retrieval은 최신 accepted Generation만 사용.
Identityjira_id → iv_ → kc_ → kg_ → ka_(attempt_no) → ki_ → ke_.
EmbeddingBAAI/bge-m3, 1024 dimensions. 변경 없는 text는 재사용하는 방향.
Retrieval현재 baseline IndexFlatIP / cosine / Top-3 / no threshold / no reranker.
운영 갱신delta-first. full rebuild는 복구/검증/마이그레이션 경로.
MCP 역할검색/근거 복원만 담당. 생성형 Agent는 외부 OpenCode.
MCP 서비스 형태local stdio는 MVP 검증용. 최종은 중앙 Remote MCP.
서비스 설정.env 기본, OS env가 override. secret은 Git에 커밋하지 않음.

8. 아직 결정되지 않은 핵심 정책

Project가 사라졌을 때

Jira에서 삭제된 것인지, 서비스 계정 권한만 회수된 것인지, 일시 장애인지 구분해야 합니다. 기존 Knowledge의 active 비활성화 시점은 아직 미정입니다.

팀원별 Jira 권한

중앙 MCP가 서비스 계정이 볼 수 있는 모든 Jira 지식을 모두에게 제공해도 되는지, 사용자별 필터링이 필요한지 미정입니다.

Sync cadence

몇 분/몇 시간/몇 일 주기로 돌릴지 아직 미정입니다.

Watermark 전략

정확한 updated timestamp 경계, overlap window, 중복 재수집 허용 범위를 다음 Sync Contract에서 결정합니다.

Vector atomicity

DB Active 상태와 FAISS 갱신을 어떤 순서로 안전하게 전환할지 미정입니다.

Remote MCP 운영

TLS, auth, reverse proxy, 배포 방식, timeout/concurrency는 아직 Freeze하지 않았습니다.
