3. 구현된 Loop A

Jira serverInfo → fixed upper → Project Discovery 전체 성공 → project_id Registry → Initial / Delta / Catch-up / Unavailable → lower = committed_watermark - 5m → updated >= lower AND updated < upper → ORDER BY updated ASC, id ASC → RAW detail / comments durable → Issue / Comment / Structure Parser → per-Issue ANALYSIS → Knowledge Input → semantic_v2 → NEW / CHANGED / UNCHANGED → candidate cursor checkpoint → Project Source Commit → Watermark + Source Ready + supersede

4. semantic_v2에서 다시 뒤집지 않을 것

Hash에 남김

Issue/Comment 본문, created_at, author, 업무 status/context, Attachment metadata, 관계, Custom Field.

Hash에서 제외

issue.updated_at, comment.updated_at, source_path/source_page, other_package_available 같은 실행 범위 파생 metadata.

Timestamp만 바뀌면 UNCHANGED이며 실제 업무 내용이 바뀌어야 CHANGED가 됩니다.

5. Source History / Latest-Only

Source History 상태 A → B → C → D 모두 보존 Loop B B pending → superseded C pending → superseded D latest + Source-ready → process

중간 Source 상태는 삭제하지 않습니다. 비싼 OpenCode/Embedding/Publish만 최신 Source 상태에 집중하고, 중간 상태가 왜 처리되지 않았는지는 State와 구조화 로그로 추적합니다.

6. Same-Run Resume

fixed upper 최초 한 번 결정 candidate 1 완료 → cursor durable candidate 2 실패 → Watermark 유지 resume(source_run_id) → 같은 fixed upper → 완료 Discovery snapshot 재사용 → cursor 이전 candidate skip → 실패 지점부터 재시도 → 전체 완료 후 Source Commit

9. 다음 구현 · Loop B

Latest-Only Single Worker

sync_issue_change의 Source-ready + latest Work만 claim합니다. OpenCode가 느린 동안 더 최신 Source가 들어와도 구버전 결과가 Knowledge/Embedding/Publish로 넘어가지 않도록 stale guard를 세 경계에서 적용합니다.

latest + source-ready claim → latest_processing_started → OpenCode → latestness re-check → stale이면 superseded / stop → 아니면 Knowledge / Review / Evidence → Embedding → Publish 직전 latestness re-check → Atomic Publish → PUBLISHED
