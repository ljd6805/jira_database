8. 정식 서비스 Update 방향 · 이미 합의됨

운영 기본 = delta-first unchanged → 기존 embedding/index 재사용 added → cache 확인 → 필요 시 embed → add changed → old remove/tombstone → cache/embed → add removed → remove/tombstone full rebuild → maintenance / recovery / migration / backfill
Vector cache 후보

H(embedding_text_hash, embedding_contract_hash). 같은 text + 같은 ec_면 vector 재사용 가능.

Incremental exact 후보

IndexIDMap2(IndexFlatIP) + stable int64 vector_id. 현재 Pilot 구현에는 아직 적용하지 않았습니다.

HNSW/IVF 전환은 실제 latency/RAM/QPS/recall@k benchmark가 필요할 때 별도 production-hardening에서 결정합니다. 이 작업을 M10 Evidence Builder와 섞지 않습니다.

9. M10의 책임 경계

사용자 질문 → M9 BGE-M3 + FAISS → Top-k candidate rank + score + emb_ + ki_ ↓ M10 1. ki_로 Knowledge statement 조회 2. ki_ → ke_ Evidence refs 조회 3. Evidence type별 source resolve 4. Agent가 쓰기 쉬운 Evidence package 구성 5. MCP interface로 제공 ↓ Agent / LLM → Knowledge + 근거를 함께 사용
M10의 핵심 목적

“검색된 문장이 맞아 보인다”에서 끝내지 않고, 왜 그런 답을 할 수 있는지 Jira 원문 근거까지 정확히 round-trip하게 만드는 것입니다.

10. M10에서 아직 결정하지 않은 것

Evidence Package Schema

후보별 어떤 필드를 Agent/MCP에 전달할지 아직 확정하지 않았습니다.

Evidence Resolver Contract

version/comment/attachment/relationship/custom field 등 type별 resolver의 출력 규격과 failure 정책을 설계해야 합니다.

MCP Tool Surface

검색+근거 조회를 하나의 tool로 할지, search와 resolve를 분리할지 아직 결정하지 않았습니다.

Candidate/Evidence Budget

Top-3 모두의 Evidence를 어느 정도까지 싣는지, 길이 제한/중복 제거 정책은 아직 결정하지 않았습니다.

Quality Gate

Evidence round-trip, missing evidence, stale active snapshot, citation correctness를 어떤 자동 Gate로 막을지 설계해야 합니다.

API / MCP Error Contract

no result, partial evidence, resolver failure, DB mismatch 시 반환 형식과 실패 강도를 정해야 합니다.

중요

이 항목들은 아직 합의되지 않았습니다. 새 세션에서 먼저 설계 문서를 만들고 사용자와 결정한 뒤 구현합니다.
