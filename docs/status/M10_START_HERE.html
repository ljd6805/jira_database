Jira 원본 ↓ M0 수집/정규화 Issue별 사실 ↓ M1 한 Package Knowledge Input ↓ M2 의미 추출 Knowledge Item ↓ M3/M4 품질 Loop + 실전 검증 검증된 Knowledge ↓ M5 측정 DB 설계 근거 ↓ M6/M7 설계 + SQLite 구조화 Knowledge DB ↓ M8 BGE-M3 vector ↓ M9 Top-3 Knowledge 후보 ↓ M10 실제 Jira Evidence가 붙은 Package ↓ Agent / LLM 최종 답변

3. 절대 다시 바꾸면 안 되는 Identity 구조

jira_id ↓ iv_ issue_version · source_hash ↓ kc_ knowledge contract ↓ kg_ knowledge_generation ↓ ka_ knowledge_attempt · attempt_no ├─ ki_ knowledge_item │ └─ ke_ knowledge_evidence └─ knowledge_review → review_finding Embedding ec_ embedding contract emb_ embedding artifact Retrieval rc_ retrieval contract fi_ FAISS index artifact FAISS position ≠ emb_ ≠ ki_
중요

knowledge_attempt가 실제 retry 회차입니다. Knowledge Item과 Review는 Generation이 아니라 Attempt에 연결됩니다. M10은 이 구조를 재설계하지 않습니다.

8. 현재 M10 추천 설계

① 후보 중심 Evidence Package

rank/score + Knowledge + Evidence를 candidate 한 덩어리로 반환합니다.

② M7 6종 Resolver 재사용

새 Evidence 문법을 만들지 않고 기존 round-trip 계약 위에 source read 기능을 추가합니다.

③ candidate 단위 Runtime 격리

깨진 candidate는 제외+warning, 정상 candidate는 계속 반환합니다. Offline Gate는 missing 0을 강제합니다.

④ Top-3 + canonical Evidence 우선 전부

근거 없는 threshold나 Evidence 제한은 아직 추가하지 않습니다.

⑤ MCP 2 tools

search_jira_knowledge + get_jira_issue.

⑥ stale active 재검증

M9의 ki_가 여전히 active accepted인지 M10에서 다시 확인합니다.

9. M10에서 하지 말아야 할 것

- M7 DB Identity를 다시 설계하지 않기 - M8 Embedding Unit/Chunk를 임의 변경하지 않기 - M9 Top-k/threshold/reranker를 근거 없이 바꾸지 않기 - FAISS position을 stable Knowledge ID로 사용하지 않기 - MCP 내부에 별도 생성형 LLM을 넣지 않기 - production delta-first / HNSW / IVF를 M10에 섞지 않기 - Evidence 없이 LLM 답변만 만들어 완료로 판단하지 않기 반드시 할 것 DESIGN → IMPLEMENTATION → VALIDATION → DOCUMENTATION SYNC
