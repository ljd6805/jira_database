1. M2만으로는 왜 부족했나?

Context 누적

Issue A, B, C를 같은 대화 Context에서 계속 처리하면 이전 Issue의 내용이 다음 Issue 판단에 섞일 수 있습니다.

자기확증

같은 모델 Context가 자기가 만든 결과를 바로 검토하면 처음의 잘못된 추론을 계속 정답처럼 유지할 수 있습니다.

구조 오류와 의미 오류 혼합

필수 JSON field 누락처럼 코드로 확정 가능한 오류까지 LLM에게 판단시키면 비용과 비결정성이 늘어납니다.

Review 점수 과신

높은 점수 하나가 사실 왜곡이 없다는 보증서는 아닙니다. 결함 유형을 직접 찾아야 합니다.

2. 최종 실행 구조

Orchestrator ↓ 경로·상태만 관리 Fresh Worker · Issue 1건 ↓ Knowledge 생성 Python Validator ↓ 구조 PASS Fresh Defect Reviewer ↓ 의미 결함 검사 PASS / REGENERATE ↓ 필요 시 새 Worker Context에서 전체 재생성
핵심은 Reviewer 하나 추가가 아닙니다. Primary Context에는 workflow state만 남기고, 실제 Issue 의미는 매번 작은 child context에 격리하는 것이 핵심입니다.

4. Fresh Context란?

Primary Context전체 작업의 진행 상태를 관리하는 Context입니다. Issue 본문을 계속 쌓지 않습니다.
Fresh Worker현재 Issue를 처리하기 위해 새로 시작한 Worker Context입니다. 이전 Issue의 추론 흔적을 가져오지 않습니다.
Fresh ReviewerWorker와 별도의 새 Context에서 원본 입력과 결과를 검토합니다.
Attempt같은 Issue Knowledge를 생성한 한 번의 실제 시도입니다. 이 개념은 M6/M7에서 DB entity로 발전합니다.
Fresh Context 비유 시험 채점자가 이전 학생 답안에 대한 메모를 머릿속에 계속 들고 다음 학생을 채점하는 대신, 학생마다 새 답안지와 채점 기준만 보고 시작하는 것과 비슷합니다.

5. 왜 한 번에 Issue 하나만 처리했나?

규칙이유
한 번에 Issue 하나Issue별 결과·Review·Attempt 이력을 정확히 대응시키기 쉽습니다.
Worker / Reviewer 병렬 금지현재 Issue가 terminal state가 되기 전에 다음 Issue와 상태가 섞이지 않게 합니다.
Attempt마다 새 Worker이전 잘못된 추론에 고착되는 self-anchoring을 줄입니다.
부분 Patch 금지결함만 땜질하다 전체 의미 일관성이 깨지는 것을 피하고 원본 Input에서 전체 재생성합니다.
Reviewer는 보조 필터Review PASS를 절대적인 품질 인증서로 취급하지 않습니다.
처리량보다 품질 구조를 먼저 검증 파일럿 단계에서 병렬성을 최대화하지 않았습니다. 먼저 Context 격리와 재생성 이력이 명확한 구조를 만드는 것이 목적이었습니다.

6. Validator와 Reviewer의 차이

Python Validator가 잘하는 것

JSON parse 가능 여부, field 존재 여부, 타입, 정규식, evidence reference 형식처럼 답이 하나인 규칙.

LLM Reviewer가 필요한 것

원문보다 인과를 과장했는지, 핵심 사실을 빠뜨렸는지, 분류가 의미상 어색한지처럼 의미 판단이 필요한 결함.

설계 원칙: deterministic code로 확정할 수 있는 일은 code에 맡기고, 의미 해석이 필요한 일만 LLM에 맡깁니다.
