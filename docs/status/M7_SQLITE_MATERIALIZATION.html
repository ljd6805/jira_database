1. “Materialization”이 정확히 무엇인가?

프로젝트에서 Materialization은 M4/M5의 JSON artifact를 읽어 M6의 Logical Contract에 맞는 실제 SQLite row로 만드는 작업을 뜻합니다.

Knowledge Input / Knowledge / Review / Profile artifacts ↓ deterministic loader SQLite Schema v1 · 15 tables ↓ validation Evidence round-trip · Active uniqueness · FK · integrity · idempotency

중요: JSON을 단순히 한 컬럼에 통째로 넣는 것이 아니라, M6가 정의한 Entity와 관계를 실제 row와 ID로 materialize합니다.

4. raw와 canonical을 둘 다 기록하는 이유

Raw baseline 503

“과거 artifact에 실제 무엇이 있었는가?”를 보여주는 역사적 사실입니다. 사후에 원본 JSON을 고치지 않습니다.

Canonical DB 502

“현재 DB 계약에서 중복 없이 유효한 Evidence 관계가 몇 개인가?”를 보여줍니다.

비유 원본 영수증에 같은 품목이 실수로 두 줄 찍혀 있었다면 영수증 사진은 그대로 보존하되, 재고 DB에는 같은 물건을 중복 재고로 세지 않는 것과 비슷합니다.

5. 실데이터에서 발견한 두 가지 Historical Contract Drift

Review critical_issues object · 2건

Schema v0.3의 string[] 기대와 다른 historical object 형태가 남아 있었습니다. 원본은 수정하지 않고 compatibility layer가 type/location/message를 보존합니다.

Duplicate Evidence · 1건

같은 Knowledge Item 안에서 동일 Evidence ref가 한 번 중복됐습니다. DB UNIQUE contract는 약하게 만들지 않고 첫 occurrence만 canonical row로 적재합니다.

공통 원칙 과거 artifact를 “현재 규칙에 맞게 예쁘게” 고쳐 쓰지 않습니다. History는 그대로 두고 compatibility/canonicalization 경계에서 수용하며, 미래 Validator는 같은 잘못이 새로 생기지 않게 강화합니다.

6. M7 Gate는 무엇을 검사했나?

Count 정합성

M5 baseline과 M7 materialized count를 비교하고 raw/canonical 차이는 명시적으로 설명 가능해야 합니다.

Active Generation

30개 Issue 모두 승인된 active Generation이 정확히 하나씩 존재해야 합니다.

Evidence Resolver

Accepted Knowledge의 6종 Evidence가 실제 Source row로 모두 돌아가야 합니다.

Foreign Key / SQLite Integrity

끊어진 FK가 없고 PRAGMA integrity_check가 정상이어야 합니다.

Idempotency

같은 Run을 다시 materialize한 두 번째 snapshot이 첫 번째와 동일해야 합니다.
