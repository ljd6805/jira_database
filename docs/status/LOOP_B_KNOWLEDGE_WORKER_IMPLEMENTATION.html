2. 파일럿과 현재 자동화의 차이

기존 30건 파일럿

사람이 OpenCode에서 Prompt 입력 → jira-knowledge-orchestrator → 30개 Issue 순차 처리 → Knowledge / Review 생성

현재 운영 자동화

Python Loop B → State에서 latest Work 1건 선택 → 동적 Prompt 생성 → opencode run --agent jira-knowledge-orchestrator → Knowledge / Review 생성 → Python deterministic Gate → State checkpoint

따라서 Issue마다 사람이 OpenCode Agent를 직접 실행하는 작업은 자동화됐습니다. 반면 runner 자체를 정기적으로 시작하는 Scheduler는 아직 없습니다.

4. Python이 OpenCode에 전달하는 동적 Prompt

jira-knowledge-orchestrator v0.9로 Jira Knowledge Extraction 1건을 수행해줘. [KNOWLEDGE INPUT] <이번 Issue input JSON> [KNOWLEDGE OUTPUT] <이번 Work staging output> [KNOWLEDGE REVIEW] <이번 Work staging review dir> 지정한 로컬 INPUT FILE만 사실 근거로 사용해 기존 Worker → Validator → Reviewer 규칙대로 처리해. 외부 Jira/Web/MCP를 조회하지 말고, 최종 Knowledge와 Attempt별 Review JSON을 지정 경로에 저장해.

즉 Agent 이름만 전달하는 것이 아닙니다. 이번 실행마다 달라지는 Input/Output/Review 경로와 Local-only 경계가 Prompt로 같이 전달됩니다.

6. Skill 사용은 어떻게 요구되나?

Permission

Worker 본문

따라서 설계와 Agent 정의상 Skill 사용은 REQUIRED입니다. 하지만 사내 OpenCode 1.18.12 실제 실행 로그에서 Skill load가 발생한 것을 직접 확인한 Real Run은 아직 없습니다.

8. 왜 staging이 필요한가?

V2 OpenCode 시작 ↓ 느림 Loop A가 V3 Source Commit ↓ V2 = superseded ↓ V2 OpenCode 결과 도착 ↓ latest re-check = false ↓ canonical Knowledge 승격 X Embedding X Publish X

OpenCode가 느린 낮 시간에도 구버전 Knowledge가 서비스 최신 상태를 덮어쓰지 않게 합니다.

10. 파일럿 30건 Prompt와 현재 Per-Work Prompt

파일럿

INPUT DIR 30건 확인 → 전체 30건 순차 처리 → 전체 deterministic summary

운영

State가 Work 1건 선택 → Input FILE 1개 → Knowledge/Review 1건 → Processing Run / State가 전체 현황 관리

따라서 파일럿의 “30개인지 확인” 같은 Batch 지시는 현재 Prompt에 그대로 복사하지 않았습니다. Stable rule은 Agent/Skill, 실행 범위는 State/Python이 담당합니다.
