State DB latest + Source-ready Knowledge Work 조회 → processing_run 생성 → claim_work_item → knowledge_status = running OpenCode staging → data/knowledge/runs/<source_run>/staging/<processing_run>/<work>/... → jira-knowledge-orchestrator → Worker → Python Validator → Reviewer → final Review PASS 확인 Latest-Only Gate → OpenCode 응답 직후 work_item_is_latest 재검사 → stale이면 canonical 승격 금지 Canonical Knowledge → data/knowledge/runs/<source_run>/issues/<issue>.json → reviews/*.review.attemptN.json → AtomicTextWriter로 승격 State checkpoint → iv_ 계산 → Knowledge Contract 기반 kg_ 계산 → knowledge_status = completed → Embedding/Publish가 남았으므로 work_status = pending

3. 왜 staging이 필요한가?

정상 결과

OpenCode가 쓴 파일을 바로 공식 Knowledge로 취급하지 않습니다. JSON/Reviewer/latest 검증 후 canonical 위치로 원자 승격합니다.

느린 동안 Source 변경

V2 OpenCode가 돌던 중 V3가 Commit되면 V2 staging 결과는 남을 수 있지만 canonical Knowledge로 승격되지 않습니다.

V2 OpenCode 시작 ↓ 느림 Loop A가 V3 Source Commit ↓ V2 = superseded ↓ V2 OpenCode 결과 도착 ↓ latest re-check = false ↓ canonical promotion X Embedding X Publish X

4. 성공 판정은 LLM 마지막 문장이 아니다

OpenCode exit code만으로도 충분하지 않습니다. 아래를 모두 확인합니다.

5. Knowledge Generation identity

issue_version_id = iv_(jira_id + source_hash) Knowledge Contract knowledge_schema_version skill_version runtime_version model_profile ↓ logical_hash ↓ knowledge_generation_id = kg_(iv_ + contract)

model_profile을 runner에서 필수로 받습니다. OpenCode 설정/Worker/Reviewer 모델 구성이 바뀌었는데 같은 kg_로 섞이는 것을 막기 위해서입니다.

6. A → B → A와 stale-running

A Knowledge 처리 시작 knowledge_status = running ↓ B Source Commit A work_status = superseded ↓ 나중에 Jira가 다시 A semantic state A의 같은 sw_ 재활성화 work_status = pending knowledge_status = running (과거 stale checkpoint) ↓ 새 Worker는 running도 retryable로 간주 ↓ A를 다시 검증 처리 → knowledge_status = completed

이미 완성된 Knowledge/Embedding을 가진 Published A가 돌아오는 경우는 기존 artifact 재사용 정책이 유지됩니다. 이 보강은 완료되지 않은 stale-running이 다시 최신이 되는 경우를 위한 것입니다.

7. Processing Run 상태

현재 구현은 Knowledge checkpoint까지만 완료합니다. 따라서 Knowledge가 성공해도 아직 Embedding/Publish가 남아 있으면 processing_run.run_status = partial입니다.

Knowledge 성공 → Work knowledge_status = completed → Work 다시 pending (다음 stage resume용) → processing_run = partial Work 0 → processing_run = completed 선택 Work 전부 superseded → processing_run = completed 선택 Work 전부 Knowledge 실패 → processing_run = failed

Embedding/Publish가 연결된 뒤에는 한 Processing Run이 끝까지 PUBLISHED를 만드는 최종 형태로 확장합니다.

8. 실행 방법

# model_profile은 반드시 명시
python tools/run_knowledge_worker.py \
  --model-profile internal-opencode-knowledge-v1

# 이미 opencode serve를 띄워 재사용하는 경우
python tools/run_knowledge_worker.py \
  --model-profile internal-opencode-knowledge-v1 \
  --opencode-attach http://localhost:4096

# 순차 처리 수 조정
python tools/run_knowledge_worker.py \
  --model-profile internal-opencode-knowledge-v1 \
  --limit 3

초기 구현은 Single Worker입니다. --limit 3도 병렬 실행이 아니라 한 Processing Run에서 순차로 최대 3개를 처리합니다.
