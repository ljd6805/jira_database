Loop B Incremental Embedding을
latest-only로 구현했습니다.

Knowledge DB에 준비된 최신 candidate Generation 하나만 BGE-M3로 임베딩하고, 느린 API 호출 중 더 최신 Jira Source가 들어오면 구버전 Embedding을 다음 Publish 단계로 넘기지 않습니다.

1. 이번 구현 범위

Generation 단위 Corpus

load_generation_embedding_corpus()가 한 kg_의 accepted Knowledge Item만 deterministic 순서로 읽습니다.

Latest-only BGE-M3

OperationalEmbeddingWorker가 Source-ready/latest Work만 처리합니다.

Atomic staging artifact

Work별 corpus.jsonl과 embeddings.jsonl을 임시 파일 후 os.replace로 저장합니다.

Independent Processing Run

Embedding stage도 별도 processing_run으로 실행되고 완료 후 Publish 단계가 이어받도록 Work를 다시 pending으로 돌립니다.

2. 안전 순서

Knowledge DB candidate + accepted attempt → latest / Source Ready 확인 → embedding_status = running → Generation corpus 생성 → BGE-M3 호출 → latest 재확인 → embeddings.jsonl atomic 저장 → latest 재확인 → embedding_status = completed → work_status = pending → 다음 Publish stage가 이어받음

3. 느린 Embedding API 중 새 Version이 들어오면

Old Work A · BGE-M3 호출 중 ↓ Loop A에서 New Work B SOURCE_COMMITTED ↓ A → superseded ↓ BGE-M3 A 응답 도착 ↓ latestness 재검사 FAIL ↓ A embedding_status는 completed로 만들지 않음 A final embeddings artifact도 Publish 경로로 넘기지 않음 B가 다음 latest Work

이 규칙은 OpenCode 처리 중 stale guard와 같은 철학입니다.

5. 자동 검증

Candidate corpus

active 전환 전 candidate Generation도 Embedding 대상으로 읽음.

Success path

Corpus/Embedding artifact 생성 후에만 State completed.

Stale race

BGE-M3 호출 중 newer Source Commit 시 old Work completed 차단.

Retry

Embedding API 실패 시 latest Work는 failed로 남아 재시도 가능.

Processing Run

Embedding 완료 후 Work pending release, run은 Publish 미완료라 partial.

CI

전체 GitHub Actions pytest 회귀 PASS.

7. 다음 구현

Retrieval staging + Atomic Publish

다음 단계는 단순 FAISS 생성보다 더 중요합니다. Knowledge DB의 active Generation 전환과 FAISS active artifact 전환은 서로 다른 durability domain이므로, 둘 중 하나만 먼저 보이는 Half-Publish를 막는 coherent publish bundle/pointer 설계가 필요합니다.
