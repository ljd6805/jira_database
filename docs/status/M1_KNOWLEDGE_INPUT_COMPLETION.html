1. 입력과 출력

[ANALYSIS] issues.jsonl comments.jsonl attachments.jsonl issue_relationships.jsonl custom_field_catalog.jsonl custom_field_values.jsonl ↓ issue_key 기반 deterministic JOIN IssueKnowledgeInputBuilder ↓ [KNOWLEDGE INPUT] issues/<ISSUE_KEY>.json
핵심: Builder는 RAW를 다시 읽지 않습니다. HTML 정제·타입 검증은 M0의 ANALYSIS에서 이미 끝났기 때문입니다.

2. 왜 “Issue 1건 = Package 1건”인가?

읽기 단순화

Agent는 하나의 파일만 읽으면 해당 Issue의 설명, 댓글, 첨부 메타데이터, 관계, Custom Field를 볼 수 있습니다.

Context 격리

나중에 Issue별 fresh context를 만들기 쉬워집니다. 다른 Issue의 내용이 섞일 가능성을 줄입니다.

재사용 / 캐시

Issue별 package와 의미 hash가 있으므로 변경되지 않은 Issue를 다시 처리할지 판단하기 쉬워집니다.

3. M1에서 “하지 않는 일”

하지 않음

“이 증상 원인은 X다”, “Y가 최종 결정이다”, “Z를 해야 한다”처럼 의미를 새로 만들어내지 않습니다.

하는 일

“설명에 이 문장이 있다”, “댓글 ID 123에 이 내용이 있다”, “이 Attachment metadata가 있다”처럼 이미 존재하는 사실을 구조화합니다.

오류 원인도 분리됩니다.
Knowledge Input이 틀리면 deterministic Parser/JOIN 문제이고, Knowledge Input은 맞는데 후속 지식이 틀리면 Agent/Prompt/Skill 문제로 범위를 좁힐 수 있습니다.

4. Package 안에는 무엇이 들어가나?

영역보존 방식이유
Issue정규화된 핵심 Issue 사실Package의 중심 entity입니다.
Comment전체 보존 · sequence → comment_id 정렬댓글 순서가 문제 해결 과정의 시간 흐름을 담을 수 있기 때문입니다.
Attachmentmetadata · content_available=false파일 내용은 아직 분석하지 않았다는 사실을 명확히 합니다.
Relationshipcanonical edge + 현재 Issue의 role/direction관계 문구를 모델이 반대로 추론하지 않게 합니다.
외부 endpointother_package_available=false 가능상대 Issue package가 파일럿 밖이어도 관계 자체는 버리지 않습니다.
Custom Field현재 Issue의 non-null 값만 정의와 결합220개 Catalog 전체를 매 package마다 복제하지 않습니다.

5. source_path와 source_hash는 왜 필요한가?

Portable source_path

PC 절대 경로 대신 가능한 한 DATA ROOT 기준 상대경로를 사용합니다. 데이터 의미와 설치 위치를 분리합니다.

Semantic source_hash

Issue·Comment·Attachment·Relationship·Custom Field의 의미 사실을 canonical JSON으로 만들고 SHA-256을 계산합니다. 생성 시각이나 로컬 경로는 제외합니다.

source_hash 비유 Package의 “내용 지문”입니다. 파일 위치가 바뀌어도 내용이 같으면 같은 지문이 되고, 의미 있는 사실이 바뀌면 지문이 바뀝니다.
same semantic facts → same source_hash different facts → different source_hash

이 결정이 뒤의 M6에서 Issue Version을 판단하는 핵심 근거로 발전합니다.

6. Completion Gate와 Manifest

ANALYSIS 완료 확인

Issue / Comment / Attachment / Relationship / Custom Field 입력이 모두 완료 상태인지 먼저 확인합니다.

30개 Package를 원자적으로 작성

중간에 실패한 JSON을 정상 package처럼 남기지 않습니다.

stale package 정리

현재 ANALYSIS에 없는 과거 package가 결과 폴더에 유령처럼 남지 않게 snapshot 전체를 맞춥니다.

마지막에 manifest 작성

manifest.status=completed는 모든 package가 정상적으로 준비됐다는 완료 표식입니다.

중간 종료 시 새 manifest를 남기지 않습니다. “파일 몇 개가 보인다”와 “완료된 run”을 구분하기 위한 장치입니다.
