왜 재나?

DB 테이블 관계, Evidence 저장 방식, Embedding Unit을 “대충 이럴 것”이 아니라 실제 분포에 근거해 정하기 위해서입니다.

🧭
주의

30건 파일럿의 최대값을 전체 Jira의 영구 제한으로 쓰지 않습니다. 분포는 설계 근거이지 절대 상한이 아닙니다.

비유 창고 선반을 만들기 전에 실제 박스 30개의 크기와 무게를 재는 단계입니다. 가장 큰 박스가 19개 칸을 썼다고 “앞으로 모든 박스는 19칸 이하”라고 규칙을 박지는 않습니다.

전체 파이프라인에서 M5는 어디인가?

[M4] 실제 Jira 30건에서 Knowledge 생성 성공 ↓ [M5] 만들어진 결과의 크기·분포·Evidence·Attempt를 측정 ← 지금 여기 ↓ [M6] 측정값을 근거로 DB의 Entity와 관계를 설계 ↓ [M7] 그 설계를 실제 SQLite로 구현 ↓ [M8~M10] Vector 검색 + Evidence + MCP
M4와 차이

M4는 “파이프라인이 성공했는가?”, M5는 “성공한 결과가 실제로 어떻게 생겼는가?”를 봅니다.

M6와 차이

M5는 설계하지 않고 측정합니다. M6가 그 측정값을 보고 DB 구조를 결정합니다.

M5 완료 후

Knowledge Item 수, Evidence 1:N, retry 분포처럼 DB 설계에 필요한 실제 근거가 생겼습니다.

M5의 핵심 역할 “아마 이 정도겠지”를 버리고, 실제 데이터를 재서 다음 설계의 근거를 만드는 단계입니다.

1. M5가 측정한 것

M4 Knowledge / Review 30건 ↓ profile_knowledge_run.py ↓ 크기 · Category · Empty Array · Statement 길이 Evidence 수/종류 · Review Attempt · Outlier ↓ M6 DB Logical Schema M8 Embedding Unit 판단의 실측 근거

Privacy/보존 원칙: Profiler는 statement 원문을 profile 결과에 복사하지 않고 길이와 위치 정보 위주로 기록합니다.

7. 숫자에서 M6 설계로 어떻게 이어졌나?

Item이 여러 개다

Issue 하나에 평균 9.5개 Knowledge Item → Item은 독립 entity로 저장할 가치가 있습니다.

Evidence가 1:N이다

Item당 최대 13 ref → Evidence 별도 entity와 round-trip 계약이 필요합니다.

Attempt가 반복된다

30건 중 6건 재생성 → 최종 결과만 저장하면 품질 이력과 retry lineage가 사라집니다.

History와 검색 대상은 다르다

중간 Attempt 이력은 보존하되 기본 검색은 승인된 최종 Knowledge만 대상으로 해야 합니다.

M5 Gate PASS / DONE M6는 이제 추측이 아니라 실제 30건 분포를 근거로 Logical Schema를 설계할 수 있게 됐습니다.

8. 초보자가 자주 오해할 부분

Q. max 19 Item이니 DB에서 20개까지만 허용하면 되나?아니요. 30건 파일럿의 관찰값을 미래 전체 Jira의 hard limit로 사용하지 않습니다.
Q. Evidence 503은 M7 DB에도 그대로 503인가?아닙니다. M7 실데이터 적재에서 historical duplicate 1개가 발견되어 raw baseline 503은 보존하고 canonical DB row는 502가 됩니다.
Q. M5가 Embedding을 만들었나?아니요. Embedding은 M8 책임입니다.
