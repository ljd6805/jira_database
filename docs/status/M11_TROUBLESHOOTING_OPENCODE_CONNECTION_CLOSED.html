1. 처음 관찰한 문제

다른 프로젝트 workspace └─ opencode.jsonc cwd = "." opencode mcp list → jira-knowledge failed → MCP error -32000: Connection closed

2. 첫 번째 수정 · Python runpy warning

<frozen runpy>:128: RuntimeWarning: 'jira_collector.mcp_server.server' found in sys.modules ...

mcp_server.__init__가 server.py를 eager import한 상태에서 python -m jira_collector.mcp_server.server를 다시 실행해 발생했습니다. create_mcp_server를 lazy import로 바꿔 경고를 제거했습니다.

3. MCP stdio 자체는 정상인지 분리 검증

OpenCode를 제외하고 공식 MCP Python Client가 서버 subprocess를 직접 띄워 initialize → tools/list를 수행했습니다.

python tools/jira_knowledge/validate_m11_stdio_transport.py tool_count: 2 tools: get_jira_issue, search_jira_knowledge M11_STDIO_HANDSHAKE = PASS

이 결과로 MCP 서버 코드와 stdio handshake 자체는 정상임을 확인했습니다.

4. 실제 연결 실패의 핵심 · workspace / cwd

OpenCode local MCP cwd = "." ↓ "." = OpenCode를 실행한 workspace ↓ 다른 프로젝트에서 실행하면 jira_database/.env와 상대 artifact 기준을 사용하지 못함

Local stdio MCP는 OpenCode가 child process를 직접 실행합니다. 따라서 별도로 서버를 미리 띄우는 방식이 아니며, 상대 cwd는 OpenCode workspace를 기준으로 해석됩니다.

5. 해결 확인

jira_database 프로젝트 루트 ├─ .env ├─ data/ ├─ MCP code └─ opencode.jsonc ↓ opencode mcp list ↓ jira-knowledge CONNECTED ↓ Tool 2개 discovery PASS 명시적 Tool call PASS 자동 Tool selection PASS 근거 요청 → description/comment Evidence PASS
최종 판정: 초기 Connection closed는 M11 완료를 막는 문제가 아닙니다. 같은 서비스 workspace 기준 local Pilot에서 모든 M11 Gate가 PASS했습니다.

6. 재발 시 확인 순서

1. MCP 서비스 workspace 확인 2. cwd 상대경로 기준 확인 3. python -m jira_collector.mcp_server.server 직접 실행 4. validate_m11_stdio_transport.py 실행 5. opencode mcp list 확인 6. 필요 시 Python executable 절대경로로 격리 테스트

7. 최종 서비스에서는 이 문제가 어떻게 달라지나?

팀 공용 중앙 Remote MCP 서비스에서는 팀원 OpenCode가 local Python child process를 실행하지 않습니다. 중앙 서버 URL로 접속하므로 클라이언트 workspace의 cwd에 DB/FAISS/.env가 의존하지 않게 됩니다.

팀원 OpenCode ── Remote MCP / HTTPS ──→ 중앙 MCP 서버 ├─ .env ├─ SQLite └─ FAISS
