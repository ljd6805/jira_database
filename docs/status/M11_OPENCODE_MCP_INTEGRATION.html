2. 실제 사용자 흐름

일반적인 과거 유사 문제 탐색 질문 ↓ OpenCode가 MCP/Tool 이름 지시 없이 판단 ↓ search_jira_knowledge 자동 호출 ↓ Knowledge + Evidence를 이용해 답변 ↓ 사용자가 근거를 추가 질문 ↓ Jira description / comment 원문 Evidence 제시 M11-05 = PASS M11-06 = PASS

공개 문서에는 실제 업무 질문, Issue key, Jira 원문을 남기지 않고 동작 형태와 Evidence type만 기록합니다.

3. Local Pilot 연결

jira_database 프로젝트 루트 ├─ .env ├─ data/ ├─ MCP code └─ opencode.jsonc ↓ OpenCode가 child process로 local stdio MCP 실행 ↓ python -m jira_collector.mcp_server.server ↓ Tool discovery / Tool call / Auto selection / Evidence trace PASS

Local stdio MCP는 사용자가 서버를 미리 실행해 두는 구조가 아닙니다. OpenCode가 command를 보고 MCP child process를 직접 기동합니다.

4. 실제 stdio 경계 검증

python tools/jira_knowledge/validate_m11_stdio_transport.py tool_count: 2 tools: get_jira_issue, search_jira_knowledge M11_STDIO_HANDSHAKE = PASS

OpenCode를 제외한 공식 MCP client subprocess initialize → tools/list도 PASS했습니다.

5. 서비스 설정 정책 · .env

결정: 서비스 실행에 필요한 값은 .env를 기본으로 사용합니다. local Pilot에서는 프로젝트 루트, 최종 중앙 서비스에서는 서버 배포 디렉터리의 .env를 사용합니다.
JIRA_KNOWLEDGE_DB_PATH JIRA_RETRIEVAL_ARTIFACT_DIR BGE_M3_ENDPOINT BGE_M3_API_KEY optional BGE_M3_HEADERS_JSON optional 우선순위 1. 명시적 test env 2. OS 환경 변수 3. .env

6. 처음 다른 프로젝트에서 실패했던 이유

다른 OpenCode workspace + cwd = "." ↓ MCP cwd도 그 workspace ↓ jira_database/.env / 상대 artifact 기준과 불일치 ↓ Connection closed

이 문제는 MCP 자체의 stdio 호환성 문제가 아니었습니다. 같은 jira_database 루트에서 Pilot을 실행해 정상 연결과 실제 Tool 사용을 확인했습니다.

7. 최종 팀 공용 서비스 구조

팀원 A OpenCode ─┐ 팀원 B OpenCode ─┼── Remote MCP / HTTPS ─→ 중앙 jira-knowledge MCP 팀원 C OpenCode ─┘ ├─ SQLite ├─ FAISS ├─ .env └─ BGE-M3 API

팀원 PC가 jira_database clone, SQLite, FAISS, BGE secret을 소유하지 않도록 하는 것이 최종 목표입니다. Remote MCP Service Target에 목표 아키텍처를 정리했습니다.

8. M11 완료의 의미

검색 가능

OpenCode가 사용자 질문을 보고 Jira MCP 검색을 스스로 선택할 수 있습니다.

근거 가능

필요하면 Knowledge에서 실제 description/comment Evidence source까지 추적할 수 있습니다.

Agent 독립

MCP는 생성형 LLM을 포함하지 않고 외부 Agent가 Tool로 소비합니다.
