M11은 프로젝트 내부에 Agent를 구현하는 단계가 아닙니다. M10에서 완성한 read-only MCP 서버를 외부 소비자인 OpenCode Agent에 등록하고, 실제 Agent가 두 Tool을 발견·호출·활용할 수 있는지 검증하는 통합 Pilot입니다.

범위

무엇을 하고, 무엇을 하지 않나?

하는 것

OpenCode에서 jira-knowledge MCP를 실행하고 search_jira_knowledge, get_jira_issue 두 Tool을 실제 Agent가 사용하는지 확인합니다.

하지 않는 것

이 저장소 안에 Agent framework, planner, sub-agent, memory, loop를 새로 구현하지 않습니다.

1. 전체 연결

jira_database └─ jira-knowledge MCP ├─ search_jira_knowledge └─ get_jira_issue │ stdio ▼ OpenCode Agent │ ▼ 사용자 질문 │ ▼ Knowledge + Evidence 기반 답변

2. 서비스 설정 정책 · .env

결정: 실제 서비스 실행에 필요한 환경 값은 프로젝트 루트의 .env에 둡니다. PowerShell의 $env:나 Linux export는 개발·진단·일시 override 용도로만 사용합니다.
설정용도서비스 .env

M10_REAL_RUN_QUERYM10 검증기 전용 질문서비스에는 넣지 않음

3. 설정 우선순위

1. 명시적으로 주입한 test env → 테스트 재현성용, .env를 읽지 않음 2. OS 환경 변수 → CI / 진단 / 긴급 override 3. .env → 실제 서비스의 기본 설정

python-dotenv는 override=false로 읽기 때문에 이미 존재하는 OS 환경 변수를 덮어쓰지 않습니다.

4. 보안 원칙

.env는 Git 제외

실제 DB 경로, BGE endpoint/header/key 등은 공개 저장소에 커밋하지 않습니다.

.env.example만 공유

변수 이름과 설명만 저장소에 남기고 실제 값은 비워둡니다.

Windows와 Linux는 경로 값이 달라도 괜찮습니다. 배포 환경별 .env가 그 차이를 흡수합니다.

7. Windows → Linux

현재 Pilot은 Windows에서 진행하지만 서비스 설정 계약은 OS 독립적으로 .env를 사용합니다. Linux 포팅 시 코드는 그대로 두고 경로와 필요한 endpoint 값만 Linux 환경의 .env로 교체하는 방향을 기본으로 합니다.
