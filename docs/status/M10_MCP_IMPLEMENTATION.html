이미 검증된 M9 검색과 M10 Evidence 복원을 그대로 재사용합니다.

비유 집 안 배선을 다시 만드는 것이 아니라, 이미 잘 동작하는 전기 시스템 앞에 표준 콘센트 두 개를 설치한 것입니다.

1. 외부에 보이는 도구는 정확히 2개

search_jira_knowledge

자연어 질문을 받아 BGE-M3 Query Embedding → M9 FAISS Top-k → M10 Evidence Package까지 한 번에 반환합니다.

get_jira_issue

Issue key를 이미 알고 있을 때 현재 active Issue snapshot, 댓글, 관계, 첨부 metadata, custom field를 읽습니다.

Tool 수를 늘리지 않았습니다. search/resolve를 별도 MCP call로 쪼개지 않아 Agent가 불필요한 반복 호출을 할 필요가 없습니다.

2. 내부 구조

src/jira_collector/mcp_server/ ├─ service.py ← 검색/Evidence를 도구 친화 API로 조합 ├─ runtime.py ← M7 DB + M9 artifact + BGE runtime load ├─ server.py ← MCPServer + 2 tool 등록 └─ __init__.py Agent ↓ MCP search_jira_knowledge ↓ query embedding → M9 search → M10 builder ↓ Evidence Package

3. 읽기 전용을 말로만 선언하지 않음

MCP Tool Annotation read_only_hint = true open_world_hint = false 그리고 실제 SQLite 연결 URI mode=ro PRAGMA query_only = ON

MCP annotation은 Client에게 주는 힌트이므로 보안 경계로만 믿지 않습니다. DB 연결 자체가 DELETE/UPDATE/INSERT를 거부하도록 이중으로 막았습니다.

테스트: read-only 연결에서 DELETE FROM knowledge_item을 시도하면 SQLite OperationalError가 발생하는 것을 확인했습니다.

4. MCP 내부에는 생성형 LLM이 없음

MCP가 하는 일 query → BGE-M3 → FAISS → Knowledge → Evidence MCP가 하지 않는 일 Evidence를 읽고 자연어 최종 답변 생성

최종 답변은 이 MCP를 사용하는 Agent의 LLM 책임입니다. 따라서 검색 오류와 답변 오류를 계속 분리할 수 있습니다.
