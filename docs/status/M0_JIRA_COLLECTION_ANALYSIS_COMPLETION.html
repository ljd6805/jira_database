왜 필요했나?

Jira 화면은 사람이 읽기 좋지만, 프로그램이 반복 처리하려면 원본을 일정한 형태로 안전하게 저장해야 합니다.

🧱
무엇을 만들었나?

Jira API 응답을 RAW로 보존하고, 그 RAW를 Issue·Comment·관계·Custom Field 등의 ANALYSIS JSONL로 변환했습니다.

➡️
그래서 무엇이 가능해졌나?

다음 단계는 Jira 서버를 다시 두드리지 않고 로컬의 검증된 사실 데이터만 사용해 작업할 수 있게 됐습니다.

비유 Jira를 도서관이라고 하면, M0는 책을 요약하는 단계가 아닙니다. 먼저 책을 안전하게 복사해 보관하고, 제목·저자·목차처럼 찾기 쉬운 목록을 따로 만드는 단계입니다.

1. M0의 입력과 출력

Jira REST API ↓ 읽기 전용 Collector ↓ [RAW] Jira JSON snapshot ↓ Jira 재호출 없음 Parser / Exporter ↓ [ANALYSIS] 정규화 JSONL
RAWJira에서 읽은 사실을 가능한 한 손대지 않고 보존한 기준 데이터입니다. Parser가 잘못돼도 RAW에서 다시 만들 수 있습니다.
ANALYSISRAW에서 결정적으로 파생한 분석 친화 데이터입니다. HTML 정리, 타입 정규화, 관계 표준화가 끝난 상태입니다.
Checkpoint수집이 중간에 끊겼을 때 어디까지 끝났는지 기억하는 표시입니다. 처음부터 다시 받을 필요를 줄입니다.
Atomic write파일을 절반만 쓴 상태로 남기지 않기 위해 임시 파일을 완성한 뒤 한 번에 교체하는 저장 방식입니다.

2. 왜 RAW를 먼저 저장했나?

가장 중요한 결정은 Raw First였습니다. AI나 Parser가 틀려도 원본 사실로 돌아갈 수 있어야 하기 때문입니다.

피한 구조

Jira → 즉시 요약/가공 → 가공 결과만 저장

가공 로직이 틀리면 무엇이 원래 사실이었는지 확인하기 어렵습니다.

채택한 구조

Jira → RAW 보존 → ANALYSIS 파생

후속 로직이 바뀌어도 RAW에서 재처리할 수 있고, Jira API 재호출도 줄일 수 있습니다.

책임 분리 Collector는 Jira 통신·pagination·rate limit·retry·원본 저장을 담당하고, Parser/Exporter는 로컬 RAW만 읽어 정규화합니다.

3. 실제 수집 규칙

항목확정 규칙쉽게 해석하면
프로젝트인증 계정이 조회 가능한 모든 프로젝트 발견프로젝트 key를 코드에 박아두지 않고 계정이 볼 수 있는 목록을 API로 찾습니다.
파일럿 Issue프로젝트별 최근 수정 Issue 최대 30개전체 프로젝트를 찾되, 첫 실험에서는 각 프로젝트의 양만 제한합니다.
Commentdedicated endpoint를 startAt=0부터 끝까지 전체 수집Issue 응답 안에 댓글이 일부만 들어오는 환경 차이에 의존하지 않습니다.
Attachment바이너리 다운로드 안 함, metadata만 보존파일 내용 분석은 뒤로 미루고 파일명·크기·유형 같은 사실만 확보합니다.
Rate limit20 req/min · concurrency=1최대 속도보다 Jira 서버에 부담을 주지 않는 안전한 수집을 우선합니다.
TLSverify_ssl 기본 true, 필요 시 설정으로 false사내 인증서 환경 대응을 코드 하드코딩이 아니라 설정으로 분리했습니다.
재개SQLite checkpoint / resume중간 실패 후 이미 끝난 Issue를 다시 받지 않습니다. 이 SQLite는 아직 업무지식 DB가 아닙니다.

4. 저장되는 모습

RAW

data/raw/runs/<run_id>/projects/<project_key>/ ├─ project.json ├─ issue_search/page_*.json └─ issues/<issue_key>/ ├─ issue.json └─ comments/page_*.json

ANALYSIS

issues.jsonl comments.jsonl attachments.jsonl issue_relationships.jsonl custom_field_catalog.jsonl custom_field_values.jsonl summary.json parse_warnings.jsonl

핵심: ANALYSIS가 편해서 RAW를 버리는 것이 아닙니다. RAW는 사실의 기준이고 ANALYSIS는 이후 프로그램이 쓰기 좋은 파생 계층입니다.

5. 관계와 Custom Field는 어떻게 다뤘나?

Relationship

Issue Link와 Parent/Subtask를 방향이 일관된 canonical edge로 바꿨습니다. 나중에 “A가 B를 막는다” 같은 관계를 같은 방식으로 조회하기 위함입니다.

Custom Field

필드 정의 Catalog와 Issue별 실제 값을 분리했습니다. Plugin 필드는 선언된 schema만 믿지 않고 실제 값의 형태도 따로 기록합니다.

오해 주의 M0는 Jira 내용을 “이해”하거나 “원인”을 찾지 않습니다. 여기서 하는 것은 사실을 잃지 않고 구조를 정리하는 일뿐입니다.

8. M1으로 무엇을 넘겼나?

분산된 ANALYSIS 사실

Issue, Comment, Attachment, Relationship, Custom Field가 각각 검증된 JSONL로 존재합니다.

안정적인 식별자

Issue key, Comment ID, Attachment ID, 관계 ID 등 후속 단계가 다시 연결할 수 있는 키를 보존했습니다.

완료 여부를 판정할 근거

summary/warning과 checkpoint가 있어 일부만 만들어진 데이터를 완료 결과처럼 넘기지 않습니다.

Q. M0에서 LLM을 썼나?아니요. M0는 Jira 사실 수집과 deterministic 정규화 단계입니다.
Q. M0의 SQLite가 지금의 Knowledge DB인가?아니요. 당시 SQLite는 Collector의 checkpoint/resume 상태 저장용입니다. 실제 Knowledge DB materialization은 M7입니다.
