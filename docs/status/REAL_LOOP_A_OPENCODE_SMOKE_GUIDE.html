REAL SMOKE GUIDE · UPDATED 2026-09-01

Project 1개 → Issue 1개 → Source Ready → Real OpenCode

Production/Pilot data를 건드리지 않고 data_smoke/에서 실제 Jira Loop A와 실제 사내 OpenCode Knowledge Automation을 연속 검증합니다. 2026-09-01 실제 Linux Smoke에서 발견된 stale running 복구, headless runtime model, permission 규칙까지 반영합니다.

0. 이번 Smoke의 성공 정의

G1 · REAL LOOP A Project 1개 발견 → Issue 최대 1개 수집 → RAW / ANALYSIS / Knowledge Input 생성 → SOURCE_COMMITTED → Source Ready Work 1건 G2 · REAL INTERNAL OPENCODE Source-ready latest Work 1건 → stale in-flight recovery → run_knowledge_worker.py → opencode run --model codemate/CodeLLMPro --agent jira-knowledge-orchestrator → Worker → Skill → Validator → Reviewer → Knowledge / Review artifact 생성 → knowledge_status = completed 별도 확인 실제 jira-knowledge-extraction Skill load trace → OpenCode 실행 trace가 보일 때 확인 → trace가 없으면 이 항목만 PENDING 유지

8. Source Ready Work 확인

python - <<'PY'
import sqlite3
from pathlib import Path

db = Path("data_smoke/state/collector.db")
con = sqlite3.connect(db)
con.row_factory = sqlite3.Row
rows = con.execute("""
SELECT work_item_id, observed_issue_key, work_status,
       last_observed_source_run_id, last_source_committed_run_id,
       knowledge_status, embedding_status, publish_status
FROM sync_issue_change
ORDER BY created_at, work_item_id
""").fetchall()

print(f"work_count = {len(rows)}")
for row in rows:
    source_ready = (
        row["last_source_committed_run_id"] is not None
        and row["last_source_committed_run_id"] == row["last_observed_source_run_id"]
    )
    print(dict(row))
    print(f"SOURCE_READY = {source_ready}")
PY
G1 PASS 조건

최소 한 Work에서 last_source_committed_run_id = last_observed_source_run_id이고 실제 RAW/ANALYSIS/Knowledge Input이 존재합니다.

11. model_profile과 opencode_model은 다른 값입니다

이름예역할
--model-profileinternal-opencode-knowledge-v1Knowledge Generation identity에 기록하는 논리적 구성 이름. Worker/Reviewer/Skill/Schema 등 계약 버전을 묶어 표현합니다.
--opencode-modelcodemate/CodeLLMPro실제 opencode run --model에 전달되는 Runtime LLM ID입니다.
model_profile internal-opencode-knowledge-v1 │ └─ “이 Knowledge를 어떤 논리적 구성으로 만들었나?” opencode_model codemate/CodeLLMPro │ └─ “지금 실제 OpenCode가 어떤 LLM을 호출하나?”
왜 분리했나?

기존에는 model_profile 이름이 있어도 실제 opencode run 명령에 모델을 전달하지 않았습니다. 그래서 TUI에서 잘 되던 모델과 headless 기본 모델이 달라질 수 있었습니다. 이제 Runtime model을 명시적으로 고정합니다.

12. Real Internal OpenCode Knowledge Smoke

# 일반 실행 · CodeLLMPro가 기본 Runtime model
python tools/run_knowledge_worker.py \
  --local-config config/settings.smoke.yaml \
  --model-profile internal-opencode-knowledge-v1 \
  --opencode-model codemate/CodeLLMPro \
  --limit 1

# 이전 Worker가 확실히 비정상 종료되어 running에 고착된 Smoke Work가 있을 때
python tools/run_knowledge_worker.py \
  --local-config config/settings.smoke.yaml \
  --model-profile internal-opencode-knowledge-v1 \
  --opencode-model codemate/CodeLLMPro \
  --stale-after-seconds 0 \
  --limit 1

codemate/CodeLLMPro는 현재 기본값이므로 옵션을 생략해도 같습니다. 하지만 Real Smoke 기록에서는 실제 사용 모델을 눈으로 확인하기 쉽도록 명시하는 것을 권장합니다.

14. OpenCode가 멈춘 것처럼 보일 때

Python Worker 시작 → opencode_event=knowledge_run_started 로그 → subprocess.run(opencode run ...) → OpenCode stdout/stderr는 Python이 capture → 종료 전까지 터미널에는 OpenCode 세부 출력이 보이지 않을 수 있음 → opencode_event=knowledge_run_finished 로그

이번 개정에서는 최소한 issue_key / agent / model / timeout을 포함한 시작·종료 structured log를 남깁니다. 실제 OpenCode 내부 trace가 필요하면 Python wrapper와 분리해 opencode run --print-logs --log-level DEBUG ...로 직접 진단합니다.

15. Permission Error: 권한을 풀지 말고 불필요한 Tool 호출을 제거합니다

2026-09-01 Real Smoke CodeLLMPro + jira-knowledge-orchestrator → headless 실행 자체는 정상 → 모델이 시작 직후 bash로 echo "=== WORKSPACE ===" 실행 시도 → Orchestrator permission의 bash:* = deny에 의해 차단 → permission system은 정상 동작
해결 원칙

bash: allow로 풀지 않습니다. Per-Work Orchestrator에는 workspace preflight가 필요 없으므로 echo/pwd/ls/cat/find/test/mkdir 같은 shell 탐색을 금지했습니다. Worker의 Bash는 deterministic validate_knowledge.py만 허용하며 Reviewer는 Bash가 필요 없습니다.

18. Skill-load trace는 별도 항목

Knowledge Smoke 성공과 실제 Skill load trace 증명은 구분합니다. Agent 정의상 Worker는 jira-knowledge-extraction Skill 사용이 REQUIRED지만, 실제 trace가 보이지 않으면 Skill-load 확인만 PENDING으로 남깁니다.

19. 2026-09-01 실제 Smoke에서 발견한 stale running 결함

1차 Knowledge Run → LLM 문제 → Knowledge output JSON 없음 → 정상적으로 failed 처리 2차 Run → failed Work 재선택 → work_status=running → knowledge_status=running → 실행 중 비정상 종료 → terminal cleanup까지 도달하지 못함 3차 Run → running Work는 backlog selector에서 제외 → selected_count=0 → Work가 영구 고착될 수 있음
결론

일반 Exception Retry만으로는 충분하지 않습니다. 프로세스 kill, 세션 종료, 서버 장애처럼 Python cleanup이 실행되지 않는 경우를 위한 Crash Recovery / Stale In-flight Recovery가 필요합니다.

20. 구현된 자동 복구 계약

Runner 시작 → running Work 조회 → stage 상태도 running인지 확인 → last_processing_run_id 확인 → Processing Run이 이미 terminal이면 즉시 orphan 판정 또는 → updated_at이 stale cutoff보다 오래됐는지 확인 → stale Work를 failed backlog로 복구 → 중단된 processing_run을 failed로 닫음 → structured log stale_inflight_recovered stale_processing_run_closed → 같은 Runner에서 바로 재선택/재처리

State Schema v3는 변경하지 않았습니다. 현재의 updated_at, last_processing_run_id, processing_run.run_status만 사용합니다. Knowledge와 Embedding runner 모두 같은 복구 모듈을 사용합니다.

21. 실패했을 때 무엇을 지우나?

Loop A / Source Sync 실패 → 원인 수정 → rm -rf data_smoke → G1부터 재시작 가능 G1 PASS 후 Knowledge/OpenCode 실패 → data_smoke 삭제 금지 → error_message / processing_run 기록 보존 → 정상 failed이면 그냥 Knowledge Worker 재실행 → running 고착이면 --stale-after-seconds 0으로 recovery + 재실행 Embedding에서 같은 종류의 running 고착 → data_smoke 삭제 금지 → run_embedding_worker.py --stale-after-seconds 0 사용 가능
