이 프로젝트는 도대체 무엇을 만드는가?

Jira에 흩어진 업무 경험을 “원문 근거를 잃지 않는 검색 가능한 지식”으로 만들고, 나중에 Agent가 MCP를 통해 찾아 쓰게 만드는 프로젝트입니다.

1. 사실을 안전하게 확보Jira → RAW → ANALYSIS → Issue별 Knowledge Input
2. 검색할 의미를 추출하고 품질 검증Knowledge Schema/Skill → Fresh Worker/Reviewer → Human Validation
3. History와 근거를 잃지 않는 DB 구축Issue Version → Generation → knowledge_attempt → Item → Evidence → SQLite
4. 검색 인프라 구축현재 M8 Embedding → M9 FAISS → M10 Evidence Builder/MCP Functional MVP
한 문장 비유 Jira를 그냥 AI에게 통째로 던지는 게 아니라, 원본 보관소와 검증된 색인 카드를 먼저 만들고, 지금은 그 색인 카드에 “의미 좌표”를 붙이는 중입니다.

3. 현재 DB Identity를 쉬운 말로

jira_id ↓ 같은 Jira 업무의 장기 ID iv_ Issue Version ↓ source_hash가 바뀔 때만 새 의미 Version kc_ Knowledge Contract ↓ 어떤 Schema/Skill 규칙인가 kg_ Knowledge Generation ↓ 한 Version+Contract의 retry lineage ka_ knowledge_attempt · attempt_no 1/2/3... ↓ 실제 생성 시도 ki_ Knowledge Item ↓ 검색할 의미 문장 ke_ Knowledge Evidence ↓ 실제 원문 근거
Generation → Attempt가 핵심입니다. knowledge_attempt가 실제 1차/2차/3차 생성 회차이고 ka_는 attempt_no와 Generation을 기반으로 결정됩니다. 실패한 시도의 Review History도 가능한 범위에서 보존합니다.

4. M7이 왜 중요한가?

실제 DB

M6 설계가 문서에만 있는 것이 아니라 15개 SQLite table과 deterministic loader로 구현됐습니다.

근거 복원

Accepted Knowledge의 Evidence가 summary/description/comment/attachment/relationship/custom_field source로 모두 돌아가야 합니다.

재실행 안정성

같은 Run을 두 번 materialize해도 snapshot이 같아 idempotent=true를 확인했습니다.

M5 raw Evidence 503 M7 canonical Evidence 502 Historical exact duplicate 1개 → raw는 수정하지 않음 → DB는 canonical 502 Evidence Failure 0 FK Failure 0 Integrity OK failures []

5. 현재 M8에서 “Chunk 안 함”은 무슨 뜻인가?

M5에서 285개 Knowledge statement 길이를 재보니 mean 114.01자, p95 206.4자, max 447자였습니다. 이미 각각이 짧은 atomic statement여서 M8 baseline은 Knowledge Item 1개 = Embedding Unit 1개로 정했습니다.

잘못된 해석

“BGE-M3에서는 Chunk를 쓰면 안 된다.”

정확한 해석

“현재 corpus에서는 Chunk가 필요하다는 실측 근거가 아직 없으므로 baseline에서 추가하지 않는다.”

6. M8-02에서 구현된 안전장치

Deterministic identity

ec_는 embedding contract, emb_는 Item+text hash+contract 기반 artifact ID입니다.

Response mapping

응답 배열 위치를 맹신하지 않고 OpenAI-compatible data[].index를 기준으로 input과 vector를 연결합니다.

Dimension guard

모든 vector가 정확히 1024인지 검사하고 다르면 실패합니다.

Retry 분리

network/timeout/429/5xx는 제한 재시도, 400/401/403/404와 schema/index/dim 오류는 즉시 실패합니다.

Atomic publish

5개 batch가 모두 성공한 뒤에만 final embedding artifact가 나타납니다.

M9 boundary

M8은 vector 생성까지. FAISS index/retrieval은 아직 만들지 않습니다.

7. 지금 해야 할 실제 Action

Gate 숫자 확인

corpus_rows=285, embedding_rows=285, batch_count=5, embedding_dimension=1024.

M8 완료 기록 동기화

실제 API Gate가 PASS해야 M8을 닫고 M9 FAISS로 이동합니다.

현재 병목은 “실제 사내 BGE-M3 응답 검증” 하나입니다.

8. M9와 M10은 무엇을 하게 되나?

M9 · FAISS + Active Retrieval

검증된 1024-d vector를 FAISS에 넣고, 질문을 같은 BGE-M3로 vector화해 active Knowledge Top-K를 찾고 embedding_id → knowledge_item_id mapping을 검증합니다.

M10 · Functional MVP Gate

검색된 Knowledge/Evidence를 Agent가 쓸 수 있는 증거 패키지로 만들고 MCP를 통해 제공하는 첫 기능형 MVP Gate입니다.

순서를 섞지 않습니다. 실제 embedding이 검증되지 않은 상태에서 FAISS나 MCP를 먼저 붙이면 vector 생성 오류와 retrieval 오류를 구분하기 어려워집니다.
