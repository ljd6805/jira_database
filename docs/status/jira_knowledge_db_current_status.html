3. G4를 구현하며 바뀐 핵심 설계

처음 생각했던 Cross-DB ATTACH 방식은 폐기했습니다.

초기 구현은 Knowledge DB와 State DB를 SQLite ATTACH한 뒤 하나의 transaction으로 묶으려 했습니다. 그러나 State 개정 3은 의도적으로 WAL을 사용하고, SQLite의 multi-file crash atomicity 조건과 맞지 않았습니다. 테스트를 쉽게 만들기 위해 WAL을 끄지 않고 G4 프로토콜 자체를 다시 설계했습니다.

최종 G4 1. latest publish-ready Work claim 2. target + 현재 active Generation 전체 snapshot 계산 3. immutable Retrieval bundle staging 4. FAISS / mapping / manifest / Generation set 검증 5. latestness 재검사 + State BEGIN IMMEDIATE 6. Knowledge DB transaction old active(target Jira) → historical target candidate → active ← service-facing commit point 7. State transaction work_status → published publish_status → published processing_run → completed
State 개정 3 그대로 유지

G4 때문에 State Schema를 올리지 않았고 WAL도 그대로 유지합니다. active Knowledge Generation 집합과 정확히 같은 Generation 집합을 가진 immutable Retrieval bundle만 서비스 head로 인정합니다.

4. G4 테스트가 검증하는 것

첫 Publish

candidate → active, State published, 실제 FAISS 검색까지 연결되는지 검증합니다.

Full Snapshot 교체

A v1 + B에서 A v2 Publish 시 Retrieval에는 A v2 + B만 남고 A v1은 historical이 되는지 검증합니다.

State WAL 유지

Publish 전후 State DB journal mode가 계속 WAL인지 확인합니다.

Crash / Race 복구

Knowledge head commit 뒤 State 실패와 staging 중 다른 Issue Publish race를 강제로 만들고 fail-closed 및 재시도 수렴을 확인합니다.

MCP 요청 중 Publish

요청이 시작된 Knowledge read snapshot과 같은 Generation 집합의 FAISS를 사용하므로 중간 Publish가 발생해도 한 요청은 끝까지 같은 head를 봅니다.

하위 호환

기존 JIRA_RETRIEVAL_ARTIFACT_DIR 직접 지정 경로도 유지합니다.

5. MCP의 G4 연결 방식

권장 · Operational Root

JIRA_RETRIEVAL_ARTIFACT_ROOT를 설정하면 각 MCP 검색 요청이 시작될 때 Knowledge DB read snapshot을 만들고, 그 snapshot의 active Generation 집합과 정확히 맞는 runs/<processing_run_id> bundle을 선택합니다.

하위 호환 · Direct Directory

기존 JIRA_RETRIEVAL_ARTIFACT_DIR도 계속 지원합니다. ROOT가 있으면 ROOT가 우선합니다.

MCP request → Knowledge DB BEGIN read snapshot → active Generation IDs 읽기 → 같은 Generation 집합의 immutable Retrieval bundle 선택 → 그 bundle manifest로 query embedding → 그 bundle FAISS 검색 → 같은 Knowledge snapshot으로 Evidence resolve → request 종료 / read snapshot 종료
Publish가 요청 중간에 일어나도 안전

이미 시작된 요청은 옛 Knowledge snapshot + 옛 FAISS bundle을 끝까지 함께 보고, 다음 요청부터 새 active Generation + 새 FAISS bundle을 봅니다. 따라서 MCP 재시작을 G4 Publish의 필수조건으로 두지 않습니다.
