3. G4를 구현하며 바뀐 핵심 설계

처음 생각했던 Cross-DB ATTACH 방식은 폐기했습니다.

초기 구현은 Knowledge DB와 State DB를 SQLite ATTACH한 뒤 하나의 transaction으로 묶으려 했습니다. 하지만 CI에서 실제 State DB가 WAL임을 확인했고, SQLite의 multi-file crash atomicity 조건과 맞지 않았습니다. 테스트를 쉽게 만들기 위해 WAL을 끄지 않고 G4 프로토콜 자체를 다시 설계했습니다.

최종 G4 1. latest publish-ready Work claim 2. target + 현재 active Generation 전체 snapshot 계산 3. immutable Retrieval bundle staging 4. FAISS / mapping / manifest / Generation set 검증 5. latestness 재검사 + State BEGIN IMMEDIATE 6. Knowledge DB transaction old active(target Jira) → historical target candidate → active ← service-facing commit point 7. State transaction work_status → published publish_status → published processing_run → completed
State 개정 3 그대로 유지

G4 때문에 State Schema를 올리지 않았고 WAL도 그대로 유지합니다. active Knowledge Generation 집합과 정확히 같은 Generation 집합을 가진 immutable Retrieval bundle만 서비스 head로 인정합니다.

4. G4 CI가 검증한 것

첫 Publish

candidate → active, State published, 실제 FAISS 검색까지 연결됩니다.

Full Snapshot 교체

A v1 + B에서 A v2 Publish 시 Retrieval에는 A v2 + B만 남고 A v1은 historical이 됩니다.

State WAL 유지

Publish 전후 State DB journal mode가 WAL인지 확인합니다.

Crash / Race 복구

Knowledge head commit 뒤 State 실패와 staging 중 다른 Issue Publish race를 강제로 만들고 fail-closed 및 재시도 수렴을 확인합니다.

CI #1102 · PASS → 기존 회귀 + G4 WAL-safe 테스트 PASS → Cross-DB ATTACH 설계 폐기 후 corrected protocol 검증 완료

5. MCP의 G4 연결 방식

권장 · Operational Root

JIRA_RETRIEVAL_ARTIFACT_ROOT를 설정하면 MCP 시작 시 Knowledge DB의 active Generation 집합과 정확히 맞는 runs/<processing_run_id> bundle을 찾아 pin합니다.

하위 호환 · Direct Directory

기존 JIRA_RETRIEVAL_ARTIFACT_DIR도 계속 지원합니다. ROOT가 있으면 ROOT가 우선합니다.

Hot reload는 아직 하지 않습니다.

한 요청 안에서 query embedding manifest와 FAISS index가 바뀌는 race를 피하기 위해 G4에서는 MCP 시작 시 하나의 bundle을 고정합니다. safe hot reload는 필요성이 확인될 때 별도 설계합니다.
