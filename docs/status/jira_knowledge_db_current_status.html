핵심 아키텍처 원칙

1
[RAW] Source of Truth

Jira API 원본. 재처리·감사의 최종 기준.

2
[ANALYSIS] 결정적 정규화

Issue/Comment/Attachment/Relationship/Custom Field를 생성형 LLM 없이 파싱.

3
[KNOWLEDGE INPUT] Issue 단위 사실 계약

Worker가 다른 Issue를 읽지 않아도 되도록 한 파일로 조립.

4
[KNOWLEDGE] 검색용 의미 압축

문제/목표, 발견, 작업·결정, 결과, 미해결 항목을 Evidence와 함께 추출.

5
[REVIEW] 결함 확률 감소

Fact/Causal/Evidence/Classification/Missing/Duplication Audit. 품질 인증기는 아님.

6
[DB/VECTOR] 검색 구조

Knowledge를 찾고 Evidence locator로 실제 Jira 원문을 복원.

7
Agent + MCP

MCP는 deterministic retrieval, Agent가 원문을 읽고 최종 답변.

Knowledge Extraction Skill v0.9 상세

Skill은 Issue 한 건의 의미 추출 규칙만 담당하고, 순서·검증·재생성은 Orchestrator/Worker/Reviewer/Validator가 분담합니다.

구조

jira_database/ ├─ .opencode/ │ ├─ agents/ │ │ ├─ jira-knowledge-orchestrator.md │ │ ├─ jira-knowledge-worker.md │ │ └─ jira-knowledge-reviewer.md │ └─ skills/jira-knowledge-extraction/ │ ├─ SKILL.md │ ├─ CHANGELOG.md │ └─ references/ │ ├─ knowledge.schema.json │ ├─ output-example.json │ ├─ review.schema.json │ └─ review-example.json └─ tools/jira_knowledge/validate_knowledge.py

Issue 한 건의 Loop

Orchestrator (본문을 읽지 않고 경로/상태만 관리) ↓ 새 Worker Subagent ↓ [KNOWLEDGE INPUT] 1건 Skill v0.9 → Knowledge 생성 ↓ Python Validator ├─ FAIL → 같은 Worker에서 구조 수정/재검증 └─ PASS ↓ 새 Defect Reviewer ↓ Fact → Causal → Evidence → Classification → Missing Knowledge → Duplication Audit ↓ PASS = score≥8.5 AND Critical=0 AND Major=0 ├─ YES → 다음 Issue └─ NO → 새 Worker Context에서 원본+Review로 재생성 Issue당 최대 생성 3회 → 실패 시 REVIEW_REQUIRED

Evidence Audit

statement를 원자 사실 A/B/C로 분해해 각각 직접 Evidence가 있는지 확인합니다.

확실성 보존

못 찾음 ≠ 배제, 영향일 수도 있음 ≠ 주원인, 다른 조건에서도 발생 ≠ 원인이 아님.

중간 결과

승인·후속검증이 남은 중요한 결과는 삭제하지 않고 key_findings에 보존합니다.

Decision/Open

“적용하기로 했다”는 decision, “추가 검증 필요”는 open item으로 분리합니다.

Trade-off

최종 선택 이유를 이해하는 데 필요한 대안의 부작용과 비교 결과를 보존합니다.

저가치 제거

다음 주/내일 일정, 파일 전달, 잡담보다 재발방지·결정·핵심 비교를 우선합니다.

Reviewer Audit

Audit검사대표 오류
Fact사실 생성/반전/수치·상태측정 정상 → 미측정
Causal원인·배제·해결 표현 강도확인되지 않음 → 배제
Evidence복합 statement의 직접 근거핵심 인과 주장 근거 일부 누락
ClassificationFinding/Decision/Outcome/Open승인 전 결과를 Outcome 처리
Missing반증·trade-off·Decision 누락대안 부작용 누락으로 선택 이유 상실
Duplication핵심 중복·저가치 정보같은 개선안을 Decision/Open에 반복
모델 결정MAX는 일부 복잡한 케이스에서 약간 더 섬세했지만 처리 시간이 10배 이상 느렸습니다. 검색용 의미 압축이라는 목적에서는 Pro가 충분해 Pro Worker + Pro Reviewer로 고정했습니다.
256K Context 대응Orchestrator는 Jira 본문을 읽지 않습니다. Worker/Reviewer는 Issue 한 건만 child context에서 읽고, 운영 규모가 커지면 Primary Session도 30~50건 단위로 새로 시작합니다.

Knowledge Schema v0.1

knowledge_schema_version issue_key issue_summary problem_or_goal[] key_findings[] actions_and_decisions[] outcomes[] open_items[] 각 item = { statement, evidence_refs[] }

BGE-M3 적용 기준

Model

BAAI/bge-m3 · TEI · OpenAI-compatible embeddings

Limits

dense 1024-d · batch 최대 64 · 200 requests/min · input 약 8192 tokens

운영

단일 outbound worker · 보수적 요청 간격 · cache/resume · manifest

Chunk는 아직 미확정실제 Jira Knowledge Profiling과 Retrieval 평가에서 Knowledge Item 단위와 Issue 묶음을 비교한 뒤 확정합니다.

지금부터의 실행 순서

1
실제 Jira 30건 Knowledge 생성

Pro + Skill v0.9 Review Loop. Review JSON까지 보존.

2
5~10건 사람 샘플 검토

원문과 직접 대조. 검색을 왜곡할 사실 반전/심각 인과 과장이 반복되는지 확인.

3
Knowledge/Review Profiling

item 수, 길이, evidence 수, empty 비율, review attempts/결함 유형 측정.

4
DB Logical Schema → SQLite

Evidence round-trip, ID/Join, source_hash 증분 정책을 실제 분포에 맞게 확정.

5
Chunk → BGE-M3 → FAISS

검색 단위를 확정하고 임베딩·캐시·Index 생성.

6
Retrieval 평가

실제 업무 질문으로 기대 Issue가 Top-5에 안정적으로 들어오는지 확인.

7
Evidence Builder + MCP

search_jira_knowledge / get_jira_issue 두 읽기 도구로 시작.
