Knowledge Extraction Skill v0.9

Skill은 한 Issue의 의미 추출 규칙만 담당합니다. 전체 순서와 품질 Loop는 Agent/코드가 담당합니다.

Orchestrator (경로/상태만 관리) ↓ Worker Subagent · Issue 1건 ↓ Skill v0.9 [KNOWLEDGE] 생성 ↓ Python Validator · 구조/Evidence ID ↓ Defect Reviewer Fact → Causal Claim → Evidence → Classification → Missing → Duplication Audit ↓ PASS = score≥8.5 AND Critical=0 AND Major=0 ├─ PASS → 다음 Issue └─ FAIL → 새 Worker Context로 재생성 최대 3회 → REVIEW_REQUIRED

사실 보존

못 찾음 ≠ 배제, 가능성 ≠ 확정 원인, 확인되지 않음 ≠ 검증 미완료.

Evidence Audit

복합 statement를 원자 사실로 나누어 각각 직접 근거를 확인.

Trade-off 보존

최종 선택 이유를 설명하는 대안·부작용·중간 결과를 삭제하지 않음.

Reviewer의 역할Reviewer는 품질 인증기가 아니라 오류 확률을 낮추는 보조 필터입니다. 최종 사실 판단은 RAW/ANALYSIS 원문 Evidence로 돌아갑니다.
모델 결정MAX는 일부 복잡 케이스에서 조금 더 섬세했지만 10배 이상 느렸습니다. 검색용 의미 압축 목적에서는 Pro가 충분해 Pro Worker + Pro Reviewer로 고정했습니다.

전체 파이프라인과 책임 경계

Jira REST ↓ [RAW] Source of Truth ↓ deterministic parser [ANALYSIS] 정규화 사실 ↓ deterministic join [KNOWLEDGE INPUT] Issue 1건 계약 ↓ Pro Worker + Skill v0.9 [KNOWLEDGE] 검색용 의미 압축 ↓ Validator + Reviewer [REVIEW] ↓ [DB] SQLite + Evidence locator ↓ Chunk → BGE-M3(1024-d) → [VECTOR] FAISS ↓ Retriever → Evidence Builder → MCP ↓ 상위 Agent가 원문 Evidence를 읽고 최종 답변 --- Phase 2 --- Scheduler → Incremental Jira Sync → Change Set → 필요한 Stage만 재실행 → staging DB/Index → 검증 → Atomic Publish → Monitoring/Alert
Functional / Operational 경계Phase 1에서는 Stage의 입력·출력 계약과 검색 품질을 검증합니다. Phase 2에서는 그 계약을 바꾸기보다 언제 실행할지, 무엇만 다시 실행할지, 실패 시 어떻게 복구할지, 어떤 일관 snapshot을 서비스할지를 시스템화합니다. 제어 흐름과 변경 탐지는 deterministic code가 담당하고 LLM은 Knowledge 의미 추출처럼 지능이 필요한 좁은 구간에 둡니다.
