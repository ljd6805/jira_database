Run Reporting 보강

초기 LLM 최종 보고에서 Attempt/PASS/Critical/Major 집계가 서로 맞지 않았습니다. Knowledge 생성 문제가 아니라 단순 집계 책임 문제로 판단해 summarize_knowledge_run.py를 추가하고 Orchestrator는 그 결과만 사용하도록 변경했습니다.

Human Validation 결론

대표 5건 전체를 직접 확인했고 검색 의미를 해치는 품질 문제는 발견되지 않았습니다. 선택 배열이 비어 있어도 issue_summary와 다른 Knowledge 항목에 핵심 의미가 충분히 보존되면 정상으로 판단합니다. 필드 채움률보다 검색 의미 보존이 기준입니다.

Reviewer PASS ≠ 사실 100% 보증Reviewer는 결함 감소 필터입니다. [KNOWLEDGE]는 검색용 의미 압축이며 최종 사실 확인은 Evidence reference를 통해 [KNOWLEDGE INPUT] → [ANALYSIS] → [RAW]로 돌아갑니다.

핵심 아키텍처 원칙

Source of Truth

[RAW]는 재처리와 감사의 최종 기준입니다. [ANALYSIS]는 생성형 LLM 없이 결정적으로 정규화합니다.

Semantic Compression

[KNOWLEDGE]는 사실 원장이 아니라 검색을 위한 의미 압축입니다. 모든 statement는 evidence_refs로 원문 위치를 추적합니다.

Context Isolation

Orchestrator는 경로만 관리하고 Worker/Reviewer는 Issue 한 건씩 새 Context에서 처리합니다. 30개 본문을 한 Context에 넣지 않습니다.

Local-only M4

M4에서 Jira Web/API/MCP/Connector에 다시 접근하지 않습니다. 지정된 로컬 Knowledge Input만 사실 입력입니다.

Deterministic Control

Validator와 Run 집계처럼 규칙적인 작업은 Python이 담당합니다. LLM은 의미 추출/검토처럼 지능이 필요한 구간에만 둡니다.

MCP Boundary

MCP 내부에는 생성형 LLM을 두지 않고 retrieval과 Evidence 복원만 결정적으로 수행합니다.

Jira REST API ↓ M0 collection [RAW] ↓ deterministic parser [ANALYSIS] ↓ IssueKnowledgeInputBuilder [KNOWLEDGE INPUT] ↓ Pro Worker + Skill v0.9 [KNOWLEDGE] ↓ Validator + Defect Reviewer [REVIEW] ↓ Human Validation / Profiling [DB] SQLite + Evidence locator ↓ Chunk → BGE-M3 → [VECTOR] FAISS ↓ Retriever → Evidence Builder → MCP → Agent

M4 완료 기록 · Prompt Runbook

M4는 완료됐지만 재현 가능한 단계 산출물로 계속 보존합니다. M4는 로컬에 고정된 Knowledge Input 30건에서 Knowledge를 재현 가능하게 생성하는 단계였으며, Stable Rule은 Agent/Skill에 두고 Prompt에는 Run ID와 경로 같은 실행 변수만 전달했습니다.

1. 입력 파일 탐색 문제와 해결

1건 Smoke Test는 정확한 파일 경로를 직접 read해 성공했지만 다건 실행에서 Orchestrator의 Glob이 0건을 반환했습니다. 원인은 Windows 경로가 아니라 .gitignore의 data/ 규칙을 탐색 도구도 따르는 것이었습니다.

# .gitignore — 실제 Jira 데이터는 계속 Git 제외 data/ # .ignore — OpenCode/ripgrep에서 M4 입력/출력만 다시 노출 !data/ data/* !data/knowledge_input/ !data/knowledge_input/** !data/knowledge/ !data/knowledge/**
Troubleshooting정확한 경로의 read는 성공하는데 Glob이 0건이면 파일 부재를 단정하지 말고 프로젝트 CWD와 .gitignore/.ignore를 먼저 확인합니다.

2. 1건 Smoke Test 프롬프트 패턴

jira-knowledge-orchestrator v0.9로 M4 실제 Jira Knowledge Extraction 1건을 수행해줘. [KNOWLEDGE INPUT] data/knowledge_input/runs/20260804T043628Z/issues/<ISSUE_KEY>.json [KNOWLEDGE OUTPUT] data/knowledge/runs/20260804T043628Z/issues/<ISSUE_KEY>.json [KNOWLEDGE REVIEW] data/knowledge/runs/20260804T043628Z/reviews 지정한 로컬 INPUT FILE만 사용해 기존 Agent 규칙대로 처리하고 최종 상태만 요약해줘.

3. 2026-08-24 실제 30건 실행에 입력한 프롬프트

jira-knowledge-orchestrator v0.9로 M4 실제 Jira Knowledge Extraction 전체 30건을 수행해줘. [KNOWLEDGE INPUT] data/knowledge_input/runs/20260804T043628Z/issues [KNOWLEDGE OUTPUT] data/knowledge/runs/20260804T043628Z/issues [KNOWLEDGE REVIEW] data/knowledge/runs/20260804T043628Z/reviews INPUT 폴더의 Issue JSON 30건 전체를 순차 처리해줘. 처리 시작 전에 입력 JSON이 정확히 30건인지 확인하고, 30건이 아니면 실행하지 말고 INPUT_ERROR로 알려줘. 모든 처리가 끝나면 다음만 요약해줘. - 전체 Issue 수 - PASS 수 - 재생성 발생 Issue 수 - REVIEW_REQUIRED 수 - 실패/INPUT_ERROR 수 - Issue별 최종 상태와 generation attempt 수
실행 이력 보존용 Prompt이 프롬프트로 30건 생성 자체는 완료됐지만 마지막 집계를 LLM이 직접 계산하면서 숫자 불일치가 발생했습니다. 문제 해결 후에도 이 Prompt는 M4 당시 실행 이력으로 삭제하지 않습니다.

4. 현재 권장 30건 재실행 프롬프트

jira-knowledge-orchestrator v0.9로 M4 실제 Jira Knowledge Extraction 전체 30건을 수행해줘. RUN_ID: 20260804T043628Z [KNOWLEDGE INPUT] data/knowledge_input/runs/20260804T043628Z/issues [KNOWLEDGE OUTPUT] data/knowledge/runs/20260804T043628Z/issues [KNOWLEDGE REVIEW] data/knowledge/runs/20260804T043628Z/reviews INPUT의 30건 전체를 기존 Agent 규칙대로 순차 처리해줘. 최종 보고는 LLM이 직접 집계하지 말고 deterministic run summarizer 결과만 사용해줘.

5. 기존 산출물의 집계만 다시 실행

python tools/jira_knowledge/summarize_knowledge_run.py \ data/knowledge_input/runs/20260804T043628Z/issues \ data/knowledge/runs/20260804T043628Z/issues \ data/knowledge/runs/20260804T043628Z/reviews

재생성 발생 = 최종 attempt ≥ 2. Critical/Major 발생 = 어느 attempt에서든 해당 결함이 Review JSON에 기록됨. 정합성이 깨지면 추정하지 않고 REPORT_ERROR.

6. 실제 Deterministic 집계

target_issue_count = 30 input_error_count = 0 first_pass_count = 24 second_pass_count = 5 third_pass_count = 1 review_required_count = 0 incomplete_count = 0 regenerated_issue_count = 6 24 + 5 + 1 = 30 2차 PASS 5 + 3차 PASS 1 = 재생성 Issue 6

7. Human Validation

- 사실 왜곡: 없음 / 있음 - 과도한 인과 확정: 없음 / 있음 - 중요한 정보 누락: 없음 / 있음 - 분류 오류: 없음 / 있음 - evidence 추적 가능: 예 / 아니오 - 검색용 Knowledge로 사용 가능: 예 / 아니오 - 비고

대표 5건을 직접 대조했고 5/5에서 검색 의미를 해치는 품질 문제를 발견하지 않았습니다. 선택 필드가 비어 있어도 전체 Knowledge에 핵심 의미가 충분히 보존되면 정상입니다.

Knowledge Schema v0.1

knowledge_schema_version issue_key issue_summary problem_or_goal[] key_findings[] actions_and_decisions[] outcomes[] open_items[] item = { statement, evidence_refs[] }

Knowledge 역할

검색용 의미 압축. 빈 배열 허용. 확실성 보존. 중요한 비교·반증·Decision·trade-off를 우선하고 일정/파일전달/잡담을 낮은 가치로 봅니다.

Review Gate

score >= 8.5 AND critical_error == false AND major_issue_count == 0 Critical >=1 → score <=7.9 Major >=1 → score <=8.4
