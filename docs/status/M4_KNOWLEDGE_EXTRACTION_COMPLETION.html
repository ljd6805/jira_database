전체 파이프라인에서 M4는 어디인가?

[M3] 생성→검증→Review→재생성 품질 Loop 설계 ↓ [M4] 그 Loop를 실제 Jira 30건으로 끝까지 돌려 검증 ← 지금 여기 ↓ [M5] 실제 산출물의 크기·분포·Evidence 수를 측정 ↓ [M6~M7] 측정값을 근거로 DB 설계·SQLite 구현 ↓ [M8~M10] Vector 검색 + 실제 근거 + MCP
M3와 차이

M3는 절차를 만든 단계이고, M4는 그 절차가 실제 데이터에서도 버티는지 확인한 단계입니다.

M5와 차이

M4는 “잘 동작하는가?”를 보고, M5는 “실제 결과가 얼마나 크고 어떤 분포인가?”를 잽니다.

M4 완료 후

합성 예가 아니라 실제 Jira 30건에서 품질 Loop와 재생성 방식이 작동한다는 근거가 생겼습니다.

M4의 핵심 역할 설계 문서에서만 그럴듯했던 Knowledge 생성 파이프라인을 실제 업무 데이터로 통과시킨 첫 실전 Gate입니다.

1. M4의 사실 입력 경계

[KNOWLEDGE INPUT] data/knowledge_input/runs/20260804T043628Z/issues ↓ Fresh Worker + Skill v0.9 ↓ Python Validator ↓ Fresh Defect Reviewer ↓ PASS / REGENERATE · 최대 3 Attempt ↓ Deterministic Run Summary ↓ Human Validation
중요: M4는 Jira 수집 단계가 아닙니다. 외부 Jira Web/API/MCP/Connector를 다시 사용하지 않고, M1에서 고정한 로컬 Knowledge Input만 사실 입력으로 사용했습니다.

의미: “Reviewer가 모두 한 번에 맞혔다”가 아니라, 품질 Loop가 필요한 경우 재생성을 수행하면서 최대 3 Attempt 안에 30건을 모두 terminal PASS로 만들었다는 뜻입니다.

4. 실행 중 실제로 발견한 문제 ① — 파일을 못 찾음

증상

1건 Smoke Test는 정확한 파일 경로를 직접 읽어 성공했지만, 다건 실행에서 Orchestrator의 Glob이 Knowledge Input 파일을 찾지 못했습니다.

원인

Windows 경로 문제가 아니라, OpenCode/ripgrep 탐색이 Git의 data/ ignore 규칙을 함께 따르고 있었습니다.

# root .ignore의 의도 Git에서는 실제 Jira data/를 계속 추적하지 않음 OpenCode 탐색에서는 knowledge_input / knowledge 경로만 허용
해결의 핵심 보안 때문에 Git에서 제외한 실제 데이터를 저장소에 올리지 않으면서, 로컬 Agent에게 필요한 하위 경로만 탐색 가능하게 분리했습니다.

5. 실행 중 실제로 발견한 문제 ② — LLM의 숫자 집계

처음 구조

30건 실행 후 LLM이 “PASS 몇 건, 재생성 몇 건”을 직접 세어 보고했습니다. 결과에서 서로 맞지 않는 숫자가 발견됐습니다.

수정 구조

summarize_knowledge_run.py가 파일들을 deterministic하게 읽어 통계를 계산하고, Orchestrator는 그 결과만 사용합니다.

교훈 LLM은 의미 해석에는 유용하지만 단순 산술·집계까지 맡길 이유가 없습니다. 답이 하나인 일은 코드가 더 싸고 재현 가능하며 검사하기 쉽습니다.

6. Human Validation은 무엇을 봤나?

자동 Reviewer가 놓칠 수 있는 문제를 확인하기 위해 대표 5건을 사람이 Knowledge Input과 최종 Knowledge로 직접 대조했습니다.

✓ 사실 왜곡 여부
✓ 과도한 인과 확정 여부
✓ 중요한 정보 누락 여부
✓ Category 분류 적절성
✓ Evidence 추적 가능 여부
✓ 검색용 Knowledge로 사용 가능 여부
결과: 5 / 5 완료, 검색 의미를 해치는 품질 문제 발견되지 않음.
빈 배열은 실패가 아닙니다. 예를 들어 problem_or_goal=[]여도 전체 Knowledge가 핵심 검색 의미를 보존하고 Evidence로 추적 가능하면 품질 문제로 판단하지 않았습니다.

7. M4가 남긴 설계 원칙

Issue 단위 Fresh Context가 실데이터에서도 유효

사내 LLM 성능 제약을 고려할 때 작은 Context와 명확한 경계가 안정적이었습니다.

의미는 LLM, 구조·통계는 code

역할을 분리할수록 오류 원인을 찾기 쉽고 재현성이 높아집니다.

Reviewer는 품질 인증서가 아님

결함 감소용 2차 필터이며 중요한 구간에서는 사람 검증이 여전히 가치가 있습니다.

Knowledge는 원문 대체물이 아님

최종 사실 확인은 Evidence를 따라 Knowledge Input / ANALYSIS / RAW로 되돌아갑니다.
