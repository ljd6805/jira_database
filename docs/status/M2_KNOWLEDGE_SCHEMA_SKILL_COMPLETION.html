안전장치

모든 Knowledge Item은 원문 근거인 Evidence reference를 가져야 하며, 원문의 확실성보다 더 강하게 말하면 안 됩니다.

비유 Knowledge Input이 책 전체라면 Knowledge는 도서관의 색인 카드입니다. 색인 카드가 책을 대신하지는 않지만, “내가 찾는 내용이 어느 책에 있는지” 빠르게 좁혀 줍니다.

전체 파이프라인에서 M2는 어디인가?

[M1] Issue 한 건의 사실 전체를 한 Package로 준비 ↓ [M2] 긴 사실을 검색하기 좋은 의미 카드로 압축 ← 지금 여기 ↓ [M3] 그 의미 카드를 더 안정적으로 만들 품질 Loop ↓ [M4~M7] 실데이터 검증·측정·DB 저장 ↓ [M8~M10] Vector 검색 + 원문 Evidence + MCP
M1과 차이

M1은 사실을 그대로 모으고, M2는 그 사실에서 검색 가치가 높은 의미를 뽑습니다.

M3와 차이

M2는 “어떤 Knowledge를 만들 것인가”를 정하고, M3는 “그 Knowledge를 어떻게 안정적으로 만들고 검토할 것인가”를 정합니다.

M2 완료 후

긴 Jira 전체를 매번 검색하지 않고 짧은 Knowledge Item을 검색 후보로 사용할 기반이 생깁니다.

M2의 핵심 역할 Jira 원문을 버리는 요약이 아니라, 원문으로 돌아갈 수 있는 검색용 의미 색인을 만드는 단계입니다.

1. 데이터 계층부터 구분하기

[RAW] 사실의 최종 기준 ↓ [ANALYSIS] 결정적으로 정규화된 사실 ↓ [KNOWLEDGE INPUT] Issue 한 건의 완전한 사실 Package ↓ [KNOWLEDGE] 검색용 의미 압축
가장 중요한 문장 Knowledge는 사실 원장이 아닙니다. 잘못된 Knowledge가 생기면 Evidence를 따라 Knowledge Input / ANALYSIS / RAW로 돌아갈 수 있어야 합니다.

2. 왜 그냥 Issue 전체를 검색하지 않았나?

Issue 전체는 너무 많은 맥락을 포함

긴 댓글 흐름, 전달 내용, 일정, 중요하지 않은 절차가 검색 의미를 희석할 수 있습니다.

너무 복잡한 Ontology도 피함

초기부터 RootCause/Symptom/Resolution 같은 거대한 지식 체계를 확정하지 않고, 실제 Jira에서 반복적으로 나타나는 최소 범주만 사용했습니다.

M2의 전략: “정보를 많이 구조화”하는 것보다 “틀리지 않으면서 검색에 도움이 되는 최소 의미 구조”를 먼저 안정화합니다.

3. Light Structured Schema v0.1

필드아주 쉬운 뜻예시 성격
issue_summary이 Issue가 전체적으로 무엇에 관한 것인지문제 + 핵심 방향 + 현재 상태의 짧은 설명
problem_or_goal[]왜 이 일을 시작했는지문제, 조사 목적, 달성 목표
key_findings[]과정 중 중요하게 알아낸 것관찰, 비교, 반증, 중간 시험, 정량 결과
actions_and_decisions[]실제로 한 일 또는 명시적으로 채택한 결정실행한 조치, 선택한 방향
outcomes[]후속 판단에 실제로 채택된 결과종결 판단, 승인된 결과
open_items[]아직 남은 것추가 확인, 미해결, 후속 검증
빈 배열은 정상입니다. 예를 들어 아직 명확한 Outcome이 없다면 outcomes=[]가 맞습니다. Schema 칸을 채우기 위해 사실을 만들어내면 오히려 품질이 나빠집니다.

4. Knowledge Item과 Evidence

Knowledge Item { "statement": "검색할 가치가 있는 의미 문장", "evidence_refs": ["comment:...", "description", ...] }
statement검색에 사용할 의미 문장입니다. 원문의 내용을 사람이 다시 찾기 쉽게 압축한 표현입니다.
evidence_refs그 statement를 뒷받침하는 원문 위치입니다. summary / description / comment / attachment / relationship / custom_field를 가리킬 수 있습니다.
Evidence round-tripKnowledge에서 출발해 실제 근거가 있는 원문 계층까지 되돌아갈 수 있는 성질입니다. M6/M7에서 DB 계약으로 더 엄격해집니다.

5. Certainty Preservation — 가장 중요한 품질 규칙

LLM은 문장을 자연스럽게 만들면서 원문보다 강하게 단정하기 쉽습니다. M2는 이 위험을 명시적으로 막았습니다.

원문 의미잘못 강화한 표현왜 문제인가
“못 찾았다”“배제했다”검색 실패와 원인 배제는 다른 판단입니다.
“다른 조건에서도 발생했다”“그 조건은 원인이 아니다”관찰 하나만으로 인과를 완전히 제거할 수 없습니다.
“영향일 수도 있다”“주원인이다”가능성을 확정 사실로 바꿉니다.
“확인되지 않았다”“아직 검증하지 않았다”검증을 했는데 못 찾은 것과 검증 자체를 안 한 것은 다릅니다.
원칙 문장을 더 그럴듯하게 만드는 것보다 원문의 불확실성, 반증, trade-off, 시간 흐름을 보존하는 것이 우선입니다.

6. 어떤 내용을 Knowledge로 남기는가?

높은 검색 가치

핵심 발견, 비교·반증, 최종 결과, 실제 Decision, 재발 방지, 중요한 trade-off.

중간 검색 가치

중요 중간 시험, 핵심 정량 결과처럼 이후 판단에 도움이 되는 사실.

낮은 검색 가치

단순 일정, 파일 전달, 잡담, 검색 가치가 낮은 반복 절차.

주의: “낮은 검색 가치”가 “원문에서 삭제”된다는 뜻은 아닙니다. 원문은 M1/ANALYSIS/RAW에 그대로 남고, Knowledge에 선택적으로 압축하지 않는다는 뜻입니다.

7. Pro vs MAX 결정은 어떻게 읽어야 하나?

후보저장소가 실제로 지지하는 결론
MAX일부 복잡 case에서 조금 더 섬세했지만 처리 시간이 Pro보다 10배 이상 느렸습니다.
Pro원문 Evidence로 되돌아갈 수 있는 “검색용 의미 압축” 목적에는 충분하다고 판단해 채택했습니다.
문서가 지어내지 않는 부분 합성 30건 원본 dataset, Skill v0.1~v0.8 전체 artifact, case별 raw score와 정확한 처리시간 수치는 현재 repository에 별도 artifact로 보존되어 있지 않습니다. 따라서 이 HTML도 그 숫자를 추정하지 않습니다.

9. M3로 넘어가기 전에 확인

Q. Knowledge가 RAW보다 더 믿을 만한 사실 원본인가?아니요. Knowledge는 검색용 의미 압축입니다. 사실 확인은 Evidence를 통해 하위 사실 계층으로 돌아갑니다.
Q. 모든 Schema 배열이 채워져야 좋은 Knowledge인가?아니요. 해당 의미가 없으면 비어 있어야 합니다.
Q. Reviewer 운영은 M2에서 완성됐나?아니요. 품질 Loop와 Context Isolation은 M3의 책임입니다.
