1. Knowledge는 사실 원장이 아니다

[RAW] 사실 최종 기준 ↓ [ANALYSIS] 결정적 정규화 사실 ↓ [KNOWLEDGE INPUT] Issue 단위 사실 계약 ↓ [KNOWLEDGE] 검색용 의미 압축

Knowledge 결과가 틀렸더라도 Evidence를 따라 Knowledge Input / ANALYSIS / RAW로 돌아갈 수 있어야 하며, Knowledge가 원문을 대체해서는 안 됩니다.

2. Light Structured Schema v0.1

필드역할
issue_summary문제 + 핵심 방향 + 현재 상태를 짧게 표현
problem_or_goal[]Issue가 존재하는 이유, 문제 또는 목표
key_findings[]관찰, 비교, 반증, 중간 시험, 정량 사실 등 검색 가치 높은 발견
actions_and_decisions[]실제 수행 조치 또는 명시적으로 채택한 결정
outcomes[]후속 의사결정이나 종결 판단에 충분히 채택된 결과
open_items[]추가 확인, 남은 검증, 미해결 항목
빈 배열은 정상. Schema를 채우기 위해 사실을 만들어내는 것보다 해당 범주가 비어 있는 편이 정확합니다.

3. Evidence와 확실성 보존

모든 Item은 Evidence 필수

{statement, evidence_refs[]} 구조. summary / description / comment / attachment / relationship / custom_field ref를 허용합니다.

Certainty Preservation

원문이 확정하지 않은 내용을 “원인·배제·무관·해결·확정”으로 강화하지 않습니다.

"못 찾았다" ≠ "배제했다" "다른 조건에서도 발생" ≠ "원인이 아니다" "영향일 수도 있다" ≠ "주원인이다" "확인되지 않았다" ≠ "아직 검증하지 않았다"

댓글 sequence와 반증·trade-off를 보존하고, 승인/후속 검증이 남은 중간 결과는 기본적으로 key_findings에 둡니다.

4. 검색 가치 우선순위

높음

핵심 발견, 비교/반증, 최종 결과, 실제 Decision, 재발방지, 중요한 trade-off.

중간

중요 중간 시험, 핵심 정량 결과.

낮음

단순 일정, 파일 전달, 잡담, 중요하지 않은 절차.

5. Pro vs MAX 결정

모델저장소가 지지하는 결론
MAX일부 복잡 case에서 조금 더 섬세했지만 처리 시간이 Pro 대비 10배 이상 느림

복원 시 추정하지 않은 부분: 합성 30건 원본 dataset, v0.1~v0.8 Skill 전체 버전, case별 raw score와 정확 처리시간은 repository에 별도 artifact로 남지 않았습니다. 이 HTML도 그 빈칸을 지어내지 않습니다.
