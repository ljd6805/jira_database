2. 왜 IndexFlatIP인가?

Exact

285개 전부와 거리를 계산해 approximate recall 손실이 없습니다.

No training

IVF처럼 centroids를 학습할 필요가 없습니다.

작은 규모

285 × 1024 × 4 bytes ≈ 1.11 MiB라 메모리 최적화가 필요 없습니다.

지금 HNSW/IVF를 쓰지 않는 이유

빠르게 만들 수는 있지만 현재 규모에서는 복잡도만 늘고 exact baseline을 잃습니다. 나중에 데이터가 커졌을 때 Flat 대비 recall/latency를 측정하며 도입하는 편이 안전합니다.

3. Cosine은 FAISS에서 어떻게 계산하나?

M8 vector → float32 copy → L2 normalize → IndexFlatIP.add() 사용자 질문 → BGE-M3 1024-d → L2 normalize → IndexFlatIP.search() normalized inner product = cosine similarity
중요

M8 API가 이미 normalized vector를 반환한다고 가정하지 않습니다. M9에서 항상 normalize한 복사본을 index에 넣고 원본 JSONL은 수정하지 않습니다.

5. Position은 ID가 아니다

FAISS position ↓ index.mapping.jsonl embedding_id · emb_ ↓ knowledge_item_id · ki_ ↓ M10 Knowledge + Evidence
Canonical order

embedding_id ascending 순서로 index를 만들 것을 제안합니다. source JSONL row 순서가 달라도 같은 embedding set이면 같은 mapping order를 만들기 위해서입니다.

temp index + temp mapping → load/search/mapping validation → index/mapping replace → manifest LAST publish manifest/hash mismatch → invalid index로 거부

7. M9 identity 제안
