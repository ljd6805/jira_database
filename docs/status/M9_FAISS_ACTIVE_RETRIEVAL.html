2. 왜 지금 IndexFlatIP인가?

Exact

285개 전부와 비교해 approximate recall 손실이 없습니다.

No training

IVF처럼 centroids를 학습할 필요가 없습니다.

작은 규모

285 × 1024 × 4 bytes ≈ 1.11 MiB라 메모리 최적화가 필요 없습니다.

Flat은 영구 구조가 아닙니다

현재는 exact baseline과 정답 기준을 확보하기 위해 Flat을 선택합니다. 이후 HNSW/IVF를 도입할 때 Flat Top-k와 비교해 recall 손실을 측정할 수 있습니다.

Flat 검색은 query마다 모든 vector를 비교하므로 데이터와 동시 query가 늘수록 CPU 비용이 커집니다. 그래서 개수 하나만 보고 전환하지 않고 실제 운영 지표를 봅니다.

ANN 검토 Trigger p95 search latency > 서비스 목표 index RAM > memory budget 예상 QPS에서 CPU saturation rebuild/reload 시간이 운영 목표 초과 Flat 검색이 end-to-end query 병목

4. 그때 비교할 ANN 후보

IndexHNSWFlat

training 없이 빠른 검색과 높은 recall을 얻기 쉽습니다. 대신 graph memory overhead가 있고 FAISS HNSW는 remove 제약이 있습니다.

IndexIVFFlat

일부 inverted list만 검색해 큰 N에서 계산량을 줄입니다. 대신 training과 nlist/nprobe tuning이 필요합니다.

IndexFlatIP

ANN의 품질을 검증하는 exact test oracle로 계속 보존합니다.

ANN 평가 Flat Top-k = exact reference ANN Top-k = candidate → recall@k → p50 / p95 latency → memory → build time → query throughput

5. Cosine은 FAISS에서 어떻게 계산하나?

M8 vector → float32 copy → L2 normalize → IndexFlatIP.add() 사용자 질문 → BGE-M3 1024-d → L2 normalize → IndexFlatIP.search() normalized inner product = cosine similarity
중요

M8 API가 이미 normalized vector를 반환한다고 가정하지 않습니다. M9에서 항상 normalize한 복사본을 index에 넣고 원본 JSONL은 수정하지 않습니다.

7. Position은 ID가 아니다

FAISS position ↓ index.mapping.jsonl embedding_id · emb_ ↓ knowledge_item_id · ki_ ↓ M10 Knowledge + Evidence
Canonical order

embedding_id ascending 순서로 index를 만들 것을 제안합니다. source JSONL row 순서가 달라도 같은 embedding set이면 같은 mapping order를 만들기 위해서입니다.

8. index를 바꿔도 상위 계약은 유지

현재 IndexFlatIP ↓ faiss position → emb_ → ki_ 향후 HNSW / IVF ↓ faiss position → emb_ → ki_ M10 인터페이스는 동일
설계 핵심

index_type은 retrieval contract identity에 포함하지만, Knowledge/Evidence identity는 index 구현과 분리합니다. 검색 엔진 내부만 교체할 수 있게 합니다.
