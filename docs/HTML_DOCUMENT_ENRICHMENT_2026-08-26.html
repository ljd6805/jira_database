1. 왜 이 작업을 했나?

기존 장점

수치, Gate, Entity, 결정 이력은 비교적 정확하게 정리되어 있었습니다.

기존 한계

source_hash, Generation/Attempt, canonical Evidence처럼 프로젝트를 이미 아는 사람에게는 익숙한 개념을 설명 없이 사용하는 구간이 많았습니다.

보강 목표

“왜 필요한가 → 입력/출력 → 쉬운 비유 → 정확한 계약 → 실제 숫자 → 오해 → 다음 단계” 순서로 읽을 수 있게 했습니다.

2. Source 우선순위

Current 상태 README.md / PIPELINE_OVERVIEW.md / Current Status / Relationship Map Milestone 당시 사실 Completion Record Markdown 현재 설계 계약 DB_LOGICAL_SCHEMA.md / M7_SQLITE_MATERIALIZATION.md / M8_EMBEDDING_CHUNK_BGE_M3.md 결정 변경 이유 Decision Log HTML Visual Companion 위 authoritative source를 쉽게 설명하되 더 강한 새 사실을 만들지 않음
충돌 규칙 HTML의 쉬운 설명이 authoritative Markdown과 충돌하면 Markdown/Current Contract가 우선합니다.

4. Milestone별 핵심 설명 포인트

M0

RAW First와 checkpoint SQLite가 Knowledge DB와 다르다는 점.

M1

Issue 1 = Package 1, source_hash를 “의미 내용의 지문”으로 설명.

M2

Knowledge는 사실 원장이 아니라 “검색용 색인 카드”.

M3

Orchestrator/Worker/Validator/Reviewer를 관리·작성·기계검사·의미검토로 분리.

M4

30/30 PASS의 의미와 .ignore/LLM 집계 문제를 구조적 교훈으로 설명.

M5

실측 max/p95가 hard limit가 아니라 설계 근거임을 명확화.

M6

Issue/Version/Generation/Attempt를 문서 버전/번역 재시도 비유로 설명.

M7

raw Evidence 503과 canonical 502가 서로 모순이 아님을 상세 설명.

M8

Embedding=의미 좌표, FAISS=검색 index로 분리하고 M8/M9 경계 명확화.

5. Archive 처리 결정

docs/status/archive/jira_knowledge_db_current_status_v16_M5.html은 본문을 수정하지 않았습니다.
Documentation Policy는 archive를 “당시 상태 그대로 보존”하도록 규정합니다. 따라서 과거 M5 시점의 상태를 현재형으로 소급 재작성하지 않고, 대신 docs/index.html에서 “현재 판단에 사용 금지” 경고를 강화했습니다.

7. 이 작업에서 바꾸지 않은 것

  • Milestone 상태 자체를 새로 변경하지 않았습니다. 현재 상태는 M7 PASS / M8 CURRENT입니다.
  • DB Schema, ID hash material, Evidence contract, BGE-M3 API contract를 새로 결정하지 않았습니다.
  • 과거 Completion Record의 사실을 현재 시점 기준으로 덮어쓰지 않았습니다.
  • Archive HTML을 현재 상태처럼 재작성하지 않았습니다.
결론 이번 변경은 프로젝트 기능/Schema 변경이 아니라, 기존 사실과 현재 상태를 더 쉽게 복원할 수 있도록 하는 Documentation UX 개선입니다.

8. 후속 유지보수 규칙
