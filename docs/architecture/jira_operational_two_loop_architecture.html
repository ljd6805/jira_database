0-3. Source Ready Gate는 무엇인가?

“row가 존재한다”와 “그 row를 지금 처리해도 안전하다”를 구분하는 안전장치입니다.

물류센터 비유

트럭에서 상자를 내리는 중에도 상자는 창고에 존재합니다. 하지만 하역 전체가 끝나기 전에는 출고하면 안 됩니다.

🚚

시스템으로 바꾸면

상자 = Work Item row

하역 완료 = Project Source Commit

출고 승인 = Source Ready

0-4. Gate가 없으면 어떤 문제가 생기나?

❌ Gate 없음

ABC-1 Source 저장 + row 생성 ABC-2 Source 실패 Project Commit 실패 그 사이 Loop B가 ABC-1 처리 가능 → 실패한 Source window 일부가 Publish될 수 있음
부분 성공을 완전한 Source 상태처럼 오해

✅ Gate 있음

ABC-1 row는 durable하게 남김 ABC-2 Source 실패 Project Commit 실패 → Ready Gate 계속 닫힘 → Loop B claim 금지
복구 정보는 남기면서 잘못된 Publish는 차단

0-5. Gate는 언제 닫히고 열리는가?

시간 순서대로 위에서 아래로 읽습니다.

T1

Source Run 시작

sr_101 시작.

RUN START
T2-A

Issue 관찰 · Source 저장

실제 Source 파일을 먼저 durable하게 저장합니다.

GATE CLOSED
T2-B

Work Item row UPSERT

last_observed_source_run_id = sr_101. row는 있어도 아직 claim 금지.

GATE CLOSED
T3

Project Source Commit

Watermark와 committed run을 같은 State DB transaction에서 갱신하고, 같은 Issue의 이전 미완료 Work를 supersede합니다.

COMMIT
T4

Ready + Latest

현재 관찰이 Commit됐고 더 최신 Work에 밀리지 않았다면 Loop B가 claim할 수 있습니다.

CLAIMABLE
❌ row 존재 → 바로 처리
✅ row 존재 → Source Commit → 최신성 확인 → 처리

0-6. DB에서는 어떻게 claim 가능 여부를 판단하나?

last_observed_source_run_id

가장 최근 관찰한 Source Run.

last_source_committed_run_id

그 관찰이 Commit까지 성공한 Run.

work_status

pending/failed만 재처리 후보.

superseded_by_work_item_id

NULL이어야 현재 최신 Work.

Loop B claim 가능 last_source_committed_run_id IS NOT NULL AND last_source_committed_run_id = last_observed_source_run_id AND work_status IN ('pending','failed') AND superseded_by_work_item_id IS NULL

0-7. 왜 Commit과 supersede를 같은 transaction으로 처리하나?

① source_project_runsource_status = source_committed
② project_statecommitted_watermark = upper
③ 새 Work Itemlast_source_committed_run_id = current
④ 이전 미완료 Workwork_status = superseded
네 상태를 SAME State DB TRANSACTION에서 COMMIT

Watermark만 전진하거나 Gate만 먼저 열리는 모순을 막고, 최신 Work와 구버전 Work의 상태도 한 순간에 일관되게 바꿉니다.

0-8. 더 최신 Source 상태가 들어오면?

ABC-123 Source History 상태 A → 상태 B → 상태 C A = 이미 published → History로 보존 B = pending/failed/running → superseded by C C = Source Ready + latest → Loop B 처리 대상 B가 이미 OpenCode 호출 중이었다면 → 응답 후 latestness re-check → stale 확인 → Active Knowledge/Embedding/Publish 중단

Source History를 삭제하는 정책이 아닙니다. 비싼 AI 처리를 최신 상태에 집중하는 정책입니다.

0-9. 한 문장으로

Work Item row는 “처리할 일이 생겼다”, Source Ready는 “안전하다”, Latest는 “지금 처리할 가치가 있다”를 뜻합니다.

1. 최종 구조

Loop A · SOURCE SYNC source_sync_run → Project Discovery → Delta/Initial/Catch-up → RAW / ANALYSIS / Knowledge Input → semantic_v2 (Source 변경 판별 프로필) → NEW / CHANGED / UNCHANGED → Work Item durable → Project SOURCE_COMMITTED + Watermark → Ready open + 이전 미완료 Work supersede ↓ sync_issue_change latest-only durable backlog Loop B · KNOWLEDGE PROCESSING / PUBLISH processing_run → latest + source-ready Work claim → OpenCode Knowledge → latestness re-check → Review / Evidence → Knowledge DB → BGE-M3 / FAISS staging → latestness re-check → Atomic Publish → PUBLISHED Always-on Retrieval last-known-good Published Corpus → MCP → OpenCode User

2. 왜 두 Loop로 나누는가?

LLM 지연 격리

OpenCode가 느려도 Jira Source 최신화는 계속됩니다.

독립 Cadence

Source와 Processing 주기·중지·재시도를 따로 제어합니다.

Failure Isolation

Jira 장애와 AI/Embedding 장애가 서로의 진행을 막지 않습니다.

Backlog 가시성

Source 최신성과 Publish 지연을 따로 측정합니다.

비용 절약

중간 Source 상태의 불필요한 AI 처리를 supersede합니다.

Last-known-good

새 Publish 실패 중에도 기존 검색 서비스는 유지됩니다.

3. 두 Loop 사이 공식 계약

Loop B 소비 조건
Project SOURCE_COMMITTED + durable sync_issue_change + Source Ready + latest Work = claim 가능

4. Run Identity

source_sync_run

Loop A 실행. Jira Discovery/Source/Watermark 책임.

processing_run

Loop B 실행. 최신 backlog 소비/Publish 책임.

두 Run은 1:1 대응하지 않습니다.

6. Queue는 SQLite State DB로 시작

Loop A producer → Work Item INSERT / UPSERT → Source Commit에서 Ready + supersede 정리 Loop B consumer → latest + ready + pending/failed 조회 → 처리 / checkpoint / published

초기 Single Worker에서는 외부 MQ를 도입하지 않습니다.
