Source Sync와 Knowledge Publish를
두 개의 독립 Loop로 운영한다

Jira Download/정제와 OpenCode 기반 지식화/Embedding/Publish를 하나의 직렬 Run으로 묶지 않습니다. 두 Loop 사이에는 durable Work Item backlog를 두고 각 Loop를 독립적으로 스케줄링·재시도·관찰합니다.

FROZEN · TWO-LOOP ADOPTED · IMPLEMENTATION BASELINE

1. 최종 구조

Loop A · SOURCE SYNC Scheduler A → source_sync_run 시작 / fixed upper → Project Discovery → Project별 Delta / Initial / Catch-up → Jira Download → RAW → ANALYSIS → Knowledge Input → semantic_v2 source_hash → NEW / CHANGED / UNCHANGED → NEW/CHANGED durable sync_issue_change UPSERT → Project SOURCE_COMMITTED → committed_watermark = upper → Source Run 종료 durable boundary ↓ sync_issue_change pending / failed backlog ↓ Loop B · KNOWLEDGE PROCESSING / PUBLISH Scheduler or Worker B → processing_run 시작 → backlog에서 처리 대상 선택 → OpenCode Knowledge Generation → Review / Evidence → Knowledge DB → BGE-M3 Embedding → FAISS staging / mapping 검증 → Atomic Publish → Work Item PUBLISHED → Processing Run 종료 상시 서비스 Published Corpus → FAISS → Evidence/MCP → OpenCode User

2. 왜 두 Loop로 나누는가?

LLM 지연 격리

OpenCode가 느려도 Jira Source 최신화는 계속됩니다.

독립 Cadence

Source Loop와 Processing Loop를 서로 다른 주기와 정책으로 운영할 수 있습니다.

Failure Isolation

Jira 장애와 OpenCode/Embedding 장애가 서로의 진행을 막지 않습니다.

Backlog 가시성

Source는 앞서고 Publish가 밀리는 상황을 명시적으로 측정합니다.

야간 Catch-up

시간대에 따라 OpenCode 처리량이 좋아지면 backlog를 빠르게 소진할 수 있습니다.

독립 제어

Processing Loop만 정지·재개하거나 concurrency를 바꿔도 Source Loop는 유지됩니다.

3. 두 Loop 사이의 계약

SOURCE_COMMITTED + durable sync_issue_change Work Item = Loop A가 Loop B에 넘기는 공식 경계

Loop B는 Jira를 다시 읽지 않고 Work Item과 Source 산출물을 기준으로 진행합니다. Loop A는 OpenCode/Embedding 완료를 기다리지 않습니다.

중요: Source Commit과 Publish는 이제 단지 논리적으로 분리된 것이 아니라 서로 다른 실행 Loop에서 실제로 독립 수행됩니다.

4. Run Identity도 분리합니다

source_sync_run

Jira Discovery, Delta, Source Commit, Watermark를 책임지는 Loop A 실행 이력입니다.

source_run_id = sr_ + UUID4

processing_run

Backlog 소비, OpenCode, Review, Embedding, Publish를 책임지는 Loop B 실행 이력입니다.

processing_run_id = pr_ + UUID4

한 Source Run과 한 Processing Run은 동일한 사건이 아니며 서로 1:1로 대응할 필요도 없습니다.

5. 운영 State의 현재 Domain Table

source_sync_run

Loop A Run.

project_state

Project current state / Watermark.

source_project_run

Source Run × Project 이력 / cursor.

sync_issue_change

두 Loop 사이 durable Work Item/backlog.

processing_run

Loop B Run / 처리량·실패 관찰.

기존 Schema v1의 sync_run과 sync_project_run 단일-Run 의미는 2-Loop 채택으로 대체되었습니다.

6. Work Item은 Durable Queue 역할을 합니다

Loop A NEW / CHANGED → deterministic work_item_id → sync_issue_change INSERT / UPSERT Loop B knowledge_status / embedding_status / publish_status 기준 조회 → 처리 → 단계별 checkpoint → published

초기에는 별도 Kafka/RabbitMQ를 도입하지 않습니다. 단일 Processing Worker 기준으로 SQLite State DB를 durable backlog로 사용하고, 실제 병목/동시성 요구가 확인되면 lease 또는 외부 Queue를 추가 검토합니다.

7. 최신성은 하나의 Run 상태로 보지 않습니다

Source Lag

현재 시각과 Project committed watermark의 차이.

Publish Lag

현재 Source Head와 실제 Published Head의 차이.

Backlog

미처리 Work Item 수와 가장 오래된 대기시간.

서비스 상태: Source Loop가 completed여도 Publish는 밀릴 수 있고, Processing Loop가 실패해도 기존 Published Knowledge는 계속 검색됩니다.

10. 아직 별도 결정이 필요한 것

중간 Version supersede 정책

Source Loop가 V2→V3→V4를 빠르게 만들었는데 Processing Loop가 아직 V2를 시작하지 않았다면, 모든 Version을 지식화할지 최신 pending Version만 처리할지는 아직 Freeze하지 않습니다. Source Version은 모두 보존한다는 원칙은 유지합니다.

Multi-worker claim/lease

초기 Single Worker에서는 필수가 아닙니다. Processing Worker를 병렬화할 때 lease_owner / lease_until / retry scheduling을 별도 설계합니다.
