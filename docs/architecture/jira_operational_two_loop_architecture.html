CONTINUOUS JIRA KNOWLEDGE SERVICE · ARCHITECTURE DECISION · 2026-08-28

Source Sync와 Knowledge Publish를
두 개의 독립 Loop로 운영한다

Jira Download/정제와 OpenCode 기반 지식화/Embedding/Publish를 하나의 직렬 Run으로 묶지 않습니다. 두 Loop 사이에는 durable Work Item backlog를 두고, Project Source Commit까지 완료된 Work만 Processing하도록 Source Ready Gate를 둡니다.

FROZEN · TWO-LOOP · SOURCE READY GATE · IMPLEMENTATION BASELINE

1. 최종 구조

Loop A · SOURCE SYNC Scheduler A → source_sync_run / fixed upper → Project Discovery → Delta / Initial / Catch-up → Jira Download → RAW / ANALYSIS / Knowledge Input → semantic_v2 hash → NEW / CHANGED / UNCHANGED → NEW/CHANGED Work Item row durable → Project SOURCE_COMMITTED → Watermark advance → Work Item Source Ready Gate open → Source Run 종료 ↓ durable boundary sync_issue_change backlog only source-ready is claimable ↓ Loop B · KNOWLEDGE PROCESSING / PUBLISH Scheduler / Worker B → processing_run → source-ready Work Item claim → OpenCode Knowledge Generation → Review / Evidence → Knowledge DB → BGE-M3 Embedding → FAISS staging / mapping validation → Atomic Publish → PUBLISHED → Processing Run 종료 Always-on Retrieval Published Corpus → FAISS → Evidence/MCP → OpenCode User

2. 왜 두 Loop로 나누는가?

LLM 지연 격리

OpenCode가 느려도 Jira Source 최신화는 계속됩니다.

독립 Cadence

Source와 Processing의 실행 주기·중지·재시도를 따로 제어합니다.

Failure Isolation

Jira 장애와 OpenCode/Embedding 장애가 서로의 진행을 막지 않습니다.

Backlog 가시성

Source는 최신인데 Publish가 밀리는 상태를 명시적으로 측정합니다.

야간 Catch-up

시간대별 OpenCode 처리량이 좋아질 때 backlog를 소진할 수 있습니다.

독립 운영

Processing Loop만 멈춰도 Source Loop와 Retrieval은 유지됩니다.

3. 두 Loop 사이의 공식 계약

Project SOURCE_COMMITTED + durable sync_issue_change + Source Ready Gate OPEN = Loop B가 소비 가능한 공식 경계

Work Item row가 존재한다는 사실만으로는 충분하지 않습니다. Candidate 처리 중 row를 먼저 저장할 수 있기 때문에 현재 Source 관찰이 Project Source Commit까지 확정되었는지 확인해야 합니다.

Loop B eligible last_source_committed_run_id IS NOT NULL AND last_source_committed_run_id = last_observed_source_run_id

4. 왜 Ready Gate가 필요한가?

Gate가 없으면

ABC-1 Work Item row 생성 ABC-2 Source 실패 Project 전체 Source Commit 실패 그 사이 Loop B가 ABC-1 처리 → 아직 Commit되지 않은 Source window를 지식화

Gate가 있으면

T2 row 생성 / last_observed 갱신 → gate closed T3 Project Source Commit → watermark + last_source_committed same transaction → gate open 그 다음 Loop B claim

5. Run Identity

source_sync_run

Jira Discovery, Delta, Source Commit, Watermark를 책임지는 Loop A 실행.

source_run_id = sr_ + UUID4

processing_run

Backlog 소비, OpenCode, Embedding, Publish를 책임지는 Loop B 실행.

processing_run_id = pr_ + UUID4

두 Run은 1:1 대응하지 않습니다.

6. Operational State Domain

source_sync_run

Loop A Run.

project_state

Project identity / Watermark.

source_project_run

Run×Project / cursor.

sync_issue_change

durable backlog + ready/stage state.

processing_run

Loop B Run / 처리량.

7. Queue는 SQLite State DB로 시작

Loop A producer → Work Item INSERT / UPSERT → Source Ready Gate open after Project Commit Loop B consumer → ready + pending/failed 대상 조회 → 처리 → stage checkpoint → published

초기 Single Worker에서는 Kafka/RabbitMQ를 도입하지 않습니다. 병렬 처리 요구가 확인되면 claim/lease 또는 외부 Queue를 별도 설계합니다.

8. 최신성은 하나의 Run 상태가 아닙니다

Source Lag

Project committed watermark 기준 최신성.

Publish Lag

Source Head와 실제 Published Head 차이.

Backlog

source-ready 미처리 Work 수와 oldest age.

9. 장애 격리

상황계속 가능한 것
OpenCode 느림/장애Loop A Source Sync + last-known-good Retrieval
Jira 장애Loop B의 이미 source-ready backlog 처리 + Retrieval
Embedding/Publish 장애Loop A + 기존 Published Retrieval

10. Processing Run의 성공 기준

Source Run과 별개로 selected Work의 결과를 기준으로 completed/partial/failed를 기록합니다. 시스템 전체는 Source Lag / Publish Lag / Backlog / Throughput으로 봅니다.

11. 아직 남은 별도 결정

Intermediate Version supersede

V2→V3→V4가 Loop B 시작 전에 쌓이면 모든 semantic Version을 처리할지 미시작 구버전을 supersede할지 아직 Freeze하지 않았습니다.

Multi-worker claim / lease

초기 Single Worker 이후 병렬성이 필요할 때 결정합니다.
