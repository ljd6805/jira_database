Source Sync와 Knowledge Publish를
두 개의 독립 Loop로 운영한다

Jira Download/정제와 OpenCode 기반 지식화/Embedding/Publish를 하나의 직렬 Run으로 묶지 않습니다. 두 Loop 사이에는 durable Work Item backlog를 두고, Project Source Commit까지 완료된 Work만 Processing하도록 Source Ready Gate를 둡니다.

FROZEN · TWO-LOOP · SOURCE READY GATE · IMPLEMENTATION BASELINE

0. 이 문서를 읽기 전에: 네 단어만 먼저 이해하기

아래 네 단어만 잡으면 뒤의 설계가 훨씬 쉬워집니다. 특히 row와 Source Ready Gate는 이 문서 전체를 이해하는 열쇠입니다.

RowDB 테이블의 가로 한 줄. 하나의 기록(record)을 뜻합니다.
Work ItemLoop B가 나중에 처리해야 할 “작업표” 한 장입니다.
Backlog아직 처리하지 않은 Work Item들이 쌓여 있는 대기 목록입니다.
Source Ready Gate그 Work Item을 Loop B가 지금 가져가도 안전한지 검사하는 문입니다.
가장 쉽게: Loop A가 작업표를 만들고 → Gate가 안전을 확인하고 → Loop B가 작업표를 가져가 처리합니다.

0-1. 먼저, row가 정확히 무엇인가?

row는 데이터베이스 테이블의 가로 한 줄입니다. 엑셀에서 한 줄을 생각하면 됩니다. 열(column)은 “어떤 정보를 적는 칸인지”, row는 “그 칸들을 채운 기록 한 건”입니다.

0-3. Source Ready Gate는 무엇인가?

한 문장으로 말하면, “이 Work Item이 DB에 존재한다”와 “이 Work Item을 처리해도 안전하다”를 구분하는 안전장치입니다.

택배 물류센터 비유

트럭 한 대에 상자 100개가 오기로 했습니다. 40개를 내린 순간 이미 창고에는 상자가 존재합니다.

하지만 트럭 하역이 실패해서 나머지 60개가 누락될 수도 있습니다.

🚚

우리 시스템으로 바꾸면

상자 1개 = Work Item row

트럭 하역 완료 = Project Source Commit

출고 승인문 = Source Ready Gate

왜 row를 Commit 뒤에만 만들지 않고 미리 만드는가?Loop A가 중간에 죽어도 어디까지 처리했는지 복구할 수 있어야 하기 때문입니다. 실제 Source와 Work Item 상태를 durable하게 남기는 것은 crash safety에 유리합니다. 대신 미완료 상태의 row를 Loop B가 잘못 가져가지 못하도록 Gate를 둡니다.

0-4. Gate가 없으면 실제로 어떤 문제가 생기는가?

예를 들어 ABC 프로젝트에서 이번 Source Run이 ABC-1과 ABC-2를 확인해야 한다고 하겠습니다.

❌ Gate 없음

T1 · sr_101 시작 T2 · ABC-1 다운로드 성공 → 파일 저장 성공 → Work Item row 생성 [Loop B가 row 발견] → ABC-1 Knowledge 생성 시작 T3 · ABC-2 다운로드 실패 → Project Source Commit 실패 → Watermark도 전진하면 안 됨 하지만... ABC-1은 이미 Loop B가 처리/Publish할 수 있음
결과: “실패한 Source Window의 일부”가 지식 시스템으로 먼저 흘러갈 수 있습니다.

✅ Gate 있음

T1 · sr_101 시작 T2 · ABC-1 다운로드 성공 → 파일 저장 성공 → Work Item row 생성 → Gate CLOSED T3 · ABC-2 다운로드 실패 → Project Source Commit 실패 → Gate 계속 CLOSED Loop B 조회 → ABC-1 row는 보이지만 claim 불가 → 처리하지 않고 기다림
결과: Source Run이 완전하게 Commit되지 않았으므로 잘못된 Publish가 시작되지 않습니다.

0-5. Gate는 언제 닫히고, 언제 열리는가?

한 줄에 다섯 단계를 억지로 넣지 않고, 실제 시간 순서대로 위에서 아래로 읽습니다. 왼쪽은 시점, 가운데는 실제 동작, 오른쪽은 그 순간의 Gate 상태입니다.

T1

Source Run 시작

sr_101이 시작됩니다. 아직 Issue를 관찰하기 전 단계입니다.

RUN START
T2-A

Issue 관찰 · Source 저장

Jira에서 Issue를 읽고 실제 Source 파일을 durable하게 저장합니다. Project 전체 Commit은 아직 아닙니다.

GATE CLOSED
T2-B

Work Item row UPSERT

last_observed_source_run_id = sr_101로 기록합니다. row는 존재하지만 아직 Loop B가 가져가면 안 됩니다.

GATE CLOSED
T3

Project Source Commit

Project의 Source 처리가 완결되면 Watermark와 last_source_committed_run_id를 같은 transaction에서 갱신합니다.

COMMIT
T4

Source Ready Gate OPEN

last_observed_source_run_id와 last_source_committed_run_id가 같은 Run을 가리킵니다. 이제 Loop B가 안전하게 claim할 수 있습니다.

GATE OPEN
❌ Work Item row 생성 → 바로 Loop B 처리
✅ Work Item row 생성 → Project Commit 확인 → Gate OPEN → Loop B 처리

0-6. DB에서는 Gate를 어떻게 판단하는가?

핵심 필드는 두 개입니다.

last_observed_source_run_id

“이 Work Item의 semantic 상태를 가장 최근에 어느 Source Run에서 관찰했는가?”

last_source_committed_run_id

“그 관찰이 Project Source Commit까지 성공했다고 확인된 Source Run은 무엇인가?”

Loop B가 claim 가능한 조건 last_source_committed_run_id IS NOT NULL AND last_source_committed_run_id = last_observed_source_run_id
last_observedlast_source_committedGate뜻
sr_101NULLCLOSED이번 관찰이 아직 한번도 Commit되지 않음
sr_101sr_100CLOSED과거 Run은 Commit됐지만 이번 관찰 sr_101은 아직 미확정
sr_101sr_101OPEN현재 관찰이 Project Commit까지 완료됨

0-7. 왜 Watermark와 Gate를 “같은 transaction”으로 열어야 하나?

Project Commit 순간에는 아래 세 상태가 한 번에 같이 바뀌어야 합니다.

① source_project_runsource_status = source_committed
② project_statecommitted_watermark = upper
③ Work Itemlast_source_committed_run_id = current
세 개를 SAME DB TRANSACTION에서 COMMIT

예를 들어 Watermark만 먼저 전진하고 프로세스가 죽으면 “Source는 최신이라고 표시되는데 Work Item Gate는 닫혀 있는” 모순 상태가 생깁니다. 반대로 Gate만 먼저 열리면 아직 Source Commit이 끝나지 않았는데 Loop B가 처리할 수 있습니다. 그래서 세 상태를 원자적으로 함께 Commit합니다.

0-8. 이미 처리했던 semantic 상태가 다시 나타나면?

ABC-123 상태 변화 A → B → A 예전에 A용 Work Item row가 이미 존재 새 Source Run sr_205에서 A를 다시 관찰 → 기존 A row의 last_observed_source_run_id = sr_205 → committed는 아직 과거 run → Gate 일시 CLOSED Project Source Commit 성공 → last_source_committed_run_id = sr_205 → Gate 다시 OPEN 기존 Knowledge / Embedding은 재사용 가능 필요하면 Publish만 다시 활성화

즉 Gate는 “한번 열리면 영원히 열린 문”이 아닙니다. 현재 관찰이 새 Source Run으로 이동하면 다시 닫히고, 그 Run의 Source Commit이 확인되어야 다시 열립니다.

0-9. 여기까지를 한 문장으로

Work Item row는 “처리할 일이 생겼다”는 기록이고, Source Ready Gate는 “그 일을 지금 처리해도 안전하다”는 승인입니다.
row가 있으면 backlog에 있다는 뜻인가?

넓게 보면 그렇습니다. 하지만 Loop B 관점에서는 row 전체가 곧바로 처리 가능한 queue는 아닙니다. 그중 Source Ready Gate가 열린 row만 실제 claim 대상입니다.

Gate가 별도의 테이블인가?

아닙니다. 현재 설계에서는 별도 Gate 테이블이 아니라 last_observed_source_run_id와 last_source_committed_run_id의 관계로 Gate 상태를 계산합니다.

Gate가 Jira 데이터를 검증하는가?

내용의 정답 여부를 검사하는 Gate는 아닙니다. “현재 Source 관찰이 프로젝트 단위 Commit까지 완료됐는가”라는 운영 일관성을 검사합니다.

그럼 Review Gate와 같은 것인가?

아닙니다. Source Ready Gate는 Loop A→Loop B 경계의 Source 안정성 Gate입니다. Knowledge Review/Evidence는 그 이후 Loop B 내부의 품질 검증 단계입니다.

1. 최종 구조

Loop A · SOURCE SYNC Scheduler A → source_sync_run / fixed upper → Project Discovery → Delta / Initial / Catch-up → Jira Download → RAW / ANALYSIS / Knowledge Input → semantic_v2 hash → NEW / CHANGED / UNCHANGED → NEW/CHANGED Work Item row durable → Project SOURCE_COMMITTED → Watermark advance → Work Item Source Ready Gate open → Source Run 종료 ↓ durable boundary sync_issue_change backlog only source-ready is claimable ↓ Loop B · KNOWLEDGE PROCESSING / PUBLISH Scheduler / Worker B → processing_run → source-ready Work Item claim → OpenCode Knowledge Generation → Review / Evidence → Knowledge DB → BGE-M3 Embedding → FAISS staging / mapping validation → Atomic Publish → PUBLISHED → Processing Run 종료 Always-on Retrieval Published Corpus → FAISS → Evidence/MCP → OpenCode User

2. 왜 두 Loop로 나누는가?

LLM 지연 격리

OpenCode가 느려도 Jira Source 최신화는 계속됩니다.

독립 Cadence

Source와 Processing의 실행 주기·중지·재시도를 따로 제어합니다.

Failure Isolation

Jira 장애와 OpenCode/Embedding 장애가 서로의 진행을 막지 않습니다.

Backlog 가시성

Source는 최신인데 Publish가 밀리는 상태를 명시적으로 측정합니다.

야간 Catch-up

시간대별 OpenCode 처리량이 좋아질 때 backlog를 소진할 수 있습니다.

독립 운영

Processing Loop만 멈춰도 Source Loop와 Retrieval은 유지됩니다.

3. 두 Loop 사이의 공식 계약

Project SOURCE_COMMITTED + durable sync_issue_change + Source Ready Gate OPEN = Loop B가 소비 가능한 공식 경계

Work Item row가 존재한다는 사실만으로는 충분하지 않습니다. Candidate 처리 중 row를 먼저 저장할 수 있기 때문에 현재 Source 관찰이 Project Source Commit까지 확정되었는지 확인해야 합니다.

Loop B eligible last_source_committed_run_id IS NOT NULL AND last_source_committed_run_id = last_observed_source_run_id

4. 왜 Ready Gate가 필요한가?

Gate가 없으면

ABC-1 Work Item row 생성 ABC-2 Source 실패 Project 전체 Source Commit 실패 그 사이 Loop B가 ABC-1 처리 → 아직 Commit되지 않은 Source window를 지식화

Gate가 있으면

T2 row 생성 / last_observed 갱신 → gate closed T3 Project Source Commit → watermark + last_source_committed same transaction → gate open 그 다음 Loop B claim

5. Run Identity

source_sync_run

Jira Discovery, Delta, Source Commit, Watermark를 책임지는 Loop A 실행.

source_run_id = sr_ + UUID4

processing_run

Backlog 소비, OpenCode, Embedding, Publish를 책임지는 Loop B 실행.

processing_run_id = pr_ + UUID4

두 Run은 1:1 대응하지 않습니다.

6. Operational State Domain

source_sync_run

Loop A Run.

project_state

Project identity / Watermark.

source_project_run

Run×Project / cursor.

sync_issue_change

durable backlog + ready/stage state.

processing_run

Loop B Run / 처리량.

7. Queue는 SQLite State DB로 시작

Loop A producer → Work Item INSERT / UPSERT → Source Ready Gate open after Project Commit Loop B consumer → ready + pending/failed 대상 조회 → 처리 → stage checkpoint → published

초기 Single Worker에서는 Kafka/RabbitMQ를 도입하지 않습니다. 병렬 처리 요구가 확인되면 claim/lease 또는 외부 Queue를 별도 설계합니다.

8. 최신성은 하나의 Run 상태가 아닙니다

Source Lag

Project committed watermark 기준 최신성.

Publish Lag

Source Head와 실제 Published Head 차이.

Backlog

source-ready 미처리 Work 수와 oldest age.

9. 장애 격리

상황계속 가능한 것
OpenCode 느림/장애Loop A Source Sync + last-known-good Retrieval
Jira 장애Loop B의 이미 source-ready backlog 처리 + Retrieval
Embedding/Publish 장애Loop A + 기존 Published Retrieval

10. Processing Run의 성공 기준

Source Run과 별개로 selected Work의 결과를 기준으로 completed/partial/failed를 기록합니다. 시스템 전체는 Source Lag / Publish Lag / Backlog / Throughput으로 봅니다.

11. 아직 남은 별도 결정

Intermediate Version supersede

V2→V3→V4가 Loop B 시작 전에 쌓이면 모든 semantic Version을 처리할지 미시작 구버전을 supersede할지 아직 Freeze하지 않았습니다.

Multi-worker claim / lease

초기 Single Worker 이후 병렬성이 필요할 때 결정합니다.
