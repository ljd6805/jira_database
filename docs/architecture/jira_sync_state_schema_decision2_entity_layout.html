S1에서 기존 collector.db를 명시적 Migration으로 확장하기로 했습니다. S2에서는 Sync Contract의 상태 역할을 실제 SQLite 테이블로 얼마나 분리할지 결정합니다.

S1 FIXED · S2 REVIEWING · RECOMMENDATION = 4 PHYSICAL TABLES

1. 초안의 5개 논리 역할

sync_run

한 번의 Sync 실행.

project_registry

Project identity와 visible/unavailable 상태.

project_sync_state

Project별 Watermark와 최근 성공 상태.

sync_project_run

특정 Run에서 특정 Project의 처리 기록.

sync_issue_change

NEW/CHANGED Work Item과 downstream checkpoint.

중요: 논리 역할이 다섯 개라는 것과 실제 DB 테이블이 반드시 다섯 개여야 한다는 것은 다른 문제입니다.

2. 두 가지 실질 후보

A · 5 TABLES

논리 역할 그대로 분리

sync_run project_registry project_sync_state sync_project_run sync_issue_change

장점: 책임이 매우 명확합니다.

단점: project_registry와 project_sync_state는 둘 다 project_id당 1행이며 거의 항상 같이 조회됩니다.

B · RECOMMENDED

Project 현재 상태를 하나로 합침

sync_run project_state sync_project_run sync_issue_change

장점: Project 하나의 현재 identity/visibility/watermark를 한 행에서 이해할 수 있습니다.

장점: 1:1 테이블 join과 migration 복잡도를 줄입니다.

3. 왜 Registry와 Sync State를 합치는가?

Project P100 identity project_id = 10000 current_key = ABC current_name = Project Alpha 현재 Source 상태 visibility = unavailable committed_watermark = 2026-08-20 13:00 last_seen_at = 2026-08-20 last_source_success_at = 2026-08-20 이 정보는 모두 “Project P100의 현재 장기 상태”를 설명함

두 정보군은 수명도 같고 cardinality도 project_id : row = 1 : 1입니다. unavailable이 되어도 Watermark를 같은 row에서 그대로 보존할 수 있어 D6의 의미도 직관적으로 표현됩니다.

4. 추천하는 4개 물리 테이블

테이블질문주요 데이터
sync_run이번 Sync 전체는 어떻게 끝났나?run ID, upper, discovery/source/publish/run status, 시간
project_state이 Project는 누구이며 지금 어디까지 읽었나?project_id, current key/name, visibility, first/last seen, committed_watermark, 최근 source success/error
sync_project_run이번 Run에서 이 Project를 어떻게 처리했나?lower/upper, status, candidate/new/changed/unchanged count, error
sync_issue_change이 Issue 변경분은 어디까지 반영됐나?jira_id, source_hash/profile, change_kind, source/knowledge/embedding/publish checkpoint, error

5. 현재 상태와 History를 분리하는 기준

Current State

project_state는 Project당 한 행으로 현재값만 유지합니다.

Watermark, visibility, current key/name 같은 “다음 Sync가 바로 읽어야 할 값”입니다.

History / Audit

sync_run과 sync_project_run은 실행마다 행을 추가해 과거를 보존합니다.

따라서 project_state에 과거 Watermark를 모두 쌓을 필요가 없습니다.

6. sync_issue_change는 왜 별도여야 하나?

Issue 하나의 downstream 처리는 Project Run보다 오래 살아남을 수 있습니다.

Run R100 ABC-42 Source Commit ✓ Knowledge 실패 ✗ Run R101 같은 jira_id + source_hash → 기존 Work Item Resume → Knowledge부터 계속

따라서 Project 수준 행에 JSON 같은 형태로 집어넣지 않고, 안정적인 Work Item row로 독립시켜야 D5 Checkpoint/Resume와 D7 Source Commit/Publish를 제대로 표현할 수 있습니다.

7. Migration 관점

S1의 Migration 필수 조건은 그대로 적용

S2에서 테이블 수를 4개로 정하더라도 기존 collection_runs, project_runs, issue_checkpoints, artifacts를 즉시 변환하거나 삭제하지 않습니다.

legacy MVP tables → 그대로 보존 versioned migration → 새 operational tables 추가 새 Sync 구현 → 새 테이블 사용 legacy collector/resume → 회귀 검증 후 호환 유지

운영 전환이 안정화된 뒤에만 legacy table 통합/정리를 별도 Migration으로 검토합니다.

8. S2 추천 결론

논리 역할은 5개를 기억하되, 물리 테이블은 4개로 만든다.

project_registry + project_sync_state ↓ merge project_state 최종 후보 1. sync_run 2. project_state 3. sync_project_run 4. sync_issue_change

이 안을 확정하면 다음 S3에서는 각 테이블의 status enum과 필수 컬럼을 하나씩 Freeze합니다.

아직 S2는 FIXED 아님. 사용자 승인 후 4-table 구조를 Schema Contract에 반영합니다.
