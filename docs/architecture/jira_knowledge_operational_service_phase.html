POST-MVP SERVICE PHASE · 2026-08-27

M0~M11은 MVP였습니다.
이제 Jira 변화가 자동으로 서비스에 반영되어야 합니다.

최종 목표는 한 번 만들어 둔 검색 DB가 아니라, Jira의 프로젝트·이슈·댓글·관계 변화가 지속적으로 Knowledge DB와 Embedding/FAISS에 반영되고 팀원들이 중앙 MCP로 항상 최신 지식을 조회하는 운영 서비스입니다.

M0~M11 = FUNCTIONAL MVP DONE · NEXT = CONTINUOUS JIRA KNOWLEDGE SERVICE

1. 초반 목표와 지금의 위치

초기 수집기 설계부터 있던 목표

인증 계정이 접근 가능한 Jira 프로젝트 전체를 발견하고, 실패 격리·checkpoint·재개 가능한 수집기를 만드는 것이 출발점이었습니다.

MVP에서 일부러 미룬 것

자동 주기 스케줄러와 실행 간 증분 동기화는 초기 수집기 범위에서 명시적으로 제외했습니다. M0~M11에서 핵심 기능을 검증한 뒤 운영 단계에서 다루기 위한 경계였습니다.

M0~M11 수집 → 정규화 → Knowledge → SQLite → Embedding → FAISS → Evidence/MCP → OpenCode = 기능이 실제로 되는지 검증한 MVP 이후 운영 서비스 Jira 변화 감지 → 변경분만 재처리 → 검색 인덱스 갱신 → 중앙 MCP로 계속 제공

2. 운영 서비스의 전체 목표

Jira ↓ 주기적 Project Discovery 새 프로젝트 / 기존 프로젝트 / 접근 상태 확인 ↓ Delta Issue Sync 신규 이슈 / 수정 이슈 / 댓글·관계·필드 변화 ↓ RAW / Issue Version 갱신 source_hash 동일 → reuse source_hash 변경 → 새 Issue Version ↓ Knowledge 재생성 변경된 Version만 Generation / Attempt / Item / Evidence 갱신 ↓ Embedding / FAISS Delta Update 변경 없는 Knowledge 재사용 변경/추가 Knowledge만 embed + index 반영 ↓ Central Remote MCP 팀원 OpenCode가 최신 Active Knowledge 조회

3. 반드시 서비스해야 하는 네 축

A. 지속적인 Jira 업데이트

마지막 성공 동기화 지점을 기준으로 신규/수정 이슈를 반복 수집하고, 실패 후 재개 가능해야 합니다. 운영 기본은 full rebuild가 아니라 delta-first입니다.

B. Project 추가·변화 반영

동기화 때마다 접근 가능한 프로젝트를 다시 discovery하여 새 프로젝트를 자동 발견하는 방향이 기본입니다. 프로젝트 제거/권한 상실 시 기존 지식 처리 정책은 별도 보안 결정이 필요합니다.

C. 변경사항의 하위 파이프라인 전파

Jira 변경이 RAW에만 머물면 안 됩니다. Issue Version → Knowledge → Embedding → FAISS Active Retrieval까지 변경분이 끝까지 반영돼야 합니다.

D. 팀 공용 MCP 서비스

중앙 서버가 DB/FAISS/.env/BGE 설정을 소유하고 팀원 OpenCode는 Remote MCP endpoint를 소비합니다. local stdio는 MVP 검증용으로 종료합니다.

4. Project Discovery의 운영 해석

매 Sync 시작 ↓ 현재 서비스 계정이 조회 가능한 프로젝트 목록 discovery ↓ 기존 project registry와 비교 ├─ 신규 project → 초기 ingest 대상 ├─ 기존 project → delta sync 대상 └─ 사라진 project → 권한/삭제 상태 판단 필요

따라서 프로젝트 추가를 매번 사람이 config에 등록하는 방식보다, Jira API의 project discovery를 서비스 동기화의 첫 단계로 재사용하는 것이 현재 설계와 잘 맞습니다.

5. Delta Sync의 기본 원칙

상태운영 처리
unchanged기존 Issue Version / Knowledge / Embedding 재사용
newRAW 저장 → Version → Knowledge → Embedding → FAISS 추가
changed새 RAW/Issue Version → 새 Generation/Item/Evidence → 기존 Active 교체 → Embedding/Index 갱신
removed / no access즉시 삭제로 단정하지 않음. 서비스 계정 권한 상실·Jira 삭제를 구분하는 정책을 먼저 Freeze
중요:

전체 프로젝트·전체 이슈를 매번 다시 Knowledge/Embedding 처리하는 구조는 운영 기본이 아닙니다. 전체 rebuild는 복구·마이그레이션·검증용 경로로 남깁니다.

6. 기존 Identity 설계를 그대로 활용합니다

jira_id ↓ issue_version · iv_ source_hash 동일 → 기존 Version 재사용 source_hash 변경 → 새 Version ↓ knowledge_generation · kg_ ↓ knowledge_attempt · ka_ + attempt_no ↓ knowledge_item · ki_ ↓ knowledge_evidence · ke_ Active Retrieval은 최신 accepted Generation만 사용 History는 감사/재현을 위해 보존

즉 M6~M10에서 만든 Version/Generation/Attempt/Active 구분은 MVP용 임시 구조가 아니라 지속 업데이트를 가능하게 하기 위한 운영 기반입니다.

7. Embedding / FAISS 운영 방향

Knowledge statement hash 동일 → 기존 embedding 재사용 새/변경 Knowledge → BGE-M3 embedding 생성 → vector cache 확인 → Active FAISS mapping 갱신 obsolete Knowledge → active retrieval에서 제거 또는 tombstone full index rebuild → 유지보수 / 복구 / migration 경로

정확한 index update 구현은 다음 단계에서 Freeze합니다. 현재 확정된 원칙은 delta-first이며, HNSW/IVF 같은 index 교체는 실제 규모와 latency 측정 뒤 결정합니다.

8. 중앙 MCP는 운영 파이프라인의 마지막 서비스 경계입니다

[Background Sync Pipeline] Jira → RAW → Knowledge DB → Embedding/FAISS │ │ 최신 Active corpus ▼ [Central Remote MCP] │ HTTPS ┌──────────┼──────────┐ ▼ ▼ ▼ OpenCode A OpenCode B OpenCode C

Remote MCP 서버화만 먼저 해도 Jira 데이터가 갱신되지 않으면 결국 오래된 지식을 서비스하게 됩니다. 따라서 Remote MCP는 지속 동기화 파이프라인과 함께 운영 서비스로 설계해야 합니다.

9. 운영 자동화와 관찰성

Scheduling

얼마나 자주 동기화할지는 아직 Freeze하지 않습니다. 다만 수동 실행만으로 서비스하지 않는 것이 목표입니다.

Checkpoint / Retry

실패한 project/issue부터 재개하고 이미 성공한 변경분을 불필요하게 다시 처리하지 않아야 합니다.

Observability

sync run, 신규/변경 project/issue 수, Knowledge/Embedding update 수, 실패·지연·MCP health를 운영자가 확인할 수 있어야 합니다.

10. 서비스화에서 새로 반드시 결정해야 할 보안 항목

프로젝트 권한 상실

서비스 계정이 더 이상 특정 프로젝트를 조회하지 못할 때 과거에 수집한 지식을 계속 검색 가능하게 둘지 즉시 비활성화할지 정책이 필요합니다.

팀원별 Jira 권한

초기 MVP는 사용자별 Jira 권한 재현을 범위 밖으로 두었습니다. 중앙 MCP를 팀에 제공할 때 모든 사용자가 동일 접근권한인지, 사용자별 필터링이 필요한지 반드시 결정해야 합니다.

12. 아직 Milestone 번호를 붙이지 않는 이유

다음 단계가 단순한 Remote MCP 구현이 아니라 동기화·증분 처리·검색 갱신·서비스·운영을 포함한다는 점을 먼저 복원했습니다. 다음 대화에서 이 전체 범위를 어떤 Milestone들로 나눌지 결정한 뒤 번호를 확정합니다.
