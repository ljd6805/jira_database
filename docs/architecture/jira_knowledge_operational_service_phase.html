OPERATIONAL SERVICE TARGET · 2026-08-28

Continuous Jira Knowledge Service
2-Loop Operational Phase

Functional MVP를 지속 운영 서비스로 확장합니다. Source 최신화와 Knowledge/Embedding/Publish를 독립 실행하고, Central MCP는 마지막 정상 Published Corpus만 제공합니다.

1. 목표 아키텍처

Jira Server ↓ [Loop A · SOURCE SYNC] source_sync_run → Discovery → Delta / Initial / Catch-up → RAW / ANALYSIS / Knowledge Input → semantic_v2 → SOURCE_COMMITTED / Watermark → sync_issue_change backlog ↓ durable backlog [Loop B · KNOWLEDGE PROCESSING / PUBLISH] processing_run → OpenCode Knowledge → Review / Evidence → Knowledge DB → BGE-M3 → FAISS staging → Atomic Publish ↓ Published Corpus ↓ Central Remote MCP ↓ Team OpenCode ↓ Users

2. Loop A의 운영 책임

Discovery

현재 visible Project scope를 완전하게 파악하고 project_id Registry를 유지합니다.

Delta-first

Project별 Watermark + 5분 overlap + fixed upper로 변경 후보만 읽습니다.

Source Commit

semantic change classification과 durable Work Item을 저장한 뒤 Watermark를 전진합니다.

Loop A는 OpenCode, Embedding, FAISS 완료를 기다리지 않습니다.

3. Loop B의 운영 책임

Backlog Consume

pending/failed Work Item을 선택해 독립 Processing Run으로 처리합니다.

Knowledge

OpenCode 생성, Review, Evidence, Knowledge DB lineage를 담당합니다.

Publish

Embedding/FAISS를 staging에서 검증하고 실제 Retrieval active view를 atomic하게 전환합니다.

Loop B는 Jira Source를 다시 다운로드하지 않고 Loop A의 durable Source/Work Item을 소비합니다.

4. Central MCP의 책임

MCP는 Sync Engine이 아닙니다. Source Loop나 Processing Loop를 실행하지 않고 현재 Published Corpus를 읽어 Knowledge + Evidence를 Tool로 제공합니다.
Published Corpus → FAISS Top-K → Knowledge DB → Evidence Resolver → search_jira_knowledge / get_jira_issue → OpenCode

새 Publish가 실패해도 MCP는 last-known-good Published Corpus를 계속 제공합니다.

5. State Plane

Table책임
source_sync_runLoop A 실행 이력 / fixed upper / Source 상태
project_stateProject identity / visibility / committed Watermark
source_project_runSource Run×Project lower/upper/count/cursor
sync_issue_change두 Loop 사이 durable semantic backlog + downstream checkpoint
processing_runLoop B 실행 이력 / 처리량 / 실패

State DB는 기존 data/state/collector.db를 explicit migration으로 확장합니다.

6. Data Plane

Knowledge DB Issue / Issue Version → Knowledge Generation → Attempt / Review → Knowledge Item → Evidence Embedding / Retrieval artifacts → BGE-M3 vectors → FAISS index / mapping → Published active pointer

State Plane과 Data Plane은 stable logical ID로 연결하며 cross-DB physical FK는 요구하지 않습니다.

7. 독립 Scheduling

Source Scheduler

Jira freshness 요구를 기준으로 cadence를 정합니다. OpenCode 상태에 영향받지 않습니다.

Processing Scheduler / Worker

Backlog/처리량/OpenCode latency를 기준으로 실행합니다. 야간 catch-up 같은 정책을 별도로 적용할 수 있습니다.

정확한 시간대별 cadence/concurrency는 아직 Freeze하지 않습니다. 먼저 실제 processing_run 데이터로 처리량을 측정합니다.

8. 운영 KPI

Source Lag

Project watermark 최신성.

Publish Lag

Source Head와 Published Head 차이.

Backlog Depth

대기 Work Item 수.

Oldest Pending Age

최장 대기시간.

Processing Throughput

시간당 Published 수.

Latency / Error

시간대/Stage별 Processing 성능.
