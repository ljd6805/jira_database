2. 이미 확정한 두 가지

D1 FIXED

Project별 Watermark

Project마다 “여기까지 안전하게 수집했다”는 책갈피를 따로 둡니다. 한 Project 실패가 다른 Project의 진행을 막지 않습니다.

D2 FIXED

5분 Overlap + 고정 upper

lower = watermark - 5분, updated >= lower AND updated < upper 범위로 조회합니다. 정렬은 updated ASC, id ASC를 기본 계약으로 둡니다.

3. Decision 3 — 후보와 실제 변경은 다릅니다

Jira의 updated는 “이 Issue를 다시 검사해 보라”는 신호입니다. 그것만 보고 Knowledge를 다시 만들지는 않습니다.

JQL updated 범위 검색 ↓ 변경 후보 Issue 발견 ↓ 최신 source snapshot 구성 ↓ source_hash 계산 ↓ 기존 상태와 비교 ├─ 처음 보는 jira_id → NEW ├─ 같은 jira_id + hash 다름 → CHANGED └─ 같은 jira_id + hash 같음 → UNCHANGED
핵심: updated는 후보 탐색용, source_hash는 실제 변경 판정용입니다.

4. 세 가지 상태를 아주 쉽게

NEW

우리 시스템이 처음 보는 jira_id입니다.

jira_id = 10042 기존 source 상태에 없음 → NEW

새 Issue Version부터 Knowledge, Embedding, FAISS까지 처리합니다.

CHANGED

같은 Issue인데 실제 업무 내용 묶음의 지문이 달라졌습니다.

jira_id = 10042 old hash = AAA new hash = BBB → CHANGED

새 Issue Version을 만들고 변경분을 downstream에 전달합니다.

UNCHANGED

Overlap 때문에 다시 발견했지만 실제 내용은 같습니다.

jira_id = 10042 old hash = AAA new hash = AAA → UNCHANGED

기존 Version / Knowledge / Embedding을 재사용합니다.

5. 왜 issue_key가 아니라 jira_id인가?

ABC-123 같은 Issue Key는 사람이 보기 좋은 이름입니다. Jira 내부 ID는 같은 Issue의 안정적인 identity로 사용합니다.

어제 jira_id = 10042 issue_key = OLD-123 Key 변경 / Project 이동 오늘 jira_id = 10042 issue_key = NEW-987 → 같은 jira_id → NEW 아님 → 현재 key/project metadata는 갱신
현재 DB도 이 원칙입니다. issue.jira_id가 Primary Key이고 동일 jira_id가 다시 들어오면 현재 issue_key/project_key를 갱신합니다.

6. 왜 source_hash를 쓰나?

source_hash는 Issue 하나의 “업무 내용 묶음 지문”입니다. 현재 코드도 Issue, Comment, Attachment metadata, Relationship, Custom Field를 한 묶음으로 canonicalize해서 SHA-256을 계산합니다.

Issue 핵심 내용 + Comments + Attachment metadata + Relationships + Custom Fields ↓ canonical JSON SHA-256 ↓ source_hash

Description은 그대로여도 댓글이 새로 추가되거나 관계/Custom Field가 달라지면 hash가 달라질 수 있습니다.

단, hash에 정확히 어떤 필드를 넣을지는 Decision 4에서 다시 봅니다. 특히 updated_at 같은 시간 정보가 “실제 지식 변화”인지 따로 판단합니다.

7. Overlap이 있어도 비싼 재처리를 막을 수 있습니다

Watermark 10:30 Overlap 5분 → 10:25~ 구간 다시 조회 ABC-1 다시 발견 → hash 같음 → UNCHANGED → downstream 없음 ABC-2 다시 발견 → hash 같음 → UNCHANGED → downstream 없음 ABC-3 댓글 추가 → hash 다름 → CHANGED → downstream 실행

Overlap 때문에 Jira 후보를 조금 더 확인하더라도 Knowledge 생성이나 BGE-M3 embedding 같은 비싼 작업은 실제 new/changed에만 수행합니다.

8. 처리 규칙 초안

판정조건Issue VersionKnowledge / Embedding / FAISS
NEWjira_id가 기존 source 상태에 없음새 Version전체 downstream
CHANGEDjira_id 존재 + source_hash 변경새 Version변경분 downstream
UNCHANGEDjira_id 존재 + source_hash 동일기존 Version 재사용재사용, 새 생성 없음

9. 중요한 경계 — source 변경과 Publish 성공은 다릅니다

Jira source 수집과 CHANGED 판정은 성공했지만 Knowledge 생성이 실패할 수도 있습니다.

Jira source 수집 SUCCESS source_hash 판정 CHANGED Knowledge 생성 FAILED 다음 Sync에서 "Jira 내용이 그대로니까 UNCHANGED, 끝" 으로 처리하면 안 됨 → source 변경 사실은 durable하게 기억 → 실패한 downstream은 다시 수행
정확한 checkpoint와 publish 상태는 Decision 5와 7에서 확정합니다. Decision 3에서는 source 변경 판정과 서비스 반영 완료를 같은 것으로 보지 않는다는 경계만 둡니다.

10. Decision 3 추천 결론

PROPOSED

jira_id + source_hash로 NEW / CHANGED / UNCHANGED를 판정한다.

jira_id 없음 → NEW jira_id 있음 + hash 다름 → CHANGED jira_id 있음 + hash 같음 → UNCHANGED

Jira updated는 Delta 후보 탐색에만 사용합니다. Issue Key가 바뀌어도 같은 jira_id라면 새로운 Issue로 보지 않습니다.

아직 D3는 FROZEN 아님. 승인하면 FIXED로 올리고 Decision 4 source_hash v2로 넘어갑니다.
