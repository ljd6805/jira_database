3. Decision 6 — Project Registry란?

Registry는 우리 서비스가 지금까지 만난 Jira Project의 주소록입니다. 매 Sync마다 현재 Jira가 보여주는 Project 목록과 비교합니다.

어제 Registry P100 / ABC / Project Alpha P200 / DEF / Project Delta 오늘 Discovery P100 / ABC / Project Alpha P300 / NEW / New Project 비교 P100 → 기존 Project · visible P200 → 기존 Project · 이번에는 not visible P300 → 새 Project · visible

4. Project Identity

project_id = Identity

같은 Project를 장기간 추적하는 기준값입니다.

project_id = 10000 → Registry identity

project_key / name = 현재 표시값

사람이 읽는 현재 값이며 바뀔 수 있습니다.

ABC / Project Alpha → current metadata

Issue에서 jira_id와 Issue Key를 분리한 것과 같은 원칙입니다.

6. “안 보임”은 “삭제됨”이 아닙니다

현재 서비스 계정에서 보이지 않는 이유는 삭제, Archive, 권한 변경 등 여러 가지일 수 있습니다. 원인을 추측하지 않습니다.

Project가 목록에서 사라짐 ↓ 관찰 가능한 사실 = 현재 서비스 계정에서 not visible ↓ Registry visibility_state = unavailable 하지 않는 것 → deleted라고 단정 X → History 삭제 X → Watermark 초기화 X

7. Discovery 자체가 실패하면 Registry를 바꾸지 않습니다

page 1 SUCCESS page 2 SUCCESS page 3 API ERROR → Discovery = INCOMPLETE → Project 비교 결과를 신뢰하지 않음 → 기존 visibility_state 그대로 유지
유지할 안전 규칙: Project가 unavailable이라고 판단하는 것은 Discovery 전체가 정상 완료된 경우에만 허용합니다.

8. 수정된 핵심 정책 — unavailable이어도 Retrieval은 유지

Project가 현재 Jira에서 보이지 않는다는 이유만으로 이미 구축한 과거 Knowledge의 의미가 사라지는 것은 아닙니다.

어제 P100 visible Knowledge active last_synced_at = 2026-08-27 10:30 오늘 Discovery SUCCESS P100 not visible ↓ visibility_state = unavailable sync = paused ↓ 기존 Knowledge / Embedding / FAISS → 그대로 Retrieval 가능
수정안: unavailable은 Source Sync 상태이지 Retrieval 차단 상태가 아닙니다. 과거 Jira 지식은 계속 검색할 수 있습니다.

9. 대신 “얼마나 최신인가”를 표시합니다

현재 갱신되는 Project와 오래 전 마지막으로 수집된 Project를 같은 최신성으로 보이면 혼동할 수 있습니다. 검색 가능 여부와 최신성은 분리합니다.

visibility_state

visible / unavailable

현재 Jira Source와 동기화 가능한가?

last_synced_at

마지막 정상 Source Sync 시각.

지식의 최신성을 판단하는 정보입니다.

retrieval_state

기본은 enabled.

Jira visibility와 자동 연동하지 않습니다.

검색 결과 예 Project ABC source_state = unavailable last_synced_at = 2026-08-20 13:00 retrieval = enabled → "현재 Jira 갱신은 중단됐지만 8/20 시점의 지식은 검색 가능"

10. Retrieval을 정말 막고 싶을 때는 별도 정책으로

향후 보안 또는 운영 정책상 특정 Project를 검색에서 빼야 한다면 Jira visibility와는 별도의 명시적 제어값으로 처리하는 편이 안전합니다.

visibility_state = unavailable ≠ retrieval_enabled = false 관리자가 명시적으로 차단해야 할 때만 retrieval_enabled = false

즉 Project가 안 보인다는 기술적 상태가 곧바로 “과거 지식을 삭제하거나 숨겨라”는 정책으로 번역되지 않습니다.

11. Watermark는 그대로 보존합니다

P100 unavailable committed_watermark = 2026-08-20 13:00 → 앞으로 이동 X → 초기화 X → 삭제 X

다시 접근 가능해졌을 때 이 지점에서 이어서 갱신하기 위해 필요합니다.

12. 다시 같은 Project가 보이면 Initial Ingest하지 않습니다

여기서는 사용자의 제안을 채택하는 것이 더 효율적입니다. 같은 project_id가 Registry에 이미 있고 Watermark도 남아 있다면 처음부터 전부 다시 받을 이유가 없습니다.

P100 unavailable watermark = 8/20 13:00 ↓ 8/27 다시 visible ↓ lower = 8/20 12:55 (5분 overlap) upper = 이번 Sync 고정 상한 ↓ Catch-up Delta Sync ↓ NEW / CHANGED / UNCHANGED ↓ 필요한 변경분만 downstream
수정안: 기존 project_id의 재등장 = Catch-up Delta Sync. 전체 Initial Ingest는 하지 않습니다.

13. 단, Delta만으로 완벽히 알 수 없는 한 가지

Project가 안 보이던 기간에 Issue가 삭제되었다면, 다시 접근했을 때 그 Issue는 Jira 검색 결과 자체에 나타나지 않을 수 있습니다. 그래서 단순 updated Delta만으로는 “사라진 Issue”를 완벽히 감지할 수 없습니다.

8/20 마지막 Sync ABC-10 존재 8/21~8/26 Project unavailable ABC-10 삭제 8/27 다시 visible updated Delta 검색 → ABC-10은 이미 없어서 검색 결과에 나오지 않음 → 우리 DB에는 과거 ABC-10이 남아 있음
중요: 이것은 Full Initial Ingest가 필요하다는 뜻은 아닙니다. 필요하다면 재접근 시 가벼운 Reconcile을 별도로 수행해 현재 Issue ID 목록과 Registry를 비교하면 됩니다.

14. Reconcile은 “전체 재수집”과 다릅니다

하지 않을 것 · Full Re-ingest

모든 Issue의 Description, Comment, Custom Field 등을 처음부터 다시 수집.

비용이 큽니다.

필요 시 할 것 · Lightweight Reconcile

현재 Project의 Issue ID/key 목록처럼 가벼운 기준 목록만 대조.

삭제/누락 후보만 따로 판단합니다.

Recovery 기본 Catch-up Delta Sync 선택적 보완 Lightweight Issue-ID Reconcile ≠ Full Initial Ingest

15. 새 Project와 재등장 Project는 다릅니다

상황기준처리
완전히 처음 보는 ProjectRegistry에 project_id 없음Initial Ingest 후 Watermark 생성
예전에 수집했던 Project가 다시 보임Registry에 같은 project_id + Watermark 존재Catch-up Delta, 필요 시 lightweight Reconcile
같은 key인데 project_id가 다름새 project_id새 Project로 취급

16. Registry와 Retrieval 상태는 분리합니다

Project Registry / Sync State

project_id current_key current_name visibility_state last_seen_at committed_watermark last_source_sync_at

Retrieval Policy

retrieval_enabled last_published_at freshness / stale metadata

Jira visibility가 변했다고 자동으로 검색을 끄지 않습니다.

17. Decision 6 수정 추천안

REVISED PROPOSAL

Project가 unavailable이어도 과거 Knowledge Retrieval은 유지한다.

Project identity = project_id Discovery complete + 기존 Project 미표시 → visibility_state = unavailable → Source Sync만 pause → Watermark 보존 → 기존 Retrieval 유지 → last_synced_at / stale 상태 표시 같은 project_id 재등장 → Initial Ingest X → 보존 Watermark + 5분 overlap Catch-up Delta → 필요 시 lightweight Reconcile 완전히 새로운 project_id → 최초 Initial Ingest
이 수정안의 장점: 과거 Jira Knowledge의 가치를 보존하면서도, 다시 접근 가능해졌을 때 전체 재수집 없이 자연스럽게 증분 갱신할 수 있습니다.
