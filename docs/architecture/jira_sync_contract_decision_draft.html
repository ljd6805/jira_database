3. Decision 1 · 확정 내용

FIXED

Project마다 독립적인 committed Watermark를 가진다.

Project A → 10:30 Project B → 09:50 ← 이번 Sync 실패 Project C → 10:30 다음 Sync A → 10:30 부근부터 B → 09:50 부근부터 다시 C → 10:30 부근부터

한 Project 실패가 다른 Project의 진행을 막지 않도록 합니다. Watermark는 해당 Project의 Jira source 수집과 변경 후보 확인이 안전하게 끝난 뒤에만 전진합니다.

4. Decision 2 — Overlap이 왜 필요한가?

Watermark가 10:30이라고 해서 다음 조회를 정확히 10:30 이후부터만 시작하면 경계에 걸린 변경을 놓칠 가능성이 있습니다. 그래서 책갈피보다 몇 쪽 앞에서 다시 읽습니다.

10:25다시 확인 시작
→
10:30지난 Watermark
→
10:40이번 Sync 상한
지난 committed watermark = 10:30 Overlap = 5분 이번 Sync upper bound = 10:40 실제 조회 범위 10:25 이상 ~ 10:40 미만 10:25~10:30 데이터는 다시 볼 수 있음 → 중복 후보 허용 → 뒤의 source_hash 판정에서 unchanged면 재처리하지 않음
핵심 생각: Sync에서는 “조금 더 읽는 비용”보다 “한 건을 영원히 놓치는 위험”이 더 큽니다. 중복은 뒤에서 제거할 수 있지만, 누락은 발견하기 어렵습니다.

5. 왜 0분이 아니라 최소한의 Overlap을 두나?

시간 경계

JQL의 날짜/시간 표현은 분 단위이므로 같은 분에 여러 변경이 모일 수 있습니다. 경계를 딱 잘라 읽는 것보다 겹쳐 읽는 편이 안전합니다.

검색 중 데이터 이동

페이지를 읽는 동안 Jira가 계속 변경되면 검색 결과 위치가 움직일 수 있습니다. Atlassian도 pagination에서 이런 현상을 설명합니다.

중복은 안전하게 제거 가능

Overlap으로 같은 Issue를 다시 수집하더라도 이후 Jira ID와 source_hash로 unchanged를 판별할 수 있습니다.

6. Overlap을 너무 작게/크게 잡으면?

값장점문제
0분중복 최소경계 누락에 가장 취약
1분분 단위 경계는 어느 정도 보호여유가 작고 운영 환경 차이에 민감
5분안전 여유가 있고 중복량도 작음일부 Issue를 다시 확인함
30분+누락 방지 여유 큼매 Sync마다 불필요한 재조회가 많아짐
현재 추천: 파일럿/초기 운영은 5분 Overlap. Jira 호출 제한이 20 req/min이고 delta-first 구조이므로 5분 정도의 중복 후보 비용은 감당 가능하고, 누락 방지 쪽에 더 무게를 두는 것이 좋습니다.

7. 조회 범위는 시작점뿐 아니라 끝점도 고정합니다

Overlap만 두고 조회 상한을 열어두면, 페이지를 읽는 동안 새 Issue가 계속 들어와 결과 위치가 흔들릴 수 있습니다. 따라서 이번 Sync가 책임질 끝 시각도 먼저 정합니다.

lower = committed_watermark - 5 minutes upper = sync 시작 시 정한 안전한 기준 시각 JQL 개념 project = ABC AND updated >= lower AND updated < upper ORDER BY updated ASC, id ASC

왜 >= lower?

Overlap 구간의 시작점까지 다시 포함해 누락보다 중복을 선택합니다.

왜 < upper?

이번 실행이 읽는 데이터 집합을 고정합니다. upper 이후 변경은 다음 Sync가 담당합니다.

주의: 구체적인 Jira server timezone 변환/upper 시각 획득 방식은 구현 명세에서 실제 사내 Jira 응답으로 검증합니다. 이 Decision에서는 “고정 lower/upper 범위를 사용한다”는 계약만 다룹니다.

8. Pagination 정렬도 함께 안전하게

ORDER BY updated ASC, id ASC updated가 같은 Issue가 여러 개여도 → Jira id를 두 번째 기준으로 사용 → 페이지 간 순서를 더 안정적으로 유지

Atlassian은 동일 정렬값이 많을 때 결과 순서를 보장하기 어렵기 때문에 두 번째 정렬 기준을 추가하는 방식을 안내합니다. 따라서 Delta 조회도 단일 updated 정렬보다 안정적인 tie-breaker를 둡니다.

9. Decision 2의 현재 추천 결론

PROPOSED

Project별 Delta 조회에 5분 Overlap과 고정 upper bound를 사용한다.

lower = project.committed_watermark - 5m upper = 이번 Sync가 시작할 때 고정한 기준 시각 updated >= lower updated < upper ORDER BY updated ASC, id ASC

Overlap에서 생긴 중복 후보는 허용합니다. 실제 재처리 여부는 다음 Decision인 new / changed / unchanged 판정에서 결정합니다.
