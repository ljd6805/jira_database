3. Decision 4 — source_hash는 무엇을 뜻해야 하나?

source_hash는 “이 Issue의 업무 지식 재료가 실제로 달라졌는가?”를 판단하는 지문입니다. 따라서 단순한 시스템 시간 변화 때문에 지문이 달라지면 안 됩니다.

source_hash가 달라짐 ↓ CHANGED 판정 ↓ 새 Issue Version ↓ Knowledge 재생성 ↓ Embedding / FAISS 갱신 즉 hash에 무엇을 넣는지가 곧 "무엇을 진짜 변경으로 볼 것인가"를 결정함

4. 현재 구현은 어떻게 되어 있나?

현재 builder는 Issue, Comment, Attachment metadata, Relationship, Custom Field를 한 묶음으로 만들고 경로만 제외한 뒤 SHA-256을 계산합니다.

Issue summary / description / status / priority created_at / updated_at Comments comment_id / sequence / author created_at / updated_at / body Attachments / Relationships / Custom Fields ↓ source_path / source_page만 제거 ↓ canonical JSON ↓ SHA-256 source_hash
문제 후보: 현재는 Issue의 updated_at과 Comment의 updated_at도 hash에 포함됩니다. 본문은 그대로인데 Jira가 timestamp만 바꾸면 새 Version으로 판정될 수 있습니다.

5. 쉬운 예 — 내용은 같은데 시간만 바뀌었다면?

어제

description = "retry 3회 적용" status = Resolved updated_at = 10:30 hash = AAA
→

오늘

description = "retry 3회 적용" status = Resolved updated_at = 10:35 현재 방식이면 hash = BBB 가능

업무 내용은 하나도 달라지지 않았는데 새 Issue Version과 Knowledge를 만들 수 있습니다. 운영에서는 이런 재처리를 피하는 편이 좋습니다.

6. 그렇다고 모든 시간을 빼면 안 됩니다

created_at은 유지

Issue나 Comment가 언제 생성됐는지는 실제 사실의 일부일 수 있습니다. 잘못된 시간이 정정되었다면 그것도 데이터 변화로 볼 가치가 있습니다.

updated_at은 제외 추천

이 값은 “Jira가 마지막으로 수정됐다고 기록한 시각”입니다. 실제 지식 내용은 별도로 hash에 이미 포함되므로 변경 탐지 지문에는 중복 신호가 됩니다.

핵심 구분: updated_at은 Delta 후보를 찾는 데는 중요하지만, 최종 semantic change를 판단하는 source_hash에는 넣지 않는 방향입니다.

영역포함제외

Commentcomment_id, sequence, author, created_at, body, formatupdated_at, source_path, source_page

보수적 원칙: 이번 v2에서는 불필요하다고 확신할 수 있는 updated_at만 추가로 제외합니다. 작성자, 생성 시각, 관계 상태, Custom Field 등 Knowledge 결과에 영향을 줄 수 있는 값은 섣불리 빼지 않습니다.

8. 실제 내용이 바뀌면 당연히 hash도 바뀝니다

Description 수정

원인/해결 내용이 달라짐 → hash 변경 → CHANGED.

댓글 추가/수정

comment_id/body가 달라짐 → hash 변경 → CHANGED.

Status / Custom Field / 관계 변경

업무 상태나 관계 지식이 달라짐 → hash 변경 → CHANGED.

9. hash 규칙 자체에도 Version이 필요합니다

중요한 부분입니다. v1에서 v2로 계산 규칙을 바꾸면 같은 Jira 내용도 hash 문자열이 달라질 수 있습니다. 따라서 hash 규칙 자체의 버전을 명시해야 합니다.

source_hash_profile = semantic_v2 semantic_v1 path 제외 updated_at 포함 semantic_v2 path 제외 issue.updated_at 제외 comment.updated_at 제외
추천: package/manifest 또는 DB가 어떤 hash profile로 계산됐는지 알 수 있게 기록합니다. 그래야 향후 v3가 생겨도 “내용이 바뀐 것”과 “hash 알고리즘이 바뀐 것”을 구분할 수 있습니다.

10. Decision 4 추천 결론

PROPOSED

source_hash v2는 업무 내용 중심의 semantic hash로 만든다.

계속 포함 → Issue 실제 내용/상태 → Comment 내용/작성자/생성시각 → Attachment metadata → Relationship → Custom Field 추가 제외 → issue.updated_at → comment.updated_at → 기존 source_path / source_page 그리고 → source_hash_profile = semantic_v2 기록

updated_at은 Delta 후보 조회용으로 보존하지만 semantic Version 생성의 직접 재료에서는 제외합니다.
