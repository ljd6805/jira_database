4. Decision 1 — 왜 Project별 Watermark인가?

Watermark는 “여기까지 안전하게 확인했다”는 책갈피였습니다. 여기서 중요한 것은 책갈피를 하나만 둘지, Project마다 따로 둘지입니다.

전역 Watermark 하나

A 성공 B 실패 C 성공 전체 Watermark ?

B 때문에 전체를 앞으로 못 넘기거나, 억지로 넘기면 B 변경을 놓칠 수 있습니다.

VS

Project별 Watermark

A → 10:30 B → 09:50 ← 실패 지점 유지 C → 10:30

A와 C는 정상 진행하고, 다음 Sync에서 B만 09:50부터 다시 확인할 수 있습니다.

추천안: Watermark는 Project별로 관리합니다. 이유는 Project 단위 실패 격리와 현재 Collector의 project boundary 구조를 그대로 살릴 수 있기 때문입니다.

7. Decision 1의 현재 추천 결론

PROPOSED

Project마다 독립적인 committed watermark를 가진다.

project_sync_state ├─ project_identity ├─ committed_watermark ├─ last_success_run_id └─ last_error

Project 하나가 실패해도 다른 Project의 진행을 막지 않습니다. 실패한 Project는 watermark를 움직이지 않고 다음 Sync에서 그 지점부터 다시 확인합니다.
