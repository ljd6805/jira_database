3. Decision 6 — Project Registry란?

Registry는 우리 서비스가 지금까지 만난 Jira Project의 주소록입니다. 매 Sync마다 Jira가 현재 보여주는 목록과 이 주소록을 비교합니다.

어제 Registry P100 / ABC / Project Alpha P200 / DEF / Project Delta 오늘 Jira Project Discovery P100 / ABC / Project Alpha P200 / DEF / Project Delta P300 / NEW / New Project 비교 P100 → 기존 Project P200 → 기존 Project P300 → 새 Project
왜 필요한가? 지금 Collector는 매 Run마다 보이는 Project를 수집하지만, “지난 Run에는 있었는데 이번 Run에는 없다”는 장기 상태를 별도로 기억하지 않습니다. 운영 서비스에는 Run을 넘는 Project 기억이 필요합니다.

4. Project의 진짜 Identity는 무엇으로 볼까?

현재 ProjectDiscovery는 key와 name을 주로 사용하지만 Jira 응답에는 Project ID도 있습니다. 운영 Registry에서는 Project ID를 authoritative identity로 쓰는 것을 추천합니다.

project_id — Identity

같은 Project를 장기간 추적하기 위한 기준값입니다.

project_id = 10000 → Registry Primary Identity

project_key / name — 현재 표시값

사람이 읽기 좋은 현재 이름입니다. 변경될 수 있으므로 Registry에서 최신값을 갱신합니다.

ABC / Project Alpha → 현재 metadata
Issue와 같은 철학입니다. Issue도 jira_id를 identity로 쓰고 Issue Key는 현재 표시 이름처럼 취급했습니다. Project도 같은 원칙으로 맞추는 편이 일관됩니다.

5. 매 Sync의 Discovery 결과는 세 부류로 나눕니다

상황판정처리
Registry에도 있고 이번에도 보임EXISTING / VISIBLEkey/name 최신화 후 Delta Sync
Registry에 없고 이번에 처음 보임NEW / VISIBLERegistry 등록 후 Initial Ingest
Registry에는 있는데 이번 목록에서 안 보임UNAVAILABLE 후보Discovery 전체 성공 여부를 먼저 확인한 뒤 상태 변경

6. 중요한 점 — “안 보임”은 “삭제됨”과 같지 않습니다

Jira Project 목록은 현재 로그인한 서비스 계정이 볼 수 있는 Project 목록입니다. 따라서 어제 있던 Project가 오늘 사라졌다고 원인을 단정할 수 없습니다.

가능성 A · 삭제/Archive

Project 자체가 더 이상 운영 대상이 아닐 수 있습니다.

가능성 B · 권한 상실

Project는 살아 있지만 서비스 계정의 Browse 권한이 사라졌을 수 있습니다.

가능성 C · 일시 오류

Discovery API 호출이나 pagination 자체가 실패했을 수 있습니다.

추천 용어: 원인을 추측해 deleted라고 기록하지 않고, 관찰한 사실만 unavailable 또는 not_visible로 기록합니다.

7. Discovery 자체가 실패했다면 Project 상태를 바꾸면 안 됩니다

Project Discovery 시작 page 1 성공 page 2 성공 page 3 API ERROR ✗ 이 결과만 보고 "뒤쪽 Project들이 모두 사라졌다" 라고 판단하면 안 됨 → Discovery Run = FAILED / INCOMPLETE → 기존 Registry visibility 상태 유지 → 어떤 Project도 unavailable로 바꾸지 않음
Fail-safe 규칙: Project Discovery가 끝까지 성공한 경우에만 “지난번엔 있었는데 이번에는 없다”는 비교를 신뢰합니다.

8. 성공한 Discovery에서 기존 Project가 사라졌다면?

여기서는 보안 쪽을 우선하는 것이 좋습니다.

어제 P100 = visible Knowledge = active 오늘 Discovery 전체 SUCCESS P100 없음 ↓ P100 visibility = unavailable ↓ Active Retrieval에서 즉시 제외 ↓ RAW / Version / Knowledge History는 보존

검색에서는 즉시 숨김

서비스 계정이 현재 볼 수 없는 Project의 과거 Knowledge를 계속 팀에 노출하지 않습니다.

데이터는 삭제하지 않음

과거 RAW, Issue Version, Knowledge, Review, Evidence는 감사·복구를 위해 그대로 보존합니다.

추천 정책: unavailable = fail-closed. 검색 제공은 차단하지만 History는 삭제하지 않습니다.

9. Watermark는 어떻게 하나?

P100 visibility = unavailable committed_watermark = 기존 값 그대로 보존 → 앞으로 이동 X → 초기화 X → 삭제 X

나중에 Project가 다시 보이면 과거 마지막 안전 지점을 알고 있어야 복구할 수 있기 때문입니다.

10. 새 Project를 처음 발견하면?

MVP의 프로젝트별 30개 제한은 검증용 제한이었습니다. 운영 서비스에서 새 Project를 처음 편입할 때는 전체 범위를 알아야 합니다.

새 Project P300 발견 ↓ Registry 등록 ↓ Initial Ingest = 접근 가능한 Issue 전체를 기준선으로 수집 ↓ NEW / CHANGED / UNCHANGED 원칙 적용 ↓ Knowledge / Embedding / Retrieval Publish ↓ 이후부터 Delta Sync
추천: 운영의 새 Project는 전체 Initial Ingest를 기본으로 합니다. 프로젝트별 30건 제한은 MVP Pilot 설정으로만 남깁니다.

11. unavailable Project가 다시 나타나면?

권한이 복구되었거나 Project가 다시 활성화될 수 있습니다. 이 경우 과거 Knowledge를 바로 다시 노출하기보다는 최신 상태 확인이 먼저입니다.

P100 unavailable ↓ 다음 Discovery에서 다시 visible ↓ Registry visibility = visible ↓ Catch-up / Reconcile 수행 ↓ 현재 상태가 안전하게 Publish됨 ↓ Active Retrieval 재허용
왜 바로 재노출하지 않나? 안 보이던 기간 동안 Issue가 수정·삭제됐을 수 있기 때문입니다. 재등장 시에는 최신 상태 확인을 거친 뒤 검색에 다시 넣는 것이 안전합니다. 구체적인 Reconcile 구현 방식은 후속 구현 설계에서 정합니다.

12. Registry에 최소한 무엇을 기억할까?

아직 물리 DB Schema를 Freeze하는 단계는 아니지만 논리적으로는 아래 정보가 필요합니다.

project_registry ├─ project_id ← authoritative identity ├─ current_key ├─ current_name ├─ visibility_state ← visible / unavailable ├─ first_seen_run_id ├─ last_seen_run_id ├─ last_seen_at ├─ unavailable_since nullable └─ unavailable_reason 예: not_visible_after_successful_discovery project_sync_state ├─ project_id ├─ committed_watermark ├─ last_source_success_run_id └─ last_error
분리 이유: Registry는 “Project가 현재 보이는가?”를 기억하고, Sync State는 “어디까지 수집했는가?”를 기억합니다. 역할이 다릅니다.

13. 이 Decision이 해결하지 않는 것

사용자 개인별 Jira 권한

Registry는 서비스 계정이 볼 수 있는 범위를 관리합니다. 팀원 A와 B가 Jira에서 서로 다른 권한을 가진 경우를 그대로 재현하는 문제는 별도 서비스 권한 설계가 필요합니다.

Issue 단위 삭제/권한 상실

Project는 보이지만 특정 Issue만 삭제되거나 비공개가 된 상황은 updated Delta만으로 완전히 잡기 어렵습니다. 향후 Reconcile 정책에서 별도로 다뤄야 합니다.

14. Decision 6 추천 결론

PROPOSED

Project Registry를 만들고 “현재 보임 여부”를 보수적으로 관리한다.

1. Project identity = project_id 2. key / name = mutable metadata 3. Discovery 전체 성공 후에만 Registry 비교 4. 새 Project = 전체 Initial Ingest 5. 기존 Project가 사라짐 = unavailable 6. unavailable 즉시 Active Retrieval 차단 7. RAW / History / Watermark는 보존 8. 삭제 vs 권한 상실은 억지로 구분하지 않음 9. 다시 보이면 Catch-up/Reconcile 후 Retrieval 재허용
