3. Decision 5 — Checkpoint와 Resume를 아주 쉽게

Checkpoint는 게임의 저장 지점입니다. Resume는 다시 실행했을 때 저장된 지점부터 이어서 하는 것입니다.

작업 1 성공 ✓ 작업 2 성공 ✓ 작업 3 실패 ✗ 작업 4 아직 - 프로그램 재시작 → 작업 1, 2를 다시 하지 않음 → 작업 3부터 다시 시작
목표: 실패했다고 전체 파이프라인을 처음부터 반복하지 않습니다. 이미 안전하게 끝난 결과는 재사용합니다.

4. 현재 프로젝트에 이미 있는 Checkpoint

현재 Collector는 한 Collection Run 안에서 Project와 Issue 상태를 SQLite에 기록합니다.

collection_run ├─ project A completed ├─ project B partial │ ├─ issue 1 completed │ ├─ issue 2 completed │ └─ issue 3 failed └─ project C completed resume_run() → completed Issue는 skip → pending / running / failed / partial 대상 재개
좋은 기반: 이 구조는 그대로 살립니다. 새 운영 서비스는 이 Checkpoint를 버리는 것이 아니라 downstream까지 확장합니다.

5. 왜 Source와 Downstream Checkpoint를 나눠야 하나?

① Source 수집 Checkpoint

Jira Issue와 Comment 등을 어디까지 안전하게 가져왔는지 기억합니다.

Jira → RAW → ANALYSIS → source_hash → change classification

② Downstream Checkpoint

확인된 NEW/CHANGED가 지식 서비스에 어디까지 반영됐는지 기억합니다.

Knowledge → Review / DB → Embedding → Retrieval publish

두 층을 분리하면 Jira 수집은 이미 끝났는데 Knowledge 생성만 실패했을 때 Jira를 다시 호출하지 않아도 됩니다.

6. 대표 상황 A — Jira 수집 도중 실패

Sync Run R100 Project A Issue 1 source completed ✓ Issue 2 source completed ✓ Issue 3 source failed ✗ Issue 4 pending - 프로세스 재시작 → 가능하면 같은 R100을 Resume → R100의 고정 lower / upper를 그대로 사용 → Issue 1, 2는 skip → Issue 3부터 재개
추천: 중단된 Sync Run을 재개할 수 있으면 같은 Run을 우선 재개합니다. 그래야 Decision 2에서 고정한 조회 window가 움직이지 않습니다.

7. 같은 Run을 재개할 수 없다면?

운영자가 Run을 폐기했거나 상태가 손상되어 같은 Run을 재개하지 못할 수도 있습니다. 그때는 안전한 fallback이 필요합니다.

R100 폐기 Project A committed_watermark = 10:30 그대로 새 Sync Run R101 lower = 10:30 - 5분 overlap → 다시 후보 조회 → source_hash로 중복 제거 → 누락 없이 복구

즉 same-run resume가 1순위, 새 Run + committed watermark + overlap이 2순위 안전망입니다.

8. 대표 상황 B — Jira는 성공, Knowledge만 실패

jira_id = 10042 source_hash = BBB Source snapshot COMPLETED ✓ Change classification CHANGED ✓ Knowledge generation FAILED ✗ Embedding PENDING - Retrieval publish PENDING - 다음 재개 → Jira 다시 수집 X → CHANGED 다시 판정 X → Knowledge generation부터 재시도
이게 Decision 5의 핵심입니다. 다음 Sync에서 Jira가 그대로라서 source_hash가 BBB로 같더라도 “이미 서비스 반영 완료”라고 착각하지 않습니다. BBB에 대한 downstream 미완료 상태를 따로 기억합니다.

9. Downstream 작업의 Identity

어떤 변경분에 대한 작업인지 흔들리지 않으려면 Run ID보다 Issue Version identity가 중요합니다.

jira_id = 10042 source_hash = BBB source_hash_profile = semantic_v2 ↓ 하나의 변경 Work Item ↓ Stage별 Checkpoint

즉 새 Sync Run이 시작되어도 같은 jira_id + source_hash라면 과거에 실패한 downstream 작업을 이어갈 수 있습니다.

10. Stage 상태는 단순하게

상태뜻재시작 시
pending아직 시작하지 않음실행 대상
running실행 중프로세스가 죽었다면 완료로 간주하지 않고 재검증/재시도
completed해당 Stage 산출물이 안전하게 완료재사용 / skip
failed오류로 끝남retry 대상
원칙: running은 성공이 아닙니다. 완료 표식이 없으면 안전하게 다시 시도합니다.

11. Resume 규칙을 한 줄로

각 Work Item에서 가장 앞의 "completed가 아닌 Stage"를 찾는다 ↓ 그 Stage부터 다시 실행한다 ↓ 앞의 completed Stage는 재사용한다 ↓ 뒤의 Stage는 선행 Stage 성공 후 순서대로 진행한다

Source 실패

Source 단계부터 재개.

Knowledge 실패

Knowledge부터 재개.

Embedding 실패

Knowledge 재생성 없이 Embedding부터 재개.

12. 전체 rollback은 하지 않습니다

Project A가 성공하고 B가 실패했다고 A를 과거 상태로 되돌리지는 않습니다.

Project A source completed → 보존 Project B source failed → B만 retry Project C source completed → 보존 Work Item X Knowledge completed → 보존 Work Item Y Embedding failed → Y embedding만 retry
추천: 성공한 독립 작업은 durable하게 보존하고 실패한 경계만 재시도합니다. 전역 rollback은 하지 않습니다.
