M0~M11에서 만든 Functional MVP와, 그 위에 추가하는 2-Loop Continuous Service를 하나의 그림으로 연결합니다. 이제 시스템은 “한 번 끝까지 실행하는 Pipeline”이 아니라 “Source를 계속 받는 Loop와 Knowledge를 계속 발행하는 Loop”로 운영됩니다.

0. 먼저 전체를 한 장으로

[Loop A · SOURCE SYNC] Jira → Project Discovery → Delta Download → RAW → ANALYSIS → Knowledge Input → semantic_v2 hash → NEW / CHANGED / UNCHANGED → SOURCE_COMMITTED + Watermark → sync_issue_change durable backlog ↓ [대기열 / 비동기 경계] ↓ [Loop B · KNOWLEDGE PROCESSING / PUBLISH] OpenCode Knowledge → Review / Evidence → Knowledge DB → BGE-M3 Embedding → FAISS staging / mapping → Atomic Publish ↓ [상시 RETRIEVAL SERVICE] Published Corpus → FAISS Top-3 → Evidence Resolver → MCP → OpenCode User
🏭
공장 비유

Loop A는 원재료 입고팀, backlog는 안전한 대기 창고, Loop B는 가공·검사·진열팀, MCP/OpenCode는 고객에게 상품을 찾아주는 창구입니다.

1. M0~M11 Functional MVP는 무엇을 이미 증명했나?

2-Loop는 새 운영 구조이지만, 내부의 처리 기술은 이미 M0~M11에서 검증했습니다.

2. Loop A · Jira Source를 최신으로 유지

A1

source_sync_run 시작

Run ID를 만들고 이번 Run의 fixed upper를 저장합니다.

sr_ + UUID4fixed upper
A2

Project Discovery

현재 계정이 볼 수 있는 Project 목록을 완전히 읽고 project_id Registry와 비교합니다.

A3

Initial / Delta / Catch-up

새 Project는 Initial Ingest, 기존 Project는 Watermark-5분부터 Delta, 재등장 Project는 retained Watermark 기반 Catch-up을 합니다.

A4

RAW → ANALYSIS → Knowledge Input

원본을 보존하고, 프로그램 친화 구조로 정리하고, 한 Issue의 사실을 한 Package로 조립합니다.

A5

semantic_v2 hash

Jira updated가 아니라 실제 업무 의미가 달라졌는지 판단합니다.

A6

NEW / CHANGED만 Work Item

UNCHANGED는 기존 지식을 재사용하고, NEW/CHANGED만 deterministic sync_issue_change를 만듭니다.

A7

SOURCE_COMMITTED + Watermark

Project Source window 전체가 안전한 경우에만 source_committed와 Watermark를 같은 Transaction으로 Commit합니다.

3. 두 Loop 사이 · durable backlog

sync_issue_change work_item_id = sw_ + hash(jira_id + source_hash + profile) knowledge_status embedding_status publish_status first_discovered_source_run_id last_observed_source_run_id last_processing_run_id
왜 파일 폴더만으로 넘기지 않나? Loop B가 느리거나 서버가 재시작돼도 “어떤 변경을 아직 처리해야 하는가?”가 durable State로 남아야 하기 때문입니다.

4. Loop B · Knowledge Processing / Publish

B1

processing_run 시작

Backlog에서 처리 대상을 선택합니다. Source Run과 별개 ID/수명주기를 가집니다.

pr_ + UUID4
B2

OpenCode Knowledge Generation

Issue 사실에서 검색 가치가 높은 문제/목표/발견/조치/결과/Open Item을 만듭니다.

B3

Review / Evidence

품질을 검증하고 필요하면 재생성합니다. 각 Knowledge Item이 실제 Jira Evidence로 돌아갈 수 있어야 합니다.

B4

Knowledge DB

Issue Version → Generation → Attempt → Item → Evidence의 족보를 저장합니다.

B5

BGE-M3 Embedding

승인된 Knowledge Item을 1024차원 의미 Vector로 바꿉니다.

B6

FAISS staging

새 Embedding과 mapping을 사용자에게 노출하기 전 staging에서 검증합니다.

B7

Atomic Publish

실제 Retrieval active view를 새 버전으로 전환한 뒤에만 State를 published로 기록합니다.

5. 상시 Retrieval Service는 두 Loop와 별개로 계속 동작

사용자 질문 → OpenCode → MCP search_jira_knowledge → 질문 Embedding → FAISS Published Corpus Top-3 → Knowledge Item → Evidence Resolver → 실제 Jira 근거 → OpenCode 최종 답변

Loop B가 실패하거나 backlog가 쌓여도 마지막 정상 Published Corpus는 계속 제공됩니다.

6. Source Head와 Published Head

Source Head

Loop A가 가장 최근 안전하게 Commit한 Jira semantic state.

Published Head

현재 실제 Retrieval이 사용자에게 제공하는 semantic state.

Source Head = V5 Published Head = V3 → Source Loop는 최신 → Processing Loop는 V4/V5 backlog 처리 중 → 사용자 검색은 V3 last-known-good

7. 왜 OpenCode가 느려도 전체 시스템이 밀리지 않나?

낮시간

Loop A: 정상 cadence Loop B: 느림 Backlog: 증가 가능

밤시간

Loop A: 독립 cadence Loop B: 처리량 증가 Backlog: 감소 / catch-up

2-Loop는 병목을 제거하지 않고 격리하고 측정 가능하게 만듭니다.

12. 아직 남은 설계

중간 Version supersede

Loop A가 V2→V3→V4를 만들었는데 Loop B가 아직 V2를 시작하지 않았다면, 모든 Version을 OpenCode로 처리할지 미시작 구버전을 skip/supersede할지 결정해야 합니다. Source Version은 모두 보존합니다.

Multi-worker

초기 Single Worker 이후 병렬 처리 필요가 확인되면 Queue claim/lease를 추가합니다.
