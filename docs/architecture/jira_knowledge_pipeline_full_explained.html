Jira 한 건이
AI의 답변 근거가 되기까지

이 문서는 M0~M11에서 검증한 전체 파이프라인과, D1~D8로 FROZEN한 Continuous Sync / Publish 운영 Loop까지 한 번에 이해하기 위한 학습 지도입니다.

핵심 관점: 이 시스템은 “Jira를 LLM에게 통째로 던지는 프로그램”이 아닙니다. 원본을 보존하고 → 사실을 정리하고 → 지식을 만들고 → 검색 가능하게 만들고 → 다시 원문 근거로 돌아오며, 백그라운드 Sync가 필요한 부분만 반복 갱신합니다.
먼저 30초

0. 전체를 한 장으로 보면

사용자 질문은 아래의 검색 경로를 타고, 백그라운드에서는 별도의 Sync Loop가 이 검색 재료를 계속 갱신합니다.

[사용자 검색 경로] Jira에서 축적된 Published Knowledge ↓ SQLite ↓ BGE-M3 Embedding ↓ FAISS 질문과 가까운 Knowledge Top-3 검색 ↓ Evidence Resolver 실제 Jira 근거 복원 ↓ MCP ↓ OpenCode 질문 판단 → MCP 호출 → 최종 답변 작성 [백그라운드 갱신 경로] 다음 Sync → Project Discovery → Delta Source → Source Commit → NEW/CHANGED만 Knowledge/Embedding 준비 → 안전한 Publish → 다음 Sync ... 반복
🏭
공장 + 물류 비유

Jira가 원재료 창고라면 RAW/ANALYSIS는 입고와 정리, Knowledge는 제품 가공, SQLite는 이력 관리, BGE-M3/FAISS는 물류 검색, MCP는 출고 창구입니다. Continuous Sync는 공장 뒤에서 계속 재고를 확인하고 새로 바뀐 원재료만 다시 생산 라인에 올리는 운영 담당자입니다.

2. Jira 수집 — 먼저 사실을 가져옵니다

첫 단계의 목표는 AI가 아닙니다. Jira에서 필요한 사실을 빠짐없이, 읽기 전용으로, 다시 재현할 수 있게 가져오는 것입니다.

입력: Jira 서버출력: JSON 응답20 req/minconcurrency 1

M0 · DONE

3. RAW — Jira 원본을 그대로 보존합니다

RAW는 이 프로젝트에서 매우 중요합니다. Parser나 LLM이 나중에 틀려도 “원래 Jira에는 뭐라고 적혀 있었지?”로 돌아갈 수 있는 기준입니다.

RAW가 하는 일

Jira API 응답을 run/project/issue 단위 JSON 파일로 저장합니다. 원본 사실의 기준점입니다.

RAW가 하지 않는 일

원인 분석, 요약, 지식 생성, 검색 최적화는 하지 않습니다.

data/raw/runs/<run_id>/ └─ projects/<project_key>/ ├─ project.json ├─ issue_search/page_*.json └─ issues/<issue_key>/ ├─ issue.json └─ comments/page_*.json
Raw First가공 결과가 마음에 안 들면 Jira를 다시 호출하는 것이 아니라 RAW에서 다시 처리할 수 있습니다.
M0 · DONE

4. ANALYSIS — 원본을 “프로그램이 읽기 쉬운 사실표”로 바꿉니다

RAW는 안전하지만 복잡합니다. ANALYSIS는 의미를 만들어내는 단계가 아니라, RAW에서 사실을 일정한 형식으로 정리하는 단계입니다.

RAW JSON ↓ deterministic parser / exporter issues.jsonl comments.jsonl attachments.jsonl issue_relationships.jsonl custom_field_catalog.jsonl custom_field_values.jsonl

Issue

제목, 설명, 상태, 우선순위 같은 핵심 필드를 정리합니다.

Comment

댓글 ID, 순서, 작성자, 본문을 일정한 구조로 만듭니다.

Relationship / Custom Field

Issue 관계와 사내 Custom Field도 별도 구조로 보존합니다.

🧺
비유

마트에서 장을 본 뒤 식재료를 냉장고 칸별로 정리하는 단계입니다. 아직 요리를 하지는 않습니다.

M1 · DONE

5. Knowledge Input — 한 Issue의 사실을 한 봉투에 모읍니다

ANALYSIS에는 Issue, Comment, 관계, Custom Field가 따로 흩어져 있습니다. Knowledge Input은 이들을 Issue 하나 기준으로 다시 조립합니다.

Issue DEMO-42 ├─ issue ├─ comments[] ├─ attachments[] ├─ relationships[] ├─ custom_fields[] └─ source_hash

왜 한 봉투로 묶나?

Knowledge 생성 Agent가 여러 JSONL을 직접 찾아다니지 않아도 Issue 하나의 사실을 한 번에 볼 수 있게 합니다.

source_hash

이 Issue의 의미 데이터가 이전과 같은지 비교하기 위한 지문입니다. 운영 Sync에서는 semantic_v2 규칙으로 실제 변경 여부를 판정합니다.

중요Knowledge Input도 아직 “지식”이 아닙니다. 지식을 만들기 위한 검증된 사실 재료 묶음입니다.
M2~M4 · DONE

6. Knowledge + Review — 사실에서 “검색할 가치가 있는 의미 문장”을 만듭니다

여기서 처음 생성형 LLM이 등장합니다. Issue 전체를 그대로 검색하지 않고, 업무적으로 유용한 지식 문장으로 정리합니다.

Knowledge Input ↓ Knowledge Generation ↓ Attempt 1 ├─ issue_summary ├─ problem_or_goal ├─ key_findings ├─ actions_and_decisions ├─ outcomes └─ open_items ↓ Review ├─ PASS → accepted └─ REGENERATE → Attempt 2 ...

Knowledge

“이 Issue에서 무엇이 문제였고, 무엇을 했고, 결과가 어땠나?”를 짧은 의미 단위로 정리합니다.

Attempt

1차 생성이 품질 기준을 못 넘으면 2차, 3차로 다시 생성합니다. 덮어쓰지 않고 이력을 보존합니다.

Review

사실 충실도, Evidence coverage 같은 기준으로 결과를 검증하고 PASS 여부를 결정합니다.

🧑‍🍳
비유

ANALYSIS가 손질된 식재료라면, Knowledge 생성은 요리이고 Review는 맛과 위생 검사를 하는 단계입니다. 검사에 실패하면 다시 요리합니다.

M5~M6 · DONE

7. Profiling + Logical Schema — 실제 데이터를 재고, 저장 설계도를 만듭니다

지식을 만들었다고 곧바로 DB를 짜지 않았습니다. 먼저 실제 Knowledge가 얼마나 크고, Evidence가 몇 개이고, retry가 얼마나 생기는지 측정한 뒤 DB 관계를 정했습니다.

M5 · Profiling

실제 Knowledge/Evidence/Retry 분포를 측정합니다. “우리 데이터가 실제로 어떻게 생겼나?”를 확인하는 단계입니다.

M6 · Logical Schema

Issue, Version, Generation, Attempt, Item, Evidence를 서로 다른 Entity로 분리하고 관계를 확정했습니다.

Issue └─ Issue Version └─ Knowledge Generation ├─ Attempt 1 → Review: REGENERATE └─ Attempt 2 → Review: PASS ├─ Knowledge Item ├─ Knowledge Item └─ ... 각 Item에 Evidence 연결
핵심“언제 파이프라인을 실행했나”와 “Issue 내용이 실제로 바뀌었나”를 분리했습니다. 그래서 같은 source_hash면 같은 Issue Version을 재사용할 수 있습니다.
M7 · DONE / PASS

8. SQLite — 설계도를 실제 검색용 지식 DB로 만듭니다

M6의 논리 구조를 실제 SQLite 테이블로 구현한 단계입니다. History는 보존하지만 검색에는 최신 승인 지식만 쓰도록 구분합니다.

History 저장

과거 Issue Version, 실패 Attempt, Review 이력도 남깁니다.

Active Retrieval

Issue 하나당 현재 검색에 사용되는 active Generation은 최대 하나입니다.

Evidence Round-trip

Knowledge Item이 실제 description/comment/relationship 등으로 돌아갈 수 있게 연결합니다.

History Storage 과거 Version / 과거 Attempt / Review ≠ Active Retrieval Corpus 현재 active Generation + accepted Attempt의 Knowledge Item
🗃️
비유

SQLite는 단순 문서 보관함이 아니라 “어느 문서 버전에서 어떤 요약을 만들었고, 몇 번째 시도가 승인됐고, 그 문장은 어떤 원문을 근거로 하는가”를 기록한 족보입니다.

M8 · DONE / PASS

9. BGE-M3 Embedding — Knowledge 문장을 의미 좌표로 바꿉니다

컴퓨터는 문장의 의미를 그대로 비교하기 어렵습니다. 그래서 Knowledge 문장을 1024개의 숫자로 바꿉니다.

"부팅 중 통신 timeout이 발생했다" ↓ BGE-M3 [0.013, -0.087, 0.221, ... 총 1024개 숫자] 뜻이 비슷한 문장 ↓ 의미 공간에서도 가까운 위치

입력

SQLite의 active + accepted Knowledge Item.

출력

Knowledge Item 하나당 1024차원 vector.

Identity

emb_ → ki_ 연결을 유지해서 vector를 원래 문장으로 되돌릴 수 있습니다.

실제 검증현재 MVP에서는 285개 Knowledge Item → 285개 Embedding, 1024차원, mapping/identity failure 0으로 검증했습니다.
M9 · DONE / PASS

10. FAISS — 질문과 의미가 가까운 Knowledge를 찾습니다

BGE-M3가 좌표를 만들었다면, FAISS는 그 좌표들 중 질문과 가까운 후보를 찾는 검색 엔진입니다.

사용자 질문 ↓ BGE-M3 질문 vector ↓ FAISS IndexFlatIP ↓ 가까운 Knowledge Top-3 ↓ knowledge_item_id (ki_) 후보

FAISS가 잘하는 것

1024차원 벡터들 중 의미적으로 가까운 후보를 매우 빠르게 찾는 것.

FAISS가 모르는 것

원본 Jira 문장, 댓글 ID, 실제 Evidence 내용은 모릅니다. 그것은 다음 단계에서 DB를 통해 복원합니다.

오해 금지FAISS position ≠ embedding_id ≠ knowledge_item_id 입니다. 배열 위치, Embedding identity, Knowledge identity는 서로 다른 개념입니다.
M10 · DONE / REAL-RUN PASS

11. Evidence + MCP — 찾은 지식에 실제 Jira 근거를 붙입니다

M9가 “관련 있어 보이는 Knowledge”를 찾았다면, M10은 “그 말의 근거가 Jira 어디에 있나?”를 다시 찾아 붙입니다.

FAISS Top-3 ↓ ki_ Knowledge Item ↓ ke_ Knowledge Evidence ↓ SQLite source ├─ summary ├─ description ├─ comment ├─ attachment metadata ├─ relationship └─ custom field ↓ Evidence Package ↓ MCP tools

search_jira_knowledge

자연어 질문 → Top-3 Knowledge + 실제 Evidence Package.

get_jira_issue

Issue key를 알고 있을 때 해당 Issue의 현재 snapshot을 더 깊게 조회.

중요한 아키텍처MCP 내부에는 생성형 LLM이 없습니다. 검색과 근거 복원만 담당합니다. 최종 설명은 OpenCode 같은 외부 Agent가 작성합니다.
M11 · DONE / PASS

12. OpenCode — 실제 사용자가 질문하는 최종 소비자입니다

M11에서는 만든 MCP를 OpenCode에 연결해 실제 Agent가 스스로 Tool을 발견하고 필요할 때 호출하는지 검증했습니다.

사용자: 자연어 업무 질문 ↓ OpenCode Agent ↓ "Jira에서 찾아보는 게 좋겠다" search_jira_knowledge 자동 선택 ↓ Knowledge + Evidence ↓ Agent가 여러 근거를 읽고 설명 ↓ 사용자에게 최종 답변

Tool discovery

Auto Tool Selection

Evidence 추적

근거 요청 시 실제 description/comment Evidence까지 되돌아갔습니다.

한 문장으로Sync Loop는 “Jira에서 무엇이 달라졌나?”를 반복 확인하고, Publish Loop는 “새 지식이 완전히 준비됐나?”를 확인합니다. 둘 사이에서 기존 Published Knowledge가 서비스 공백을 막아줍니다.

Project가 안 보이면

그 Project만 Sync에서 건너뜁니다. Jira Source Lifecycle과 Knowledge Lifecycle은 별개이므로 기존 지식은 계속 검색됩니다.

Project가 다시 보이면

처음부터 재수집하지 않고 보존한 Watermark + 5분 Overlap으로 Catch-up Delta Sync합니다.

Run이 FAILED여도

이번 갱신 Run의 실패일 뿐입니다. 기존 Published Knowledge와 MCP 검색 서비스는 그대로 유지됩니다.

15. ID 족보 — 처음 보면 무섭지만 역할은 단순합니다

ID는 “무엇이 무엇에서 만들어졌는지” 잃지 않기 위해 붙입니다. 모두 외울 필요는 없고, 앞에서 뒤로 내려가는 족보만 이해하면 됩니다.

16. 가상의 Issue 하나가 전체 파이프라인을 여행한다면

실제 사내 Issue 내용 대신 DEMO-42라는 가상의 예로 흐름만 보겠습니다.

① JiraDEMO-42에 “부팅 때 통신 timeout”이라는 Issue와 댓글들이 존재합니다.
② RAWJira API의 issue.json, comment page를 그대로 저장합니다.
③ ANALYSISIssue, Comment, 관계, Custom Field를 정규화된 JSONL로 나눕니다.
④ Knowledge InputDEMO-42의 모든 사실을 한 JSON package로 모으고 semantic_v2 source_hash를 계산합니다.
⑤ KnowledgeLLM이 “문제”, “조치”, “결과” 같은 의미 문장을 만들고 각 문장에 Evidence를 연결합니다.
⑥ Review1차 결과가 부족하면 재생성하고, PASS된 Attempt를 accepted로 선택합니다.
⑦ SQLiteIssue Version → Generation → Attempt → Item → Evidence의 족보를 저장합니다.
⑧ BGE-M3승인된 Knowledge Item을 1024차원 vector로 바꿉니다.
⑨ FAISS사용자가 “부팅 통신 timeout 사례”라고 물으면 DEMO-42 관련 Knowledge가 Top-3에 들어옵니다.
⑩ Evidence해당 Knowledge의 ke_를 따라 실제 description/comment 원문을 복원합니다.
⑪ MCP/OpenCodeOpenCode가 Knowledge + Evidence를 읽고 사용자에게 근거 기반 답변을 작성합니다.
⑫ 다음 SyncDEMO-42가 수정되면 Delta 후보로 다시 수집하고 semantic_v2 hash에 따라 changed/unchanged를 판정합니다. changed면 새 결과를 준비하되 Publish 완료 전까지 기존 Published Knowledge를 계속 제공합니다.

17. 용어 사전 — 이 문서에서 자주 나오는 말

이 용어들만 익숙해지면 이후 설계 대화가 훨씬 편해집니다.

Pipeline데이터가 여러 처리 단계를 순서대로 지나가는 전체 흐름.
Run파이프라인 또는 Sync를 한 번 실행한 작업 단위.
RAWJira에서 받은 원본에 가장 가까운 보존 데이터. 사실의 기준.
ANALYSISRAW에서 deterministic하게 정리한 분석 친화 사실 데이터.
Knowledge Input한 Issue의 Issue/Comment/관계/Custom Field 사실을 묶은 LLM 입력 package.
Knowledge원본 사실에서 뽑은 검색 가치가 있는 의미 문장.
EvidenceKnowledge 문장을 뒷받침하는 실제 Jira summary/description/comment 등.
Version같은 Jira Issue의 내용이 실제로 달라진 의미 상태.
Generation특정 Version을 특정 Knowledge Contract로 지식화한 작업 lineage.
AttemptGeneration 안에서 실제 수행한 1차·2차·3차 생성 시도.
Active / Published현재 검색 서비스에서 실제로 제공 중인 검증 완료 Knowledge 상태.
Historical감사/재현을 위해 DB에 남기는 과거 상태. Jira에서 삭제된 과거 지식도 보존 정책에 따라 Retrieval에 계속 활용될 수 있습니다.
Embedding문장의 의미를 비교할 수 있도록 만든 숫자 vector.
Vector여러 숫자로 된 좌표. 이 프로젝트의 BGE-M3 dense vector는 1024차원.
FAISSvector 사이의 가까움을 빠르게 찾아주는 검색 인덱스.
Top-K검색 결과에서 가장 가까운 후보 K개. 현재 baseline은 Top-3.
MCPAgent가 검색/get_issue 같은 기능을 표준 Tool로 호출하게 해주는 서비스 경계.
RAG질문에 관련 근거를 먼저 검색한 뒤 그 근거를 LLM에게 주어 답하게 하는 방식.
source_hashIssue 의미 데이터의 지문. 운영 계약은 semantic_v2를 사용합니다.
Checkpoint중간 실패 후 어디부터 다시 시작할지 기억하는 저장 지점.
WatermarkProject별로 “지난번 어디까지 안전하게 Source Commit했나”를 기억하는 책갈피.
OverlapWatermark보다 5분 앞에서 다시 읽어 경계 누락을 방지하는 안전 구간.
Delta전체가 아니라 지난번 이후의 신규/변경 후보.
Source CommitJira Source와 변경 판정을 안전하게 저장해 Watermark 전진이 가능한 상태.
Publish새 Knowledge, Evidence, Embedding, FAISS/Mapping이 모두 일치하고 실제 Retrieval 전환까지 끝난 상태.
Project Registryproject_id 기준으로 지금까지 만난 Project와 visible/unavailable 상태를 기억하는 주소록.
Idempotent같은 입력을 다시 처리해도 중복이나 다른 결과를 만들지 않는 성질.
Atomic publishDB/Vector/FAISS가 서로 다른 세대를 보이지 않도록 완성된 Published 상태를 한 번에 전환하는 원칙.
Remote MCP각 PC의 local stdio가 아니라 중앙 서버에 올려 여러 OpenCode가 네트워크로 쓰는 MCP.

18. 문제가 생기면 “어느 층의 문제인가?”부터 보면 됩니다

전체 구조를 이해하면 디버깅도 쉬워집니다. 모든 오류를 “LLM이 이상하다”로 몰아가지 않는 것이 중요합니다.

사실이 틀렸다

RAW / ANALYSIS / Knowledge Input을 봅니다. Jira 수집이나 정규화 문제일 가능성이 큽니다.

요약이 이상하다

Knowledge / Review / Evidence 연결을 봅니다. 생성 품질 또는 검증 문제입니다.

검색이 엉뚱하다

Embedding / FAISS / Published corpus를 봅니다. LLM 답변보다 검색 품질 문제일 수 있습니다.

근거가 안 나온다

ki_ → ke_ → source Evidence round-trip을 봅니다.

OpenCode가 Tool을 안 쓴다

MCP 연결, Tool discovery, Agent Tool 선택 문제를 봅니다.

최신 Jira가 검색 안 된다

Sync Run → Project 상태 → Watermark → Source Commit → Knowledge/Embedding → Publish 중 어디에서 멈췄는지 봅니다.

전체를 이해했다는 기준“Jira → RAW → ANALYSIS → Knowledge → SQLite → Embedding → FAISS → Evidence → MCP → OpenCode”와 “다음 Sync → Delta → Source Commit → Publish → 다음 Sync” 두 흐름을 설명할 수 있으면 충분합니다.
