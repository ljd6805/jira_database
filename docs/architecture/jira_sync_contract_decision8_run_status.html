SYNC CONTRACT · DECISION 8 · 2026-08-27

한 번의 Sync가
성공했는지 어떻게 말할까?

D7에서 Source Commit과 Publish를 분리했습니다. 마지막 D8에서는 한 Sync Run 전체를 completed / partial / failed 중 무엇으로 기록할지 정합니다.

D1~D7 FIXED · D8 REVIEWING · LAST DECISION

1. 먼저 세 가지 상태를 구분합니다

Run 상태 하나만 보면 원인을 알기 어렵습니다. 따라서 내부적으로 Source 상태와 Publish 상태를 따로 기록하고, 마지막에 Run 상태를 집계하는 방식을 추천합니다.

source_status = Jira Project Discovery + 각 visible Project Source window 처리 결과 publish_status = 이번 Run에서 생긴 NEW/CHANGED Work Item의 Knowledge→Embedding→Retrieval 반영 결과 run_status = source_status + publish_status를 사람이 보기 쉽게 집계한 최종 상태

2. COMPLETED — 이번 Run이 맡은 일을 모두 끝냄

조건

Project Discovery = SUCCESS 현재 visible Project → 모든 Source window = SOURCE_COMMITTED 이번 Run의 NEW / CHANGED Work Item → 모두 PUBLISHED 또는 → NEW / CHANGED가 없어서 Publish 작업 자체가 없음 결론 run_status = completed

변경이 0건이어도 실패가 아닙니다. 확인할 범위를 정상적으로 확인했고 새로 Publish할 것이 없었다면 completed입니다.

3. PARTIAL — 일부는 안전하게 끝났지만 남은 일이 있음

대표 상황

Project A Source Commit ✓ Project B Source 실패 ✗ Project C Source Commit ✓ 또는 Source Commit 전부 ✓ ABC-1 Publish ✓ ABC-2 Embedding 실패 ✗ ABC-3 Publish ✓ 결론 run_status = partial

이미 성공한 Project/Stage는 그대로 보존합니다. 실패한 경계만 D5 Checkpoint/Resume 규칙으로 다시 수행합니다.

중요: Source는 전부 성공했지만 Publish가 일부 또는 전부 남은 경우도 partial입니다. 최신 Jira 사실은 확보했지만 이번 Run의 서비스 반영이 아직 완성되지 않았기 때문입니다.

4. FAILED — 신뢰할 수 있는 Sync 진행 자체를 만들지 못함

추천 정의

예 1 Project Discovery 자체가 FAILED / INCOMPLETE → 이번 Run이 책임질 Project 범위를 신뢰할 수 없음 예 2 Discovery는 성공했지만 처리해야 할 visible Project의 Source window가 모두 실패 → durable Source Commit이 하나도 없음 결론 run_status = failed

failed는 “검색 서비스가 망가졌다”는 뜻이 아닙니다. 기존 Published Knowledge는 그대로 서비스됩니다. 단지 이번 Sync Run이 새 Source 진행을 신뢰성 있게 남기지 못했다는 뜻입니다.

5. unavailable Project는 실패가 아닙니다

D6에서 기존 Project가 현재 Jira에 안 보이면 그 Project는 이번 Source Sync에서 그냥 건너뛰기로 했습니다. 따라서 unavailable 자체를 Run 실패로 세지 않습니다.

Registry A = visible B = unavailable C = visible 이번 Run A Source Commit ✓ B SKIPPED_UNAVAILABLE C Source Commit ✓ Publish 필요한 변경분 모두 완료 ✓ → run_status = completed

B의 기존 Knowledge는 계속 Retrieval되고, Watermark도 보존됩니다.

6. 새 Project가 하나도 없고 변경도 0건이면?

Discovery SUCCESS 모든 visible Project Source window SUCCESS NEW = 0 CHANGED = 0 UNCHANGED만 존재 Publish work = 0 → completed

“아무것도 바뀌지 않았다”는 정상적인 Sync 결과입니다.

7. Source는 성공했는데 Publish가 전부 실패하면?

Discovery SUCCESS Project A/B/C Source Commit ✓ Watermark advance ✓ NEW/CHANGED = 5건 Publish 성공 = 0건 Publish 실패 = 5건 Source에는 durable progress가 있음 하지만 검색 반영은 미완료 → run_status = partial → 기존 Published Knowledge는 계속 제공 → 다음 Resume은 실패 Stage부터

이 경우를 failed로 부르면 Source Commit까지 성공한 중요한 진척을 숨기게 됩니다. 그래서 partial이 더 정확합니다.

8. 내부 상태는 이렇게 두는 것을 추천합니다

필드예시 값의미
discovery_statuscompleted / failedProject 목록 비교를 신뢰할 수 있는가
source_statuscompleted / partial / failedvisible Project Source window 처리 결과
publish_statuscompleted / partial / failed / not_requiredNEW/CHANGED의 서비스 반영 결과
run_statuscompleted / partial / failed운영자가 보는 최종 집계 상태

9. 현재 Collector와 달라지는 점

현재 finish_run()은 Project 하나라도 실패하면 partial로 처리하고, 모든 Project가 실패해도 별도 failed 상태로 구분하지 않습니다.

현재 MVP failure_count > 0 또는 unfinished > 0 → partial 운영 Contract 제안 신뢰 가능한 진행 없음 → failed 일부 durable progress 있음 + 미완료 있음 → partial 모든 책임 범위 완료 → completed

구현 단계에서 이 집계 규칙을 운영 Sync State에 새로 반영합니다. 기존 MVP 상태 DB를 억지로 의미 변경하지 않고 확장하는 편이 안전합니다.

10. Decision 8 추천 결론

PROPOSED

최종 Run 상태는 세 가지로 고정합니다.

COMPLETED = Discovery 성공 + 모든 visible Project Source Commit 완료 + 모든 필요한 Publish 완료(또는 not_required) PARTIAL = durable한 성공 결과가 하나 이상 있음 + Source 또는 Publish에 미완료/실패가 남음 FAILED = Discovery를 신뢰할 수 없거나 + 처리해야 할 Source 범위에서 durable progress를 하나도 만들지 못함 UNAVAILABLE Project = 실패로 세지 않고 skip
D8까지 승인되면: D1~D8 전체 결정을 하나의 공식 FROZEN Sync Contract HTML로 합치고, 다음 구현 단계인 Sync State / Project Registry DB Schema 설계로 넘어갑니다.
