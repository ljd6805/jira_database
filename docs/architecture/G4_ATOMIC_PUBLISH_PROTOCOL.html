1. Atomic Publish를 한 문장으로

“새 책과 새 색인을 같이 공개한다.”

Knowledge DB를 책 본문, FAISS를 책의 색인이라고 생각하면 쉽습니다. 본문은 새 버전인데 색인이 옛 버전이거나, 색인은 새 버전인데 본문이 아직 candidate라면 검색 결과가 깨집니다. G4는 이 두 가지가 항상 같은 Generation 집합을 가리키게 합니다.

2. 왜 단순히 “순서대로 3개 실행”하면 안 되나?

Knowledge를 먼저 active

FAISS가 아직 옛 bundle이면 검색 후보와 Evidence Resolver가 서로 다른 Generation을 봅니다.

FAISS를 먼저 새 것으로 교체

FAISS가 아직 candidate Generation을 가리키면 Evidence Resolver는 active가 아니므로 결과를 정상 Evidence로 열 수 없습니다.

따라서 “A 먼저, B 나중”의 순서 문제가 아니라 둘을 같은 service head로 식별하는 규칙이 필요합니다.

3. 처음 시도했던 설계와 왜 폐기했나?

초기 아이디어

Knowledge DB와 State DB를 SQLite ATTACH DATABASE로 한 connection에 붙이고, Generation active 전환과 State published를 하나의 cross-database transaction으로 commit하려 했습니다.

[처음 생각] Knowledge DB ─┐ ├─ ATTACH + 하나의 COMMIT → 완벽한 Atomic? State DB ─────┘
실제 CI가 설계 문제를 발견

State Schema 개정 3은 새 DB를 의도적으로 WAL journal mode로 만듭니다. SQLite 공식 문서상 여러 attached DB의 crash-safe atomic commit은 main DB가 WAL이 아닐 때 보장됩니다. 즉 테스트를 통과시키려고 State를 DELETE mode로 바꾸면 기존 운영 정책을 훼손하는 셈입니다.

선택지판단이유
테스트에서 WAL 끄기폐기실제 운영과 다른 테스트가 되어 결함을 숨김
운영 State를 DELETE journal로 변경폐기G4 때문에 이미 정한 State WAL 정책을 흔들 이유가 없음
Cross-DB transaction에 의존하지 않는 프로토콜채택State WAL을 그대로 유지하면서 fail-closed / retry 가능

참고: SQLite 공식 문서 · ATTACH DATABASE · Temporary Files / Super-journal · Atomic Commit

4. 최종 G4 프로토콜 · 7단계

Publish Work claim

Knowledge/Embedding 완료 + Source Ready + latest Work 하나만 잡습니다.

2

target Generation + 다른 Jira의 현재 active Generation 집합을 계산합니다.

3

각 Generation의 검증된 Embedding을 합쳐 새 FAISS/index/mapping/manifest를 만듭니다.

4
Integrity Gate

row 수, contract, dimension, hash, mapping, normalization, Generation 집합을 다시 검증합니다.

5
Latest 재검사 + State lock

BEGIN IMMEDIATE로 짧게 State write lock을 잡아 commit 경계에서 Source/다른 Publish 변화를 막습니다.

6

Knowledge DB 한 transaction에서 같은 Jira의 old active를 historical로 내리고 target을 active로 올립니다.

5. “Retrieval pointer 파일”이 따로 없는 이유

G4에서는 current.txt나 symlink 같은 별도 mutable pointer를 만들지 않았습니다. 대신 Knowledge DB의 active Generation 집합 자체를 service head identity로 사용합니다.

Knowledge DB

현재 서비스에 노출되어야 할 Generation ID 집합을 결정합니다.

active = { kg_A2, kg_B1, kg_C4 }
Retrieval bundle

publish.bundle.json과 mapping의 Generation 집합이 정확히 같은 bundle만 active 후보가 됩니다.

bundle generations = { kg_A2, kg_B1, kg_C4 } → MATCH → 사용 가능
핵심 효과

staging 파일은 먼저 만들어져도 active Generation 집합과 다르므로 서비스에 보이지 않습니다. Knowledge DB transaction이 commit되는 순간에만 그 Generation 집합과 정확히 맞는 prebuilt bundle이 존재하게 됩니다.

8. 왜 Full Snapshot을 다시 만들까?

현재 G4는 일부러 단순하게 갑니다.

새 Jira 한 건만 바뀌어도 현재 active Generation들의 Embedding을 모아 FAISS 전체 snapshot을 다시 만듭니다. 초기 운영 규모에서는 correctness가 delta index mutation보다 중요합니다.

장점

새 bundle 하나만 검증하면 되고, 이전 index에 잘못된 vector가 남는 문제를 피합니다. rollback/비교도 쉽습니다.

나중 최적화

데이터가 충분히 커져 rebuild 비용이 실제 병목으로 확인될 때만 shard/delta/compaction을 별도 설계합니다. G4에서 미리 복잡하게 만들지 않습니다.

9. MCP는 어떻게 새 head를 읽나?

MCP START │ ├─ JIRA_KNOWLEDGE_DB_PATH │ └─ active Generation set 읽기 │ └─ JIRA_RETRIEVAL_ARTIFACT_ROOT └─ runs/* 중 Generation set이 정확히 같은 bundle 찾기 │ ▼ validation PASS │ ▼ searcher + manifest pin │ ▼ MCP READY
시작 시 pin

MCP가 실행 중인 한 요청 도중 manifest/index가 갑자기 바뀌지 않게, 현재 구현은 MCP 시작 시 active bundle을 결정하고 고정합니다. 새 Publish를 서비스 프로세스에 반영하려면 MCP를 재시작하거나 향후 별도 safe reload를 구현합니다.

왜 요청마다 자동 hot-reload하지 않나?

질문 embedding은 Retrieval manifest의 모델/프로필/차원과 맞아야 합니다. 한 요청 중 head가 바뀌면 query vector는 옛 contract, 검색기는 새 index를 쓰는 race가 생길 수 있습니다. G4에서는 이 복잡도를 넣지 않습니다.

10. CI가 직접 검증하는 시나리오

Initial Publish

첫 candidate → active, State published, 실제 FAISS search까지 확인합니다.

Full Snapshot

A+B active 뒤 A v2 Publish 시 A v1이 빠지고 A v2+B만 남는지 확인합니다.

WAL Preserve

Publish 전후 State journal mode가 계속 WAL인지 확인합니다.

Checkpoint Failure

Knowledge commit 직후 State 실패를 강제로 만들고 재실행이 published로 수렴하는지 확인합니다.

Concurrent Publish Race

Staging 도중 다른 Issue가 Publish되면 낡은 snapshot을 거부하고 재시도하는지 확인합니다.

Idempotency

이미 처리된 backlog에서 worker를 다시 실행해도 중복 Publish가 생기지 않는지 확인합니다.
