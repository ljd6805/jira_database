아주 쉽게 이해하기

G3까지 만든 Knowledge와 Embedding은 아직 candidate입니다. G4는 검증된 새 Knowledge와 새 FAISS Retrieval bundle을 서로 같은 버전 묶음으로 서비스에 공개합니다.

1. 한 문장으로: 새 책과 새 색인을 같이 공개한다

본문과 색인이 서로 다른 버전이면 검색은 깨집니다.

Knowledge DB를 책 본문, FAISS를 색인이라고 생각하면 쉽습니다. 새 본문을 공개했는데 색인은 옛 버전이거나, 새 색인이 아직 candidate 본문을 가리키면 안 됩니다.

2. 왜 단순히 순서대로 바꾸면 안 되나?

Knowledge를 먼저 active

서비스가 옛 FAISS를 계속 사용하면 검색 후보는 옛 Generation인데 Evidence Resolver는 새 active만 허용하게 됩니다.

FAISS를 먼저 교체

새 FAISS가 아직 candidate Generation을 가리키면 검색 후보를 active Knowledge로 정상 복원할 수 없습니다.

즉 A→B 순서를 고르는 문제가 아니라, Knowledge와 Retrieval이 같은 Generation 집합이라는 사실을 하나의 서비스 head 규칙으로 만들어야 합니다.

3. 처음 시도한 ATTACH 설계는 왜 폐기했나?

초기 아이디어

Knowledge DB와 State DB를 SQLite ATTACH DATABASE로 붙여 Generation active 전환과 State published를 한 transaction에서 commit하려 했습니다.

처음 생각 Knowledge DB ─┐ ├─ ATTACH + COMMIT → 두 DB 모두 Atomic? State DB ─────┘
CI가 실제 구조와의 충돌을 발견했습니다.

Operational State 개정 3은 의도적으로 WAL journal mode를 사용합니다. SQLite 공식 문서상 여러 attached DB의 crash-safe atomic commit은 WAL이 아닌 rollback-journal 조건이 필요합니다. 따라서 테스트를 통과시키기 위해 WAL을 끄는 것은 잘못된 해결책입니다.

선택판단이유
테스트에서 State WAL 끄기폐기운영과 다른 테스트가 되어 결함을 숨김
State 운영 정책을 DELETE journal로 변경폐기G4 때문에 이미 결정한 State 정책을 흔들 이유가 없음
Cross-DB transaction에 의존하지 않는 프로토콜채택WAL 유지 + fail-closed + 재시도 수렴 가능

참고: SQLite 공식 문서 · ATTACH DATABASE · Temporary Files / Super-journal · Atomic Commit

5. Active Retrieval은 별도 pointer 파일이 아니라 Generation 집합으로 찾는다

current.txt나 symlink 같은 mutable pointer를 따로 두지 않았습니다. Knowledge DB의 active accepted Generation ID 집합 자체가 service head identity입니다.

Knowledge head
active accepted Generations = { kg_A2, kg_B1, kg_C4 }
Retrieval head
bundle Generation set = { kg_A2, kg_B1, kg_C4 } mapping Generation set도 동일 + artifact validation PASS → 사용 가능
중요한 효과

staging bundle이 먼저 생성되어도 아직 active 집합과 다르면 서비스가 선택하지 않습니다. Knowledge head가 commit된 뒤에만 정확히 같은 Generation 집합의 검증 bundle이 Retrieval head가 됩니다.

8. 왜 매 Publish마다 Full Snapshot을 다시 만드나?

현재는 correctness를 우선합니다.

한 Jira만 바뀌어도 현재 active Generation 전체의 Embedding을 모아 새 FAISS snapshot을 만듭니다. 초기 운영 규모에서는 delta index mutation보다 검증과 복구가 단순한 구조가 더 중요합니다.

장점

새 bundle 하나만 검증하면 되고, 이전 index에 stale vector가 남는 문제를 피합니다. artifact 비교와 rollback 분석도 쉽습니다.

나중 최적화

실제 데이터 규모에서 rebuild가 병목으로 확인될 때만 shard/delta/compaction을 별도 설계합니다.

9. 실행 중인 MCP는 어떻게 Publish와 충돌하지 않나?

단순 startup pin은 충분하지 않았습니다.

MCP가 옛 FAISS를 메모리에 고정한 채 Knowledge DB만 새 active로 바뀌면, 옛 검색 후보가 historical이 되어 Evidence Resolver와 어긋날 수 있습니다. 그래서 최종 구현은 요청 단위 read snapshot을 사용합니다.

MCP search request 시작 │ ▼ Knowledge DB BEGIN read snapshot │ ▼ 이 snapshot이 보는 active Generation 집합 읽기 │ ▼ 정확히 같은 Generation 집합의 immutable FAISS bundle 선택 │ ├─ 같은 bundle manifest로 query embedding ├─ 같은 bundle FAISS로 Top-k 검색 └─ 같은 Knowledge DB read snapshot으로 Evidence resolve │ ▼ request 완료 → read snapshot 종료
Publish가 요청 도중 일어나면

이미 시작된 요청은 SQLite WAL read snapshot 덕분에 끝까지 옛 Knowledge + 옛 FAISS를 같이 봅니다.

다음 요청부터

새 read snapshot은 새 active Generation + 새 FAISS bundle을 선택합니다. MCP 프로세스 재시작은 G4의 필수조건이 아닙니다.

JIRA_RETRIEVAL_ARTIFACT_ROOT가 이 운영 모드를 사용합니다. 기존 JIRA_RETRIEVAL_ARTIFACT_DIR 직접 지정 방식은 M9/M11 호환 경로로 유지합니다.

10. 자동 테스트가 직접 검증하는 시나리오

Initial Publish

첫 candidate → active, State published, 실제 FAISS search를 확인합니다.

Full Snapshot

A+B active 뒤 A v2 Publish 시 A v1은 빠지고 A v2+B만 남습니다.

WAL Preserve

Publish 전후 State journal mode가 WAL인지 확인합니다.

Checkpoint Failure

Knowledge commit 뒤 State 실패를 강제로 만들고 재실행이 published로 수렴하는지 확인합니다.

Concurrent Publish Race

staging 중 다른 Issue Publish로 snapshot이 낡으면 commit을 거부하고 재시도합니다.

MCP Mid-request Switch

요청 중 writer가 active Generation을 바꿔도 현재 요청이 기존 read snapshot으로 Evidence를 정상 복원하는지 검증합니다.
