1. DB 용어를 이 문서에서 어떻게 읽을까?

row테이블의 가로 한 줄. 예: sync_issue_change row 하나 = 처리해야 할 semantic Work Item 한 건.
PK · Primary Key그 row를 유일하게 식별하는 대표 ID. 같은 PK row는 둘 존재할 수 없습니다.
FK · Foreign Key같은 SQLite DB 안의 다른 table row를 DB가 직접 검증하며 가리키는 연결입니다.
Logical Reference다른 DB의 ID를 문자열로 보관하는 연결. SQLite FK가 아니므로 애플리케이션 검증이 필요합니다.

1
source_sync_run

2
project_state + source_project_run

프로젝트의 장기 Watermark와 이번 Run의 cursor/count를 분리해 기록합니다.

3
sync_issue_change

NEW/CHANGED semantic 상태를 Work Item row로 durable하게 기록합니다.

4
Source Ready + Latest Gate

Project Source Commit 완료 + 최신 Work인지 확인한 row만 claim할 수 있습니다.

5
processing_run → Knowledge DB

Loop B가 Work를 지식화·검증·Embedding·Publish하고 상태를 다시 Work row에 기록합니다.

4. Source Ready Gate는 v3에서 “Latest Gate”까지 합쳐서 본다

row가 존재한다는 것과 Loop B가 가져가도 된다는 것은 다릅니다. v3는 Source Commit뿐 아니라 “더 최신 Work가 이미 생겼는가?”까지 검사합니다.

Loop B claimable = last_source_committed_run_id IS NOT NULL AND last_source_committed_run_id = last_observed_source_run_id AND work_status IN ('pending','failed') AND superseded_by_work_item_id IS NULL
Gate가 없으면

ABC-123 V2 row가 먼저 생긴 뒤 Project Source Commit이 실패해도 Loop B가 V2를 처리할 수 있습니다. 더 나쁜 경우 V3가 이미 발견됐는데 V2가 늦게 publish되어 최신 Knowledge를 덮을 수 있습니다.

→
Gate + Latest-Only가 있으면

Project Source Commit 전에는 CLOSED. V3가 Commit되면 V2 pending/failed/running은 superseded로 표시되고 V3만 claim 가능합니다. Running V2 응답이 늦게 와도 publish 직전 latestness를 다시 확인해 stale publish를 막습니다.

T3 Project Source Commit · SAME State DB transaction 1) source_project_run.source_status = source_committed 2) project_state.committed_watermark = upper 3) 새 Work Item Ready Gate OPEN 4) 같은 jira_id의 이전 pending/failed/running Work → work_status = superseded → superseded_by_work_item_id = new work_item_id 5) COMMIT

8. 현재 문서들을 합쳐 보니 드러나는 Integration Seam

source_sync_run과 Knowledge DB의 pipeline_run 관계는 별도 명시가 필요합니다.

현재 State DDL v3는 운영 Source Run을 source_sync_run.source_run_id (sr_...)로 정의합니다. 반면 이미 구현된 Knowledge DB v1은 기존 M0~M7 observation scope를 pipeline_run.run_id로 저장하고 issue_version.source_run_id 등이 이를 FK로 참조합니다. 현재 검토한 문서/코드에는 두 Run identity 사이의 별도 mapping table 또는 “둘은 항상 동일 ID다”라는 계약이 명시돼 있지 않습니다.

이 문서에서는 억지로 같은 것으로 그리지 않았습니다.

확실히 연결된 것은 Work Item의 jira_id + source_hash, 그리고 Loop B가 채우는 issue_version_id / knowledge_generation_id logical reference입니다. 실제 v3 구현 전에 Run identity를 어떻게 연결할지는 별도 설계 결정으로 Freeze하는 편이 안전합니다.

10. Knowledge Item에서 Jira 원문까지 되돌아가는 길

RAG에서 중요한 것은 “좋은 문장을 저장했다”가 아니라 그 문장이 어떤 Jira 원문에서 나왔는지 다시 증명할 수 있는가입니다.

Knowledge Item (ki_) ↓ 1:N Knowledge Evidence (ke_) ↓ evidence_type + evidence_ref ├─ summary / description → issue_version ├─ comment:5001 → comment(run_id, issue_key, comment_id) ├─ attachment:7001 → attachment(run_id, attachment_id) ├─ relationship:9001 → relationship(run_id, relationship_id) └─ custom_field:... → custom_field_value(run_id, issue_key, field_id) ↓ ANALYSIS / RAW source_path ↓ MCP Evidence Package
M7/M10에서 이 round-trip은 실제 데이터로 검증되었습니다.
M7은 502 canonical Evidence row의 integrity를 만들었고, M10은 resolver를 통해 실제 source를 복원해 MCP evidence package로 제공했습니다.

11. 자주 헷갈리는 질문

Q. Work Item이라는 table이 따로 있나요?

이름이 work_item인 table은 없습니다. sync_issue_change table의 row 하나가 Work Item 하나입니다.

Q. Jira Issue 하나 = Work Item 하나인가요?

아닙니다. Work Item은 jira_id + source_hash + source_hash_profile의 특정 semantic 상태를 나타냅니다. 같은 Issue가 A→B로 바뀌면 A/B Work가 존재할 수 있고, v3 Latest-Only 정책은 아직 처리되지 않은 구버전을 supersede합니다.

Q. State DB의 issue_version_id는 FK인가요?

State DB 안에서는 아닙니다. Knowledge DB의 issue_version을 가리키는 logical reference입니다.

Q. FAISS도 SQLite table인가요?

아닙니다. FAISS는 vector index artifact입니다. Knowledge identity는 ki_이고 FAISS physical position은 identity가 아니므로 mapping을 통해 Knowledge Item으로 돌아옵니다.

Q. 왜 source_sync_run과 source_project_run을 둘 다 두나요?

source_sync_run은 전체 실행, source_project_run은 그 실행 속 Project별 세부 작업입니다. 프로젝트 하나의 실패/재개 상태를 다른 Project와 분리하기 위해 필요합니다.

Q. project_state와 source_project_run의 차이는?

project_state는 Run을 넘어 유지되는 장기 Watermark/visibility 기억이고, source_project_run은 이번 Run의 cursor/count/status입니다.
