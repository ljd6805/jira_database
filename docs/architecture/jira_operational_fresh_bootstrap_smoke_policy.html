OPERATIONAL BOOTSTRAP POLICY · 2026-08-31

Smoke는 완전히 격리하고,
정식 운영 검증은 Fresh Start로 시작합니다.

파일럿 DB는 운영으로 반드시 승계해야 하는 자산이 아니라 검증 산출물로 봅니다. 공식 Real Test 경로는 legacy DB Migration이 아니라 깨끗한 새 Operational State / Knowledge DB를 만드는 Fresh Bootstrap입니다.

1. 최종 결정

SMOKE config/settings.smoke.yaml → storage.data_root = ./data_smoke → 새 State DB / RAW / ANALYSIS / Knowledge Input → production/pilot data와 완전 분리 → Migration 사용하지 않음 → --project-key로 Project 1개만 선택 가능 FORMAL REAL TEST 기존 파일럿 DB는 삭제 또는 별도 보관 → 깨끗한 ./data에서 새 DB 생성 → State Schema 개정 3을 처음부터 생성 → Full Initial Ingest → 이후 정상 Delta Sync → Migration 사용하지 않음 LEGACY COMPATIBILITY ONLY 기존 collector.db를 꼭 이어써야 하는 특별한 경우 → explicit Migration → backup / fingerprint / integrity Gate

2. 왜 Fresh Start가 더 좋은가?

상태 해석이 단순

파일럿 run/resume 흔적과 운영 Watermark가 섞이지 않습니다.

Migration 위험 제거

legacy fingerprint와 old resume compatibility를 정식 검증 경로에서 제거합니다.

재현성 향상

빈 환경에서 Initial Ingest부터 스스로 상태를 만드는지 검증합니다.

3. 삭제해도 되는 것과 보존해야 하는 것

종류권장이유
collector.db, Knowledge DB, FAISS, embedding stagingFresh Start 시 제거 가능재생성 가능한 운영 산출물
data_smoke/Gate 종료 후 통째로 제거 가능운영 상태와 독립된 임시 검증 환경
M0~M11 HTML 완료 문서 / Real-run 기록보존검증 이력
필요한 RAW / ANALYSIS 샘플선택 보존회귀 분석 가치

4. Smoke 전용 Data Root

# config/settings.smoke.yaml
storage:
  data_root: "./data_smoke"

data_smoke/는 Git에서 제외됩니다.

5. --project-key 안전 규칙

--project-key → Smoke 전용 → data_root의 마지막 디렉터리가 data_smoke일 때만 허용 → 지정 Project 하나만 snapshot / State / Watermark / Work 대상 → 다른 Project는 Source Sync하지 않음 → --resume-source-run-id와 함께 사용 금지 → 실패하면 data_smoke 삭제 후 새 Smoke Run
왜 이렇게 제한하나?

--max-issues-per-project 1은 일부 candidate만 처리하고 Project Watermark를 전진시키므로 production partial ingest에 사용하면 안 됩니다. 격리된 Smoke DB에서는 Watermark가 disposable이므로 안전합니다.

6. 현재 권장 Smoke 명령

python tools/run_source_sync.py \
  --local-config config/settings.smoke.yaml \
  --project-key YOUR_PROJECT_KEY \
  --max-issues-per-project 1

Project 1개, Issue 최대 1개로 Source Ready Work를 만든 뒤 그 Work를 Real OpenCode Smoke에 사용합니다.

7. 상세 실행 절차

Project 1개 → Source Ready → Real OpenCode 단계별 실행 가이드를 그대로 따라갑니다.

8. 정식 Real Test

1. 파일럿 운영 산출물 정리 2. 깨끗한 ./data 준비 3. Migration 실행하지 않음 4. Loop A Full Initial Ingest - --project-key 사용하지 않음 - --max-issues-per-project 사용하지 않음 5. Project별 Source Commit / Watermark 생성 6. Loop B latest-only Knowledge Automation 7. Knowledge DB / Embedding / Atomic Publish 8. 이후부터 Delta Sync 운영

9. Migration의 위치

Fresh Start

Migration 불필요. 빈 DB가 현재 Schema로 초기화됩니다.

Legacy 재사용

Migration 필수. 기존 collector.db를 계속 써야 할 때만 사용합니다.
