OPERATIONAL BOOTSTRAP POLICY · 2026-08-31

Smoke는 완전히 격리하고,
정식 운영 검증은 Fresh Start로 시작합니다.

파일럿 DB는 운영으로 반드시 승계해야 하는 자산이 아니라 이미 목적을 다한 검증 산출물로 봅니다. 따라서 공식 Real Test 경로는 legacy DB Migration이 아니라 깨끗한 새 Operational State / Knowledge DB를 만드는 Fresh Bootstrap입니다.

1. 최종 결정

SMOKE config/settings.smoke.yaml → storage.data_root = ./data_smoke → 새 State DB → 새 RAW / ANALYSIS / Knowledge Input → 새 Knowledge DB / Embedding staging → production/pilot data와 완전 분리 → Migration 사용하지 않음 FORMAL REAL TEST 기존 파일럿 DB는 삭제 또는 별도 보관 → 깨끗한 ./data에서 새 DB 생성 → State Schema 개정 3을 처음부터 생성 → Full Initial Ingest → 이후 정상 Delta Sync → Migration 사용하지 않음 LEGACY COMPATIBILITY ONLY 기존 collector.db를 꼭 이어써야 하는 특별한 경우 → explicit Migration → backup / fingerprint / integrity Gate

2. 왜 Fresh Start가 더 좋은가?

상태 해석이 단순

파일럿 run/resume 흔적과 운영 Watermark가 섞이지 않습니다. 첫 project_state부터 모두 현재 계약으로 생성됩니다.

Migration 위험 제거

legacy fingerprint, backfill, old resume compatibility 같은 전환 복잡도를 정식 검증 경로에서 제거합니다.

재현성 향상

새 시스템이 완전히 비어 있는 환경에서 Initial Ingest부터 Publish까지 스스로 만들 수 있는지 검증할 수 있습니다.

3. 삭제해도 되는 것과 보존해야 하는 것

종류권장이유
collector.db, Knowledge DB, FAISS index, embedding stagingFresh Start 시 제거 가능재생성 가능한 운영 산출물
Smoke의 data_smoke/Gate 종료 후 통째로 제거 가능운영 상태와 완전히 독립된 임시 검증 환경
M0~M11 HTML 완료 문서 / Real-run 기록보존파일럿에서 무엇을 검증했는지 증명하는 프로젝트 이력
필요한 RAW / ANALYSIS 샘플선택 보존문제 재현·회귀 분석에 가치가 있을 수 있음
주의

“DB를 지운다”와 “프로젝트 검증 이력을 지운다”는 같은 뜻이 아닙니다. DB는 새로 만들더라도 파일럿 완료 문서와 결정 기록은 계속 남깁니다.

4. Smoke 전용 Data Root

현재 설정 로더는 local YAML을 base 설정 위에 merge하므로 Smoke에서는 storage root만 바꾸면 됩니다.

# config/settings.smoke.yaml
storage:
  data_root: "./data_smoke"
data_smoke/ ├─ state/ │ └─ collector.db ├─ raw/ ├─ analysis/ ├─ knowledge_input/ ├─ knowledge/ ├─ knowledge_db/ ├─ embedding/ └─ retrieval/ Git → data_smoke/ 전체 ignore

5. Smoke 실행의 목적

목표 실제 Jira 1차 연결 → Loop A가 실제 Source를 읽음 → RAW / ANALYSIS / Knowledge Input 생성 → semantic_v2 분류 → Source Commit → Source Ready Work 생성 → 그 Work 중 1건을 Real OpenCode Smoke에 사용

Smoke DB의 Watermark는 production의 Watermark가 아닙니다. Smoke 결과는 운영 continuity의 기준으로 사용하지 않습니다.

6. 현재 CLI의 한계

--max-issues-per-project 1은 접근 가능한 모든 Project에서 최대 1건씩 처리합니다. 따라서 Project가 많으면 Smoke Work도 여러 개 생길 수 있습니다.

현재 안전한 사용 python tools/run_source_sync.py \ --local-config config/settings.smoke.yaml \ --max-issues-per-project 1 → data_smoke/에서만 실행 → 여러 Source-ready Work가 생겨도 운영 DB에는 영향 없음 → 그중 1건만 OpenCode Smoke에 사용

향후 필요하면 --project-key 전용 Smoke filter를 추가합니다. 현재 정책에서는 필수 조건은 아닙니다.

7. 정식 Real Test 절차

1. 파일럿 운영 산출물 정리 - 기존 collector.db / Knowledge DB / FAISS 등을 삭제 또는 별도 보관 2. 깨끗한 ./data 준비 3. Migration 실행하지 않음 4. Loop A Full Initial Ingest - --max-issues-per-project 사용하지 않음 - 모든 접근 가능한 Project의 baseline 수집 5. Project별 Source Commit / Watermark 생성 6. Loop B latest-only Knowledge Automation 7. Knowledge DB / Embedding / Atomic Publish 8. 이후부터 Delta Sync 운영

8. Migration의 새 위치

공식 Fresh Start

Migration 불필요. 빈 DB가 현재 Schema로 바로 초기화됩니다.

Legacy 재사용

Migration 필수. 기존 collector.db를 계속 써야 할 때만 explicit migration을 사용합니다.

따라서 “Migration REQUIRED”라는 과거 문장은 앞으로 “legacy DB를 재사용하는 경우 Migration REQUIRED”라고 읽습니다.
