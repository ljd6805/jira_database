LEARNING DOCUMENT · 2026-08-27

Sync Contract를
아주 쉽게 이해해 봅시다

지금 필요한 것은 코드를 쓰는 것이 아니라, Jira가 계속 바뀔 때 우리 시스템이 무엇을 기억하고, 무엇을 다시 읽고, 어디까지 처리할지 이해하는 것입니다.

이 문서는 학습용입니다. Watermark, Overlap 같은 개념을 이해하기 위한 자료이며, 구체적인 숫자와 정책은 아직 확정하지 않습니다.
먼저 이것만

0. 전체 그림 — Sync는 “지난번 이후 바뀐 것만 다시 가져오는 일”

매번 Jira 전체를 처음부터 다시 읽는 대신, 지난번 이후 바뀐 것만 찾아서 Knowledge DB와 검색 인덱스를 최신으로 만드는 것이 Continuous Sync입니다.

📚
도서관 비유

도서관에 책이 10만 권 있는데 어제 책 7권만 바뀌었다면, 오늘 10만 권을 다시 검사할 필요는 없습니다. “어디까지 확인했는지” 기억하고, 그 이후 바뀐 책만 보면 됩니다.

지난 Sync 때까지 확인한 지점 ↓ Jira에서 그 이후 변경 후보를 찾음 ↓ 실제로 내용이 바뀌었는지 확인 ↓ 바뀐 것만 Knowledge / Embedding / FAISS 갱신 ↓ 다음 Sync가 시작할 지점을 저장
한 문장Sync Contract는 “다음 번에 어디서부터 다시 확인하고, 무엇을 변경으로 인정하고, 실패하면 어디서 다시 시작할지” 정하는 약속입니다.
1

Sync Run — 동기화 한 번을 하나의 작업으로 묶기

예를 들어 오전 9시에 Jira 업데이트 확인을 시작해서 9시 12분에 끝났다면, 그 한 번의 실행 전체를 하나의 Sync Run이라고 부릅니다.

09:00Sync Run 시작
→
Project 확인A, B, C 발견
→
변경 Issue 확인총 6건 후보
→
Knowledge 갱신실제 변경 3건
→
09:12Sync Run 종료
현재 프로젝트에도 비슷한 구조가 이미 있습니다.state_store.py에는 collection_runs, project_runs, issue_checkpoints가 있어 한 번의 수집 실행 내부 상태를 이미 기록합니다. 앞으로는 이 개념을 “실행과 실행 사이”까지 확장하는 것이 핵심입니다.
2

Project Discovery — 지금 내가 볼 수 있는 프로젝트 목록 확인

Sync가 시작되면 먼저 “현재 서비스 계정이 Jira에서 어떤 프로젝트를 볼 수 있는가?”를 확인합니다.

기존 Project

지난번에도 있었고 이번에도 보입니다. → 변경 Issue만 확인합니다.

새 Project

지난번에는 없었는데 이번에 처음 보입니다. → 초기 수집 대상입니다.

사라진 Project

지난번에는 있었는데 이번 목록에는 없습니다. → 삭제인지 권한 상실인지 판단 정책이 필요합니다.

지난번 Registry: A B 이번 Discovery: A B C 결과 A = 기존 B = 기존 C = 새 프로젝트
현재 코드도 Project Discovery 자체는 이미 합니다.project_discovery.py가 접근 가능한 프로젝트 목록을 읽습니다. 아직 없는 것은 “지난번 목록과 비교해서 새 프로젝트인지 판단하는 영구 Registry”입니다.
3

Watermark — “지난번에 여기까지 봤다”는 책갈피

Watermark가 이번 Sync Contract에서 가장 중요한 개념입니다. 어렵게 들리지만 사실상 책갈피입니다.

🔖
책갈피 비유

500페이지짜리 책을 120페이지까지 읽고 책갈피를 꽂았습니다. 다음 날 책을 펼칠 때 1페이지부터 다시 읽지 않고 120페이지 근처에서 시작합니다. Watermark가 바로 그 책갈피입니다.

Jira에서는 어떻게 쓰나?

지난번 성공 Sync가 확인한 마지막 시점 = 10:00 ↑ Watermark 다음 Sync → 10:00 근처 이후에 수정된 Issue를 찾아본다
Watermark 없음처음 실행입니다. 어디서 시작할지 모르므로 초기 수집이 필요합니다.
Watermark = 10:00지난번에 10:00 부근까지 안전하게 확인했다는 뜻입니다.
새 Watermark이번 Sync가 안전하게 처리된 뒤 다음 시작점을 저장합니다.
중요Watermark는 “마지막으로 본 Jira Issue의 번호”가 아니라, 보통 “여기까지의 변경을 안전하게 처리했다”는 시간/경계 정보를 의미합니다.
4

Overlap — 책갈피보다 조금 앞에서 다시 읽기

Watermark가 10:00이라도 다음 Sync를 정확히 10:00부터 딱 잘라 시작하지 않고, 조금 이전 시간부터 다시 확인하는 방법이 Overlap입니다.

🎞️
동영상 비유

영상을 보다가 10분 지점에서 끊겼습니다. 다음에 10:00.000에서 정확히 재생하는 대신 9:55부터 다시 보면 앞뒤 맥락을 놓칠 가능성이 줄어듭니다. 5초를 중복해서 보는 것은 조금 귀찮지만, 장면 하나를 놓치는 것보다 훨씬 안전합니다.

왜 굳이 중복해서 읽을까?

Overlap 없음

경계 시점에 있는 Issue가 시간 표현, 처리 지연, 실행 중단 같은 이유로 빠지면 영원히 놓칠 수 있습니다.

VS
Overlap 있음

일부 Issue를 다시 읽을 수 있지만, 같은 데이터인지 확인해서 버리면 됩니다. 중복은 처리할 수 있지만 누락은 복구가 어렵습니다.

예시 · 아직 확정값 아님 지난 Watermark = 10:00 Overlap = 5분 다음 검색 시작 = 09:55 ↑ 5분을 일부러 다시 확인
핵심 철학중복은 허용하고, 누락을 막습니다. 중복으로 다시 가져온 데이터는 뒤에서 source_hash로 “내용이 같은가?”를 확인하면 됩니다.
아직 확정하지 않은 것Overlap을 정확히 몇 분으로 할지는 나중에 실제 Jira 동작과 운영 주기를 보고 결정합니다. “5분”은 현재 추천 예시일 뿐입니다.
5

Delta — 전체가 아니라 “달라진 부분”

Delta는 수학 냄새가 나지만 여기서는 그냥 변경분이라는 뜻입니다.

🧾
가계부 비유

어제 잔액과 오늘 잔액을 비교할 때 통장 개설일부터 모든 거래를 다시 계산하지 않고, 어제 이후 거래만 봅니다. 그 “새 거래 부분”이 Delta입니다.

Full Sync 100,000개 Issue 전부 확인 Delta Sync 지난 Sync 이후 변경 후보 23개만 확인
운영 기본 방향현재 프로젝트 문서도 운영 단계의 기본을 delta-first로 잡고 있습니다. Full rebuild는 장애 복구, 검증, 마이그레이션처럼 특별한 때 남겨두는 방향입니다.
6

“Jira에서 수정됨”과 “우리 지식이 바뀜”은 같은 말이 아닙니다

Jira의 updated 값은 “이 Issue를 다시 확인해 보세요”라는 초인종으로 보는 것이 쉽습니다. 최종 판정은 아닙니다.

Jira updated 변경 ↓ "이 Issue 다시 확인해!" ↓ Issue + Comment + 관계 + Custom Field 수집 ↓ 실제 업무 내용 비교 ↓ 정말 바뀌었나?

후보는 맞지만 실제 내용 동일

Jira 내부 메타데이터가 바뀌었거나, 우리 Knowledge에 영향을 주지 않는 변화일 수 있습니다. → 기존 Knowledge 재사용 가능.

실제 내용 변경

Description, 댓글, 상태, 관계 등 우리가 중요하게 보는 정보가 바뀌었습니다. → 새 Version과 Knowledge 처리 필요.

쉽게 말하면updated는 “문을 열어볼 집 주소를 찾는 용도”, source_hash는 “집 안이 실제로 달라졌는지 확인하는 용도”입니다.
7

source_hash — Issue 내용의 지문

Hash는 긴 데이터를 짧은 고정 길이 값으로 바꿔 비교하는 방법입니다. 여기서는 한 Issue의 의미 있는 내용을 모아 지문처럼 사용합니다.

🫆
지문 비유

두 사람의 이름을 일일이 비교하지 않고 지문이 같은지 보는 것처럼, 긴 Jira 내용 전체를 매번 필드 하나씩 비교하지 않고 안정적인 hash 값을 비교합니다.

Issue 내용 A → source_hash = abc123 다음 Sync에서 다시 수집 → source_hash = abc123 → 내용 동일 → unchanged 다음 Sync → source_hash = xyz999 → 내용 변경 → changed

현재 프로젝트의 source_hash는 무엇을 보나?

영역현재 Knowledge Input에 포함의미
Issuesummary, description, status, priority 등이슈 본문 변화 감지
Comments댓글 본문과 식별 정보추가/수정 논의 감지
Attachments현재는 메타데이터첨부 메타 변화 감지
Relationships연결 Issue 관계관계 변화 감지
Custom Fields정규화된 값업무 필드 변화 감지
검토 포인트 · 아직 결정 아님현재 코드에서는 Issue/Comment의 updated_at도 package에 들어가므로 hash에 영향을 줄 수 있습니다. 운영 단계에서는 “시간만 달라졌지만 실제 지식 내용은 같은 경우”까지 새 Version으로 만들지 검토할 필요가 있습니다. 이 부분은 Sync Contract 확정 때 따로 결정합니다.
8

new / changed / unchanged — 결국 세 가지로 나누기

한 Issue를 다시 읽은 뒤에는 어렵게 생각할 필요 없이 세 통에 나누면 됩니다.

NEW

처음 보는 Issue

우리 DB에 Jira identity가 없습니다.

처리: 새 Version → Knowledge → Embedding → FAISS.

CHANGED

기존 Issue, 내용 변경

기존 identity는 있지만 source_hash가 달라졌습니다.

처리: 새 Version부터 downstream 갱신.

UNCHANGED

다시 읽었지만 동일

source_hash가 같습니다.

처리: 기존 Version/Knowledge/Embedding 재사용.

이 구조가 중요한 이유Overlap 때문에 같은 Issue를 다시 가져오더라도 대부분 unchanged로 판정해 값비싼 Knowledge 생성과 Embedding을 다시 하지 않을 수 있습니다.
9

왜 Watermark를 Project마다 따로 두나?

Project A는 성공했고 Project B는 실패했다면, 둘의 “책갈피”가 같으면 안 됩니다.

Project A ✅ 성공 → watermark = 11:00 Project B ❌ 실패 → watermark = 10:00 그대로 Project C ✅ 성공 → watermark = 11:00
📖
여러 권의 책 비유

A책은 200페이지까지 읽고, B책은 80페이지에서 잠들었습니다. 다음 날 세 책 모두 200페이지부터 읽으면 B책의 81~199페이지를 통째로 놓칩니다. 그래서 책마다 책갈피가 따로 있어야 합니다.

추천 방향운영 Sync에서는 Project별 Watermark를 두는 설계가 안전합니다. 현재 Collector가 이미 Project 단위로 실패를 격리하는 철학과도 잘 맞습니다.
10

Checkpoint / Resume — 중간에 죽어도 처음부터 다시 하지 않기

Checkpoint는 “여기까지는 끝냈다”는 저장점이고, Resume은 거기서 다시 시작하는 것입니다.

🎮
게임 저장 비유

보스 직전까지 갔는데 게임이 꺼졌습니다. 저장 기능이 없으면 처음 마을부터 다시 시작해야 합니다. Checkpoint가 있으면 마지막 세이브 포인트에서 이어서 할 수 있습니다.

Project B Delta 20개 1~8 ✅ 완료 9 처리 중 💥 서버 종료 재시작 1~8 → 다시 하지 않음 9~20 → 이어서 처리
현재 프로젝트에는 이미 기반이 있습니다.issue_checkpoints와 issue_is_complete()가 같은 Collection Run 안에서 완료된 Issue를 건너뛸 수 있게 합니다. 운영 단계에서는 이를 cross-run 동기화 상태와 연결해야 합니다.
11

“Jira에서 잘 가져옴”과 “검색 서비스에 반영됨”도 다릅니다

Issue를 안전하게 RAW로 가져오는 데 성공했더라도, 그 뒤 Knowledge 생성이나 Embedding이 실패할 수 있습니다. 그래서 두 단계를 구분하면 장애 복구가 쉬워집니다.

Jira ↓ RAW + 변화 판정 ↓ [SOURCE COMMITTED] ↓ Knowledge ↓ Embedding ↓ FAISS Active 전환 ↓ [PUBLISHED]

SOURCE COMMITTED

Jira 변경분을 안전하게 가져오고 무엇이 바뀌었는지 기록했습니다.

이후 Knowledge가 실패해도 Jira를 다시 읽을 필요 없이 여기서 이어갈 수 있습니다.

PUBLISHED

새 Knowledge와 Vector가 실제 Active Retrieval에 반영됐습니다.

이때 비로소 사용자 검색 결과가 최신 상태라고 볼 수 있습니다.

이 용어도 아직 최종 계약명은 아닙니다.핵심은 이름보다 “수집 완료”와 “서비스 반영 완료”를 서로 다른 상태로 구분해야 한다는 점입니다.
12

Project가 갑자기 안 보이면 어떻게 할까?

지난번에는 보였던 Project가 이번 Discovery에 없다고 해서 바로 “삭제됐다”고 단정하면 위험합니다.

정말 삭제

Jira에서 Project 자체가 없어졌을 수 있습니다.

권한 상실

Project는 있지만 서비스 계정이 더 이상 볼 수 없을 수 있습니다.

일시 오류

Jira/API 장애 때문에 Discovery 결과가 불완전할 수도 있습니다.

그래서 즉시 데이터 삭제는 위험합니다.History/RAW는 보존하면서 Active Retrieval에서 어떻게 처리할지 별도의 보안 정책이 필요합니다.
아직 확정하지 않은 정책정상 Discovery에서 Project가 사라지면 즉시 Active에서 숨길지, 몇 회 연속 확인 후 숨길지 등은 사용자와 따로 결정해야 합니다.
13

새 Project가 발견되면 처음에는 어디까지 가져올까?

Watermark가 없는 새 Project는 “지난번 이후 변경분”이라는 기준 자체가 없습니다. 그래서 첫 수집 방식을 정해야 합니다.

MVP 방식

프로젝트당 최근 30개 Issue.

기능 검증에는 충분했습니다.

→
운영 후보

새 Project의 전체 접근 가능 Issue를 Initial Ingest.

그 후 Watermark를 만들고 Delta Sync로 전환.

새 Project C 발견 ↓ Initial Ingest ↓ 현재 상태를 한 번 기준점으로 만듦 ↓ Watermark 생성 ↓ 다음부터 Delta Sync
이것도 아직 사용자 결정 전“새 Project는 전체 초기 수집”을 현재 추천하지만, 데이터 규모나 운영 시간에 따라 범위를 조절할 수 있습니다.
14

Sync Run이 성공인지 실패인지 어떻게 말할까?

Project가 여러 개이므로 전체 Run은 단순 성공/실패 두 상태만으로는 부족할 수 있습니다.

상태쉽게 말하면예
completed대상 Project가 모두 최신 상태로 PublishedA/B/C 모두 성공
partial일부는 성공, 일부는 실패A/C 성공, B 실패
failedSync 자체가 유효하게 진행되지 못함초기 Discovery부터 실패
포인트Project B가 실패했다고 A/C까지 롤백할 필요는 없습니다. A/C는 자기 Watermark를 전진시키고, B만 다음에 다시 하면 됩니다.
15

처음부터 끝까지 하나의 예로 연결해 보기

이제 앞의 개념을 한 번에 연결해 봅시다.

[어제] Project A watermark = 10:00 Project B watermark = 10:00 [오늘 11:00 Sync 시작] 1) Project Discovery A, B, C 발견 → C는 새 Project 2) A Delta 검색 watermark 10:00 근처부터 다시 확인 → 후보 4개 3) A 후보 4개 실제 수집 Issue 1 → source_hash 동일 → unchanged Issue 2 → hash 변경 → changed Issue 3 → hash 동일 → unchanged Issue 4 → 처음 보는 ID → new 4) A 처리 changed + new 2개만 Knowledge → Embedding → FAISS 5) A 성공 → A watermark 전진 6) B 처리 중 실패 → B watermark 그대로 → 다음 Sync에서 B는 이전 지점부터 다시 7) C는 watermark가 없음 → Initial Ingest 수행 → 성공 후 첫 watermark 생성 8) Run 결과 A 성공 / B 실패 / C 성공 → 전체 Sync Run = partial
여기까지 이해되면 Sync Contract의 뼈대는 거의 이해한 것입니다.나머지는 “Overlap 몇 분?”, “새 Project 전체 수집?”, “Project 권한 상실 시 Active를 언제 숨김?” 같은 정책값을 하나씩 결정하는 문제입니다.
