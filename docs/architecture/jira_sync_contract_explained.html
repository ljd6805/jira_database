DETAILED LEARNING GUIDE · 2026-08-28

Continuous Sync는 이제
두 개의 독립 Loop입니다.

이 문서는 D1~D9를 설계 의도까지 포함해 설명합니다. 핵심은 Jira Source 최신화와 느리고 변동성이 큰 OpenCode 지식화를 같은 실행 수명주기에 묶지 않는 것입니다.

1. 문제를 먼저 보면 구조가 이해됩니다

Jira 수집은 API/파일 중심으로 비교적 예측 가능하지만, OpenCode Knowledge Generation은 사내 공용 자원 상태에 따라 처리시간 편차가 큽니다. 하나의 직렬 Loop에서는 느린 OpenCode가 다음 Jira Source Sync까지 늦출 수 있습니다.

1-Loop

Jira → 정제 → OpenCode → Embedding → Publish → 다음 Jira Sync

가장 느린 단계가 전체 cadence를 결정합니다.

2-Loop

Loop A: Jira → Source Commit → backlog Loop B: backlog → OpenCode → Publish

각 Loop가 독립적으로 계속 움직입니다.

2. Loop A · Source Sync의 책임

source_sync_run → fixed upper 저장 → Project Discovery → project_state 비교 → Project별 Initial / Delta / Catch-up → Jira Download → RAW → ANALYSIS → Knowledge Input → semantic_v2 source_hash → NEW / CHANGED / UNCHANGED → NEW/CHANGED sync_issue_change UPSERT → SOURCE_COMMITTED → Project committed_watermark = upper

Loop A의 목표는 최신 Jira 사실을 누락 없이 안전하게 확보하고, Loop B가 처리할 durable Work Item을 남기는 것입니다.

3. Loop B · Knowledge Processing / Publish의 책임

processing_run → pending / failed Work Item 선택 → OpenCode Knowledge Generation → Review / Evidence → Knowledge DB lineage 저장 → BGE-M3 Embedding → FAISS staging / mapping → 검증 → Atomic Publish → publish_status = published

Loop B는 Jira를 다시 다운로드하는 Loop가 아닙니다. Loop A가 남긴 Source 산출물과 Work Item을 소비합니다.

4. durable backlog가 왜 중요한가?

두 Loop가 독립이면 둘 사이에 “기억 장치”가 있어야 합니다. 이 프로젝트에서는 초기 운영 단계에서 별도 메시지 브로커 대신 State DB의 sync_issue_change를 durable backlog로 사용합니다.

Loop A producer NEW / CHANGED → deterministic work_item_id → sync_issue_change Loop B consumer → 상태 조회 → 처리 → checkpoint / retry → published
초기 단순성: Kafka/RabbitMQ를 먼저 넣지 않습니다. 실제 처리량과 병렬 Worker 요구가 확인된 뒤 필요하면 확장합니다.

5. D1 / D2 · Watermark와 Overlap

lower = committed_watermark - 5m upper = source_sync_run 시작 시 fixed updated >= lower updated < upper ORDER BY updated ASC, id ASC

Watermark는 Loop A 전용 progress boundary입니다. Loop B가 아직 backlog를 처리하지 않았더라도 Source window가 안전하게 Commit됐으면 Watermark를 전진할 수 있습니다.

6. D3 / D4 · 실제 변화만 Work Item으로

판정기준Loop B 작업
NEWjira_id 미존재Work Item 생성
CHANGED같은 jira_id + 다른 semantic_v2 hashWork Item 생성
UNCHANGED같은 jira_id + 같은 hash새 Work Item 없음

Jira updated는 “다시 확인할 후보”를 찾는 데 쓰이고, 실제 semantic change는 hash가 결정합니다.

7. D5 · Resume도 Loop별로 나뉩니다

Source Resume

같은 source_run의 fixed lower/upper와 stable cursor를 사용합니다. 불가능하면 retained Watermark + 5분 overlap으로 새 Source Run을 시작합니다.

Processing Resume

Work Item의 Knowledge / Embedding / Publish 상태를 보고 실패 Stage부터 이어갑니다. completed 산출물은 검증 후 재사용합니다.

8. D6 · Jira에서 안 보여도 Knowledge는 남습니다

Discovery 전체 성공 → 기존 Project가 안 보임 → project_state.visibility = unavailable → Loop A skip → Watermark 유지 → Loop B의 기존 backlog/Knowledge 처리 가능 → 기존 Published Retrieval 유지

Source Lifecycle과 Knowledge Lifecycle은 분리됩니다.

9. D7 · Source Commit과 Publish는 실제 다른 Loop입니다

Loop A V2 SOURCE_COMMITTED Loop B V2 pending 서비스 Published Head = V1 계속 사용 Loop B 완료 V2 actual atomic publish → Published Head = V2

따라서 Source Head != Published Head는 정상적으로 존재할 수 있는 eventual consistency 상태입니다.

10. D8 / D9 · Run 상태의 의미 변화

2-Loop 이전에는 한 Run에 Source와 Publish 상태를 함께 넣었지만 이제는 그렇지 않습니다.

Run주요 상태
source_sync_runDiscovery / Source / run status
processing_runselected / published / failed count + run status

시스템 전체 건강도는 하나의 run_status가 아니라 Source Lag, Publish Lag, Backlog, Throughput을 같이 봅니다.

11. 낮과 밤의 처리 편차를 어떻게 활용하나?

낮 Source Loop: 정상 cadence 유지 Processing Loop: 느림 → backlog 증가 가능 밤 Processing 처리량 향상 → backlog catch-up

2-Loop는 시간대별 성능 차이를 “문제 제거”가 아니라 “운영 제어 가능한 backlog”로 바꿉니다.

12. 반드시 보는 운영 지표

Source Lag

Jira Source 최신화 지연.

Publish Lag

검색 최신화 지연.

Backlog Depth

미처리 Work 수.

Oldest Pending

가장 오래 기다리는 Work의 age.

Processing Throughput

시간당 Publish 수.

Latency / Error

시간대·Stage별 처리시간과 실패율.

13. 아직 남은 정책

Intermediate Version supersede

V2, V3, V4가 Source Loop에서 빠르게 쌓였는데 Loop B가 아직 V2를 시작하지 않았다면 모든 Version을 지식화할지 최신 pending만 처리할지 별도 결정이 필요합니다. Source Version은 모두 보존합니다.

Multi-worker claim / lease

초기 Single Worker 이후 병렬 처리로 확장할 때 설계합니다.
