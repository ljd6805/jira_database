DETAILED LEARNING GUIDE · 2026-08-28

Continuous Sync는
두 개의 독립 Loop입니다.

D1~D9와 Source Ready Gate의 설계 의도를 자세히 설명합니다. 핵심은 Jira Source 최신화와 느리고 변동성이 큰 OpenCode 처리를 같은 실행 수명주기에 묶지 않는 것입니다.

1. 왜 1-Loop가 문제였나?

1-Loop

Jira → 정제 → OpenCode → Embedding → Publish → 다음 Jira Sync

가장 느린 단계가 전체 cadence를 결정합니다. OpenCode가 낮시간에 느리면 Jira Source freshness까지 함께 밀립니다.

2-Loop

Loop A: Jira → Source Commit → durable backlog Loop B: source-ready backlog → OpenCode → Publish

Source freshness와 Knowledge freshness를 서로 독립적으로 관리합니다.

2. Loop A · Source Sync

source_sync_run / fixed upper → Project Discovery → Initial / Delta / Catch-up → Jira Download → RAW / ANALYSIS / Knowledge Input → semantic_v2 source_hash → NEW / CHANGED / UNCHANGED → NEW/CHANGED Work Item row UPSERT → Project SOURCE_COMMITTED → Watermark + Source Ready Gate → Source Run finalize

Loop A의 책임은 “최신 Jira 사실을 안전하게 확보하고 Loop B가 나중에 처리할 수 있는 durable 작업을 준비하는 것”입니다.

3. Candidate Work Item과 Source Ready Work는 다릅니다

2-Loop 구현에서 가장 중요한 차이입니다. Candidate Issue 하나가 안전하게 파일로 저장되면 crash-safe resume을 위해 Work Item row를 먼저 만들 수 있습니다. 하지만 같은 Project window의 다른 Issue가 아직 실패할 수 있으므로 이 row를 곧바로 Loop B에 넘기면 안 됩니다.

T2 Candidate ABC-1 Source files durable → Work Item row UPSERT → last_observed_source_run_id = R100 → cursor commit 아직 last_source_committed_run_id != R100 → Loop B claim 불가 T3 Project Source Commit 모든 후보 안전 완료 → source_committed + Watermark → last_source_committed_run_id = R100 → 이제 claim 가능
Source Ready Gate:
last_source_committed_run_id IS NOT NULL AND last_source_committed_run_id = last_observed_source_run_id

4. 왜 Gate를 Project 단위로 여나?

D1/D2에서 Watermark는 Project Source window 전체의 안전성을 나타냅니다. 일부 Issue만 성공했다고 Watermark를 전진하지 않는 것과 같은 이유로, 일부 Work Item만 먼저 Loop B에 넘기지도 않습니다.

ABC Project ABC-1 candidate safe ✓ ABC-2 candidate safe ✓ ABC-3 source failure ✗ Project Source Commit = 실패 Watermark = 이전 값 유지 ABC-1/2 Work row = durable하지만 unready Loop B = consume X

5. Loop B · Knowledge Processing / Publish

processing_run → Source Ready Work 선택 → OpenCode Knowledge Generation → Review / Evidence → Knowledge DB → BGE-M3 Embedding → FAISS staging / mapping → 검증 → Atomic Publish → State publish_status = published → Processing Run finalize

Loop B는 Jira를 다시 읽는 Loop가 아닙니다. Source Ready Work와 이미 durable한 Source 산출물을 소비합니다.

6. durable backlog의 의미

sync_issue_change는 외부 MQ가 아니라 State DB 안의 durable work queue 역할을 합니다.

Loop A producer → Work row staged → Project Commit 후 source-ready Loop B consumer → source-ready + pending/failed 조회 → 처리 → checkpoint / retry / published

초기 Single Worker에서는 이 구조로 충분하며 실제 병렬 처리 요구가 확인될 때 lease나 외부 Queue를 검토합니다.

7. D1 / D2 · Watermark와 Overlap

lower = committed_watermark - 5m upper = source_sync_run 시작 시 fixed updated >= lower updated < upper ORDER BY updated ASC, id ASC

Watermark는 Loop A 전용 Source progress입니다. Loop B backlog가 남아 있어도 Project Source Commit이 안전하다면 Watermark는 전진합니다.

8. D3 / D4 · 실제 변화만 처리

판정조건처리
NEWjira_id 미존재새 semantic Work
CHANGED같은 jira_id + 다른 semantic_v2 hash새 semantic Work 또는 과거 동일 state 재활성화
UNCHANGED같은 jira_id + 같은 hash새 Work 없음

Jira updated는 candidate trigger일 뿐 semantic identity가 아닙니다.

9. D5 · Resume도 Loop별

Source Resume

같은 Source Run의 fixed lower/upper와 stable cursor를 사용합니다. Source Commit 전 Work는 unready이므로 Processing과 섞이지 않습니다.

Processing Resume

Knowledge/Embedding/Publish Stage 상태를 보고 실패 지점부터 이어갑니다. 이미 존재하는 actual artifact는 검증 후 재사용합니다.

10. D6 · Jira Lifecycle ≠ Knowledge Lifecycle

Discovery 전체 성공 → 기존 Project B unavailable → Loop A skip / Watermark 유지 → 기존 Work / Knowledge / Embedding / FAISS 보존 → Retrieval 계속 가능

11. D7 · SOURCE_COMMITTED ≠ PUBLISHED

Loop A V2 SOURCE_COMMITTED + Ready Gate Loop B V2 pending Service Published Head = V1 계속 사용 Loop B V2 actual Publish → Published Head = V2

Source Head != Published Head는 정상적인 eventual consistency 상태입니다.

12. D8 / D9 · Run 상태

단일 Sync Run 집계는 폐기됐습니다.

Run책임
source_sync_runDiscovery / Source / Watermark
processing_runSource-ready backlog consume / Knowledge / Publish

시스템 전체 건강도는 Source Lag, Publish Lag, Backlog, Throughput 조합으로 봅니다.

13. 낮/밤 OpenCode 편차

낮 Loop A 정상 cadence Loop B 느림 → source-ready backlog 증가 가능 밤 Loop B 처리량 향상 → backlog catch-up

2-Loop는 병목을 없애는 것이 아니라 Source freshness에서 격리하고 운영 지표로 드러냅니다.

14. 운영 지표

Source Lag

Watermark 최신성.

Publish Lag

Source Head vs Published Head.

Backlog Depth

Source-ready 미처리 Work 수.

Oldest Pending

최장 대기 age.

Throughput

시간당 Published 수.

Latency / Error

시간대별 OpenCode/Stage 성능.

15. 아직 남은 정책

Intermediate Version supersede

V2→V3→V4가 Processing 전에 쌓이면 모두 Knowledge 처리할지, Source history는 보존하되 미시작 구버전 Work를 supersede할지 다음에 결정합니다.

Multi-worker claim / lease

초기 Single Worker 후 실제 병렬 요구가 생길 때 설계합니다.
