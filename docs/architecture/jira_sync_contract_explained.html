DETAILED LEARNING GUIDE · CURRENT RULES · 2026-08-31

Continuous Sync는
두 개의 독립 Loop입니다.

현재 운영 규칙의 설계 의도를 자세히 설명합니다. 핵심은 Jira Source 최신화와 느리고 변동성이 큰 OpenCode 처리를 같은 실행 수명주기에 묶지 않고, Loop B에서는 최신 Source 상태만 비싼 AI 처리를 수행하는 것입니다.

0. “개정 3”을 어떻게 읽나?

현재 Sync Contract 계열의 세 번째 개정입니다.
Operational State Schema 개정 3, Knowledge DB Schema 개정 1, Document Shell 개정 1은 각각 별도 대상입니다. 숫자의 크기를 서로 비교하지 않습니다.

1. 왜 1-Loop가 문제였나?

1-Loop

Jira → 정제 → OpenCode → Embedding → Publish → 다음 Jira Sync

가장 느린 단계가 전체 cadence를 결정합니다. OpenCode가 느리면 Jira Source freshness까지 함께 밀립니다.

2-Loop

Loop A: Jira → Source Commit → durable backlog Loop B: latest + source-ready backlog → OpenCode → Publish

Source freshness와 Knowledge freshness를 서로 독립적으로 관리합니다.

2. Loop A · Source Sync

source_sync_run / fixed upper → Project Discovery → Initial / Delta / Catch-up → Jira Download → RAW / ANALYSIS / Knowledge Input → semantic_v2 source_hash → NEW / CHANGED / UNCHANGED → NEW/CHANGED Work Item row UPSERT → Project SOURCE_COMMITTED → Watermark + Source Ready Gate → 더 최신 Source 상태가 있으면 이전 미완료 Work supersede → Source Run finalize

semantic_v2는 문서 버전이 아니라 Source 내용의 의미 변화 여부를 계산하는 hash profile 이름입니다.

3. Candidate Work Item과 Source Ready Work는 다릅니다

Candidate Issue 하나가 안전하게 파일로 저장되면 crash-safe resume을 위해 Work Item row를 먼저 만들 수 있습니다. 하지만 같은 Project window의 다른 Issue가 아직 실패할 수 있으므로 이 row를 곧바로 Loop B에 넘기면 안 됩니다.

T2 Candidate ABC-1 Source files durable → Work Item row UPSERT → last_observed_source_run_id = R100 아직 Project Source Commit 전 → Loop B claim 불가 T3 Project Source Commit → source_committed + Watermark → last_source_committed_run_id = R100 → Source Ready

4. Source Ready만으로 충분하지 않습니다

현재 정책에서는 같은 Jira Issue의 여러 Source 상태 중 가장 최신 Work여야 합니다.

Loop B claim 가능 last_source_committed_run_id IS NOT NULL AND last_source_committed_run_id = last_observed_source_run_id AND work_status IN ('pending','failed') AND superseded_by_work_item_id IS NULL

즉 Source Ready + Latest가 공식 처리 경계입니다.

5. 왜 Gate를 Project 단위로 여나?

Watermark는 Project Source window 전체의 안전성을 나타냅니다. 일부 Issue만 성공했다고 Watermark를 전진하지 않는 것과 같은 이유로, 일부 Work Item만 먼저 Loop B에 넘기지도 않습니다.

ABC Project ABC-1 candidate safe ✓ ABC-2 candidate safe ✓ ABC-3 source failure ✗ Project Source Commit = 실패 Watermark = 이전 값 유지 ABC-1/2 Work row = durable하지만 unready Loop B = consume X

6. Latest-Only는 무엇을 버리고 무엇을 보존하나?

보존

RAW, ANALYSIS, source_hash, Issue Version과 관찰 이력 등 Source History는 삭제하지 않습니다.

건너뜀

같은 Jira Issue의 더 최신 Source 상태가 Commit됐다면 아직 완료하지 않은 과거 Work의 OpenCode/Embedding/Publish를 생략합니다.

ABC-123 상태 A → 상태 B → 상태 C Source History = A/B/C 모두 보존 A Work pending → superseded by C B Work failed → superseded by C C Work pending → Loop B 처리

7. Processing 중 더 최신 상태가 들어오면?

B Work = running → C SOURCE_COMMITTED → B work_status = superseded → OpenCode B 응답 도착 → worker latestness re-check → stale 확인 → Active Knowledge / Embedding / Publish 중단 → stale_inflight_detected log

외부 API 호출 자체를 강제 취소하는 것보다, 응답 후와 Publish 직전에 최신성을 다시 확인해 stale 결과가 활성 검색으로 들어가지 못하게 합니다.

8. Loop B · Knowledge Processing / Publish

processing_run → latest + source-ready Work 선택 → OpenCode Knowledge Generation → latestness re-check → Review / Evidence → Knowledge DB → BGE-M3 Embedding → FAISS staging / mapping → latestness re-check → Atomic Publish → State publish_status = published → Processing Run finalize

Loop B는 Jira를 다시 읽지 않습니다. 이미 durable한 Source 산출물을 소비합니다.

9. durable backlog의 의미

sync_issue_change는 외부 MQ가 아니라 Operational State DB 안의 durable work queue 역할을 합니다.

Loop A producer → Work row durable → Project Commit 후 Source Ready → 새 상태 Commit 시 과거 미완료 Work supersede Loop B consumer → latest + source-ready + pending/failed 조회 → 처리 → stage checkpoint / retry / published

10. Watermark와 Overlap

lower = committed_watermark - 5m upper = source_sync_run 시작 시 fixed updated >= lower updated < upper ORDER BY updated ASC, id ASC

Watermark는 Loop A 전용 Source progress입니다. Loop B backlog가 남아 있어도 Project Source Commit이 안전하다면 Watermark는 전진합니다.

11. 실제 변화만 Work로 만듭니다

판정조건처리
NEWjira_id 미존재새 Source 상태 + Work
CHANGED같은 jira_id + 다른 semantic_v2 hash새 Source 상태 + Work
UNCHANGED같은 jira_id + 같은 hash새 Work 없음

Jira updated 시각은 candidate 탐색용이지 semantic identity 자체가 아닙니다.

12. Resume도 Loop별

Source Resume

같은 Source Run의 fixed lower/upper와 stable cursor를 사용합니다. Source Commit 전 Work는 unready이므로 Processing과 섞이지 않습니다.

Processing Resume

먼저 최신 Work인지 다시 확인한 뒤 Knowledge/Embedding/Publish Stage 상태를 보고 실패 지점부터 이어갑니다.

13. SOURCE_COMMITTED ≠ PUBLISHED

Source Head와 Published Head가 잠시 다른 것은 정상입니다.

Source Head = 상태 C Published Head = 상태 A Loop B는 C를 처리 중 사용자 검색은 A last-known-good 유지 C actual Publish 후 Published Head = 상태 C

14. Run 상태

Run책임
source_sync_runDiscovery / Source / Watermark
processing_run최신 Source-ready backlog / Knowledge / Publish

시스템 전체 건강도는 Source Lag, Publish Lag, Latest Backlog, Throughput, Supersede 지표 조합으로 봅니다.

15. 운영 지표

Source Lag

Watermark 최신성.

Publish Lag

Source Head vs Published Head.

Latest Backlog

실제 처리해야 할 최신 Work 수.

Oldest Pending

최장 대기 age.

Supersede

구버전 Work를 얼마나 건너뛰었는지.

Latency / Error

OpenCode/Embedding/Publish 단계 성능.

16. 아직 남은 정책

Multi-worker claim / lease

초기 Single Worker 이후 실제 병렬 요구가 생길 때 설계합니다. Latest-Only/supersede 정책은 이미 확정되었습니다.
