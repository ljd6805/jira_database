D10 · FIXED · LATEST-ONLY KNOWLEDGE PROCESSING

Source History는 모두 보존하고,
지식화는 최신 Version만 합니다.

Loop A가 빠르고 Loop B가 느려 같은 Jira Issue의 여러 semantic Source Version이 backlog에 쌓여도, OpenCode/Embedding/Publish는 최신 Source Version만 처리합니다.

1. 최종 정책

Source History V1 → V2 → V3 → V4 모두 보존 Knowledge Processing V1 이미 Published V2 pending → superseded V3 pending → superseded V4 latest → process

중간 Version을 지식화하지 않는다고 Source History를 삭제하는 것은 아닙니다. RAW/ANALYSIS/source_hash/Issue Version 관찰 이력은 계속 남습니다.

2. 새 Version이 Source Commit될 때

같은 jira_id의 새 Source Version V4가 SOURCE_COMMITTED → V4 Source Ready → 아직 완료되지 않은 이전 Work Item(V2/V3)을 찾음 → work_status = superseded → superseded_by_work_item_id = V4 Work Item → superseded_at = now → 구조화 로그 기록

이미 Published된 과거 Version은 History로 남기며 supersede 대상이 아닙니다. 대상은 아직 Processing 가치가 남아 있던 pending/failed/running Work입니다.

3. 이미 OpenCode가 처리 중이면?

OpenCode 호출을 강제로 취소하는 것은 기본 정책으로 삼지 않습니다. 사내 API 호출은 이미 비용과 시간이 발생했고 안전한 취소 보장이 없을 수 있기 때문입니다.

V2 processing 시작 ↓ 그 사이 V3 SOURCE_COMMITTED ↓ V2 work_status = superseded ↓ OpenCode V2 응답 도착 ↓ 최신성 재검증 ↓ V2가 최신 아님 → Active Knowledge로 저장하지 않음 → Embedding 하지 않음 → Publish 하지 않음 → stale_inflight 로그

가능한 경우 Knowledge DB에 쓰기 전에 버립니다. 다만 외부 호출 완료와 Source Commit이 정확히 겹치는 극단적 race에서 후보 산출물이 잠시 저장되더라도 절대 Active/Published로 승격하지 않습니다.

4. Loop B Claim 조건

Source Ready AND work_status IN ('pending','failed') AND superseded_by_work_item_id IS NULL → claim 가능

Worker는 claim 직전, OpenCode 결과를 받은 직후, 그리고 Publish 직전에 최신성을 다시 확인합니다.

5. Logging / Monitoring

중간 Version은 지식화하지 않는 대신 운영에서 왜 건너뛰었는지 추적 가능해야 합니다. 로그에는 Jira 본문을 넣지 않고 identity와 상태만 기록합니다.

Event의미
work_item_superseded더 최신 Source Version이 Source Commit되어 구버전 Work를 대체함
processing_skip_supersededWorker가 이미 superseded된 Work를 건너뜀
stale_inflight_detected처리 중 새 Version이 들어와 결과를 폐기함
latest_processing_started최신 Work의 Processing 시작

권장 필드: timestamp, jira_id, project_id, old/new work_item_id, source_run_id, processing_run_id, stage, reason. Jira 원문/댓글 본문은 로그에 남기지 않습니다.

6. 운영 지표

superseded_work_count stale_inflight_count latest_backlog_depth oldest_latest_pending_age processing_throughput OpenCode latency/error Publish Lag

특히 supersede 비율이 높으면 Loop A와 Loop B의 처리량 차이가 크다는 뜻이므로 OpenCode 병목을 운영에서 바로 볼 수 있습니다.

7. 이 정책이 해결하는 것

  • 느린 OpenCode가 이미 가치가 떨어진 중간 Version을 계속 처리하는 낭비를 막습니다.
  • Jira Source History는 잃지 않습니다.
  • 사용자 검색에는 항상 마지막으로 안전하게 Published된 Knowledge만 노출합니다.
  • 중간 변경과 supersede는 로그/지표로 운영 관찰이 가능합니다.
