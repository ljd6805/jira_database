1. 가장 먼저: “DONE”이라고 부르면 안 되는 이유

앞으로 문서에서는 Loop B Knowledge / OpenCode DONE이라고 단독으로 쓰지 않습니다.

이 표현은 “자동화 코드를 만들었다”, “실제 사내 OpenCode에서 검증했다”, “스케줄러가 24시간 알아서 돌고 있다”를 모두 완료한 것처럼 보일 수 있기 때문입니다.

상태정확한 의미현재
Automation IMPLEMENTEDPython이 Work를 고르고 OpenCode를 호출하고 결과를 검증/저장하는 흐름이 코드로 구현됨완료
CI PASS가짜/통제된 실행 환경에서 selection, prompt, staging, validator, reviewer gate, stale guard 등을 자동 테스트함완료

Continuous Scheduling사람이 runner를 실행하지 않아도 Scheduler/Daemon이 Backlog를 보고 자동 기동함NOT IMPLEMENTED

2. 파일럿 때와 지금의 가장 큰 차이

기존 파일럿 · 사람이 시작

사람 ↓ OpenCode에서 직접 Prompt 입력 ↓ jira-knowledge-orchestrator 실행 ↓ 30개 Issue 순차 처리 ↓ Knowledge / Review 생성

현재 Loop B · Python이 시작

Python Loop B ↓ sync_issue_change에서 latest Work 선택 ↓ 동적 Prompt 생성 ↓ opencode run --agent jira-knowledge-orchestrator ↓ Issue 1건 자동 처리 ↓ 검증 / checkpoint ↓ 다음 Work

즉 Issue마다 사람이 OpenCode Agent를 직접 시작하는 작업은 자동화됐습니다. 그러나 python tools/run_knowledge_worker.py ... 자체를 정기적으로 시작하는 Scheduler는 아직 없습니다.

3. 현재 실제 OpenCode 호출은 어떻게 생겼나?

opencode run \
  --agent jira-knowledge-orchestrator \
  "<이번 Work Item용 동적 Prompt>"

이미 opencode serve를 띄운 경우에는 runner가 --attach http://...를 추가할 수 있습니다. 중요한 점은 Agent 이름만 전달하는 것이 아니라 Prompt도 함께 전달한다는 것입니다.

4. Python이 매번 만드는 동적 Prompt

현재 OpenCodeKnowledgeProcessor는 Work Item마다 다음 의미의 Prompt를 만듭니다.

jira-knowledge-orchestrator v0.9로 Jira Knowledge Extraction 1건을 수행해줘. [KNOWLEDGE INPUT] <이번 Issue의 knowledge_input JSON 경로> [KNOWLEDGE OUTPUT] <이번 Work의 staging Knowledge 경로> [KNOWLEDGE REVIEW] <이번 Work의 staging Review 디렉터리> 지정한 로컬 INPUT FILE만 사실 근거로 사용해 기존 Worker → Validator → Reviewer 규칙대로 처리해. 외부 Jira/Web/MCP를 조회하지 말고, 최종 Knowledge와 Attempt별 Review JSON을 반드시 지정 경로에 저장해.

여기에는 이번 실행마다 달라지는 값만 둡니다. 즉 Input/Output/Review 경로, 1건 처리라는 실행 범위, Local-only 경계가 동적 Prompt의 책임입니다.

6. Skill 사용은 실제로 어떻게 강제하나?

권한으로 제한

jira-knowledge-worker skill: "*": deny "jira-knowledge-extraction": allow

Worker가 아무 Skill이나 쓰는 구조가 아닙니다.

본문으로 명시

반드시 jira-knowledge-extraction Skill을 로드한다.

Worker 역할 정의에도 직접 적혀 있습니다.

따라서 설계/코드 기준으로는 해당 Skill 사용이 명시적으로 요구됩니다. 다만 실제 사내 OpenCode 실행 로그에서 Skill load가 실제 발생했는지는 아직 Real Run으로 확인하지 않았습니다.

7. Skill에는 파일럿 때 중요했던 내용이 들어 있나?

사실성

입력에 없는 사실을 만들지 않고, 근거 없는 Knowledge를 만들지 않습니다.

확실성 보존

원문보다 원인/확정 강도를 높이지 않습니다.

Evidence

모든 statement가 직접 Evidence로 추적 가능해야 합니다.

시간 흐름

댓글 sequence와 후속 결과를 보고 초기 가설이 뒤집힌 경우 반영합니다.

분류

Finding / Decision / Outcome / Open Item을 구분합니다.

Trade-off

최종 선택 이유를 설명하는 중요한 대안/부작용을 지우지 않습니다.

대표적인 금지 해석
"못 찾았다" ≠ "배제했다" "다른 조건에서도 발생" ≠ "원인이 아니다" "영향일 수도 있다" ≠ "주원인이다" "개선됐다" ≠ "완전히 해결됐다"

8. Reviewer도 파일럿 방식이 유지되나?

네. Reviewer는 단순 점수 채점기가 아니라 Defect-first Reviewer입니다.

Fact Audit ↓ Causal Claim Audit ↓ Evidence Audit ↓ Classification Audit ↓ Missing Knowledge Audit ↓ Duplication / Low-value Audit ↓ 마지막에 Score 계산

Critical 또는 Major가 있으면 PASS할 수 없도록 Hard Gate가 유지됩니다.

9. 파일럿의 30건 Prompt와 지금 Prompt가 똑같지는 않다

중요한 차이입니다.

파일럿에서는 사람이 한 번에 30개 디렉터리를 넘겨 전체 30건을 처리하도록 요청했습니다. 현재 운영 자동화는 Work Item 1건씩 Python이 선택해 OpenCode에 전달합니다.

파일럿 Batch Prompt

INPUT DIR의 30개 확인 → 30개 전체 순차 처리 → 전체 deterministic summary

운영 Per-Work Prompt

State에서 Work 1건 선택 → Input FILE 1개 전달 → Knowledge/Review 1건 처리 → State가 전체 처리 현황 관리

따라서 파일럿 Prompt의 “정확히 30건인지 확인” 같은 문장은 운영 자동화에 그대로 복사하지 않았습니다. 운영에서는 State DB의 Work Item과 Processing Run이 대상 수와 상태를 관리합니다.
