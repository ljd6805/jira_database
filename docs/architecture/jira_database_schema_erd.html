Database Schema & ERD

실제 Python DDL을 기준으로 Operational State DB와 Knowledge DB를 설명합니다. ERD 그림과 이전 상세 설명을 모두 유지합니다. 먼저 그림으로 구조를 보고, 바로 아래 카드와 관계표에서 컬럼/PK/FK/역할을 확인하는 방식입니다.

읽는 방법
그림은 관계를 빠르게 파악하는 용도, 그 아래 상세 카드는 실제 DDL을 읽는 용도입니다. 둘 중 하나를 없애지 않고 함께 유지합니다.

1. 전체 Database Landscape

DB는 두 덩어리입니다. State DB는 운영 상태를 관리하고, Knowledge DB는 실제 Jira snapshot과 Knowledge/Evidence를 저장합니다. BGE-M3/FAISS는 검색 artifact이므로 DB table과 구분합니다.

2. Operational State DB

State DB는 “내용 창고”가 아니라 운영 장부입니다. 수집 Run, Project watermark, 처리할 Issue 변경, Processing Run을 추적합니다.

State 업무 관계만 실선 연결Schema migration은 독립 관리 테이블Cross-DB 참조는 5장에서 별도 표시

source_sync_run

수집 Run
PK source_run_id
started_at · finished_at · upper_bound
discovery_status · source_status · run_status
error_summary
Loop A 수집 한 번을 나타냅니다.

project_state

프로젝트 현재 상태
PK project_id
current_key · current_name · visibility_state
FK first_seen_source_run_id → source_sync_run
FK last_seen_source_run_id → source_sync_run
FK last_source_success_run_id → source_sync_run
committed_watermark
프로젝트별 최신 상태와 watermark를 보관합니다.

source_project_run

Run × Project
PK (source_run_id, project_id)
FK source_run_id → source_sync_run
FK project_id → project_state
operation_kind · lower_bound · upper_bound
source_status · candidate/new/changed/unchanged_count
cursor_updated_at · cursor_jira_id

sync_issue_change

Loop B Work Item
PK work_item_id
FK project_id → project_state
jira_id · observed_issue_key · jira_updated_at
source_hash · source_hash_profile · change_kind
FK first_discovered_source_run_id / last_observed_source_run_id / last_source_committed_run_id → source_sync_run
FK last_processing_run_id → processing_run
FK superseded_by_work_item_id → sync_issue_change
work_status · knowledge_status · embedding_status · publish_status
Logical issue_version_id → Knowledge DB.issue_version
Logical knowledge_generation_id → Knowledge DB.knowledge_generation
Latest-Only 처리에서 실제로 선택되는 work queue입니다.

processing_run

Loop B Run
PK processing_run_id
started_at · finished_at · run_status
selected_count · published_count · failed_count · superseded_count

state_schema_migration

DB 구조 변경 이력 · 업무 FK 없음

이 테이블은 다른 업무 테이블과 연결되지 않는 것이 정상입니다. 특정 Jira Project/Run/Work Item의 기록이 아니라 collector.db 자체가 언제 어떤 Schema로 승격됐는지를 기록하는 관리 장부이기 때문입니다.

4. Knowledge DB · Knowledge / Review 영역

한 Issue version에서 Knowledge Generation이 만들어지고, 여러 Attempt를 거쳐 Knowledge Item / Evidence / Review로 이어집니다.

knowledge_generation

지식 생성 묶음
PK knowledge_generation_id
FK issue_version_id → issue_version
FK jira_id → issue
FK source_run_id → pipeline_run
FK accepted_attempt_id → knowledge_attempt
source_hash · knowledge_contract_hash · knowledge_schema_version
skill_version · runtime_version · model_profile · state · created_at

knowledge_attempt

생성 시도
PK knowledge_attempt_id
FK knowledge_generation_id → knowledge_generation
attempt_no · knowledge_content_hash
content_available · validator_status · generated_at

knowledge_item

지식 문장
PK knowledge_item_id
FK knowledge_attempt_id → knowledge_attempt
category · ordinal · statement

knowledge_evidence

근거
PK knowledge_evidence_id
FK knowledge_item_id → knowledge_item
FK source_run_id → pipeline_run
evidence_ref · evidence_type · source_issue_key · source_entity_key

knowledge_review

품질 리뷰
PK knowledge_review_id
UQ/FK knowledge_attempt_id → knowledge_attempt
score · verdict · critical_error · major_issue_count
factual_fidelity_score · evidence_coverage_score · certainty_preservation_score · classification_score · retrieval_value_score · language_quality_score
Attempt마다 review는 최대 1개이며, review가 아직 없을 수도 있으므로 부모 관점 cardinality는 1:0..1입니다.

review_finding

리뷰 지적
PK review_finding_id
FK knowledge_review_id → knowledge_review
finding_group · severity · audit_category · ordinal
finding_type · location · message

Knowledge / Review 핵심 관계

ParentChild관계의미
issueissue_version1:N한 이슈는 여러 Source version을 가질 수 있음
issue_versionknowledge_generation1:N같은 Source에서 계약/런타임 차이로 여러 generation 가능
knowledge_generationknowledge_attempt1:N재시도/재생성 이력
knowledge_attemptknowledge_item1:N한 attempt가 여러 지식 문장을 생성

knowledge_reviewreview_finding1:N여러 리뷰 지적 항목

5. State DB ↔ Knowledge DB 연결

두 DB는 별도 SQLite이므로 서로 직접 FK를 걸 수 없습니다. 아래는 애플리케이션이 검증하는 Logical Reference입니다.

sync_issue_change.jira_idLogical Reference → issue.jira_id
sync_issue_change.issue_version_idLogical Reference → issue_version.issue_version_id
sync_issue_change.knowledge_generation_idLogical Reference → knowledge_generation.knowledge_generation_id
읽는 규칙
같은 DB 안의 실제 FK와 DB를 넘는 Logical Reference를 동일한 관계로 취급하지 않습니다. 이 구분이 전체 ERD 해석의 핵심입니다.

7. Issue 한 건이 흐르는 순서

ERD를 외우지 말고 데이터 한 건을 따라가면 구조가 훨씬 단순해집니다.

1. 변경 발견sync_issue_change
2. Source 저장issue + issue_version
3. Knowledge 생성knowledge_generation
4. Attemptknowledge_attempt
5. 문장/근거knowledge_item + knowledge_evidence
6. 품질 검토knowledge_review + review_finding
7. 검색 반영BGE-M3 → FAISS
8. 상태 반영State DB published
한 문장으로 기억하면
State DB는 “해야 할 일과 완료 상태”, Knowledge DB는 “실제 저장된 내용과 근거”, FAISS는 “그 내용을 빨리 찾는 색인”입니다.
