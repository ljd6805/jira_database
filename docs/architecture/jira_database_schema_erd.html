이 문서는 기존 Relationship Map과 다릅니다. 실제 Python DDL을 기준으로 테이블, 컬럼, PK/FK, 1:N 관계를 전통적인 ERD 관점에서 읽기 위한 전용 기준 문서입니다.

왜 새 문서를 만들었나?
기존 jira_data_relationship_map.html은 데이터 흐름과 운영 개념을 탐색하기에는 좋지만, 테이블의 PK/FK와 cardinality를 전형적인 ERD처럼 읽기에는 부족했습니다. 이 문서는 그 빈칸을 채웁니다.

1. 전체 Database Landscape

이 프로젝트는 DB 하나로 끝나지 않습니다. 운영 상태를 관리하는 State DB와 Jira 원문·Knowledge·Evidence를 보관하는 Knowledge DB가 별도 SQLite로 존재하며, Embedding/FAISS는 DB가 아닌 검색 artifact입니다.

Physical FK: SQLite가 직접 무결성을 검사Logical Reference: ID 문자열로 연결, 애플리케이션이 검증

2. Operational State DB ERD

State DB는 “데이터 내용”보다 무엇을 언제 수집했고, 어떤 Issue version이 처리 대기/실행/게시 상태인지를 기록하는 운영 장부입니다.

핵심
sync_issue_change가 Loop A와 Loop B 사이의 핵심 Work Item입니다. 하지만 issue_version_id와 knowledge_generation_id는 같은 DB의 FK가 아닙니다. Knowledge DB를 가리키는 Logical Reference입니다.

3. Knowledge DB ERD

Knowledge DB는 총 15개 테이블입니다. 복잡해 보이지만 크게 ① Source/Issue 영역과 ② Knowledge/Review 영역 두 덩어리로 보면 됩니다.

4. 두 DB 사이의 실제 연결

두 SQLite 파일 사이에는 DB 엔진 차원의 FK를 만들 수 없습니다. 따라서 아래 세 연결은 의도적으로 Logical Reference입니다.

State DBKnowledge DB의미검증 주체
sync_issue_change.jira_idissue.jira_id같은 Jira Issue의 안정 IDApplication
sync_issue_change.issue_version_idissue_version.issue_version_id이 Work Item으로 materialize된 Source versionApplication
sync_issue_change.knowledge_generation_idknowledge_generation.knowledge_generation_idLoop B가 생성·게시한 Knowledge generationApplication
주의
문서에서 점선으로 그린다고 해서 “느슨해서 중요하지 않은 관계”가 아닙니다. 오히려 DB 파일을 넘기 때문에 코드의 validation과 publish transaction에서 더 신경 써야 하는 관계입니다.

5. 테이블 사전

ERD에서 박스 이름만 보고 이해가 안 될 때 이 부분을 보면 됩니다. PK, FK, LR을 먼저 찾으면 연결 구조가 빠르게 보입니다.

6. Issue 한 건이 DB를 통과하는 모습

예를 들어 Jira Issue ABC-123이 새로 변경됐다고 가정해 보겠습니다.

1. Statesync_issue_change
새 source_hash의 Work Item 생성
2. Source Commitissue + issue_version
원문 snapshot 저장
3. Knowledgeknowledge_generation → knowledge_attempt
4. Statementsknowledge_item
요약/문제/조치/결과 등
5. Evidenceknowledge_evidence
댓글·설명 등 Source 근거 연결
6. SearchBGE-M3 → FAISS
Knowledge Item vector 색인
7. State Publishsync_issue_change
published + generation ID 기록
이 흐름을 기억하면 ERD가 갑자기 단순해집니다.
State DB는 “해야 할 일과 완료 상태”, Knowledge DB는 “실제 저장된 내용과 근거”, FAISS는 “그 내용을 빨리 찾는 색인”입니다.
