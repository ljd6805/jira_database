SYNC STATE / PROJECT REGISTRY · SCHEMA DECISION 1 · FINAL · 2026-08-27

기존 State DB를
운영 Sync State DB로 확장한다

운영 Sync의 Watermark, Project Registry, Run 상태, Checkpoint, downstream 진행 상태는 기존 data/state/collector.db의 책임을 확장해 저장합니다.

S1 FIXED · OPTION A · MIGRATION REQUIRED

1. 최종 결정

A안 확정

Control Plane 기존 data/state/collector.db 재사용 현재 collection_runs project_runs issue_checkpoints artifacts 운영 확장 sync_run project_registry project_sync_state sync_project_run sync_issue_change

Knowledge DB는 Issue Version, Generation, Attempt, Knowledge Item, Evidence 등 업무지식 Data Plane에 집중합니다.

2. 왜 이 구조인가?

State DB

“작업이 어디까지 진행됐는가?”를 답합니다. Resume, Watermark, retry, error, Project 상태처럼 자주 바뀌는 Control Plane입니다.

Knowledge DB

“어떤 업무지식과 이력이 만들어졌는가?”를 답합니다. 장기 보존되는 Data Plane입니다.

책임 경계: 실행 상태와 업무지식 내용을 섞지 않습니다. 두 DB는 필요할 때 안정적인 ID로 논리적으로 연결하며 SQLite 간 물리 FK를 요구하지 않습니다.

3. Migration은 선택이 아니라 필수입니다

MANDATORY MIGRATION

기존 collector.db 파일을 재사용한다는 것은 현재 Schema를 그대로 운영에 쓰겠다는 뜻이 아닙니다. Continuous Sync에 필요한 새 상태를 추가하려면 명시적인 Schema Migration이 반드시 선행되어야 합니다.

기존 collector.db ↓ 사전 Backup / 현재 Schema 확인 ↓ Versioned Migration 실행 ↓ 기존 collection_runs / project_runs / issue_checkpoints / artifacts 보존 ↓ 새 Operational Sync 테이블 추가 ↓ Migration 후 무결성 / 기존 Resume 회귀 검증 ↓ 운영 Sync 사용 허용

4. Migration 필수 요구사항

기존 데이터 보존

과거 MVP Run, Artifact, Issue Checkpoint를 삭제하거나 의미 변경하지 않습니다.

Schema Version 관리

현재 DB가 어느 Operational State Schema인지 판별할 수 있어야 합니다.

반복 실행 안전성

이미 Migration된 DB에 다시 실행해도 중복 테이블이나 데이터 손상이 없어야 합니다.

검증 가능한 전환

Migration 전 Backup, 후 무결성 검사와 기존 Collector Resume 회귀 테스트를 Gate로 둡니다.

금지: 운영 코드가 실행되면서 암묵적으로 테이블을 몇 개 추가하고 끝내는 방식으로 전환하지 않습니다. Migration 자체를 버전이 있는 명시적 구현/검증 단위로 다룹니다.

5. 파일명은 아직 유지

collector.db라는 이름이 장기적으로 좁아 보이지만 파일 rename은 별도 Migration 범위를 만듭니다.

S1에서 확정 → 물리 DB = 기존 collector.db → 책임 = Operational Sync State까지 확장 → Migration = 필수 아직 미확정 → collector.db 이름 유지 여부 → operational_state.db 등으로 rename 여부

파일명 변경은 실제 Migration 설계 시 비용과 호환성을 보고 별도로 결정합니다.
