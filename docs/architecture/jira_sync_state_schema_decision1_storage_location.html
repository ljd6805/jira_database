SYNC STATE / PROJECT REGISTRY · SCHEMA DECISION 1 · 2026-08-27

운영 Sync 상태를
어느 DB에 저장할까?

FROZEN Sync Contract를 구현하려면 Watermark, Project Registry, Run 상태, Checkpoint, downstream Work Item을 장기간 저장해야 합니다. 첫 Schema 결정은 이 상태들의 물리 저장소 책임을 정하는 것입니다.

S1 REVIEWING · RECOMMENDATION = EXTEND EXISTING STATE DB

1. 현재 이미 두 종류의 DB 책임이 있습니다

Collector State DB

data/state/collector.db collection_runs project_runs artifacts issue_checkpoints

실행 상태, Resume, 실패 격리, 수집 Artifact를 기억합니다. 현재 CLI도 수집/재개 시 이 DB를 공통으로 엽니다.

Knowledge DB

pipeline_run issue / issue_version knowledge_generation knowledge_attempt knowledge_item / evidence review...

업무지식의 내용, Version, 생성 이력, Evidence 족보를 보존합니다. 검색/MCP가 읽는 핵심 Data Plane입니다.

쉽게 말하면: State DB는 “공장이 지금 어디까지 일했나”를 기록하고, Knowledge DB는 “공장에서 어떤 제품과 이력이 만들어졌나”를 보존합니다.

2. 세 가지 후보

A · RECOMMENDED

기존 State DB 확장

collector.db에 Project Registry, Watermark, Sync Run, downstream checkpoint를 추가합니다.

장점: 현재 Resume/Checkpoint와 같은 책임. 기존 transaction/WAL/StateStore 기반 재사용. 운영 상태가 한 곳에 모입니다.

주의: 이름은 collector.db지만 책임이 Collector보다 넓어집니다.

B

Knowledge DB에 통합

운영 상태 테이블을 Knowledge DB 안에 추가합니다.

장점: DB 파일 하나.

문제: 지식 내용과 휘발성 실행 상태가 섞입니다. MCP 조회 서비스와 Background Sync의 쓰기 책임도 강하게 결합됩니다.

C

새 Sync DB 생성

sync_state.db 같은 별도 DB를 새로 만듭니다.

장점: 이름과 책임이 명확.

문제: 기존 collector.db의 checkpoint/artifact와 새 Sync 상태가 둘로 갈라져 migration·정합성 관리가 늘어납니다.

4. 추천 아키텍처 · Control Plane / Data Plane 분리

[Control Plane · State DB] data/state/collector.db Sync Run Project Registry Project Watermark Source Checkpoint Knowledge / Embedding / Publish 진행 상태 Retry / Error / Artifact stable IDs로 참조 ↓ [Data Plane · Knowledge DB] Issue / Issue Version Knowledge Generation / Attempt Knowledge Item / Evidence Review Active / Historical Knowledge
중요: 두 SQLite DB 사이에 물리 Foreign Key를 만들 필요는 없습니다. State DB는 jira_id, source_hash, issue_version_id, knowledge_generation_id 같은 안정적인 ID를 진행 상태 참조값으로 저장하면 됩니다.

5. 왜 Knowledge DB에 넣지 않는가?

Knowledge는 오래 보존하는 결과

Issue Version, Knowledge, Evidence는 업무지식의 역사입니다. Sync Run이 실패해도 이 데이터의 의미는 변하지 않습니다.

State는 계속 변하는 실행 상태

pending → running → failed → running → completed처럼 운영 중 빈번하게 바뀝니다.

두 성격을 같은 DB에 넣는 것이 기술적으로 불가능한 것은 아니지만, 현재 프로젝트의 책임 분리에는 이득보다 결합도가 더 큽니다.

6. 기존 collector.db를 그대로 쓰는 이유

현재 StateStore(data/state/collector.db) → collection_runs → project_runs → issue_checkpoints → artifacts 운영 확장 같은 DB → sync_run → project_registry → project_sync_state → sync_project_run → sync_issue_change 기존 MVP State는 보존 새 운영 State를 추가

기존 수집 resume 기록을 지우거나 의미를 바꾸지 않고 새 테이블을 추가하는 migration 방식이 가장 안전합니다.

파일명은 별도 결정: collector.db라는 이름이 장기적으로 좁아 보이지만, 지금 파일명을 즉시 바꾸면 기존 CLI/설정/문서/migration 범위가 불필요하게 커집니다. Schema 구현 단계에서 “경로 유지 vs rename migration”을 별도 결정합니다.

7. S1 추천 결론

기존 Collector State DB를 Operational Sync State DB로 확장한다.

선택 A 물리 저장소 → 기존 data/state/collector.db 재사용 책임 → Collector 상태 + Continuous Sync 상태 + Project Registry + Watermark + downstream checkpoint Knowledge DB → 지식 내용과 검색 족보에 집중

이 선택이 확정되면 다음 Schema Decision은 S2 · 5개 Entity를 실제 테이블로 그대로 나눌지, 일부를 합칠지입니다.

아직 S1은 FROZEN 아님. 사용자 승인 후 FIXED로 올리고 S2로 넘어갑니다.
