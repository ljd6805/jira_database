S1~S4 FIXED · S5 REVIEWING · MIGRATION CONTRACT

1. 현재 DB에는 Migration 체계가 없습니다

현재 StateStore는 CREATE TABLE IF NOT EXISTS로 legacy 테이블을 생성하지만 PRAGMA user_version이나 Migration 이력은 사용하지 않습니다. 따라서 기존 DB와 새로운 운영 Schema를 구분하는 명시적 버전 체계가 필요합니다.

현재 legacy collector.db user_version = 0 또는 미사용 collection_runs project_runs issue_checkpoints artifacts → 기존 데이터는 반드시 보존 → Operational Sync Schema는 versioned migration으로만 추가

2. 추천 Version 모델

첫 Versioned Operational State Schema = v1

STATE_SCHEMA_VERSION = 1 PRAGMA user_version = 1 → S1~S4에서 확정한 Operational State Schema를 지원한다는 뜻

기존 DB의 user_version=0은 “정식 v0 Schema”라고 단정하지 않습니다. unversioned legacy 또는 빈 DB일 수 있으므로 실제 table fingerprint를 확인합니다.

DB 상태처리
빈 DB + user_version 0현재 v1 Schema를 새로 초기화.
알려진 legacy tables + user_version 0명시적 Migration 필요. Backup → migrate → validate.
user_version 1Schema fingerprint 검증 후 정상 사용.
user_version 0 + 모르는 table/schema자동 변경 거부. 운영자 확인 필요.
user_version > 지원 버전더 최신 DB로 간주하고 현재 프로그램은 쓰기 거부.

3. Normal Startup에서 기존 DB를 몰래 Migration하지 않습니다

비추천

StateStore()를 열기만 했는데 기존 운영 DB가 자동으로 변경되는 방식.

추천

새 빈 DB는 현재 Schema로 초기화 가능. 하지만 기존 legacy DB가 감지되면 정상 실행을 중단하고 명시적 migrate 명령을 요구합니다.

일반 시작 legacy DB 감지 ↓ "Migration required" 오류 ↓ 수집/Sync 시작 금지 운영자 migrate-state-db 같은 명시적 절차 실행 ↓ Backup / Migration / Validation PASS ↓ 정상 서비스 시작

구체적인 CLI 명령 이름은 구현 단계에서 확정하되, silent auto-migration 금지 원칙은 S5에서 고정하는 것을 추천합니다.

4. Migration 전에 반드시 Backup

WAL을 사용하는 SQLite 파일을 단순 OS 파일 복사로 백업하면 시점에 따라 일관성 문제가 생길 수 있습니다. Python SQLite의 Backup API처럼 SQLite가 제공하는 일관된 백업 방식을 우선 사용합니다.

Migration 시작 → concurrent writer 금지 / migration ownership 확보 → SQLite consistent backup 생성 → backup PRAGMA quick_check / integrity check → backup 파일 존재 + 읽기 가능 확인 → 그 다음에만 원본 DB 변경 허용
Backup 예시 이름: collector.db.pre-state-v1.<timestamp>.bak. 정확한 이름 규칙은 구현에서 정할 수 있지만, Migration 전 복구 가능한 백업 존재는 필수 Gate입니다.

5. 알려진 Legacy DB만 자동 Migration

user_version 0이라는 이유만으로 DB를 수정하지 않습니다. 다음 legacy fingerprint가 기대 구조와 일치하는지 먼저 검사합니다.

expected legacy tables collection_runs project_runs issue_checkpoints artifacts + 필수 column / PK / index 구조 확인 ↓ KNOWN LEGACY → migration 허용 예상하지 못한 table/column 충돌 → UNKNOWN SCHEMA → migration 중단 → 원본 DB 무변경

이 방식은 과거 수동 수정 DB나 손상 DB를 “정상 legacy”로 오인해 덮어쓰는 위험을 줄입니다.

6. Migration v1에서 하는 일

legacy tables → 삭제/rename/의미 변경하지 않음 ADD Operational State Domain Tables 1. sync_run 2. project_state 3. sync_project_run 4. sync_issue_change ADD indexes / CHECK / UNIQUE / FK within State DB ADD technical migration metadata (선택이 아닌 기술 메타데이터) SET PRAGMA user_version = 1 COMMIT
S2와 충돌하지 않음: “4개 물리 테이블”은 운영 Domain Table 기준입니다. Migration 이력용 state_schema_migration 같은 기술 메타데이터 테이블은 Domain Table 수에 포함하지 않습니다.

7. Legacy 데이터에서 Watermark를 추정하지 않습니다

중요한 Migration 정책

기존 project_runs에는 장기 Registry용 stable project_id, D2의 fixed upper, D1의 committed watermark 계약이 없습니다. 따라서 과거 수집 시각이나 마지막 Issue updated를 보고 새 Watermark를 만들어내지 않습니다.

Migration 직후 project_state = 비어 있을 수 있음 sync_run / sync_project_run / sync_issue_change = 새 운영 Run부터 생성 첫 Operational Sync → 정상 Project Discovery → project_id 기반 project_state 생성 → Initial Ingest / 이후 Delta 계약으로 상태를 시작

기존 Knowledge와 legacy collection history는 그대로 보존하지만, 새 운영 상태를 과거 데이터에서 추정 복원하지 않습니다.

8. Migration 자체도 Transactional / Idempotent하게

첫 실행

Known legacy → v1 Schema 추가 → version 기록.

두 번째 실행

이미 v1이면 Schema 검증 후 no-op. 중복 table이나 migration row를 만들지 않습니다.

Migration transaction 실패 → Schema change rollback → user_version 이전 상태 → backup 유지 재실행 → preflight부터 다시 확인 → 안전하게 재시도 가능

IF NOT EXISTS만 믿지 않고, 이미 존재하는 table/index가 기대 Schema와 같은지 검증합니다.

9. Post-Migration Validation Gate

GatePASS 조건
SQLite integrityPRAGMA quick_check 또는 더 강한 integrity 검사 PASS.
Schema versionPRAGMA user_version = 1.
Schema fingerprint4개 Domain Table + 필수 column/index/constraint 일치.
Legacy row preservation기존 4개 legacy table row count 및 핵심 데이터 보존.
Legacy StateStore regression기존 collector/resume 테스트 PASS.
New migration testsempty→v1, legacy→v1, rerun no-op, unknown schema reject, 실패 rollback 검증.
운영 사용 Gate: 이 검증 중 하나라도 실패하면 Migration 완료로 선언하지 않고 Operational Sync 실행을 허용하지 않습니다.

10. Rollback은 Down Migration보다 Backup Restore

첫 Migration은 legacy table을 파괴하지 않는 additive migration입니다. 문제가 생겼을 때 복잡한 역방향 SQL로 새 table을 되돌리기보다 검증된 pre-migration backup을 복원하는 편이 더 안전합니다.

Migration 후 심각한 문제 발견 → Sync/Collector process 정지 → 현재 DB를 forensic 보존 이름으로 이동 → pre-state-v1 backup restore → integrity 확인 → legacy collector/resume 검증 → 원인 수정 후 migration 재시도

운영 데이터가 새 v1 Schema에 쌓인 뒤의 downgrade 문제는 별도 정책입니다. 첫 cutover 단계의 rollback 기준은 Backup Restore로 둡니다.

11. Migration Audit

빠른 현재 버전 판정은 PRAGMA user_version을 사용하고, 감사/추적을 위해 기술 메타데이터 이력을 함께 남기는 것을 추천합니다.

state_schema_migration migration_id state-v1 from_version 0 / legacy-unversioned to_version 1 applied_at ... 필요 시 implementation_version 등 확장

절대 경로나 Secret을 기록할 필요는 없습니다. 필요한 경우 backup 파일의 안전한 상대 이름 정도만 운영 로그에 남깁니다.
