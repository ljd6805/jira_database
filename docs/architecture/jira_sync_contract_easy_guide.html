EASY GUIDE · 2026-08-28

Jira 최신화와 AI 지식화는
따로 달립니다.

2-Loop 구조를 물류센터로 생각하면 쉽습니다. Loop A는 Jira 물건을 안전하게 입고하는 팀이고, Loop B는 입고 완료된 물건만 가져가 검사·가공해 검색 매대에 올리는 팀입니다.

1. 왜 두 팀인가?

🚚

Loop A = 입고팀

Jira 변경분을 계속 받아 RAW/ANALYSIS로 정리하고 실제 변화인지 판정합니다. OpenCode가 느려도 멈추지 않습니다.

🏭

Loop B = 가공·진열팀

입고 완료된 변경분을 OpenCode로 지식화하고 Embedding/FAISS까지 준비해 검색 서비스에 Publish합니다.

2. 전체 흐름

Loop A · Source Sync Jira → Project Discovery → Delta Download → RAW / ANALYSIS / Knowledge Input → semantic_v2 hash → NEW / CHANGED / UNCHANGED → Work Item row 저장 → Project SOURCE_COMMITTED → Watermark 이동 → Source Ready 도장 ↓ 처리 가능한 대기열 Loop B · Knowledge Processing / Publish Source Ready Work Item → OpenCode Knowledge → Review / Evidence → Knowledge DB → BGE-M3 → FAISS 준비 → Atomic Publish → PUBLISHED

3. Watermark = 책갈피

🔖

“이 Project는 Jira를 어디까지 안전하게 읽었나?”를 기억하는 책갈피입니다. Project마다 따로 있습니다.

지난 Watermark = 10:30 Overlap 5분 → lower = 10:25 이번 Source Run upper = 10:40 Project Source 전체 안전 완료 후에만 Watermark = 10:40

4. Source Ready Gate = 입고 완료 도장

✅

창고 직원이 상자에 이름표를 먼저 붙일 수는 있습니다. 하지만 입고 검수가 끝나 입고 완료 도장이 찍히기 전에는 가공팀이 가져가면 안 됩니다. 이것이 Source Ready Gate입니다.

T2 ABC-1 상자(Work Item) 만들어짐 → 아직 Source Ready 아님 같은 Project의 ABC-2 수집 실패 가능 → Project 전체 Commit 전까지 Loop B claim 금지 T3 Project Source Commit 성공 → Watermark 이동 → ABC-1 Source Ready 도장 → 이제 Loop B가 가져갈 수 있음
정확한 조건:
last_source_committed_run_id = last_observed_source_run_id인 Work만 Loop B가 처리합니다.

5. SOURCE_COMMITTED와 PUBLISHED

SOURCE_COMMITTED

Jira 변경분을 안전하게 받고 Project 단위 검수까지 끝내 Source Ready Work를 넘길 수 있는 상태입니다.

PUBLISHED

Knowledge, Review, Embedding, FAISS까지 완성되어 실제 사용자 검색이 새 버전을 보는 상태입니다.

Source Head = V2 Published Head = V1 → 정상적인 중간 상태 → 사용자는 V1 계속 검색 Loop B가 V2 Publish 완료 → Published Head = V2

6. Backlog = 처리 대기 상자

📦

Loop A가 Loop B보다 빠르면 Source Ready 상자가 쌓입니다. 이것은 장애가 아닐 수 있지만 계속 증가하면 Processing 처리량이 부족하다는 뜻입니다.

Backlog Depth

Source Ready지만 아직 끝나지 않은 Work 수.

Oldest Pending Age

가장 오래 기다린 Work의 대기시간.

Publish Lag

Source Head와 Published Head의 차이.

7. 낮에 OpenCode가 느리면?

낮 Loop A: 계속 Source 최신화 Loop B: 느림 → backlog 증가 가능 밤 Loop B 처리량 증가 → backlog catch-up

2-Loop는 병목을 없애는 것이 아니라 Jira 최신화에서 격리하고 측정 가능하게 만듭니다.

8. NEW / CHANGED / UNCHANGED

NEW

처음 보는 jira_id. Work Item 생성.

CHANGED

같은 jira_id지만 semantic_v2 hash가 다름. Work Item 생성 또는 기존 semantic Work 재활성화.

UNCHANGED

같은 semantic state. 새 Work 없이 기존 Knowledge/Embedding 재사용.

9. Project가 안 보이면?

Project Discovery 전체 성공 → 기존 Project B가 목록에 없음 → unavailable → Loop A에서 skip / Watermark 유지 → 기존 Knowledge / Embedding / FAISS 유지 → 검색 계속 가능

10. 실패하면 어디부터 다시 하나?

Loop A

fixed lower/upper와 stable cursor를 이용해 Source를 재개합니다. Source Commit되지 않은 관찰은 Loop B가 소비하지 않습니다.

Loop B

Knowledge/Embedding/Publish 중 실패 Stage부터 재개합니다. Jira를 다시 다운로드하지 않습니다.

11. Run도 두 종류

source_sync_run → sr_ + UUID4 → Jira Source 최신화 실행 processing_run → pr_ + UUID4 → OpenCode / Embedding / Publish 실행

둘은 1:1로 대응하지 않습니다.

12. 기억할 여섯 문장

① Jira Source 최신화와 AI 지식화는 서로 기다리지 않는다.
② Work Item row가 있다고 바로 처리하지 않는다.
③ Project Source Commit까지 끝난 Source Ready Work만 Loop B가 가져간다.
④ Source Commit과 Publish는 다른 완료 경계다.
⑤ 새 Publish 전까지 기존 Published Knowledge를 계속 제공한다.
⑥ 시스템 최신성은 Source Lag + Publish Lag + Backlog로 본다.

13. 아직 남은 결정

V2→V3→V4가 Processing 전에 쌓였을 때 모든 semantic Version을 지식화할지, 아직 시작하지 않은 구버전 Work를 supersede할지는 다음에 결정합니다. Source Version 자체는 모두 보존합니다.
