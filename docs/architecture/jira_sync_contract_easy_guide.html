현재 운영 규칙을 물류센터로 생각하면 쉽습니다. Loop A는 Jira 물건을 안전하게 입고하는 팀이고, Loop B는 입고 완료 + 최신인 물건만 가져가 검사·가공해 검색 매대에 올리는 팀입니다.

0. 이 문서에서 “개정 3”은 무엇인가?

현재 Sync Contract의 세 번째 개정이라는 뜻입니다.
Knowledge DB Schema 개정 1, 문서 UI 프레임 개정 1과는 별도 번호 체계입니다. 숫자를 서로 비교하지 마세요.

1. 왜 두 팀인가?

🚚

Loop A = 입고팀

Jira 변경분을 계속 받아 RAW/ANALYSIS로 정리하고 실제 변화인지 판정합니다. OpenCode가 느려도 멈추지 않습니다.

🏭

Loop B = 가공·진열팀

입고 완료된 변경분 중 현재 최신 Work만 OpenCode로 지식화하고 Embedding/FAISS까지 준비해 검색 서비스에 Publish합니다.

2. 전체 흐름

Loop A · Source Sync Jira → Project Discovery → Delta Download → RAW / ANALYSIS / Knowledge Input → semantic_v2 (Source 변경 판별 프로필) → NEW / CHANGED / UNCHANGED → Work Item row 저장 → Project SOURCE_COMMITTED → Watermark 이동 → Source Ready OPEN → 같은 Issue의 이전 미완료 Work는 superseded ↓ 최신 + 처리 가능한 대기열 Loop B · Knowledge Processing / Publish Source Ready + Latest Work Item → OpenCode Knowledge → 최신성 재확인 → Review / Evidence → Knowledge DB → BGE-M3 → FAISS 준비 → 최신성 재확인 → Atomic Publish → PUBLISHED

3. Watermark = 책갈피

🔖

“이 Project는 Jira를 어디까지 안전하게 읽었나?”를 기억하는 책갈피입니다. Project마다 따로 있습니다.

지난 Watermark = 10:30 Overlap 5분 → lower = 10:25 이번 Source Run upper = 10:40 Project Source 전체 안전 완료 후에만 Watermark = 10:40

4. Source Ready Gate = 입고 완료 도장

✅

상자에 이름표를 먼저 붙일 수는 있지만 입고 검수가 끝나 입고 완료 도장이 찍히기 전에는 가공팀이 가져가면 안 됩니다. 이것이 Source Ready Gate입니다.

Work Item row 생성 → 아직 Source Ready 아님 Project Source Commit 성공 → Watermark 이동 → committed run 기록 → Source Ready OPEN

5. 그런데 Ready만으로 충분한가?

🆕

Latest-Only = 최신 상자만 가공

같은 Jira Issue의 상태 A, B, C가 빠르게 들어왔다면 원본 History는 모두 보존하지만 비싼 OpenCode/Embedding은 최신 상태 C만 처리합니다.

ABC-123 Source History 상태 A → 상태 B → 상태 C 모두 보존 아직 처리하지 않은 A Work → superseded 아직 처리하지 않은 B Work → superseded 최신 C Work → pending / 처리 대상
Loop B claim 조건
Source Ready이고, work_status가 pending/failed이며, 더 최신 Work에 의해 superseded되지 않은 경우에만 처리합니다.

6. SOURCE_COMMITTED와 PUBLISHED

SOURCE_COMMITTED

Jira 변경분을 안전하게 받고 Project 단위 검수까지 끝내 최신 Work를 넘길 수 있는 상태입니다.

PUBLISHED

Knowledge, Review, Embedding, FAISS까지 완성되어 실제 사용자 검색이 새 상태를 보는 시점입니다.

둘 사이에 시간차가 있어도 정상입니다. 새 Publish 전까지 사용자는 last-known-good Published Knowledge를 계속 사용합니다.

7. Backlog = 처리 대기 상자

📦

Loop A가 Loop B보다 빠르면 Work가 쌓입니다. 현재 운영에서는 latest + source-ready Work만 실제 처리 backlog로 봅니다.

Latest Backlog

지금 실제 처리해야 하는 최신 pending/failed Work 수.

Oldest Pending Age

가장 오래 기다린 최신 Work의 대기시간.

Publish Lag

Source Head와 Published Head의 차이.

8. Processing 중 더 최신 상태가 들어오면?

상태 B 처리 중 → 상태 C SOURCE_COMMITTED → B Work = superseded → OpenCode B 응답은 일단 도착 가능 → Worker가 최신성 재확인 → B가 stale임을 확인 → B 결과 Publish 금지 → C만 계속 처리

외부 호출을 억지로 중간 취소하기보다 결과가 돌아온 뒤 최신성을 다시 확인해 잘못된 Publish를 막습니다.

9. NEW / CHANGED / UNCHANGED

NEW

처음 보는 jira_id. Work Item 생성.

CHANGED

같은 jira_id지만 semantic_v2 hash가 다름. 새 Source 상태와 Work Item을 기록.

UNCHANGED

같은 semantic state. 새 Work 없이 기존 Source/Knowledge를 재사용.

10. 실패하면 어디부터 다시 하나?

Loop A

fixed lower/upper와 stable cursor를 이용해 Source를 재개합니다. Source Commit되지 않은 관찰은 Loop B가 소비하지 않습니다.

Loop B

최신성 확인 후 Knowledge/Embedding/Publish 중 실패 Stage부터 재개합니다. Jira를 다시 다운로드하지 않습니다.

11. Run도 두 종류

source_sync_run → sr_ + UUID4 → Jira Source 최신화 실행 processing_run → pr_ + UUID4 → 최신 backlog의 OpenCode / Embedding / Publish 실행

둘은 1:1로 대응하지 않습니다.

12. 기억할 일곱 문장

① Jira Source 최신화와 AI 지식화는 서로 기다리지 않는다.
② Work Item row가 있다고 바로 처리하지 않는다.
③ Project Source Commit까지 끝난 Source Ready Work만 후보가 된다.
④ 같은 Issue라면 그중 최신 Work만 Loop B가 처리한다.
⑤ Source Commit과 Publish는 다른 완료 경계다.
⑥ 새 Publish 전까지 기존 Published Knowledge를 계속 제공한다.
⑦ semantic_v2는 문서 버전이 아니라 변경 판별 프로필 이름이다.

13. 아직 남은 결정

Multi-worker claim / lease만 아직 별도 결정입니다. 중간 Source 상태를 supersede하고 최신만 처리하는 정책은 이미 현재 운영 규칙으로 확정되었습니다.
