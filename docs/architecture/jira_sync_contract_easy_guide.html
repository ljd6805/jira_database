EASY GUIDE · 2026-08-28

Jira 최신화와 AI 지식화는
따로 달립니다.

2-Loop 구조를 “물류센터” 비유로 이해하면 쉽습니다. Loop A는 Jira에서 새 물건을 받아 창고에 안전하게 입고하는 팀이고, Loop B는 입고된 물건을 검사·가공해 매대에 올리는 팀입니다.

1. 왜 굳이 Loop를 둘로 나눴을까?

🚚

Loop A = 입고팀

Jira에서 무엇이 새로 생겼고 바뀌었는지 계속 가져옵니다. OpenCode가 느리더라도 입고팀은 멈추지 않습니다.

🏭

Loop B = 가공·진열팀

입고된 변경분을 OpenCode로 지식화하고 Embedding/FAISS까지 준비한 뒤 실제 검색 매대에 올립니다.

핵심: 입고팀이 먼저 끝나도 가공팀은 아직 일하고 있을 수 있습니다. 이 상태가 정상입니다.

2. 전체 흐름

Loop A · Source Sync Jira → Project 찾기 → 지난 Watermark 이후 변경 후보 읽기 → RAW / ANALYSIS / Knowledge Input → semantic_v2 hash → NEW / CHANGED / UNCHANGED → NEW/CHANGED Work Item 저장 → SOURCE_COMMITTED → Watermark 이동 ↓ 작업 대기열 sync_issue_change ↓ Loop B · Knowledge Processing / Publish 대기 Work Item → OpenCode Knowledge → Review / Evidence → Knowledge DB → BGE-M3 Embedding → FAISS 준비 → Atomic Publish → PUBLISHED

3. Watermark = 책갈피

🔖

“이 Project는 Jira를 어디까지 안전하게 읽었지?”를 기억하는 책갈피입니다. Project마다 따로 있습니다.

지난 Watermark = 10:30 Overlap 5분 → 이번 시작점 = 10:25 이번 Source Run upper = 10:40 모든 Source 후보를 안전하게 처리한 뒤에만 Watermark = 10:40

OpenCode가 아직 지식화를 못 했더라도 Source가 안전하게 입고됐다면 Watermark는 전진할 수 있습니다.

4. SOURCE_COMMITTED와 PUBLISHED

SOURCE_COMMITTED

Jira 변경분을 안전하게 받아 정리했고, 어떤 변경인지 판정하고, Loop B가 처리할 Work Item까지 저장한 상태입니다.

PUBLISHED

Knowledge, Review, Embedding, FAISS까지 준비돼 실제 사용자 검색이 새 버전을 보게 된 상태입니다.

Jira V2 확보 = SOURCE_COMMITTED 검색은 아직 V1 OpenCode / Embedding 처리 중... V2 Publish 완료 → 검색도 V2

5. Backlog = 처리 대기 상자

📦

Loop A가 Loop B보다 빠르면 대기 상자가 쌓입니다. 이것 자체는 장애가 아니지만 계속 늘어나면 Loop B 처리량이 부족하다는 뜻입니다.

Backlog Depth

대기 중인 Work Item 개수.

Oldest Pending Age

가장 오래 기다린 변경분의 대기시간.

Publish Lag

Jira 최신 Source와 검색 최신 버전 사이 차이.

6. 낮에 OpenCode가 느리면?

낮 Loop A: R101 ✓ R102 ✓ R103 ✓ Loop B: 느림 → backlog 증가 밤 Loop A: 계속 독립 실행 Loop B: 처리량 증가 → backlog 감소

2-Loop는 느린 OpenCode를 없애지는 않습니다. 대신 그 병목이 Jira 수집까지 막지 못하게 격리합니다.

7. NEW / CHANGED / UNCHANGED

NEW

처음 보는 jira_id. Work Item을 만듭니다.

CHANGED

같은 jira_id지만 semantic_v2 hash가 다름. 새 Work Item을 만듭니다.

UNCHANGED

같은 semantic state. 새 Work Item 없이 기존 Knowledge/Embedding을 재사용합니다.

8. Project가 안 보이면?

Project Discovery 전체 성공 → 기존 Project B가 목록에 없음 → B = unavailable → 이번 Source Loop에서 skip → Watermark 유지 → 기존 Knowledge/Embedding/FAISS 유지 → 검색 계속 가능

Jira에서 안 보인다는 이유만으로 과거 업무지식을 삭제하지 않습니다.

9. 실패하면 어디부터 다시 하나?

Loop A 실패

Source cursor와 Watermark를 기준으로 같은 Source Run을 재개하거나 새 Run에서 overlap으로 다시 읽습니다.

Loop B 실패

Knowledge/Embedding/Publish 중 실패한 Stage부터 Work Item을 재개합니다. Jira를 다시 다운로드하지 않습니다.

10. Run도 두 종류

source_sync_run → Jira Source 최신화 실행 이력 → sr_ + UUID4 processing_run → OpenCode/Embedding/Publish 실행 이력 → pr_ + UUID4

두 Run은 1:1로 대응하지 않습니다. 한 Processing Run이 여러 Source Run에서 쌓인 backlog를 처리할 수 있습니다.

11. 지금 외우면 되는 다섯 문장

① Jira Source 최신화와 AI 지식화는 서로 기다리지 않는다.
② Source Commit이 끝나면 Work Item을 남기고 Loop A는 계속 간다.
③ Loop B가 느리면 backlog가 쌓이며, 그 자체는 관찰해야 할 상태다.
④ 새 Publish가 완성될 때까지 기존 Published Knowledge를 계속 제공한다.
⑤ 시스템 최신성은 하나의 Run 상태가 아니라 Source Lag + Publish Lag + Backlog로 본다.

12. 아직 남은 결정

V2→V3→V4가 빠르게 쌓였을 때 미시작 V2/V3 Knowledge Work를 모두 처리할지 최신 pending Version만 처리할지는 아직 별도 결정입니다. Source Version은 모두 보존합니다.
