EASY GUIDE · D1~D8 APPROVED

0. 전체를 한 번에 보면

이 Sync 시스템은 매일 회사 문서 보관실을 점검하는 직원과 비슷합니다.
어제 어디까지 확인했는지 책갈피를 기억하고, 경계에서 놓치지 않게 몇 쪽 되돌아가 읽고, 진짜 내용이 바뀐 문서만 새 버전으로 보관합니다. 중간에 실패하면 저장 지점부터 이어서 하고, 새 문서가 완전히 검증되기 전에는 기존 검색 결과를 그대로 제공합니다.
Project 찾기 → 지난 책갈피 확인 → 5분 되돌아가 다시 확인 → 변경 후보 수집 → 실제 내용 지문 비교 → NEW / CHANGED / UNCHANGED → 변경분만 Knowledge 생성 → Embedding / FAISS 준비 → 모두 준비되면 새 검색 결과로 교체

1. 먼저 꼭 기억할 두 문장

Jira는 현재 원본

지금 Jira에 무엇이 존재하고 누가 볼 수 있는지를 보여주는 업무 시스템입니다.

Knowledge DB는 축적 지식

과거 Jira에서 얻은 문제 해결 경험과 업무지식을 장기적으로 보존하는 저장소입니다.

그래서: Jira에서 Issue가 없어졌다고 해서 “그때 배운 해결 방법”까지 버리지 않습니다. 사진 원본이 사라져도 이미 작성한 기술 노트의 가치가 없어지는 것은 아닌 것과 같습니다.

2. Decision 1 — Project마다 Watermark를 하나씩

1
FIXED

Watermark = 책갈피

Project마다 “여기까지 안전하게 확인했다”는 책갈피를 따로 둡니다.

Project A → 10:30 Project B → 09:50 Project C → 10:30

A와 C는 성공했지만 B가 실패했다면 B 때문에 전체를 되돌리지 않습니다. B의 책갈피만 09:50에 남겨두고 다음에 거기서 이어갑니다.

왜 Project별인가? 서로 다른 세 권의 책을 읽는데 책갈피를 하나만 쓰면 어느 책을 어디까지 읽었는지 알 수 없습니다. Project마다 하나씩 두는 게 자연스럽습니다.

3. Decision 2 — 5분 Overlap

2
FIXED

Overlap = 책갈피보다 몇 쪽 앞에서 다시 읽기

지난 Watermark에서 정확히 시작하지 않고 5분 앞에서부터 다시 확인합니다.

지난 Watermark = 10:30 Overlap = 5분 다음 시작 = 10:25

10:25~10:30 데이터를 다시 볼 수도 있습니다. 하지만 중복은 나중에 지문 비교로 없앨 수 있습니다. 반대로 한 건을 놓치면 그 존재 자체를 모를 수 있습니다.

우리가 선택한 것: “조금 다시 읽는 수고”를 감수하고 “한 줄을 영원히 놓치는 위험”을 줄입니다.

또 이번 Sync가 책임질 끝 시각도 먼저 고정합니다. 그래서 실행 중 Jira가 계속 바뀌어도 이번 작업 범위가 흔들리지 않습니다.

4. Decision 3 — NEW / CHANGED / UNCHANGED

3
FIXED

updated는 초인종, source_hash는 실제 확인

Jira의 updated 시간은 “한번 확인해보세요”라는 신호일 뿐입니다.

jira_id 처음 봄 → NEW jira_id 있음 + 지문 다름 → CHANGED jira_id 있음 + 지문 같음 → UNCHANGED

NEW

처음 보는 Issue. 전체 Knowledge 파이프라인 실행.

CHANGED

같은 Issue지만 실제 내용이 달라짐. 새 Version 생성.

UNCHANGED

Overlap 때문에 다시 봤지만 실제 내용은 같음. 기존 결과 재사용.

Issue Key보다 jira_id가 중요한 이유: 사람 이름표가 바뀌어도 주민등록번호가 같으면 같은 사람인 것과 비슷합니다.

5. Decision 4 — source_hash semantic_v2

4
FIXED

source_hash = 내용의 지문

실제 업무 의미가 달라졌는지를 판별하는 지문입니다.

Description + Status / Priority + Comments + Attachment metadata + Relationships + Custom Fields ↓ semantic_v2 hash

반면 updated_at은 hash에서 뺐습니다. 내용은 그대로인데 “마지막 수정 시각”만 달라져 새 Version을 만드는 낭비를 막기 위해서입니다.

쉽게: 책 내용이 똑같은데 도서관에서 바코드를 다시 찍은 시간만 바뀌었다고 새 판본으로 보지 않습니다.

created_at은 실제 사실이 될 수 있으므로 남깁니다. 또 hash 규칙 이름 자체도 semantic_v2로 기록해 나중에 규칙이 바뀌었는지 알 수 있게 합니다.

6. Decision 5 — Checkpoint / Resume

5
FIXED

Checkpoint = 게임 세이브

중간에 실패해도 처음부터 다시 하지 않습니다.

Jira Source COMPLETED Knowledge COMPLETED Embedding FAILED FAISS PENDING 재시작 → Embedding부터
게임처럼: 10스테이지까지 클리어했는데 11스테이지에서 죽었다고 1스테이지부터 다시 하지 않습니다.

가능하면 같은 Sync Run을 그대로 이어서 재개합니다. 같은 Run을 살릴 수 없다면 마지막 committed Watermark에서 5분 Overlap을 두고 새 Run으로 안전하게 복구합니다.

성공한 Project나 Stage는 되돌리지 않습니다. 실패한 것만 다시 합니다.

7. Decision 6 — Project가 사라져도 Knowledge는 남긴다

6
FIXED

Project Registry = Project 주소록

지금까지 만난 Project를 project_id 기준으로 기억합니다.

오늘 Discovery A 보임 → Sync B 안 보임 → 이번 Sync에서 Skip C 보임 → Sync B의 기존 Knowledge → 그대로 검색 가능
핵심: 퇴사한 직원의 과거 회고록이 여전히 회사에 도움이 될 수 있는 것처럼, Jira에서 사라진 Issue의 해결 경험도 여전히 지식으로 가치가 있습니다.

Project가 다시 보이면 처음부터 다시 받지 않습니다. 남겨둔 Watermark에서 5분 앞부터 Catch-up Delta Sync를 합니다.

삭제 여부를 굳이 찾기 위한 Reconcile은 필수가 아닙니다. 삭제됐어도 Knowledge를 버리지 않을 것이기 때문입니다.

8. Decision 7 — Source Commit과 Publish를 나눈다

7
FIXED

창고 입고와 매대 진열은 다르다

Jira 데이터를 안전하게 받아둔 것과 새 Knowledge를 실제 검색에 내놓은 것은 다른 완료입니다.

SOURCE_COMMITTED

최신 Jira 원재료를 안전하게 창고에 넣은 상태.

PUBLISHED

Knowledge·Evidence·Embedding·FAISS가 모두 준비되어 매대에 진열된 상태.

현재 검색 = V1 Jira V2 수집 완료 → SOURCE_COMMITTED V2 Knowledge 생성 중 / 실패 가능 → 아직 검색은 V1 유지 V2 전체 준비 완료 → PUBLISHED → 검색을 V2로 전환
왜 이렇게 하나? 새 제품을 포장 중인데 기존 매대 상품부터 치우면 손님은 아무것도 살 수 없습니다. 새 제품이 완전히 준비될 때까지 기존 제품을 계속 제공합니다.

그래서 “DB는 V2인데 FAISS는 V1” 같은 반쯤 갱신된 상태를 사용자에게 보여주지 않습니다.

9. Decision 8 — completed / partial / failed

8
FIXED

이번 Sync가 얼마나 일을 끝냈는지 표현

이 상태는 기존 Knowledge 서비스가 살아 있는지와는 별개입니다.

상태쉽게 말하면
COMPLETED이번에 해야 할 Source와 Publish 작업을 모두 끝냄. 변경 0건이어도 정상 completed.
PARTIAL일부는 안전하게 성공했지만 남은 실패/미완료가 있음.
FAILEDProject Discovery를 신뢰할 수 없거나 이번 Source에서 의미 있는 진척을 하나도 못 만듦.
이번 Sync = FAILED 그렇다고 기존 Knowledge 서비스 = FAILED 가 아님 기존 Published Knowledge는 계속 검색 가능

안 보이는 Project는 실패로 세지 않습니다. 그냥 이번 Sync에서 Skip합니다.

10. 가상의 하루를 끝까지 따라가 보기

09:00 Sync 시작 upper = 09:00 고정 Project A watermark = 08:00 lower = 07:55 후보 3개 발견 ABC-1 → hash 같음 → UNCHANGED ABC-2 → hash 다름 → CHANGED ABC-3 → 처음 봄 → NEW Source 수집 전부 성공 → SOURCE_COMMITTED → A watermark = 09:00 ABC-2 Knowledge 생성 성공 ABC-3 Knowledge 생성 실패 ABC-2 Embedding / FAISS Publish 성공 ABC-3는 Knowledge failed checkpoint 이번 Run → 일부 성공 + 남은 실패 → PARTIAL 사용자 검색 → ABC-2는 새 Published Knowledge 사용 → ABC-3는 기존 Published Knowledge가 있으면 기존 것을 계속 사용 → 다음 Resume에서 ABC-3 Knowledge부터 재시도

11. 최종 기억법

놓치지 않기

Project별 Watermark + 5분 Overlap + fixed upper

낭비하지 않기

jira_id + semantic_v2 hash로 실제 변경만 처리

실패에 강하게

Checkpoint/Resume + Source Commit/Publish 분리

지식을 버리지 않기

Jira 삭제/비노출 ≠ Knowledge 삭제

서비스를 끊지 않기

새 Publish가 준비될 때까지 기존 Published Knowledge 유지

상태를 정확히 말하기

completed / partial / failed를 이번 Run 진척 기준으로 구분
