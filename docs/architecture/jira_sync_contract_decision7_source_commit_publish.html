D7 · FIXED · TWO-LOOP BOUNDARY · 2026-08-28

SOURCE_COMMITTED와 PUBLISHED는 다른 완료 경계입니다.

D9 2-Loop 채택으로 D7은 물리 실행 경계가 되었습니다. Source Commit은 Loop A, Publish는 Loop B가 담당하며, 두 Loop 사이에는 durable Work Item과 Source Ready Gate가 있습니다.

Loop A · SOURCE_COMMITTED

Jira Source 확보 → RAW / ANALYSIS / Knowledge Input durable → semantic_v2 hash → NEW / CHANGED / UNCHANGED 판정 → NEW/CHANGED Work Item row durable → Project Source window 전체 완료 → source_committed + Watermark → Work Item Source Ready Gate open

Loop B가 소비 가능한 정확한 조건

durable Work Item 존재만으로는 부족 Loop B eligible iff last_source_committed_run_id IS NOT NULL AND last_source_committed_run_id = last_observed_source_run_id

Candidate 처리 중 Work Item row를 먼저 저장할 수 있으므로 Project 전체 Source Commit 전에는 Loop B가 해당 row를 가져가면 안 됩니다.

왜 필요한가?

ABC-1 Source 저장 + Work row 생성 ABC-2 Source 실패 Project 전체 Source Commit 실패 Gate 없음 → Loop B가 ABC-1을 먼저 처리할 수 있음 X Gate 있음 → ABC-1 row는 durable하지만 unready → Project Source Commit 성공 후에만 claim 가능

T3 Project Commit · 같은 Transaction

1. source_project_run.source_status = source_committed 2. project_state.committed_watermark = upper 3. 현재 Project/Source Run에서 관찰한 Work Item last_source_committed_run_id = current source_run_id last_source_committed_at = now COMMIT

이 세 상태가 함께 확정돼야 Loop A가 Loop B에 작업을 넘긴 것으로 봅니다.

Loop B · PUBLISHED

source-ready Work Item → OpenCode Knowledge → Review / Evidence → Knowledge DB → BGE-M3 Embedding → FAISS staging / mapping → 검증 → actual Retrieval atomic switch → State publish_status = published

두 Loop 사이에서 허용되는 상태

Source Head = V2 Published Head = V1 Loop A completed 가능 Loop B V2 pending 가능 사용자 Retrieval = V1 유지 V2 actual Publish 후 Published Head = V2

이 상태는 오류가 아니라 정상적인 eventual consistency 구간입니다. Source Lag, Publish Lag, Backlog로 관찰합니다.

과거 semantic state 재등장

A→B→A처럼 기존 A Work Item이 다시 관찰되면 last_observed_source_run_id가 새 Source Run으로 이동해 Ready Gate가 다시 닫힙니다. 새 Project Source Commit 후 gate를 다시 열고 기존 Knowledge/Embedding을 재사용해 Publish만 재실행할 수 있습니다.

Half-Publish 금지

Knowledge DB, Embedding, FAISS/Mapping이 서로 다른 세대로 노출되지 않게 staging/검증 후 actual Retrieval을 전환합니다. State의 published 표시는 실제 전환보다 먼저 기록할 수 없습니다.
