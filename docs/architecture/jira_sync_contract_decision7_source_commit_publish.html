D7 · FIXED · CURRENT TWO-LOOP BOUNDARY · 2026-08-31

SOURCE_COMMITTED와 PUBLISHED는 다른 완료 경계입니다.

Source Commit은 Loop A, Publish는 Loop B가 담당합니다. 현재 정책에서는 두 Loop 사이에 durable Work Item과 Source Ready + Latest 조건이 있습니다.

Loop A · SOURCE_COMMITTED

Jira Source 확보 → RAW / ANALYSIS / Knowledge Input durable → semantic_v2 (Source 변경 판별 프로필) → NEW / CHANGED / UNCHANGED 판정 → NEW/CHANGED Work Item durable → Project Source window 전체 완료 → source_committed + Watermark → 새 Work Source Ready → 같은 Issue의 이전 미완료 Work supersede

Loop B가 소비 가능한 정확한 조건

durable Work Item 존재만으로는 부족 Loop B eligible iff last_source_committed_run_id IS NOT NULL AND last_source_committed_run_id = last_observed_source_run_id AND work_status IN ('pending','failed') AND superseded_by_work_item_id IS NULL

Candidate 처리 중 row를 먼저 저장할 수 있으므로 Project Source Commit 전에는 가져가면 안 되고, Source Commit 후에도 더 최신 Work에 밀린 row는 가져가면 안 됩니다.

왜 필요한가?

ABC-1 Source 저장 + Work row 생성 ABC-2 Source 실패 Project Source Commit 실패 Ready Gate 없음 → ABC-1을 잘못 처리할 수 있음 Ready Gate 있음 → ABC-1 row는 durable하지만 unready → Project Source Commit 성공 후에만 후보 그 후 더 최신 ABC-1 상태가 들어오면 → 이전 미완료 Work는 superseded → 최신 Work만 처리

Project Commit · 같은 State DB Transaction

1. source_project_run.source_status = source_committed 2. project_state.committed_watermark = upper 3. 새 Work Item last_source_committed_run_id = current source_run_id last_source_committed_at = now 4. 같은 jira_id의 이전 미완료 Work work_status = superseded superseded_by_work_item_id = new work 5. COMMIT

Ready와 latest 상태가 같은 순간에 확정돼야 Loop A가 Loop B에 올바른 작업을 넘긴 것으로 봅니다.

Loop B · PUBLISHED

latest + source-ready Work Item → OpenCode Knowledge → latestness re-check → Review / Evidence → Knowledge DB → BGE-M3 Embedding → FAISS staging / mapping → latestness re-check → actual Retrieval atomic switch → State publish_status/work_status = published

두 Loop 사이에서 허용되는 상태

Source Head = 상태 C Published Head = 상태 A Loop A completed 가능 Loop B 상태 C pending 가능 사용자 Retrieval = 상태 A 유지 상태 C actual Publish 후 Published Head = 상태 C

이 상태는 오류가 아니라 정상적인 eventual consistency 구간입니다.

Half-Publish 금지

Knowledge DB, Embedding, FAISS/Mapping이 서로 다른 세대로 노출되지 않게 staging/검증 후 actual Retrieval을 전환합니다. State의 published 표시는 실제 전환보다 먼저 기록할 수 없습니다.
