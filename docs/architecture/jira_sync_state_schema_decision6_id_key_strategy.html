SYNC STATE / PROJECT REGISTRY · SCHEMA DECISION 6 · 2026-08-27

무엇은 Jira ID를 쓰고,
무엇은 새 ID를 만들까?

Operational State의 identity를 외부 원본 identity, 실행 사건 identity, 내용 기반 Work Item identity로 구분합니다.

S1~S5 FIXED · S6 REVIEWING · ID / PK / FK / UNIQUE

1. ID를 세 종류로 나눕니다

외부 원본 Identity

Jira가 이미 제공하는 project_id, jira_id. 새로 변형하지 않습니다.

실행 Identity

한 번 실행된 Sync Run은 매번 다른 사건이므로 랜덤 고유 ID를 씁니다.

내용 Identity

같은 Jira semantic change는 여러 Run에서 다시 봐도 같은 Work Item이어야 하므로 deterministic ID를 씁니다.

2. sync_run_id · 랜덤 사건 ID

현재 MVP의 Run ID는 UTC 초 단위 timestamp라 같은 초에 두 실행이 시작되면 충돌 여지가 있습니다. Operational Sync는 이 약점을 제거합니다.

추천

sync_run_id = "sr_" + uuid4.hex 예 sr_0f4a7f0cd70a48aaabeb4e529c8b71d6

실행 시각은 started_at에 따로 저장합니다. Run ID 자체에 시간 의미를 넣지 않습니다.

왜 UUID4인가? 시간 정밀도/시계 상태에 의존하지 않고, 별도 coordination 없이 동시에 여러 실행이 생겨도 충돌 위험이 사실상 없습니다. 정렬은 started_at index로 해결합니다.

3. work_item_id · deterministic semantic-change ID

D5에서 downstream Work Item identity는 jira_id + source_hash + source_hash_profile로 이미 고정했습니다.

STATE_ID_SCHEMA_VERSION = 1 kind = "sync_issue_change" material = { jira_id, source_hash, source_hash_profile } canonical JSON → SHA-256 full lowercase hex → prefix "sw_" work_item_id = sw_<64 hex>

같은 semantic change를 R100에서 발견하고 R101에서 다시 만나도 같은 work_item_id가 나와 기존 Work Item을 Resume합니다.

기존 프로젝트와 일치: Knowledge ID도 canonical JSON + ID schema version + full SHA-256 + prefix를 사용합니다. State Work Item도 같은 철학을 따르되 별도 State ID namespace를 둡니다.

4. project_state의 PK

PRIMARY KEY = project_id

current_key는 PK나 UNIQUE로 사용하지 않습니다. Project Key는 바뀔 수 있고, 과거 Project가 사라진 뒤 같은 Key가 다른 project_id에서 재사용될 가능성도 열어둡니다.

정체성

project_id = authoritative identity.

표시값

current_key, current_name = mutable metadata.

5. sync_project_run은 복합 PK

PRIMARY KEY (sync_run_id, project_id)

“한 Run에서 한 Project 작업은 최대 한 행”이라는 실제 관계를 그대로 Key로 사용합니다. 별도 sync_project_run_id surrogate key를 만들 이유가 없습니다.

6. sync_issue_change의 PK + UNIQUE

PRIMARY KEY (work_item_id) UNIQUE ( jira_id, source_hash, source_hash_profile )

PK는 읽기 쉬운 prefixed logical ID를 사용하고, identity material 자체에도 UNIQUE를 걸어 ID 생성 코드 오류가 있어도 DB가 중복 semantic change를 막도록 이중 방어합니다.

project_id를 Work Item identity에 넣지 않음: D5에서 고정한 identity는 jira_id + source_hash + profile입니다. Issue가 Project를 이동하더라도 같은 Jira identity와 semantic state라면 같은 작업으로 다룹니다.

8. Knowledge DB 참조는 물리 FK를 걸지 않습니다

sync_issue_change.issue_version_id sync_issue_change.knowledge_generation_id → Knowledge DB의 logical ID를 저장 → cross-database SQLite FK 없음

S1의 Control Plane / Data Plane 분리를 유지합니다. Resume 시 실제 Knowledge DB에 해당 ID가 존재하는지 애플리케이션 검증으로 확인합니다.
