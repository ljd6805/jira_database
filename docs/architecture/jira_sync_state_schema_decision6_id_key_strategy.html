SYNC STATE / PROJECT REGISTRY · SCHEMA DECISION 6 · FINAL · 2026-08-27

외부 ID, 실행 ID, 내용 ID를
서로 섞지 않는다

Jira 원본 identity는 그대로 사용하고, 실행 사건은 랜덤 ID, semantic change Work Item은 deterministic ID를 사용합니다.

S6 FIXED · ID / PK / FK / UNIQUE STRATEGY

1. 세 종류의 Identity

외부 Identity

project_id, jira_id는 Jira 값을 그대로 사용합니다.

실행 Identity

sync_run_id = sr_ + UUID4 full hex. 매 Run마다 새 값입니다.

내용 Identity

work_item_id는 같은 semantic change면 언제 발견해도 같은 deterministic 값입니다.

2. 최종 Key

sync_run PK = sr_ + UUID4 full hex project_state PK = Jira project_id sync_project_run PK = (sync_run_id, project_id) sync_issue_change PK = sw_ + deterministic SHA-256 UNIQUE = (jira_id, source_hash, source_hash_profile)

3. Work Item ID Material

STATE_ID_SCHEMA_VERSION = 1 kind = sync_issue_change material = { jira_id, source_hash, source_hash_profile } canonical JSON → full SHA-256 lowercase hex → sw_ prefix

Project 이동과 무관하게 같은 jira_id + semantic state면 같은 Work Item을 Resume합니다.

4. FK 원칙

범위규칙
State DB 내부sync_run, project_state 참조는 SQLite physical FK로 강제합니다.
Knowledge DBissue_version_id, knowledge_generation_id는 logical ID만 저장하고 cross-DB physical FK는 만들지 않습니다.

5. Key로 사용하지 않는 값

Mutable

project_key, issue_key는 표시값이며 PK/identity로 쓰지 않습니다.

Operational signal

started_at, jira_updated_at, FAISS position은 stable identity가 아닙니다.

6. S6 최종 규칙

확정: 외부 원본 identity는 보존, Run은 UUID4 기반 사건 identity, Work Item은 deterministic semantic identity를 사용합니다. State DB 내부 참조만 물리 FK로 연결합니다.
