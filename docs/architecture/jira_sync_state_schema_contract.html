Sync State Schema Contract
FROZEN v2

Source Sync Loop와 Knowledge Processing/Publish Loop를 독립 실행하기 위해 v1의 단일 sync_run 모델을 폐기하고 두 종류의 Run identity와 durable backlog를 명시적으로 분리합니다.

CURRENT SOURCE OF TRUTH · STATE_SCHEMA_VERSION = 2 · IMPLEMENT THIS

1. v1에서 v2로 바뀐 이유

v1 · 구현 전 baseline sync_run = Source + Publish 집계 문제 → Source Run과 OpenCode Processing Run은 같은 사건이 아님 → LLM 지연이 큰 환경에서 독립 cadence/관찰이 어려움 v2 · 현재 source_sync_run = Loop A processing_run = Loop B sync_issue_change = 두 Loop 사이 durable backlog

v1은 실제 배포되지 않았으며 역사 문서로만 보존합니다.

2. 저장소 책임

Control Plane · collector.db

두 Loop의 Run, Project Watermark, Source cursor, durable Work Item, processing checkpoint/error를 저장합니다.

Data Plane · Knowledge DB

Issue Version, Knowledge Generation/Attempt/Item/Evidence/Review를 보존합니다.

원칙: Source 최신화와 Knowledge 최신화를 분리하지만, 두 상태를 stable ID로 추적 가능해야 합니다.

3. State Schema v2 Domain Table · 5개

source_sync_run

Loop A 실행.

project_state

Project current state / Watermark.

source_project_run

Source Run×Project 이력/cursor.

sync_issue_change

durable semantic Work Item/backlog.

processing_run

Loop B 실행/처리량.

state_schema_migration은 5개 Domain Table과 별개의 기술 메타 테이블입니다.

4. Loop A · Source State

source_sync_run → source_run_id = sr_ + UUID4 → started_at / finished_at → fixed upper_bound → discovery_status → source_status → run_status project_state → project_id → key/name/visibility → committed_watermark → last source success source_project_run → (source_run_id, project_id) → operation_kind → lower/upper → candidate/new/changed/unchanged counts → cursor_updated_at + cursor_jira_id → source_status

v1의 publish_status는 Source Run에서 제거합니다.

5. Loop B · Processing State

processing_run → processing_run_id = pr_ + UUID4 → started_at / finished_at → run_status = running|completed|partial|failed → selected_count → published_count → failed_count → backlog_before / backlog_after (nullable) → error_summary sync_issue_change → last_processing_run_id → processing_run → knowledge_status → embedding_status → publish_status

Processing Run은 Source Run과 1:1 관계가 아닙니다. 한 Processing Run이 여러 Source Run에서 만들어진 backlog를 처리할 수 있습니다.

6. Durable Work Item identity

work_item_id = sw_ + deterministic SHA-256 identity material jira_id + source_hash + source_hash_profile UNIQUE(jira_id, source_hash, source_hash_profile)

같은 semantic state를 다시 만나면 새 row를 만들지 않고 기존 Work Item을 재사용합니다.

필드v2 의미
first_discovered_source_run_id이 semantic state를 처음 발견한 Loop A Run
last_observed_source_run_id가장 최근에 같은 semantic state를 다시 본 Loop A Run
last_processing_run_id가장 최근 Loop B 처리 Run
last_published_at과거 Publish 성공 이력. 재활성화해도 보존 가능

7. Crash Safety · Loop별로 분리

Loop A

actual Source durable → Work Item/count/cursor State commit Project complete → source_committed + committed_watermark = upper → SAME transaction

Loop B

Knowledge/Embedding actual output first → State completed second actual Retrieval atomic publish first → State published second

두 Loop 사이에 분산 Transaction을 만들지 않습니다. durable Work Item이 비동기 경계입니다.

8. Run 상태 의미

Runcompletedpartialfailed
source_sync_runDiscovery 성공 + 모든 visible Project Source 책임 완료일부 Source durable progress + 일부 실패Discovery 불신뢰 또는 필요한 Source progress 없음
processing_run선택 작업 모두 완료 또는 선택 작업 0일부 durable processing progress + 일부 실패/미완료의미 있는 processing progress 없이 실패

시스템 전체에는 단일 completed/failed를 부여하지 않습니다. Source Lag, Publish Lag, Backlog가 실제 운영 상태입니다.

9. Migration Contract v2

STATE_SCHEMA_VERSION = 2 PRAGMA user_version = 2 legacy collector.db / user_version 0 → fingerprint 확인 → consistent backup → explicit migration only → legacy table/data 보존 → v2 tables additive 생성 → validation/regression PASS → cutover user_version = 1 발견 → 자동 변환 금지 → v1은 never-deployed design baseline이므로 운영자 확인 후 explicit path
