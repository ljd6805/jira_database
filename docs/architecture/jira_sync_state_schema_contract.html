4. Work Item identity는 그대로

work_item_id = sw_ + deterministic SHA-256 identity material = jira_id + source_hash + source_hash_profile UNIQUE(jira_id, source_hash, source_hash_profile)

중간 Version을 supersede해도 Work Item identity나 Source Version을 삭제하지 않습니다.

5. Work Lifecycle · v3 신규

work_status pending running published failed superseded
상태의미
pending최신 Source Ready Work, 아직 미처리
runningLoop B가 현재 처리 중
published실제 Retrieval Publish까지 완료
failed최신 Work였지만 처리 실패, 재시도 가능
superseded더 최신 Source Version이 Source Commit되어 더 이상 AI 처리 가치가 없음
superseded_by_work_item_id superseded_at supersede_reason = newer_source_version

6. Source Ready + Latest Gate

Loop B claim 가능 조건 last_source_committed_run_id IS NOT NULL AND last_source_committed_run_id = last_observed_source_run_id AND work_status IN ('pending','failed') AND superseded_by_work_item_id IS NULL

즉 Source Commit 완료뿐 아니라 같은 Jira Issue 중 현재 최신 Work여야 합니다.

7. T3 Source Commit에서 supersede도 함께 처리

새 V4 Work Item이 Project SOURCE_COMMITTED SAME State DB transaction 1. source_project_run.source_status = source_committed 2. project_state.committed_watermark = upper 3. V4 last_source_committed_run_id = current 4. 같은 jira_id의 이전 미완료 Work work_status IN (pending, failed, running) → work_status = superseded → superseded_by_work_item_id = V4 → superseded_at = now 5. COMMIT

이미 Published된 과거 Work는 History로 남기며 이 supersede 대상에 포함하지 않습니다.

8. Processing 중 새 Version이 들어오는 경우

V2 running → V3 SOURCE_COMMITTED → V2 work_status = superseded → OpenCode V2 응답 도착 → Worker 최신성 re-check → superseded 확인 → Active Knowledge 저장/Embedding/Publish 중단 → stale_inflight_detected log

API 호출 자체의 강제 취소는 기본 정책이 아닙니다. 다만 Publish 전 최신성 검사는 반드시 다시 수행합니다.

9. Stage 상태와 work_status의 역할

work_status

이 Work를 지금 처리해야 하는가? 최신성/queue lifecycle.

knowledge / embedding / publish_status

실제 각 Stage가 어디까지 갔는가? 실행 진단/Resume.

예를 들어 처리 중 superseded되면 work_status=superseded이면서 knowledge_status=running일 수 있습니다. 외부 호출이 돌아온 뒤 worker가 stale 처리 로그를 남기고 종료합니다.
