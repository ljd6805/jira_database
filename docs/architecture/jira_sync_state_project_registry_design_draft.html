Sync State / Project Registry
DB Schema 설계 초안

FROZEN Sync Contract D1~D8을 SQLite에 어떤 상태로 저장할지 설계합니다. 이 문서는 다음 구현 Milestone의 입력이며 아직 Schema를 Freeze하거나 코드를 변경하지 않습니다.

DRAFT · DESIGN ONLY · NO IMPLEMENTATION YET

1. 왜 별도 상태 DB 구조가 필요한가?

현재 MVP StateStore는 같은 Collection Run 안의 Project/Issue resume에는 충분하지만, 운영 서비스에는 Run을 넘어 Project를 기억하고 Watermark와 downstream 미완료 작업을 계속 추적해야 합니다.

현재 MVP가 기억하는 것 Run R100 안에서 → Project A completed → Project B partial → Issue X completed 운영에서 추가로 기억해야 하는 것 Run이 끝난 뒤에도 → Project A의 stable project_id → Project A watermark → Project가 visible / unavailable인지 → jira_id + source_hash Work Item이 어디까지 Publish됐는지 → 다음 Run에서 어디서 이어갈지

2. 추천하는 5개 핵심 상태 Entity

① sync_run

한 번의 운영 Sync 실행 자체.

② project_registry

지금까지 만난 Project 주소록.

③ project_sync_state

Project별 장기 Watermark와 최근 Source 상태.

④ sync_project_run

이번 Run에서 Project 하나를 어떻게 처리했는지.

⑤ sync_issue_change

NEW/CHANGED Work Item과 downstream 진행 상태.

역할 분리: Registry는 “누구인가”, Sync State는 “어디까지 읽었나”, Run은 “이번 실행에서 무슨 일이 있었나”, Issue Change는 “어떤 변경이 어디까지 반영됐나”를 답합니다.

3. Entity 관계

project_registry 1 ───── 1 project_sync_state │ │ 1 └──── N sync_project_run N ───── 1 sync_run │ │ 1 └──── N sync_issue_change sync_issue_change → jira_id + source_hash + hash_profile 기반 Work Item → Knowledge / Embedding / Publish checkpoint를 가짐

9. Source Head와 Published Head는 어디에 둘까?

D7은 최신 Source와 현재 검색에 제공되는 상태를 분리합니다. 기존 Knowledge DB의 active Generation 구조를 최대한 재사용하는 것이 좋습니다.

Source Head

최신 안전 Source는 기존 issue_version + 새로운 sync change state로 알 수 있습니다.

Published Head

기존 knowledge_generation.status = active와 retrieval artifact pointer를 재사용/확장합니다.

추천: 같은 정보를 Sync State DB에 중복 저장하기보다 기존 Knowledge DB identity를 참조해 “진행 상태”만 추가하는 방향을 우선 검토합니다.

10. 기존 StateStore와의 관계

재사용할 것

Run/Project/Issue checkpoint 개념, SQLite transaction, WAL, 실패 격리, artifact 기록.

확장할 것

project_id 기반 Registry, cross-run Watermark, fixed lower/upper, semantic change Work Item, downstream checkpoint, D8 집계.

기존 MVP DB의 의미를 억지로 바꾸기보다 운영 상태 Schema를 확장하거나 별도 migration을 명확히 두는 편이 안전합니다.

11. 다음 검토에서 확정해야 할 것

물리 DB 위치

Collector State DB에 합칠지 Knowledge DB에 합칠지, 운영 State 전용 DB를 둘지.

Status enum

Project/Stage 상태값의 최종 이름.

Work Item identity

deterministic ID를 쓸지 surrogate ID + unique key를 쓸지.

Transaction boundary

Source Commit과 Watermark 갱신을 한 transaction으로 묶는 정확한 방법.

Published pointer

FAISS/Mapping artifact를 atomic하게 전환할 물리 방식.

Migration

기존 pilot state와 Knowledge DB를 어떻게 보존하며 운영 Schema로 이동할지.

12. 현재 제안의 한 줄 요약

sync_run = 이번 실행 project_registry = Project 주소록 project_sync_state = Project별 장기 Watermark sync_project_run = 이번 Run에서 Project 하나의 Source 작업 sync_issue_change = NEW/CHANGED가 Knowledge→Embedding→Publish 어디까지 갔는지
