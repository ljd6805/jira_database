1. S3의 원칙

다음 판단에 필요한 값은 저장

Watermark, 고정 upper, Project visibility, Work Item stage처럼 다음 실행이 직접 읽는 값은 durable하게 저장합니다.

계산 가능한 값은 과하게 중복하지 않음

Knowledge DB에 이미 있는 업무지식 본문이나 Generation 내용을 State DB에 복제하지 않습니다.

Control Plane 원칙: State DB에는 “무엇이 만들어졌는가”보다 “어디까지 진행됐고 다음에 어디서 이어갈 것인가”를 저장합니다.

2. 네 테이블을 한눈에

중요한 추천: UNCHANGED는 sync_issue_change row를 만들지 않습니다. 중복 후보를 다시 봤다는 사실은 sync_project_run.unchanged_count에 남기고, downstream Work Item은 NEW/CHANGED에만 만듭니다.

7. 상태 이름을 왜 다 똑같이 하지 않나?

일반 Stage

pending → running → completed/failed가 가장 단순합니다.

Contract 경계는 이름을 보존

Project Source의 성공은 단순 completed가 아니라 source_committed, Retrieval의 성공은 published라고 기록해 D7 경계를 명확히 합니다.

Source 성공 = source_committed Knowledge = completed Embedding = completed Publish 성공 = published

8. S3 추천 결론

필수 상태는 최소하지만 Resume에 충분하게 둔다.

sync_run → fixed upper + discovery/source/publish/run aggregate project_state → identity + visibility + committed_watermark sync_project_run → Run × Project의 exact lower/upper + Source 결과 sync_issue_change → NEW/CHANGED만 durable Work Item → discovered_run과 last_attempt_run을 분리 → Knowledge / Embedding / Publish checkpoint
아직 S3는 FIXED 아님. 승인하면 이 컬럼/enum을 Schema Contract에 고정하고 다음 S4에서 transaction boundary와 Watermark commit의 원자성을 결정합니다.
