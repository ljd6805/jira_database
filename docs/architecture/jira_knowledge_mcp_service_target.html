TARGET ARCHITECTURE · 2026-08-27

최종 목표는 로컬 MCP가 아니라
팀이 함께 쓰는 중앙 MCP 서비스입니다.

현재 local stdio 연결은 OpenCode 호환성과 Tool 사용성을 검증하기 위한 Pilot입니다. 실제 서비스에서는 Jira Knowledge DB, FAISS, BGE-M3 설정을 중앙 서버가 소유하고 팀원의 OpenCode는 Remote MCP URL에 접속하는 구조를 목표로 합니다.

LOCAL STDIO = PILOT · REMOTE MCP = SERVICE TARGET
한 줄 요약

무엇이 달라지나?

현재 Pilot 팀원 PC └─ jira_database clone ├─ .env ├─ SQLite / FAISS └─ local stdio MCP ↓ OpenCode 최종 서비스 팀원 OpenCode ↓ Remote MCP / HTTPS 중앙 jira-knowledge MCP 서버 ├─ .env ├─ SQLite ├─ FAISS └─ BGE-M3 API
핵심:

팀원은 Jira Knowledge 저장소와 데이터 artifact를 각자 복제하지 않습니다. 중앙 서비스의 MCP 주소와 필요한 인증 정보만 알면 됩니다.

2. 왜 local stdio를 최종 서비스로 쓰지 않나?

팀원마다 환경 준비 필요

Python package, DB, FAISS, .env를 각 PC에 설치하면 배포와 버전 관리가 어려워집니다.

데이터 복제 문제

Jira 지식 DB와 vector artifact가 사용자 PC마다 복제되면 갱신 시점과 보안 경계가 복잡해집니다.

업데이트 어려움

MCP 코드나 index를 바꿀 때 모든 사용자 환경을 다시 맞춰야 합니다.

운영 관찰 어려움

중앙 서비스가 아니면 호출량, 오류, latency, 버전 상태를 한곳에서 보기 어렵습니다.

4. Transport 방향

1순위 · Streamable HTTP

OpenCode 1.18.12의 Remote MCP client가 먼저 시도하는 transport이며, 현재 MCP Python SDK 2.1.1 서버도 직접 지원합니다.

호환 fallback · SSE

OpenCode 1.18.12는 Streamable HTTP 연결이 실패하면 SSE도 시도합니다. 필요할 경우 호환 경로로 검증할 수 있습니다.

OpenCode 1.18.12 Remote MCP 1. Streamable HTTP 시도 2. 실패 시 SSE 시도 MCP Python SDK 2.1.1 MCPServer run("stdio") run("sse") run("streamable-http")

6. 서버 .env의 위치

앞서 확정한 .env 정책은 중앙 서비스에서도 유지합니다. 차이는 팀원 PC가 아니라 중앙 MCP 서버의 배포 디렉터리에 존재한다는 점입니다.

중앙 서버 .env JIRA_KNOWLEDGE_DB_PATH=... JIRA_RETRIEVAL_ARTIFACT_DIR=... BGE_M3_ENDPOINT=... BGE_M3_API_KEY=... optional BGE_M3_HEADERS_JSON=... optional
아직 인증 방식은 Freeze하지 않음

팀원 인증은 Bearer header, 사내 reverse proxy, OAuth 등 운영 환경을 보고 결정합니다. 인증 없이 팀 공용 네트워크에 그대로 노출하는 구조는 목표가 아닙니다.

7. OpenCode의 최종 설정 모습

정확한 URL과 인증은 서비스 구현 때 결정하지만, 팀원 측 설정은 개념적으로 다음처럼 단순해지는 것이 목표입니다.

{ "mcp": { "jira-knowledge": { "type": "remote", "url": "https://jira-knowledge-mcp.example.internal/mcp", "timeout": 30000 } } }

실제 사내 URL이나 token/header 값은 공개 저장소 문서에 넣지 않습니다.

8. 진행 순서

M11 · OpenCode Integration Pilot 현재 local stdio 연결 PASS ↓ Tool 2개 discovery / 실제 call ↓ 일반 질문의 자동 Tool 선택 ↓ Knowledge + Evidence 기반 답변 확인 ↓ M11 완료 ↓ Post-M11 · Remote MCP Service Streamable HTTP 서버화 → 인증 / TLS → 팀원 OpenCode remote 연결 → logging / health / concurrency → 팀 Pilot
왜 이 순서인가?

Tool 동작과 Agent 사용성이 먼저 검증되어야, 서버화 후 문제가 생겼을 때 기능 문제와 네트워크/인증/운영 문제를 분리해서 볼 수 있습니다.

9. 아직 결정하지 않은 것

인증 방식

Bearer / OAuth / 사내 Proxy 중 무엇을 쓸지 미정.

배포 방식

직접 프로세스, systemd, Docker 등은 아직 미정.

운영 규모

동시 사용자/QPS/timeout/cache 정책은 실제 팀 Pilot 측정 후 결정.
