PRE-IMPLEMENTATION ARCHITECTURE REVIEW · 2026-08-27

Source Sync와 Knowledge Publish를
두 개의 독립 Loop로 나눌 것인가?

Jira 수집/정제와 OpenCode 기반 지식화/Embedding을 독립 실행하는 구조를 현재 Contract와 운영 특성에 비춰 비판적으로 검토합니다.

REVIEW ONLY · NOT FROZEN · IMPLEMENTATION ON HOLD

1. 검토 대상 구조

Loop A · Source Sync Scheduler A → Project Discovery → Delta Jira Download → RAW → ANALYSIS / Knowledge Input → semantic_v2 hash → NEW / CHANGED / UNCHANGED → SOURCE_COMMITTED → Watermark advance → durable Work Item 생성 → 종료 durable boundary / backlog ↓ sync_issue_change ↓ Loop B · Knowledge Publish Scheduler / Worker B → pending Work Item claim → OpenCode Knowledge Generation → Review / Evidence → Knowledge DB → BGE-M3 Embedding → FAISS staging → Atomic Publish → Work Item published → 다음 Work Item
경계 후보: 두 Loop 사이의 계약은 파일 전달이 아니라 SOURCE_COMMITTED + durable sync_issue_change Work Item입니다.

2. 이 구조가 매력적인 이유

LLM 지연 격리

OpenCode가 느려져도 Jira Source Sync는 계속 진행할 수 있습니다. Jira 최신 사실 확보와 비싼 지식화를 분리합니다.

독립 Cadence

Source는 정해진 간격으로 빠르게 돌리고, Knowledge Loop는 지속 실행·야간 집중 실행 등 다른 정책을 사용할 수 있습니다.

Backpressure 가시화

Source는 얼마나 앞서 있고 Publish가 얼마나 밀렸는지 backlog count와 oldest pending age로 직접 측정할 수 있습니다.

Failure Isolation

OpenCode 장애가 Jira 수집 실패로 보이지 않고, Jira 장애가 이미 쌓인 Knowledge 작업 처리까지 막지 않습니다.

운영 제어

Knowledge Loop만 일시 중지하거나 concurrency를 낮춰도 Source Loop는 정상 운영할 수 있습니다.

Catch-up 용이

밤에 OpenCode 처리량이 좋아지면 낮에 쌓인 Work Item을 순차적으로 소진할 수 있습니다.

3. 그러나 자동으로 좋은 구조는 아닙니다

문제 1 · Backlog는 사라지지 않고 축적됩니다

Loop B의 장기 평균 처리량이 Loop A가 만드는 변경량보다 낮으면 Queue는 끝없이 늘어납니다. 단순 분리는 병목을 해결하지 않고 병목을 버퍼 뒤로 숨길 뿐일 수 있습니다.

문제 2 · 최신성은 Eventual Consistency가 됩니다

Jira Source는 최신인데 Retrieval은 몇 시간 전일 수 있습니다. 사용자와 운영자에게 Source freshness와 Published freshness를 분리해 보여줘야 합니다.

문제 3 · 같은 Issue가 여러 번 바뀔 수 있습니다

V2가 처리되기 전에 V3, V4가 들어오면 모든 중간 Version을 LLM으로 지식화할지, 최신만 처리할지 정책이 필요합니다.

문제 4 · Worker ownership이 필요합니다

Knowledge Worker가 2개 이상이면 같은 Work Item을 중복 처리하지 않도록 claim/lease가 필요합니다. 단순 status만으로는 crash recovery와 동시 처리 경쟁을 완전히 해결하기 어렵습니다.

4. 현재 FROZEN Schema와 충돌하는 지점

현재 Schema v1은 두 Loop를 전혀 못 쓰는 것은 아닙니다. 하지만 하나의 sync_run에 Source와 Publish 집계를 같이 넣어 두어 독립 Loop의 실행 이력을 표현하기에는 다소 어색합니다.

현재 sync_run ├─ discovery_status ├─ source_status ├─ publish_status └─ run_status sync_issue_change ├─ discovered_run_id → sync_run └─ last_attempt_run_id → sync_run
문제: Loop A의 Run과 Loop B의 실행은 동일한 사건이 아닙니다. 독립 Scheduler로 돌리면 last_attempt_run_id가 어느 Source Sync Run을 뜻해야 하는지 의미가 흐려집니다.

결론: 2-Loop를 채택한다면 구현 전에 Run 모델을 revision하는 편이 좋습니다. 아직 코드가 없으므로 지금 수정하는 비용은 낮습니다.

5. 제가 추천하는 수정안

Loop A Run source_sync_run → Jira Discovery / Delta / Source Commit → project_state / source watermark → sync_issue_change 생성 Loop B Run processing_run → Work Item consume → Knowledge / Embedding / Publish → 처리량 / latency / error / 시간 기록 Work Item sync_issue_change → discovered_source_run_id → last_processing_run_id → stage status

즉 실행 이력을 두 종류로 나눕니다. 업무 Domain Table 자체는 크게 바뀌지 않지만, 현재 sync_run을 Source Run으로 명확히 하고 Knowledge 처리용 processing_run을 별도로 두는 쪽이 운영 관찰성이 좋아집니다.

대안:

테이블을 늘리고 싶지 않다면 sync_run을 Source Run으로만 정의하고 Loop B는 Work Item의 updated_at/log만으로 운영할 수도 있습니다. 하지만 OpenCode 시간대별 성능 편차를 관리하려는 목적이라면 Processing Run 이력을 따로 갖는 편이 훨씬 유용합니다.

6. Queue는 처음부터 Kafka/RabbitMQ가 필요한가?

초기에는 아니라고 봅니다.

현재 규모에서는 collector.db의 sync_issue_change를 durable work queue처럼 사용하는 것이 더 단순합니다. 먼저 실제 backlog와 처리량을 측정한 뒤 외부 Message Queue 필요성을 판단하는 편이 좋습니다.

Source Loop → INSERT / UPSERT sync_issue_change Knowledge Loop → pending/failed 대상 조회 → transaction으로 claim → 처리 → completed/published 업데이트

단, Worker를 여러 개로 늘리는 시점에는 lease_owner, lease_until, attempt_count, next_attempt_at 같은 Queue 제어 필드가 필요할 수 있습니다. 초기 Single Worker라면 당장 넣지 않아도 됩니다.

7. OpenCode가 느릴 때 실제 효과

상황1개 직렬 Loop2개 독립 Loop
낮시간 OpenCode 매우 느림Jira 다음 Sync까지 함께 지연될 수 있음Source는 계속 최신화, Knowledge backlog만 증가
밤시간 OpenCode 빨라짐그때 Source부터 다시 통과쌓인 backlog를 바로 소진 가능
Jira 일시 장애전체 파이프라인 시작이 멈춤이미 쌓인 Knowledge Work는 계속 처리 가능
Knowledge 생성 오류전체 Run이 길어짐해당 Work Item만 retry

따라서 사용자가 지적한 시간대별 OpenCode 편차는 2-Loop를 선택할 실질적인 근거가 됩니다. 단, Queue가 계속 쌓이는지는 별도의 처리량 지표로 관리해야 합니다.

8. 꼭 필요한 운영 지표

Source Lag

현재 시각 - Project committed watermark.

Publish Lag

Source Head와 Published Head의 시간/Version 차이.

Backlog Depth

pending/failed Work Item 수.

Oldest Pending Age

가장 오래 기다린 변경분의 대기 시간.

LLM Throughput

시간당 성공 Knowledge Work Item 수.

LLM Latency / Error

시간대별 p50/p95 처리시간과 실패율.

핵심: 2-Loop의 성공 기준은 “두 프로세스가 돈다”가 아니라 backlog가 장기적으로 안정되고 Publish Lag가 허용 범위 안에 있는가입니다.

9. 중간 Version 처리 정책도 필요합니다

Source Loop가 빠름 V2 → V3 → V4 Knowledge Loop는 아직 V2 대기 중

모든 Version 처리

History가 풍부하지만 느린 OpenCode를 불필요하게 많이 사용합니다.

최신 pending 우선 / supersede

Source Version은 모두 보존하되 아직 시작하지 않은 오래된 Knowledge Work는 최신 semantic state가 있으면 superseded 처리하는 방향이 운영 효율상 유리합니다.

다만 “모든 중간 상태의 Knowledge도 반드시 남겨야 한다”는 감사 요구가 있다면 이 최적화는 사용할 수 없습니다. 이 정책은 별도 결정이 필요합니다.

10. Embedding은 같은 Loop에 두어도 되는가?

현재는 같은 Loop B 안에 두는 것이 맞다고 봅니다.

Knowledge PASS → Evidence → Embedding → FAISS staging → Publish

Embedding은 Knowledge 결과에 종속되어 있고, 지금 별도 병목이라는 증거가 없습니다. 처음부터 3개 Loop로 쪼개면 Queue와 상태 전이가 늘어납니다. 실제 측정에서 Embedding이 독립 병목이 될 때만 세 번째 Worker로 분리하는 것이 낫습니다.

12. 추천 결론 · 아직 Freeze 아님

두 Loop로 분리하는 방향을 추천합니다.

Loop A · Source Sync Jira Download + deterministic 정제 + Source Commit → 빠르고 예측 가능한 단계 Durable Boundary sync_issue_change backlog Loop B · Knowledge Publish OpenCode + Review + Embedding + FAISS Publish → 느리고 시간대 편차가 큰 단계

다만 단순히 프로세스 두 개로 나누는 것으로 끝내지 말고, Source Run과 Processing Run의 실행 identity를 분리하고 backlog/lag를 1급 운영 상태로 관리하는 것을 함께 권고합니다.

다음 결정 제안: ① 2-Loop 채택 여부, ② Processing Run 테이블 추가 여부, ③ pending intermediate Version supersede 정책을 순서대로 Freeze한 뒤 구현에 들어가는 것이 안전합니다.
