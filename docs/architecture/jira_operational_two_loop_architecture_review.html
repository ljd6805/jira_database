ARCHITECTURE REVIEW RESULT · 2026-08-28

2-Loop 검토 결과: ADOPTED

Source Sync와 Knowledge Processing/Publish를 독립 Loop로 분리하는 안을 비판적으로 검토한 뒤 공식 채택했습니다. 이 문서는 검토 이력이며 현재 구현 기준은 공식 2-Loop 아키텍처 문서입니다.

채택 이유

1. OpenCode 지연을 Jira Source 최신화에서 격리 2. Source / Processing cadence 독립 운영 3. Jira 장애와 OpenCode 장애 상호 격리 4. 낮에 backlog를 쌓고 처리량이 좋은 시간대에 catch-up 가능 5. Source Lag / Publish Lag / Backlog를 독립 관찰 가능

채택과 함께 받아들인 비용

Backlog가 자동으로 해결되는 것은 아니며, 장기적으로 Processing 처리량이 Source 변경량보다 작으면 queue가 계속 증가합니다. 따라서 backlog depth, oldest pending age, publish lag, processing throughput/latency를 반드시 운영 지표로 봅니다.

채택으로 변경된 Schema

v1 sync_run = Source + Publish 집계 v2 source_sync_run = Loop A processing_run = Loop B sync_issue_change = durable backlog

State Schema Contract v2가 현재 기준입니다.

아직 남은 별도 결정

V2→V3→V4처럼 Processing 전에 여러 semantic Version이 쌓였을 때 미시작 구버전을 supersede할지 여부와, Multi-worker claim/lease는 별도 결정입니다.

Review completed · adopted · historical decision record · 2026-08-28
