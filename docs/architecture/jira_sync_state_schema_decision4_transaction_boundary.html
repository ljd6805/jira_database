SYNC STATE / PROJECT REGISTRY · SCHEMA DECISION 4 · FINAL · 2026-08-27

Watermark는 Source Commit보다
절대 먼저 가지 않는다

파일·State DB·Knowledge DB·Embedding/FAISS가 서로 다른 저장소라는 현실을 전제로, 짧은 durable commit point와 crash-safe 순서를 고정합니다.

S4 FIXED · SHORT TRANSACTIONS · FAIL FORWARD

1. 최우선 불변식

BEGIN State DB TRANSACTION sync_project_run.source_status = source_committed project_state.committed_watermark = upper_bound COMMIT

두 값은 항상 함께 성공하거나 함께 rollback합니다. Watermark를 이 Transaction 밖에서 먼저 또는 따로 이동하는 구현은 허용하지 않습니다.

이유: Watermark가 실제 Source Commit보다 앞서가면 다음 Sync가 아직 저장하지 못한 Jira 변경분을 건너뛰어 영구 누락시킬 수 있습니다.

2. 긴 전역 Transaction은 사용하지 않습니다

Jira API, RAW 파일, Knowledge DB, Embedding API, FAISS는 하나의 SQLite rollback으로 되돌릴 수 없습니다. 따라서 전체 Pipeline을 수분 동안 하나의 DB Transaction으로 묶지 않고 단계별 짧은 commit point를 사용합니다.

T0 Run Start T1 Discovery Commit T2 Per-Candidate Source Checkpoint T3 Project Source Commit + Watermark T4 Downstream Stage Checkpoint T5 Actual Retrieval Publish T6 Run Finalize

3. T0 · Run Start

sync_run_id 생성 fixed upper_bound 결정 ↓ 한 Transaction으로 sync_run 저장 run_status = running discovery_status = pending upper_bound = fixed value

same-run Resume에서는 반드시 저장된 같은 upper_bound를 재사용합니다.

4. T1 · Discovery Commit

모든 Project page 조회 + 전체 snapshot 검증 ↓ SUCCESS일 때만 BEGIN project_state 신규/last_seen 갱신 missing Project → unavailable 갱신 sync_project_run 대상 생성 discovery_status = completed COMMIT Discovery 실패 → visibility 변경 금지 → discovery_status = failed만 기록

불완전한 Discovery 결과로 정상 Project를 unavailable 처리하지 않습니다.

5. T2 · 후보 하나의 Source Checkpoint

후보는 updated ASC, jira_id ASC 순서로 처리합니다. Source 파일을 먼저 안전하게 저장하고 semantic_v2 판정을 끝낸 뒤 State DB를 갱신합니다.

Jira Source 수집 → RAW / ANALYSIS / Knowledge Input 등 durable 저장 → semantic_v2 source_hash → NEW / CHANGED / UNCHANGED ↓ BEGIN State DB NEW/CHANGED → Work Item upsert count 갱신 cursor_updated_at + cursor_jira_id 갱신 COMMIT

파일 후 State 전 Crash

Cursor가 이동하지 않았으므로 같은 후보를 다시 처리합니다. 중복은 허용하고 누락은 막습니다.

State Commit 후 Crash

Cursor까지 durable하므로 같은 lower/upper 조회에서 다음 후보부터 Resume합니다.

6. T3 · Project Source Commit + Watermark

모든 후보 안전 처리 확인 ↓ BEGIN sync_project_run.source_status = source_committed sync_project_run.finished_at = now project_state.committed_watermark = upper_bound project_state.last_source_success_* 갱신 project_state.last_error = NULL COMMIT
Crash 시점안전한 결과
Transaction 전기존 Watermark 유지 → same-run Resume.
Transaction 중SQLite rollback → 두 상태 모두 이전 값.
Commit 후Source window 완료 + Watermark 전진. Downstream은 별도 Resume.

7. T4 · Downstream Checkpoint

Knowledge/Embedding의 completed 상태는 실제 durable 산출물이 먼저 존재하고 검증된 뒤 기록합니다.

실제 Knowledge/Embedding 생성 + durable 저장 → deterministic ID / artifact 검증 → State DB stage = completed
Crash gap: 산출물 생성 후 State 갱신 전에 죽으면 Resume에서 실제 산출물 존재를 확인해 재생성하지 않고 State를 reconcile합니다.

8. T5 · Publish

금지

publish_status = published를 먼저 기록한 뒤 실제 Retrieval을 전환하는 순서.

확정 순서

새 Knowledge/Embedding/FAISS staging 준비 → 검증 → 실제 active Retrieval 전환 → 확인 → State에 published 기록.

실제 Publish 전환 후 State 기록 전에 Crash가 나면 active pointer/artifact를 확인해 이미 Published된 사실을 reconcile합니다.

9. T6 · Run Finalize

Project Source + Work Item Publish 결과 집계 ↓ 한 State DB Transaction sync_run.discovery_status sync_run.source_status sync_run.publish_status sync_run.run_status sync_run.finished_at COMMIT

Run이 partial/failed여도 이미 성공한 Watermark나 Published Knowledge를 rollback하지 않습니다.

10. S4 최종 규칙

1. 짧은 Transaction을 사용한다. 2. 외부 산출물은 먼저 durable하게 만든다. 3. State completed/published 표시는 실제 결과보다 먼저 가지 않는다. 4. source_committed + Watermark advance는 반드시 한 Transaction이다. 5. Discovery snapshot은 전체 성공 후에만 Registry에 반영한다. 6. Per-candidate cursor는 classification/Work Item과 함께 commit한다. 7. Crash gap은 deterministic ID와 실제 artifact 검증으로 reconcile한다. 8. 실패 시 성공한 독립 결과는 보존한다.
