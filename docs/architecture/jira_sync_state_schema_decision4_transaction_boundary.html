1. 가장 위험한 사고

Watermark가 먼저 이동

watermark = 10:40 저장 ✓ 마지막 Issue Source 저장 ✗ 프로세스 종료 다음 Run → 10:40 이후부터 시작 → 누락 가능

반드시 원하는 상태

Project Source 전체 안전 완료 ↓ source_committed 표시 + watermark = upper ↓ 같은 SQLite transaction commit
S4의 최우선 불변식: sync_project_run.source_status = source_committed와 project_state.committed_watermark = upper_bound는 반드시 같은 State DB Transaction에서 함께 성공하거나 함께 rollback되어야 합니다.

2. 모든 것을 한 Transaction에 넣지는 않습니다

Jira API 호출, RAW/ANALYSIS 파일 저장, Knowledge DB 쓰기, Embedding API, FAISS 파일 교체는 서로 다른 시스템입니다. 하나의 SQLite Transaction으로 전부 묶을 수 없고, 수분 동안 DB lock을 잡는 것도 좋지 않습니다.

잘못된 생각 BEGIN TRANSACTION → Jira API 수십 번 → 파일 수백 개 저장 → LLM → Embedding API → FAISS → COMMIT 문제 → 너무 긴 transaction → 외부 시스템은 rollback 불가 → crash 시 복구가 오히려 어려움
추천: 긴 전역 Transaction 대신 작은 durable commit point를 단계별로 둡니다.

3. T0 · Sync Run 시작 Transaction

Run 시작 시 1. sync_run_id 생성 2. fixed upper_bound 결정 3. sync_run row 저장 같은 transaction → run_status = running → discovery_status = pending → upper_bound 고정

같은 Run을 Resume할 때는 이 row의 upper_bound를 다시 사용합니다. Run 도중 새 upper를 만들지 않습니다.

4. T1 · Project Discovery Commit

D6에 따라 Discovery가 중간 실패했는데 일부 Project를 unavailable로 바꾸면 안 됩니다.

Jira Project Discovery → 모든 page 조회 완료 → 전체 결과 검증 SUCCESS인 경우에만 State DB transaction 시작 → 새 project_state insert → visible Project last_seen 갱신 → 이전 Registry에는 있지만 이번에 없는 Project unavailable 갱신 → sync_project_run 대상 row 생성 → discovery_status = completed COMMIT Discovery 실패 → visibility 변경 없음 → discovery_status = failed만 기록
불변식: Project Registry의 visible/unavailable 비교 결과는 완전한 Discovery snapshot을 얻었을 때만 commit합니다.

5. T2 · 후보 Issue 하나의 Source Checkpoint

후보는 D2의 updated ASC, jira_id ASC 순서로 처리합니다. 파일은 먼저 안전하게 저장하고, 그 다음 State DB에서 cursor와 분류 결과를 함께 commit합니다.

후보 ABC-42 처리 ① Jira Source 수집 ② RAW / ANALYSIS / Knowledge Input 등 필요한 Source 산출물 파일 저장 ③ semantic_v2 source_hash 계산 ④ NEW / CHANGED / UNCHANGED 판정 ↓ ⑤ State DB 짧은 transaction NEW/CHANGED → sync_issue_change upsert 분류 count → new/changed/unchanged_count +1 resume cursor → cursor_updated_at / cursor_jira_id = ABC-42 COMMIT

파일 저장 후 DB commit 전에 죽음

cursor가 이동하지 않았으므로 같은 후보를 다시 처리합니다. 파일 저장과 Work Item 생성은 idempotent하게 재실행합니다.

DB commit 후 죽음

cursor가 ABC-42까지 이동했으므로 같은 lower/upper 재조회 후 그 다음 후보부터 Resume합니다.

현재 기반: RawStore는 임시 파일에 쓰고 fsync 후 os.replace로 교체합니다. 운영 구현에서는 이 atomic-write 패턴을 유지합니다. 극단적인 전원 장애 durability가 요구되면 parent-directory fsync까지 추가 검토합니다.

6. T3 · Project Source Commit + Watermark · 가장 중요

모든 후보 처리 완료 확인 ↓ BEGIN State DB TRANSACTION sync_project_run source_status = source_committed finished_at = now counts 최종 확정 project_state committed_watermark = sync_project_run.upper_bound last_source_success_run_id = current run last_source_success_at = now last_error = NULL COMMIT
Watermark 규칙: 이 Transaction 밖에서 Watermark를 먼저 또는 따로 갱신하지 않습니다.
Crash 시점결과
Transaction 전Project는 running/partial 상태, Watermark 이전 값 → same-run Resume.
Transaction 도중SQLite rollback → source_committed와 Watermark 둘 다 이전 상태.
Commit 후Source window는 안전 완료. Watermark upper로 이동. Downstream은 별도 Resume 가능.

7. T4 · Downstream Stage Checkpoint

Knowledge DB, Embedding artifact, FAISS는 State DB와 다른 저장소이므로 분산 Transaction을 만들지 않습니다. 대신 각 Stage의 실제 산출물을 먼저 durable하게 만들고, 확인 후 State DB status를 완료로 바꿉니다.

예: Knowledge Stage Knowledge DB에 deterministic ID로 결과 저장 / 검증 ↓ 성공 확인 ↓ State DB transaction sync_issue_change issue_version_id = ... knowledge_generation_id = ... knowledge_status = completed last_attempt_run_id = current run COMMIT
Crash gap 처리: 실제 산출물은 만들어졌는데 State status 갱신 전에 죽을 수 있습니다. 다음 Resume은 deterministic ID/산출물 존재를 먼저 확인하고, 이미 완성된 결과라면 재생성하지 않고 State를 reconcile합니다.

Embedding도 같은 원칙입니다: vector/artifact를 먼저 만들고 검증한 뒤 embedding_status = completed를 기록합니다.

8. T5 · Publish는 실제 전환이 Commit Point

D7에서 Half-Publish를 금지했습니다. 따라서 State DB의 publish_status = published가 진실의 원천이 아니라, 실제 Retrieval이 새 세대를 보도록 전환된 시점이 먼저입니다.

새 Knowledge / Embedding / FAISS mapping → staging에서 전부 준비 → 검증 PASS 실제 Publish Commit Point → active pointer / manifest / atomic artifact swap (구체 방식은 후속 결정) 전환 성공 확인 후 → State DB publish_status = published → published_at 기록

금지

publish_status = published를 먼저 기록하고 실제 FAISS 전환을 나중에 하는 순서.

허용

실제 Retrieval 전환 → 검증 → State에 published 기록.

전환 성공 후 State 기록 전에 crash가 나면 Resume 시 현재 active pointer를 확인해 이미 Publish된 사실을 reconcile합니다.

9. T6 · Run Finalize

Project Source 상태 + Work Item Publish 상태 집계 ↓ State DB transaction sync_run.discovery_status sync_run.source_status sync_run.publish_status sync_run.run_status sync_run.finished_at COMMIT

Run이 partial/failed여도 이미 commit된 Project Watermark나 Published Knowledge를 rollback하지 않습니다. D5의 fail-forward 원칙을 유지합니다.

10. S4 추천 결론

PROPOSED

짧은 Transaction + 명확한 commit point를 사용한다.

T0 Run start → sync_run + fixed upper T1 Discovery commit → 전체 discovery 성공 후 Registry 상태 반영 T2 Per-candidate checkpoint → durable Source 파일 후 → classification + count + resume cursor를 한 transaction T3 Project Source Commit → source_committed + Watermark advance를 반드시 한 transaction T4 Downstream checkpoint → 실제 durable 산출물 확인 후 stage completed T5 Publish → 실제 active Retrieval 전환이 먼저 → 검증 후 State = published T6 Run finalize → completed / partial / failed 집계
가장 중요한 한 줄: Watermark는 Source Commit보다 절대 먼저 가지 않으며, State의 completed/published 표시는 실제 durable 산출물보다 절대 먼저 가지 않습니다.

이 안을 확정하면 다음 S5에서는 Schema Migration versioning과 migration Gate를 구체화한 뒤 Schema Freeze 준비로 넘어갑니다.
