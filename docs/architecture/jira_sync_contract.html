0. “개정 3”의 뜻

이 Sync Contract 계열의 세 번째 개정이라는 뜻입니다.
Operational State Schema 개정 3, Knowledge DB Schema 개정 1과는 서로 독립된 번호입니다.

1. 전체 계약

Loop A · SOURCE SYNC source_sync_run → Project Discovery → Watermark + 5m Overlap + fixed upper → Jira Delta / Initial / Catch-up → RAW / ANALYSIS / Knowledge Input → semantic_v2 (Source 변경 판별 프로필) → NEW / CHANGED / UNCHANGED → Source History / Work Item durable → Project SOURCE_COMMITTED → Watermark advance + Source Ready → 같은 jira_id의 이전 미완료 Work superseded ↓ sync_issue_change latest-only durable backlog ↓ Loop B · KNOWLEDGE PROCESSING / PUBLISH processing_run → latest + source-ready Work Item → OpenCode Knowledge → latestness re-check → Review / Evidence → Knowledge DB → BGE-M3 / FAISS staging → latestness re-check → Atomic Publish → PUBLISHED Always-on last-known-good Published Corpus → MCP → OpenCode User

D1 · Project별 committed Watermark

FIXED

Project별 독립 Watermark를 유지합니다. Project Source window 전체가 안전하게 Commit된 경우에만 전진합니다.

D2 · 5분 Overlap + fixed upper + stable order

FIXED
lower = committed_watermark - 5m upper = source_sync_run 시작 시 고정 updated >= lower updated < upper ORDER BY updated ASC, id ASC

같은 Source Run Resume은 동일 lower/upper를 재사용합니다.

D3 · NEW / CHANGED / UNCHANGED

FIXED
종류조건처리
NEWjira_id 미존재Source 상태 + Work Item
CHANGED같은 jira_id + 다른 hash새 Source 상태 + Work Item
UNCHANGED같은 jira_id + 같은 hash새 Work Item 없음

Jira updated는 candidate trigger이고 semantic identity가 아닙니다.

D4 · semantic_v2

FIXED · INTERNAL PROFILE

semantic_v2는 문서 버전이 아니라 Source 변경 판별 hash profile 이름입니다. 업무 의미는 포함하고 경로 metadata와 Issue/Comment updated_at은 hash에서 제외합니다.

D5 · Checkpoint / Resume

FIXED · TWO-LOOP

Loop A

fixed upper, Project lower/upper, candidate count, stable cursor, Source Commit/Watermark를 durable하게 기록합니다.

Loop B

Work Item lifecycle와 Knowledge / Embedding / Publish checkpoint를 별도로 기록하고 실패 Stage부터 이어갑니다.

Loop B 실패가 Loop A 다음 Source Run을 막지 않습니다.

D6 · Project Registry / Knowledge Retention

FIXED

project_id가 authoritative identity입니다. 완전한 Discovery 성공 후에만 visible/unavailable을 판단합니다. unavailable/삭제는 Knowledge 자동 삭제나 Retrieval disable이 아닙니다.

Jira Source Lifecycle ≠ Knowledge Lifecycle

D7 · SOURCE_COMMITTED ≠ PUBLISHED

FIXED · LOOP BOUNDARY

Loop A · SOURCE_COMMITTED

Source 산출물, semantic hash/classification, durable Work Item이 안전하고 Project Source window 책임이 완료된 상태.

Loop B · PUBLISHED

최신 Knowledge/Evidence, Embedding, FAISS/Mapping이 검증되고 실제 Retrieval active view가 전환된 상태.

Loop B claim 조건
last_source_committed_run_id = last_observed_source_run_id AND work_status IN ('pending','failed') AND superseded_by_work_item_id IS NULL

D9 · Two-Loop Operational Architecture

FIXED
Loop A source_sync_run → source_project_run → project_state → sync_issue_change producer Loop B processing_run → latest source-ready sync_issue_change consumer → Knowledge / Embedding / Publish
