CONTINUOUS JIRA KNOWLEDGE SERVICE · SYNC CONTRACT · 2026-08-27

Sync Contract
FROZEN

이 문서는 Continuous Jira Knowledge Service의 지속 동기화 구현 기준입니다. Watermark, Overlap, 변경 판정, semantic hash, Checkpoint/Resume, Project Registry, Knowledge 보존, Source Commit/Publish, Run 상태를 하나의 계약으로 고정합니다.

FROZEN · D1~D8 APPROVED · IMPLEMENTATION SOURCE OF TRUTH

1. 목적과 범위

Sync의 목적은 Jira의 현재 변경분을 누락 없이 수집하고, 실제로 달라진 업무지식만 하위 파이프라인에 전달하며, 실패해도 이미 성공한 결과를 재사용하는 것입니다. Knowledge DB는 Jira의 현재 상태를 그대로 복제하는 Mirror가 아니라 과거부터 축적된 업무지식을 보존하는 저장소입니다.

Jira → Project Discovery → Project별 Delta Source Sync → source_hash 기반 NEW / CHANGED / UNCHANGED → Issue Version / Knowledge Work Item → Knowledge / Review / Evidence → Embedding / Retrieval Publish → Central MCP
핵심 원칙: Jira Source Lifecycle과 Knowledge Lifecycle은 동일하지 않습니다. Jira에서 Project/Issue가 삭제되거나 보이지 않게 되어도 이미 축적된 Knowledge를 자동 삭제하지 않습니다.

2. D1 · Project별 committed Watermark

FIXED

계약

각 Project는 독립적인 committed_watermark를 가집니다.

해당 Project의 Source window가 안전하게 처리된 경우에만 Watermark를 전진시킵니다.

실패 격리

Project A/C가 성공하고 B가 실패하면 A/C의 Watermark만 전진하고 B는 기존 Watermark를 유지합니다.

A → 10:30 committed B → 09:50 유지 · source 실패 C → 10:30 committed

3. D2 · 5분 Overlap + 고정 upper

FIXED

Delta 조회는 경계 누락보다 약간의 중복을 선택합니다.

lower = committed_watermark - 5 minutes upper = Sync Run 시작 시 고정한 상한 JQL 개념 project = ABC AND updated >= lower AND updated < upper ORDER BY updated ASC, id ASC

Overlap

이전 구간 5분을 다시 읽습니다.

Fixed upper

Run 도중 Jira가 계속 변해도 이번 Run의 책임 범위를 고정합니다.

Stable order

updated ASC, id ASC를 기본 정렬로 사용합니다.

4. D3 · NEW / CHANGED / UNCHANGED

FIXED
판정조건처리
NEW기존 Source 상태에 jira_id 없음새 Issue Version + 전체 downstream
CHANGED같은 jira_id + 새 source_hash새 Issue Version + 변경분 downstream
UNCHANGED같은 jira_id + 같은 source_hash기존 Version/Knowledge/Vector 재사용
Jira updated의 역할: 다시 검사할 후보를 찾는 신호입니다. 실제 semantic change는 source_hash로 판정합니다. Issue Key가 바뀌어도 같은 jira_id면 같은 Issue입니다.

5. D4 · source_hash semantic_v2

FIXED

source_hash는 “Jira가 언제 수정됐는가”가 아니라 “Knowledge의 업무 재료가 실제로 달라졌는가”를 나타냅니다.

영역Hash 포함Hash 제외
Issuejira_id, summary, description, format, type, status, priority, created_atupdated_at, source_path
Commentcomment_id, sequence, author, created_at, body, formatupdated_at, source_path, source_page
AttachmentID, filename, author, created_at, size, MIME, content_availablesource_path
Relationship관계 ID/type/direction/상대 Issue 정보 등 Knowledge Input에 포함되는 의미 값source_path
Custom Fieldfield ID/name/schema + 실제 value/display 정보source_path
source_hash_profile = semantic_v2

Hash 규칙 버전을 저장하여 실제 Jira 내용 변화와 hash 알고리즘 변경을 구분합니다.

6. D5 · Checkpoint / Resume

FIXED

Source Checkpoint

Jira → RAW → ANALYSIS → source_hash → change classification

Downstream Checkpoint

Knowledge / Review → Evidence / DB → Embedding → Retrieval Publish
Stage 상태의미재개 규칙
pending미시작실행
running실행 중완료 증거 없으면 재검증/재시도
completed안전 완료재사용 / skip
failed오류 종료retry
Resume 우선순위: 1) 가능한 경우 같은 Sync Run과 동일 lower/upper로 재개. 2) same-run 재개가 불가능하면 기존 committed watermark + 5분 overlap으로 새 Run을 시작합니다. 전체 rollback은 하지 않습니다.

Downstream Work Item의 안정적인 identity는 jira_id + source_hash + source_hash_profile을 기준으로 합니다.

8. D7 · Source Commit vs Publish

FIXED

SOURCE_COMMITTED

Jira Source가 안전하게 저장되고 semantic hash 및 변경 판정이 durable하게 기록되며 downstream Work Item이 생성된 상태입니다.

Project Source window 전체가 성공하면 Watermark 전진이 가능합니다.

PUBLISHED

승인 Knowledge, Evidence resolve, Embedding, FAISS/Mapping이 모두 일치하고 실제 사용자 Retrieval 전환까지 끝난 상태입니다.

현재 Published = V1 새 Source V2 = SOURCE_COMMITTED 새 Knowledge V2 = candidate V2 Publish 완료 전 → Retrieval은 V1 계속 제공 V2 전체 준비 + 검증 완료 → Published Head를 V2로 전환 → V1은 History로 보존
Half-Publish 금지: DB, Embedding, FAISS가 서로 다른 세대를 사용자에게 노출하지 않습니다. 새 Published 상태가 완성될 때까지 기존 Published Knowledge를 계속 제공합니다.

9. D8 · Sync Run 상태

FIXED

Run의 성공 여부와 기존 Knowledge 서비스의 생존 여부를 혼동하지 않습니다. Run이 failed여도 기존 Published Knowledge는 계속 제공됩니다.

run_status정확한 의미
completedDiscovery 성공 + 모든 visible Project Source Commit 완료 + 필요한 Publish 모두 완료 또는 publish not_required
partial하나 이상의 durable 성공 결과가 존재하지만 Source 또는 Publish에 실패/미완료가 남음
failedDiscovery 결과를 신뢰할 수 없거나, 처리해야 할 Source 범위에서 durable Source progress를 하나도 만들지 못함

discovery_status

Project 목록을 신뢰 가능한가

source_status

Source window 처리 결과

publish_status

서비스 반영 결과

run_status

운영자용 최종 집계

Unavailable Project: 실패로 세지 않고 SKIPPED_UNAVAILABLE로 처리합니다. 기존 Knowledge는 계속 Retrieval됩니다.

10. Contract 전체 흐름

Sync Run 시작 ↓ upper 고정 Project Discovery ├─ 처음 보는 project_id → Initial Ingest ├─ visible 기존 Project → Delta └─ unavailable 기존 Project → Skip · Knowledge는 유지 ↓ Project별 lower = watermark - 5분 ↓ updated ASC, id ASC로 후보 수집 ↓ 최신 Source snapshot + semantic_v2 hash ├─ NEW ├─ CHANGED └─ UNCHANGED → reuse ↓ Source window 전체 안전 완료 → SOURCE_COMMITTED → Project Watermark advance ↓ NEW / CHANGED Work Item → Knowledge / Review / Evidence → Embedding → FAISS / Mapping ↓ 전체 준비 후 atomic Published Head 전환 ↓ Run status 집계 completed / partial / failed

11. 이 Contract가 일부러 결정하지 않는 것

Sync cadence

몇 분/몇 시간 간격으로 실행할지는 운영 단계에서 별도 결정합니다.

팀원별 권한

중앙 MCP에서 사용자별 Jira 권한을 재현할지 여부는 Remote MCP 인증/권한 설계에서 결정합니다.

Publish atomicity 구현 방식

DB transaction, manifest pointer, artifact swap 등 구체 방식은 Incremental Retrieval 설계에서 결정합니다.

Remote MCP 배포

TLS/auth/reverse proxy/concurrency/timeout은 중앙 서비스 설계에서 결정합니다.
