2. Pilot에서 왜 Full Rebuild인가?

결정성

같은 입력으로 다시 만들 때 같은 rc_/fi_/mapping이 나오는지 검증합니다.

단순성

285개에서는 incremental mutation보다 전체 재구축이 훨씬 단순합니다.

정답 기준

Exact Flat index를 향후 ANN 비교용 test oracle로 남깁니다.

중요: Pilot full rebuild는 정식 서비스 운영 정책이 아닙니다.

3. 정식 서비스 · DELTA FIRST

변경 없음 → 아무 작업 없음 새 Knowledge → 새 embedding만 생성 → index add 변경된 Knowledge → old entry remove/tombstone → 필요한 embedding만 생성 또는 재사용 → new entry add 삭제/비활성 Knowledge → index에서 remove/tombstone

변경 감지는 기존 source_hash → issue_version → active generation → accepted attempt → knowledge_item → embedding_text_hash 계약을 활용합니다.

4. Embedding API도 필요한 경우에만

Vector cache

새 Knowledge Item identity가 생겨도 text와 embedding contract가 같다면 실제 vector 계산은 재사용할 수 있습니다.

vector_cache_key = H(embedding_text_hash, embedding_contract_hash) 새 ki_ / 새 emb_ + 같은 text hash + 같은 ec_ → BGE-M3 API 재호출 생략 → 기존 vector 재사용

emb_는 lineage identity를 보존하고, vector cache는 계산 비용 절감을 위한 별도 계층입니다.

5. 운영형 FAISS ID

Pilot

IndexFlatIP position → emb_ → ki_

순차 position 기반이므로 remove 시 뒤 번호가 이동할 수 있습니다.

Production exact 후보

IndexIDMap2(IndexFlatIP) + stable int64 vector_id vector_id ↔ emb_ ↔ ki_

Stable vector_id는 SQLite에서 collision 없이 관리하는 방식을 우선합니다.

6. ANN으로 커질 때

IVF

Explicit ID와 remove를 지원할 수 있어 incremental 운영에 비교적 자연스럽습니다.

HNSW

FAISS HNSW는 vector remove를 직접 지원하지 않으므로 tombstone/filter + periodic rebuild가 필요합니다.

Flat

항상 exact test oracle로 보존해 ANN recall@k를 검증합니다.

7. Full Rebuild는 없어지지 않는다

평상시 → delta update 주기적 / 필요시 → full rebuild

Full rebuild는 tombstone/fragmentation 정리, integrity 검사, index migration, embedding contract 변경, backfill, 장애 복구에 사용합니다.

운영 기본 = delta-first · Full rebuild = maintenance / recovery / migration
