VERSION LANGUAGE GUIDE · 2026-08-31

v1, v2, v3를
숫자만 보고 비교하지 않습니다

이 프로젝트에는 서로 다른 대상이 각자의 버전 번호를 가집니다. State Schema 개정 3과 Knowledge DB Schema 개정 1은 경쟁하는 버전이 아니라 서로 다른 물건의 번호입니다.

1. 가장 중요한 한 문장

항상 “현재/과거 상태 → 무엇의 버전인지 → 개정 번호” 순서로 읽습니다.
숫자만 보고 3 > 1이니 무엇인가 더 최신이라고 판단하지 않습니다. 서로 다른 대상의 숫자는 비교하지 않습니다.

2. 이 프로젝트의 주요 번호 체계

현재 사용

Sync Contract · 개정 3

Jira 동기화, Two-Loop, Source Ready, Latest-Only 처리 규칙의 현재 계약입니다.

현재 구현/운영 기준

Operational State Schema · 개정 3

collector.db에서 Run, Watermark, Work Item backlog와 supersede 상태를 관리하는 현재 설계입니다.

실제 구현 완료

Knowledge DB Schema · 개정 1

M7에서 실제 SQLite로 구현하고 real-run 검증까지 마친 지식 DB 스키마입니다. State DB 개정 번호와 별도입니다.

문서 UI

Document Shell / Hub Frame · 개정 1

문서의 이전/Hub/다음 버튼과 공통 UI 틀의 번호입니다. 데이터베이스와 무관합니다.

내부 이름

semantic_v2

문서 버전이 아닙니다. Jira 원문의 의미가 달라졌는지 계산하는 Source 변경 판별 hash profile 이름입니다.

기술 알고리즘 버전

STATE_ID_SCHEMA_VERSION = 2

Work Item ID를 어떤 canonical 규칙으로 만드는지 나타내는 ID 생성 알고리즘의 기술 버전입니다. Operational State 개정 2라는 뜻이 아닙니다.

SQLite 기술 marker

PRAGMA user_version = 3

현재 Operational State DB가 Schema 개정 3이라는 것을 SQLite 파일 내부에서 표시하는 기술 값입니다.

과거 보관

Baseline · 개정 1/2

설계 과정과 의사결정 이력을 보존하는 문서입니다. 현재 구현 기준으로 사용하지 않습니다.

3. 왜 숫자가 서로 안 맞는가?

Operational State Schema 개정 1 → 개정 2 → 개정 3 (현재) Knowledge DB Schema 개정 1 (실제 구현 완료) Document Shell / Hub Frame 개정 1 STATE_ID_SCHEMA_VERSION 2 (ID 생성 알고리즘 기술 버전) semantic_v2 Source 변경 판별 profile 이름 → 서로 독립된 번호 체계 → 숫자의 대소 비교 금지

5. 문서를 읽을 때 보는 순서

① 상태

현재 사용 / 구현 완료 / 과거 보관 중 무엇인지 먼저 봅니다.

② 대상

Sync Contract인지, State DB인지, Knowledge DB인지, 문서 UI인지, 내부 알고리즘인지 봅니다.

③ 개정/기술 번호

같은 대상 안에서만 번호를 비교합니다. 다른 대상끼리는 비교하지 않습니다.
